# yellow — 進め方を決めて、記録を残して、やり切る

短い一文の依頼から「**どのモードで、どこまで、誰が立ち会って**進めるか」を判定し、宣言してから
最後までやり切るための一式です。毎回長い手順書を書かなくても、依頼の一文だけで進め方が決まります。

入っているのはスキル 6 枚と、フック 5 本 (走り切らせる 3 本 + PR の仕上げを手順書に乗せる 1 本 +
導入時の設定を渡す 1 本) です。

| スキル | 何をするか |
| --- | --- |
| `dispatch` | お題から進め方を判定し、1 行で宣言してから走り切る入口。作業なら規模を問わずここを通る |
| `work` | 調べたこと・決めたことを、あとから初見の人が読める形で残す。作業ごとにディレクトリを作り、正本から一覧ページを生成する |
| `grilling` | 計画や思いつきを問い詰めて、前提を残らず洗い出す。事実は自分で調べ、ユーザーには判断だけを聞く |
| `pr-response` | Draft の PR を人間レビューに出せる状態まで仕上げる。ラベル・担当者・CodeRabbit との往復を Draft のまま回し、指摘 0 件と CI 緑が揃ってから Ready に上げる (純粋な好みの指摘だけは、拾わない判断を PR に書き残せば 0 でなくてよい) |
| `retrospective-codify` | 得た教訓を、振り返り文書ではなく仕組みの変更 (スキル追記・新設) に固定化する |
| `memory-to-skill` | その教訓をどこに置くかの判定表。`retrospective-codify` がここを開いて使う |

**6 枚は割れません。** `dispatch` は `work` を呼び、`grilling` を呼び、出荷の最後の工程で
`pr-response` を呼びます。`retrospective-codify` は `memory-to-skill` の判定表を正本として
参照します。1 枚だけ欲しい場合は、この拡張ではなく `claude/skills/` の棚を見てください。

## なぜスキルのコピーではなく拡張なのか

**フックが本体の半分だからです。** このスキル群は「宣言したら最後までやり切る」ことを求めますが、
散文の規則は忘れられます (実際に最後の工程を飛ばして完了報告した記録が残っています)。それを
機械的に押さえているのがフックで、フックはコピーでは配れません。

| フック | いつ動くか | 何をするか |
| --- | --- | --- |
| `dispatch-gate.py` | ターン終了時 | 走行中の契約が残ったままターンを終えるのを差し戻す。止まるなら理由を契約に書かせる。作業ディレクトリに計画の契約 (`plan.jsonc`) があれば `scripts/check-plan.py` も走らせ、落ちていれば差し戻す |
| `dispatch-nudge.py` | お題が来た直後 | 走行中の契約が無いターンに「これは成果物を作る依頼か?」の 1 問を差し込む。契約が走り出したら黙る |
| `work-index-gate.py` | ターン終了時 | 作業ディレクトリの正本と実ファイルが食い違ったまま終えるのを差し戻す |
| `pr-response-gate.py` | コマンドの実行前と実行後 | PR の仕上げ (ラベル・担当・レビューの往復・収束判定・Ready 昇格) を、手順書を開かずに生の `gh` で組み立て直すのを差し戻す。PR が生まれた直後には、正本の在り処を差し込むだけで止めない |
| `write-config.py` | セッション開始時 | 導入時に入れた作業置き場を、Bash から読める場所へ書き出す。置き場と共有 CSS の初期化も行う |
| `_workroot.py` | — | 走り切らせる 3 本が置き場を解くための共通部品 (フックとしては登録されない) |

**フックとスキルは同時に届く必要があります。** フックだけ先に配ると、スキルを持っていない人に
「参照先の無い問い」が降ります。拡張にまとめてあるのはそのためです。

`pr-response-gate.py` の差し戻し先 (`pr-response` スキル) も、同じ理由でこの拡張に同梱して
あります。差し戻しの案内文が指す手順書がその場にあるので、止められた側はそのまま開いて続けられます。

Why: 以前はフックだけを配り、手順書は各自の `~/.claude/commands/` にある前提にしていました。
持っていない環境では、案内先が存在しないまま止められて走行がそこで終わります (実際に「専用の
スキルがこの実行環境に無く、生の `gh` で組み立て直してはいけないので停止した」という記録が
残りました)。**止める仕組みと、止めたあとの行き先は、同時に届かないと意味がありません。**

## 導入

```text
/plugin marketplace add lrm-corp/coding-agent-equipment
/plugin install yellow@lrm-equipment
```

導入時に**作業ディレクトリを集める場所**を聞かれます。絶対パスで入れてください
(例: `/Users/自分の名前/dev/_work`)。

複数のリポジトリを横断して使うなら、それらが並んでいる**親ディレクトリの下**に置くと、案件を
またいだ一覧が 1 枚で見られます。1 つのリポジトリでしか使わないなら、そのリポジトリ直下でよいです。
ディレクトリが無ければ、次のセッション開始時に作られます。

もう 1 つ、**計画の影響先に並べるサービス・製品名** (`plan_targets`) を聞かれます。任意です。カンマ区切りで入れると、
計画の契約の `impact` にその名前の行が無いとき `check-plan.py` が落とします。空のままなら名前の抜けは検査しません
(環境変数 `YELLOW_PLAN_TARGETS` でも渡せます)。

もう 1 つ、**STG での確認の手順を持つスキルの名前** (`stg_check_skill`、例: `staging-qa`) も聞かれます。任意です。
依頼に「STG まで」とあるときだけ使います。PR が収束したらマージを頼んで待ち、マージされたらこのスキルを呼んで、
リリース作成・STG へのデプロイの見届け・STG での確認まで進めます。空のままなら、そのときに「手順を持つスキルが
設定されていない」と報告して止まります。この拡張には STG での確認の手順そのものは入っていません。

入れたあと `CLAUDE.md` に数行貼る必要があります。**貼らないと dispatch が自分から発火しません。**
文章は [reference/claude-md-snippet.md](reference/claude-md-snippet.md) にあります。

### 効いているかの確かめ方

新しいセッションを開いて、何か小さな作業 (ファイル 1 つの修正など) を頼んでみてください。
走り出す前に「▶ ... で走ります」という 1 行が出れば効いています。出ないときは次の順に見てください。

1. `/plugin` で `yellow` が有効になっているか
2. `CLAUDE.md` の文章を貼ったか。貼ったファイルが読み込まれる場所でセッションを起動しているか
3. 作業置き場が入っているか (`cat "$CLAUDE_PLUGIN_DATA/dispatch.json"` に `work_root` が出るか)

**3 が空のとき、フックは黙って何もしません。** 導入直後の人のターンを止めないための作りなので、
エラーは出ません。「差し戻しが効かない」と感じたらまずここを見てください。

## 更新

直したものを受け取るには、ターミナルから 2 つを順に実行します。**片方だけでは版が上がりません。**

```bash
claude plugin marketplace update lrm-equipment
claude plugin update yellow@lrm-equipment
```

`claude plugin list` の `Version:` が上がっているかで確かめられます。

### 旧名 `yellow-dispatch` で入れている人は、入れ直しが要ります

この拡張は以前 `yellow-dispatch` という名前で配っていました。**旧名で入れた人には、上の更新が
当たりません。** Claude Code は設定の鍵を拡張名で張るので、名前が変わると別の拡張として扱われ、
旧名のほうはカタログに無い状態で残ります (新名に `claude plugin update` を打つと
`Plugin "yellow" not found` で終わります)。**入れ直しても作業置き場は引き継がれません** —
置き場の値も置き場所も拡張名でぶら下がっているためです。

```bash
claude plugin uninstall yellow-dispatch@lrm-equipment   # 1. 旧名を外す (/plugin の画面でも同じ)
claude plugin marketplace update lrm-equipment          # 2. カタログを取り直す
claude plugin install yellow@lrm-equipment              # 3. 新名で入れる (置き場をもう 1 度聞かれます)
```

そのうえで **新しいセッションを開いて**、`cat "$CLAUDE_PLUGIN_DATA/dispatch.json"` に
`work_root` が出るのを確かめてください。ここが空のままだと、フックは黙って何もしません
(上の「効いているかの確かめ方」の 3 と同じ状態)。

`~/.claude/settings.json` に旧名の鍵 (`enabledPlugins` と `pluginConfigs` の
`yellow-dispatch@lrm-equipment`) が残っていたら、手で消してかまいません。残っていても
新名の動きには効きませんが、`/plugin` の一覧に消えた拡張が並び続けます。

**入切はセッションを開き直したときから効きます。** 拡張とフックの読み込みはセッションの開始時に
1 度だけ走るので、いま開いているセッションでは何も変わりません。

## すでに手元に同じスキルを持っている人へ — 切り替えと巻き戻し

自分の `.claude/skills/` に `dispatch` や `work` を持っている場合、拡張を入れると**同じ役割の
スキルが 2 つ並びます。** 名前は衝突しません (拡張側は `yellow:dispatch`、手元は
`dispatch`) が、両方見えていると発火先が揺れます。どちらか片方を生かしてください。

**手元のファイルは消さないでください。** 巻き戻せる状態を保つのがこの手順の目的です。

### 可動部は設定 2 ファイルだけ

| 生かす/殺すもの | 拡張側 | 手元側 |
| --- | --- | --- |
| スキル | `/plugin` で拡張ごと入切 | `skillOverrides` で 1 つずつ `off` |
| フック | 拡張の `hooks.json` が自動で載る | 自分の `settings.json` の `hooks` から外す |

**フックだけは重ねられません。** 両方生きていると差し戻しのフックが 2 回走り、それぞれ別の置き場を
見るので、片方が「契約が無い」と言って差し戻します。**スキルを `off` にする作業と、フックを外す
作業は同時にやってください。**

### 切り替える

まず戻れる状態を作ります。設定ファイルが git 管理下なら**コミットしておく**、外なら**写しを取る**。

```bash
cp ~/.claude/settings.json ~/.claude/settings.json.bak-before-yellow
```

そのうえで、手元側を黙らせます。

```jsonc
// 自分の settings.json (プロジェクト側の settings.local.json でもよい)
{
  "skillOverrides": {
    "dispatch": "off",
    "work": "off",
    "grilling": "off",
    "pr-response": "off",
    "retrospective-codify": "off",
    "memory-to-skill": "off"
  }
  // hooks からは dispatch-gate / dispatch-nudge / work-index-gate / pr-response-gate の 4 本を外す
}
```

最後に `/plugin` で `yellow` を有効にします。

### 戻す

2 手です。

```bash
# 1. 拡張を止める (/plugin の画面でも同じことができる)
claude plugin disable yellow@lrm-equipment

# 2. 設定を戻す
git checkout <settings のパス>                                  # git 管理下なら
cp ~/.claude/settings.json.bak-before-yellow ~/.claude/settings.json   # 写しから戻すなら
```

手元のスキル本体には一度も触っていないので、これで元の状態に戻ります。

**ダイヤルが 2 本あるので、4 つの状態が作れます** — 両方生かす / 拡張だけ / 手元だけ / 両方黙らせる。
うまくいかない箇所だけ手元に戻して使い続けることもできます。

## 手を入れたら、テストを走らせる

`hooks/` と `scripts/` の中身を変えたら、直したつもりのことが本当にそうなっているかを確かめる。

```bash
bash claude/plugins/yellow/dispatch/tests/run-all.sh
```

外へは 1 度も出ない (Slack にも GitHub にも送らない)。ファイルは一時ディレクトリの中だけで作るので、
自分の作業置き場は 1 バイトも変わらない。

| ファイル | 何を確かめるか |
| --- | --- |
| `tests/workroot-cases.sh` | transcript (Claude Code が hook に渡す会話の記録) の 1 行から「触ったパス」を取り出す処理。編集ツールごとの引数名、Bash の複数パスと引用符、壊れた入力、**読み取りだけのコマンドを書き込みと数えないこと** |
| `tests/stop-hook-cases.sh` | ターン終了時に差し戻す 2 本。走行中の契約・読めない契約・置き場の外の契約、検査が例外で落ちた回、再入時の沈黙、置き場が未設定のときの沈黙 |
| `tests/pr-response-gate-cases.sh` | PR の仕上げを手順書に乗せるゲート。1 回目から止める操作と往復に入ってから止める操作の分かれ目、手順書を開いたあと黙ること、出力に引用された文字列を開封と読み違えないこと、ヒアドキュメントの中身を操作と数えないこと |
| `tests/write-config-cases.sh` | 導入時の値から設定を書く処理。共有 CSS の失敗が設定の書き出しを巻き込まないこと、差し替えに失敗しても書きかけを残さないこと、相対パスと空の入力で前の設定を壊さないこと |
| `tests/link-check-cases.sh` | 成果物のリンク検査。外部 URL を検査しないこと、`?tab=1#section` 付きでもファイル名だけを見ること、壊れた URL を報告して検査を続けること |
| `tests/skill-name-cases.sh` | 本文に残った前置きの無い呼び名 (`recipient-centric:` を欠いた `commit` ほか 3 つ) の検出。4 つの呼び名それぞれを単独で拾うこと、相対パスやファイル名を名指しと数えないこと、実測ログの引用行だけを完全一致で除外すること、その引用が消えていないこと、許可行に別の古い呼び名を書き足したら見逃さないこと |

新しく分岐を足したら、その分岐を通すケースをここへ 1 行足す。**「手で 1 回動かして確かめた」で済ませない** —
次に誰かが触ったときに、その確認はもう残っていない。

## この拡張だけでは埋まらない参照

`dispatch` のモード定義は、この拡張に入っていないスキルやコマンドを名指しします。**無くても
dispatch 自体は動きます** が、その工程に来たときは手元にあるものを使うか、その工程を飛ばします。

| 名指ししているもの | 何のために呼ぶか | どうするか |
| --- | --- | --- |
| `/recipient-centric:commit` ほか 3 つの点検 | コミットを、受け取る側が読める形にするための関門 | 同じカタログの `recipient-centric` 拡張に入っている。入れていなければ通常のコミットにする |
| `/pr-create` | Draft PR の作成 | 手元のコマンド定義を使う。無ければ素の `gh` で Draft を立てる (そのあとの仕上げは同梱の `pr-response` が受け持つ) |
| `/pr-doc` | レビュワー向けの資料作り | 契約の `pr_doc` を `false` (既定) にしておけば呼ばれない |
| `slack-to-shogun` | 節目の Slack 投下 | `slack-notify` 拡張を一緒に入れる。無いときは会話で報告する |
| `dev-pipeline` 系 (開発タスクを工程ごとに回す自社の仕組み) | `pipeline` モード | その仕組みを使っていなければ、このモードは選ばれない |
| `staging-qa` `gh-stack` | Staging での QA / 積み重ね PR | 手元にあれば使う |

## 作った人の環境の話が残っている箇所

動作には影響しませんが、**そのまま読むと合わない**ものがあります。

- **工程 (phase) の語彙**は `dev-pipeline` という別の仕組みの並びに揃えてあります。使っていないなら
  `work.jsonc` の `phase` は省略してよいです (省略しても検査は通ります)
- **プロジェクトの色分け** (`scripts/gen-index.py` の `PROJECT_COLORS`) は作った人の案件略称です。
  自分の略称に書き換えてよいですが、書き換えなくても表にない略称は灰色で出るだけです
- **Why に書かれた日付と実例**は、そのルールが生まれた経緯です。自分の環境で起きたことではありません
