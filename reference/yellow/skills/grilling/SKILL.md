# grilling — 前提を残さず洗い出す

出典: [mattpocock/skills](https://github.com/mattpocock/skills/tree/main/skills/productivity/grilling) の `productivity/grilling`。手順は原文どおりで、この環境向けに足したのは 3 点だけ (発火境界 / 質問フォーマットの 3 行目 / 決定ログの置き場)。

決めたいことを 1 個の決定として置き、そこから枝分かれする決定を**設計ツリー**として広げていく。ゴールは案を出すことではなく、**暗黙の前提をゼロにして共通理解を作る**こと。

## 容赦なく詰める

このスキルは聞き取り調査ではない。**ユーザーの考えを叩いて、弱いところを出させる**もの。遠慮して問いを減らすと、名前どおりの働きをしない。

- ユーザーが**既に決めているつもりのこと**も、根拠が示されていなければ問いに戻す
- 推奨回答を当たり障りのないものにしない。**自分の判断を出して、反論させる**
- 「たぶん大丈夫」「そこは後で」で流さない。後回しにするなら、**それ自体を 1 つの決定として木に置く** (誰がいつ決めるか)
- 空気を読んで問いを削らない。**問いの数を減らす方向の判断は、事実を調査へ回すとき以外にしない**

## ラウンド制で進める

- **フロンティア** = いま聞ける問いの集まり。前提になる決定がすべて片付いた問いだけが入る
- 1 ラウンドで、フロンティアの問いを**まとめて同時に**出す。番号を振る
- 回答を待つ。**待たずに先へ進まない**
- 未確定の決定に答えが依存する問いは、**今回のラウンドでは出さない**。次に回す

回答が返るたびに決定が確定し、その先の枝が開く。フロンティアは外側へ広がっていく。

### 調査が走っている間は問いを出さない

**サブエージェントに投げた調査が 1 本でも走っている間は、問いを出さない。** 全部返ってきて、セッションが手を止めて待ちに入る瞬間に、そのラウンドぶんをまとめて 1 つの塊で出す。

ユーザーが答えられるのは、セッションが待ちになってからしかない。走っている最中に問いを流すと、こうなる。

- **ユーザーの回答が順番待ちに入る。** 打ち込んでも読まれるのは調査が返ったあとで、その間ユーザーは自分の回答が届いたのかどうか分からないまま待つ
- **1 ラウンドが小分けに割れる。** 「フロンティアをまとめて同時に出す」という約束が崩れ、ユーザーは何問残っているのかを数えられなくなる
- **問い自体が変わることがある。** 調査の返りで前提が確定し、出した問いが要らなくなる (聞かなくても分かることを聞いた形になる) か、選択肢の並びが変わる

**「調査でブロックしない」は、問いを立てる作業を止めるなという意味であって、問いを出す瞬間を早めろという意味ではない。** 調査の返りを待つ間にやることは、次のラウンドの問いを組み立てておくこと・設計ツリーを更新しておくこと。出すのは待ちに入ってから。

判定は 1 問でよい — **いま自分は、この直後にユーザーの入力を待って止まるか?** No なら出さない。

### ツリーを毎ラウンド見せる

頭の中に持つだけでなく、**設計ツリーを目に見える形で出す**。確定した決定・いま聞いている問い・まだ前提待ちの枝が、1 枚で分かる状態にする。

見せないと、ユーザーは「私が拾っていない枝」に気づけない。ツリーを出すことで**ユーザー側から枝を足せる**ようになる。これが単なる質問リストとの違い。

## 質問フォーマット

```text
❓ **Q1** — **<題>**: <文脈・とりうる選択肢>

➡️ 推奨: <推奨する答えと、その理由>
🔓 これで進む: <この回答で何が決まり、どの工程が動き出すか>
```

`🔓` の行を落とさない。CLAUDE.md の「ユーザーへの質問は選択肢 + 回答で何が進むかの形にする」は、この行が無いと満たせない。

### 問いの最後に、コピーして埋め戻せる回答フォームを付ける

ラウンドの問いを出し終えたら、**最後にそのラウンドの回答フォームを 1 つ置く。** コードブロックに入れる (そのままコピーできる)。

````text
```text
Q1=
Q2=
Q3=
```
````

守る形は 4 つ。

- **1 問 1 行。** `Q<番号>=` だけを書き、右は空にしておく。番号は問いの番号とそのまま揃える
- **フロンティアに出した問いを全部並べる。** 一部だけ載せると、載っていない問いが答えられないまま落ちる
- **推奨を各問に必ず書く。** ユーザーは `Q1=推奨通り` と 4 文字で返せる。推奨が無い問いがあると、そこだけ書く手間が跳ね上がる
- **選択肢には短い記号を振る** (`a` / `b` / `c`)。`Q2=b` で返せるようにする。長い選択肢名を書き写させない

これは飾りではなく、返ってくる速さそのものを決めている。実測ではユーザーの回答はほぼ全部この形 (`Q1=推奨通り` / `Q2=b` / `Q3=<自由文>`) で返っており、フォームを付けないと同じ内容を毎回ユーザーが手で組み立てることになる。

**AskUserQuestion (ピッカー) は使わない。** テキストで番号付きに出す。理由は 2 つあって、ピッカーは 1 コール 4 問の柵があるためラウンド制と噛み合わないことと、探索段階ではピッカーを出さない (会話で膨らませる) という判断が既に出ていること。

## 返答待ちに入るときは Slack に投下する

**ユーザーの返答が来ないと先へ進めない状態に入る瞬間は、必ず `slack-to-shogun` で報告スレッドへ投下する。** 該当するのは 2 つ。

1. ラウンドの問いを出して回答を待つとき (毎ラウンド。2 回目以降も省略しない)
2. 完了のまとめを出して「それでよい」を待つとき

投下は**問いを出すのと同じターンの中で**行う。投下せずに待ちに入らない。ユーザーは会話画面を見ていないことがあり、このスキルは待ちの時間が長い (ラウンドが何度も続く)。投下が無いと、問いを出したまま何時間も止まる。

`--header` と `--color` は「判断を仰ぐ」の節目を使う (❓ / `#8B5CF6`)。ラウンド番号を header に入れて、同じスレッドに並んだときに何回目の待ちか分かるようにする。

```text
❓ <識別子> / grilling R2 要回答      ← ラウンドの問い待ち
❓ <識別子> / grilling 合意待ち       ← 完了のまとめ待ち
```

本文に入れるのは次の 3 つ。**問いの全文はコピーしない** (推奨・`🔓` 行・設計ツリーは会話側が正本)。

- 何を聞いているか — 問いの題を番号つきで 1 行ずつ
- いま何ラウンド目で、フロンティアに何問残っているか
- 回答は会話側で受ける旨

```bash
MSG_FILE=$(mktemp)
trap 'rm -f "$MSG_FILE"' EXIT
cat > "$MSG_FILE" <<'EOF'
ラウンド 2 の問いを出した。回答待ちで止まっている。

- Q1 — 除外リストの持ち場所
- Q2 — 既存テナントの移行タイミング
- Q3 — 失敗時に誰が気づくか

フロンティアの残り: この 3 問 (Q1 の回答で次の枝が 2 本開く)
推奨と「これで進む」は会話側に出してある。回答は会話で。
EOF

# 投下は slack-notify 拡張の slack-to-shogun スキルに任せる (この拡張には送信手段が入っていない)。
# 見出しと色帯は必須なので、下の 2 つをそのまま渡す。
#   --header "❓ sec / grilling R2 要回答"   --color "#8B5CF6"
```

立会いが `away` (不在) のときは grilling 自体を走らせないので、この投下も起きない (下の「自分から発火しない場面」を参照)。

## 事実は自分で調べる

ファイル・ツール・外部データを見れば分かることは、**ユーザーに聞かない**。サブエージェントに投げる。依頼文は `agent-brief` の委譲契約 (出典義務・推測明記・報告フォーマット) に従う。

サブエージェントの結果を待つ間も、フロンティアの残りの問いを**組み立てる作業は進めてよい**。調査の返りを待って手を止めない。

ただし**出すのは調査が全部返ってからにする** (上の「調査が走っている間は問いを出さない」)。止めるのは問いを出す瞬間だけで、考えることは止めない。

ユーザーに残すのは「判断」だけ。調べれば分かることを聞くと、ユーザーの時間を使って自分の手間を省いたことになる。

## 完了する

**フロンティアが空になったら終わり。** 設計ツリーの枝をすべて辿り、暗黙の前提が 1 つも残っていない状態。回数では終わらせない。

終わったら、次に進む前に 1 回だけまとめて出す。

1. 確定したこと (決定と、そう決めた理由)
2. 捨てた枝 (検討したが採らなかった案と、その理由)

ユーザーが「それでよい」と言うまで、推奨や設計に進まない。**共通理解ができたことの確認が、このスキルの成果物。**

## 決まったことを会話に置き去りにしない

設計ツリーは会話にだけ置くと `/compact` で消える。確定した決定と捨てた枝は、作業ディレクトリの成果物 (`work` スキル) に「決定ログ」として書き出す。

`design` モードの `done_when` は「採用案と却下案が理由つきで書かれ」なので、**捨てた枝がそのまま却下案の記録になる**。工程 5 (優先順位で決める) で書き直す必要は無い。

契約 (`run-contract.jsonc`) には積まない。あれは走行中に機械が読む欄だけを置く場所で、決定ログは人間が後から読むもの。

## 自分から発火しない場面

下は**勝手に走り出さない**場面。ユーザーが明示的に呼んだら、どの場面でも走る (走行中の作業の途中でも)。

| 場面 | 行き先 |
| --- | --- |
| 新しい仕事の起点 (「〜に着手」「これ進めて」) | `dispatch` (進め方の判定が先) |
| 走行中の契約への差し戻し・追加指示 | 走行中モードへの矯正。自分からラウンドを開かない |
| 手順が確定している経路 | `ship` / `commit` / `rule-check` / `pr-create` をそのまま走らせる |
| 事実関係を確定させたいだけ | `investigate` (聞く相手はユーザーでなくコード) |
| 立会いが `away` (不在) | 走らせない。答える人がいないとフロンティアが空にならず固まる。既定で埋めて `questions_parked` に残す |

## 落とし穴

| 失敗 | 原因 | 対策 |
| --- | --- | --- |
| 思いついた問いを全部 1 ラウンドで出し、半分が前提待ちで無意味になった | フロンティアの定義を無視した | 前提が未確定の問いは次ラウンドへ送る。今回出さない |
| ユーザーに事実を聞いた (「あのファイルどうなってましたっけ」) | 調べる手間を惜しんだ | ファイル・ツール・外部データで分かることはサブエージェントへ |
| 遠慮して問いを減らし、聞き取り調査になった | 「しつこいと思われる」を判断に入れた | 問いを減らす方向の判断は、事実を調査へ回すとき以外にしない。ユーザーは詰められに来ている |
| 前提が残っているのに「だいたい見えた」で設計に進んだ | フロンティアが空になる前に切り上げた | 空になるまで続ける。長いと思ったらユーザーが止める (止める権限はこちらに無い) |
| 問いを出したまま Slack に投下せず、ユーザーが気づかないまま止まった | 会話画面を見ていると思い込んだ | 返答待ちに入るのと Slack 投下は 1 手。投下しないなら待ちに入らない |
| AskUserQuestion で出して 4 問に収まらなかった | 選択肢があるのでピッカーが合うと考えた | テキストで番号付きに出す |
| 調査が走っている最中に問いを出し、ユーザーの回答が順番待ちのまま何分も読まれなかった | 「調査でブロックしない」を、問いを出す瞬間まで早めてよいと読んだ | 出すのは待ちに入る直前。走っている間は問いを組み立てるところまでにする |
| ユーザーが回答を書くのに、問い 1 つずつ番号と答えを手で組み立てていた | 問いを出して終わりにし、返す側の手間を見ていなかった | ラウンドの最後に `Q1=` の回答フォームを 1 つ置く。推奨と選択肢の記号もセットで付ける |
| 詰め切ったのに、その内容が設計ドキュメントに残らなかった | 会話に置いたまま次の工程へ進んだ | 確定した決定と捨てた枝を作業ディレクトリの決定ログへ書き出す |
