# dispatch — 進め方を判定して、宣言して、やり切る

お題は起動時の引数で渡される。引数が無ければ、直前の会話から何をするかを読み取る。

長い手順書を書かなくて済むようにするための入口。**ユーザーが書くのはお題だけ。** 進め方はこちらが決め、指定が無い欄は既定で埋め、宣言してから走り切る。**既定は不在** — 走り出す前の確認はしない。

## 使う前に: 作業置き場の在り処を 1 回だけ解く

走行中の契約 (`run-contract.jsonc`) は**作業置き場の下**に置く。場所は拡張の導入時にダイアログで受け取っているので、セッションで 1 回だけ読み出して覚える。以下このページでは `<作業置き場>` と書く。

```bash
cat "${CLAUDE_PLUGIN_DATA}/dispatch.json"   # {"work_root": "...", "stg_check_skill": "..."} が入っている (stg_check_skill は任意。無ければ欄ごと無い)
```

出てこないときは、まだ導入時の入力が済んでいない。`/plugin` から `yellow` の設定を開いて入れてもらう。**値が無いと、やり切らせるフックが黙って何もしない側に倒れる** (導入直後の人のターンを止めないため)。

## 発火するかの判定に時間を使わない — 作業なら通す

「これは dispatch を通すほどの仕事か?」を考えない。**考えた時点で発火漏れの側に倒れる。** 判定は 1 問だけ。

> **このお題は、何か成果物を作るか・何かの状態を変えるか?**

Yes なら通す。1 ファイルの修正でも、調査でも設計でもレビューでも仕組みづくりでも、**規模を問わず通す。** 「小さいから」「すぐ終わるから」は理由にならない (小さいはずの仕事が伸びたとき、契約も見張りも無い状態で走っていることになる)。

No で済むのは次の 3 つだけ。

| 通さない | 例 |
| --- | --- |
| 走行中の契約への矯正・追加指示・質問 | 「ちがう、そこはこう」「これはどうすればいいの?」 |
| 成果物を作らない単発の実行・事実確認 | 「ブランチ名教えて」「テスト走らせて結果だけ見せて」 |
| 手順が全部指定されている依頼 | 「このファイルの 3 行目を X に置換して」 |

Why: 2026-09-03 ユーザー矯正 — 「基本的にどんな作業でも /dispatch が走るようにしたい。わざわざ /dispatch ってかくのめんどい」。それまでは「〜に着手」「実装開始」のような**語彙リスト**で発火していたため、リストに無い言い方 (「これ直しといて」) が素通りしていた。**語彙ではなく上の 1 問で判定する。** 取りこぼしは UserPromptSubmit hook (この拡張の `hooks/dispatch-nudge.py`) が走行中の契約が無いターンに 1 行差し込んで塞ぐ。

## 走行中なら再判定しない

先に走行中の契約 (`<作業置き場>/*/run-contract.jsonc` の `status` が `running`) を探す。見つかったら、いまのお題が**モードの切り替え**なのか**走行中モードへの矯正**なのかを見る。

| お題の例 | 扱い |
| --- | --- |
| 「ちがう、そこはこう」「消して」「これはどうすればいいの?」 | 矯正。再判定せず、走行中の契約のまま続ける |
| 「調査はいい、実装に入って」 | 明示的な切替。契約の `mode` を書き換えて再宣言する |

過去ログ上、ユーザー入力の 44% は 250 字未満の差し戻し・追加指示だった。ここを再判定に回すと、一言で走っていた作業が捨てられる。

## モードは 3 つの軸でできている

固定リストではなく、次の 3 軸の組み合わせ。**新しい進め方が出てきても軸は変わらない。**

| 軸 | 値 | 何が変わるか |
| --- | --- | --- |
| **成果物** (deliverable) | `modes/` のファイル名 | 何を作れば終わりか。工程が変わる |
| **到達範囲** (scope) | `single` / `chain` | 1 本で終わりか、N 本を順に消化するか |
| **立会い** (presence) | `away` (既定) / `present` | 聞かずに保留して進むか、聞いてよいか |

成果物のモード定義はこのスキルの `modes/*.md`。**ここにモードを書き写さない。** 新しいモードはファイルを 1 枚足すだけで増える (足し方は `retrospective-codify`)。

**モードを直接指定したいとき**は、お題に「ship で」のように書けばよい。その場合は Step 2 の成果物の判定を省き、到達範囲と立会いだけ決める。

---

## Step 1 — 観測する

語彙だけでは足りない。**状態を見てから決める。**

```bash
pwd; git -C . rev-parse --show-toplevel 2>/dev/null; git -C . status --short 2>/dev/null | head
ls -1t <作業置き場>/*/run-contract.jsonc 2>/dev/null   # 件数を絞らない。絞ると古い running を見落とす
ls -1 "${CLAUDE_PLUGIN_ROOT}/skills/dispatch/modes/"
```

走行中の契約があれば先に読む。**`running` が 2 本以上見つかったら、そこで止まってユーザーに聞く。**
どれが今のお題の契約かを推測で決めると、別の仕事の契約に進捗を書き込む。

## Step 2 — 3 軸を決める

各モード定義の frontmatter にある `signals` と `not_this_when` を突き合わせる。

**立会い** — **既定は `away` (不在)。** 次のどちらかに当たるときだけ `present` にする。

1. **在席の合図がある**: 見てる / いま隣で / 相談しながら / 一緒に / 確認しながら進めて / 聞いて決めたい
2. **成果物が `design`**: 設計はユーザーの判断そのものが材料なので、聞けない状態だと成果物が空になる (`modes/design.md` 工程 2 の `grilling` が走らなくなる)

「不在 / 席を外す / 寝る / あとは任せた」のような不在の宣言は既定を確かめるだけの言葉なので、**成果物が `design` 以外なら判定は変わらない。**
**`design` のときだけは、明示された不在が優先されて `away` になる** (`modes/design.md` の「このモードだけ立会いの既定が `present`」に、聞けないときの代替経路 —
外れても直せる分岐は by「暫定」で `decided` に入れて `questions_parked` に積み、書き進める。取り返しがつかないもの・本人しか知らない事実だけを `undecided` に入れて止まる — が書かれているため)。

Why: 2026-09-03 ユーザー矯正 — 「デフォルトを不在に変えてほしい」。従来は既定 `present` で、不在の宣言が無い限り走り出す前に確認していた。実測ではその確認の大半が既定で埋められるものだったので、既定を反転させ、**聞かずに走って迷いは `questions_parked` に積む**側に寄せた。

**到達範囲** — 次の語があれば `chain`。

> Stacked / スタックト / 1PRずつ / 1本ずつ / PR-1〜N / N リポ / 順番に / 全部の PR

迷ったら**狭いほう** (`single`) に倒す。範囲は後から広げられるが、広げすぎた作業は戻せない。

### 実装の依頼は、先に計画の契約を作る

成果物が `ship` でも、実装の依頼はすべて先に**計画の契約** (`plan.jsonc`) を作る。規模を問わない。作業ディレクトリは `work` スキルで作り、**同じ取り組みのものが既にあればそれを使い回す**。`modes/ship.md` の工程 2 が「契約があるか確かめ、無ければ `modes/design.md` の手順で作る」になっている。契約の欄は `references/plan-contract.jsonc`、案が割れたときの順位は `references/priorities.md`。

## Step 3 — 言われなかったことは既定で埋める

**「指定が無い = 判断を委ねられた」であって、「やらなくてよい」ではない。** 指定が無い欄は次の既定で埋め、埋めた内容を宣言と Slack に**前提として明記する**。

### 表に無い操作は、この 2 問で決める

下の既定値表は結論だけを並べたもの。**表に載っていない操作**に当たったら、次の 2 問で判定する。危険度で決めない。

1. **取り返せるか?** (元に戻す操作が存在し、自分で実行できるか)
2. **他人の時間が動き出すか?** (誰かがそれを見て作業を始めるか、外部に届くか)

両方 No なら**任されている**ので勝手にやる。どちらかが Yes なら**握る** — 実行せず、用意して報告する。

| | 取り返せる | 取り返せない |
| --- | --- | --- |
| **他人が動かない** | ローカル実行・ブランチ作成・コミット・force-push・worktree・調査スクリプト → やる | 本番でのコマンド実行・データ削除 → **握る** |
| **他人が動く** | Draft PR 作成・CodeRabbit への依頼 → やる | Ready 昇格・マージ・外部への送信・公開 → **握る** |

Why: Ready 昇格を握る理由は危険だからではない。**「私自身が目を通さずにレビュー依頼をメンバーにするのは非常識だからね」** (2026-06-26) — 同僚のレビュー時間が動き出すから。同じ軸で、送信済みのスカウト文は遡って直さない一方、未マージの PR は 7 リポ遡って直す判断が出ている。

この軸は固定ではない。実績が積まれた領域では権限が広がる (Ready 昇格は 2026-07-29 に「収束したら勝手に上げてよい」へ移った)。**既定は狭い側に置き、広げる提案は自分から出してよい。** ただし契約の `policy.draft` が `keep` (既定) のあいだは、Ready 昇格は握る側に読む。昇格してよいのは、契約に `ready` / `merge_ok` と書いたときだけ。

### 完了ラインの既定は「収束まで」。毎回言わせない

**ユーザーが「収束するまで」と書かなくても、終わりの位置は動かない。** 指示が無いときの完了ラインはここ:

> **CodeRabbit の指摘が 0 件 (inline スレッド + review 本文の折りたたみの両方) で、CI が全部 green。**
>
> ただし折りたたみのうち **純粋な好みの指摘 (`Nitpick comments`) だけは 0 でなくてよい。** 1 件ずつ裁いたうえで、拾わないと決めたものを「どれを・なぜ拾わないか」と PR のコメントに書き残していれば、それで閉じたものとして数える (`pr-response` 手順5 の条件3 の表)。折りたたみは返信でも `@coderabbitai resolve` でも畳めないので、必須 0 件に入れると「指摘のとおり直す」以外に閉じる道が無くなり、拾わないと決めた時点で永久に終われなくなる。

そこへ至る前段の操作 — 実装 / `/recipient-centric:commit` / push / Draft PR 作成 / `@coderabbitai review` の依頼 / 指摘対応 / CI 落ちの修正 — は **全部「言われなくてもやること」の側**にある。「push していいですか」「コミットしていいですか」で手を止めない。

Why: 2026-08-27 ユーザー矯正 —「毎度『収束するまで』って言わないと push 前で止まったりするのがうざい。大前提、指示がなければ CodeRabbit 収束 + CI green までやる。つまり前段の push やコミットも自ずとやるということ」。

**手を止めてよいのは次の 3 つだけ。**

| 止まってよい場面 | どうするか |
| --- | --- |
| 握る操作に当たった (Ready 昇格・マージ・本番でのコマンド実行・外部への送信) | 実行せず、用意して報告する (上の 2 問表) |
| 収束しない (同じ指摘が 2 回続いた / CI が同じ原因で 2 回落ちた) | `convergence` に記録して打ち切り、`questions_parked` へ回す |
| 判断が要る分岐に当たった | `present` なら聞く。`away` なら暫定で決めて `questions_parked` に積み、走り続ける |

`policy.draft` が既定の `keep` でも、それは **「Ready に上げないだけ」であって「Draft のまま放置してよい」ではない**。Draft のまま収束させるところまでが既定。

CodeRabbit がレート制限で動かないときも飛ばさない。15 分おきに PR の URL と `@coderabbitai review` を Slack へ投下してユーザーに投稿してもらい、レビューが返るまで回す (`pr-response` の手順4。同じ拡張に入っているので、そのまま開ける)。

### STG での確認まで走らせる — 依頼にあるときだけ

**依頼に「STG まで」「STG で確認まで」とあるときだけ**、契約の `policy.done_line` を `stg`、`policy.qa` を `staging`、`policy.draft` を `ready` にする。`ready` なのは、マージを頼むには Ready への昇格が要り、「STG まで」という依頼がそこまでを含むため (上の 2 問表で Ready 昇格は握る操作だが、この依頼では握らない)。言われなければ `converged` / `keep` のまま (STG に出すのは他人の時間が動く操作なので、既定には入れない)。

`converged` まで進めたあとの流れは `modes/ship.md` の「完了ラインが STG のとき」にある。要点だけ書くと、マージはユーザーに頼んで待ち (待つあいだ契約の `status` は `blocked`)、マージされたらリリース作成 → STG へのデプロイを見届ける → STG で確認、と続ける。**本番には何もしない。**

- **マージまで任せる** と依頼にあるときだけ、マージも自分でする (`policy.draft` を `ready` から `merge_ok` にする)。CI と CodeRabbit が収束していない PR はマージしない
- **STG での確認の手順はこの拡張に書かない。** 導入時に `stg_check_skill` として入れてもらったスキル名 (例: `staging-qa`) を呼ぶ。リリースを作ってよいかも、そのスキルとリポジトリごとの許可に従う。`stg_check_skill` が空なら「STG 確認の手順を持つスキルが設定されていない」と報告して止まる (`status` を `blocked`)

Why: マージは握る操作なので、止まる場所と待つ相手を決めておかないと、マージ待ちで黙って止まるか、勝手にマージするかのどちらかに倒れる。STG の確認手順は人ごと・リポジトリごとに違うので、拡張には書かず、入れてもらったスキルに任せる。

| 欄 | 既定 | なぜその既定か |
| --- | --- | --- |
| `scope` | `single` | 範囲は後から広げられるが、広げすぎた作業は戻せない |
| `presence` | `away` | 走り出す前の確認をしない。迷いは暫定で決めて `questions_parked` に積む。`present` にするのは在席の合図があるか、成果物が `design` のときだけ |
| `policy.draft` | `keep` | マージは不可逆。明示されない限りしない |
| `policy.done_line` | `converged` | 指示が無ければ CodeRabbit 指摘 0 + CI green まで走る。コミット・push・指摘対応の往復はこの既定に含まれる (上記「完了ラインの既定」)。依頼に「STG まで」「STG で確認まで」とあるときだけ `stg` (下記「STG での確認まで走らせる」) |
| `policy.qa` | `playwright` | コード変更した箇所は実機で確認し、**何を踏むかを先に設計し、結果を証跡として `workdir` に残す**。省略の判断はユーザーがする |
| `policy.ci_delegated` | `false` | ローカルで test / lint を回す。CI 任せは明示されたときだけ |
| `policy.impl_delegate` | `sonnet` | メインの文脈を実装コードで埋めない。判断はメイン、コードを書く手は委譲 |
| `policy.pr_doc` | `false` | `/pr-doc` は求められたときだけ作る |
| `policy.merge_policy` | `none` | review モード。投稿までで止める |
| `policy.fix_here` | `false` | review モード。指摘だけ残し、対応は別でまとめる |
| `role` | `単独` | 1 セッションで頼まれた仕事を自分で最後までやる今までの動き。`指示する側` / `実装する側` にするのは下記「担当 (role)」の合図があるときだけ |
| `notify` | `on` | Slack への投下 (Step 6・完了報告) を省略しない。`off` にするのは「このセッションは Slack 連絡禁止」のような指示があるときだけ |
| `active_hours` | 制限なし (`null`) | 見張りは時間を問わず起こす。時間帯を言われたときだけ、その時間帯の中でしか起こさない (Step 8) |
| `worktree` | `chain` なら必須 / `single` なら無し | 連鎖は長時間走るので他セッションと衝突する |

**実機 QA が立たないとき** (docker が上がらない・環境変数が無い・ログイン情報が要る) は、勝手に既定を `none` に落とさない。`questions_parked` に「何が足りなくて踏めなかったか」を書いて報告する。

## Step 4 — 原則聞かない。聞くのは `present` のときだけ

**立会いの既定は `away` なので、この Step は既定では丸ごと飛ばす。** 前提はすべて Step 3 の既定で埋め、埋めた内容を宣言と Slack に書く。違っていたらユーザーが 1 行で殴れる。

聞くのは `present` と判定したとき (在席の合図があるか、成果物が `design`) だけ。そのときも、ユーザーに前提を書かせない。**観測できず、外すと手戻りが大きいものだけ**をこちらから聞く。

### 聞き方の柵

- **答えがはっきりしている質問はしない。** 聞く前に自分のベスト案を書き (`references/priorities.md` の順位に照らす)、選べる案が実質 1 つなら、聞かずに決めて宣言する
- 聞くのは、その順位を当てても本当に割れたときだけ。そのときも**案が 3 つ以上あるか、理想形に到達する案を 1 つ入れたか、各案に「これを選ぶと何が決まるか」を書いたか**を点検する。複数選択で足りる問いを単一選択にしない。「まだ決めない / 議論したい」を選びたくなる場面 (大きなアーキ判断) ではないかも見る
- **1 回のコールにまとめる。** 最大 4 問。2 回目は出さない (走り出してから聞かない)
- 各問は**選択肢 2〜4 個**。推奨があれば先頭に置き、末尾に「(推奨)」を付ける
- 質問文に**この回答で何がアンブロックされるか**を書く
- `away` のとき (= 既定) は**聞かない。** 既定で埋めて `questions_parked` に残す
- 成果物が `design` で、まだ探索段階 (「どんな風になりそう?」) のときは**聞かない。** 会話で膨らませる。ピッカーは方向が固まってから
- 全部が既定で埋まり、観測でも足りているなら**聞かずに Step 5 へ行く**

### 聞く候補 (該当するものだけ)

| 聞くもの | 聞く条件 | 選択肢の例 |
| --- | --- | --- |
| **どこまで出すか** | 成果物が `pr`、かつ Ready / マージまで求められている気配があるとき | Draft のまま収束まで (推奨) / Ready に上げる / マージまでやる |
| **環境の準備** | 実機 QA か docker が要る | `infisical login` 済み (推奨) / これから要る / QA は次回に回す |
| **正本の在り処** | 既存の設計ドキュメントが見つからない | ゼロから調べる (推奨) / 参照先を指定する |

**それ以外は聞かない。** 既定で埋めて宣言に書けば、違ったときにユーザーが 1 行で殴れる。

## Step 5 — 1 行で宣言してから走る

判定精度 100% は狙わない。**誤判定を 1 秒で殴れるようにする**のが目的。

```text
▶ ship / chain / away で走ります。PR-1〜4 を worktree で 1 本ずつ Draft まで。自信度 85%
```

宣言したら止まらずに次へ進む。承認は待たない。違ったらユーザーが止める。

## Step 6 — Slack に進め方を投下する (必須・省略禁止)

会話画面を見ていないことがあるので、`slack-to-shogun` で投下する。**`present` でも省略しない。**

投下するのは次の 5 点。長い手順書は書かない。

**`notify` が `off` のときは投下しない** (完了報告も同じ)。代わりに同じ内容を契約の `log` に残し、`role` が `実装する側` なら依頼元へ `SendMessage` で送る。`単独` と `指示する側` で `off` なら会話の中で伝える。見張りの復帰の知らせ・促しも同じ扱いで、Slack には出さず `log` に残す。

1. 何をやると理解したか (お題を 1〜2 文で言い直す)
2. どのモードで走るか (3 軸と、そう判定した理由)
3. どこまで行ったら終わりか (`done_when`)
4. 何を前提に置いたか (聞かずに既定で埋めた事項)
5. 自信度

## Step 7 — 契約を書く

作業ディレクトリを `work` スキルで用意し、直下に `run-contract.jsonc` を置く。**`work` スキルは index.html の生成まで走らせる** (契約だけ置いて終わると置き場の `index.html` のタイルが押せなくなる)。使わない欄は消してよい。増やすときは「後から機械が読む欄か」を考えてから足す。

**新規作成に直行しない。** dispatch は「新しい仕事の起点」で発火するので新規に倒れやすいが、**続きの仕事なら既存の作業ディレクトリがある**。`work` スキルのモード 1 の冒頭に既存を探す手順があるので、そこを通る (お題が `<作業置き場>/<dir>/` 配下のファイルを正本として指しているなら、その `<dir>` が答え)。

**契約は `<作業置き場>` の中に置く。外に出さない。** Stop hook (この拡張の `hooks/dispatch-gate.py`) は導入時に入力した置き場を見ていて、**その下の契約しか読まない**。外に置くと、やり切らせる歯止めがまるごと効かなくなる。

その代わり、**成果物を 1 つも生まずに終わった作業ディレクトリは Step 10 で片付ける。** 契約は走行中の見張りのために要るもので、終わったら残す価値が無い。

```jsonc
// 実行契約。走行中はこの 1 枚が正本。ping も compact も handover も Stop hook もここを読む。
{
  // ---- 宣言 (判定した内容。ここを見れば誤判定に気づける) ----
  "declared_at": "2026-08-02 16:20",
  "prompt": "ユーザーの原文をそのまま。要約しない (誤判定の検証に使う)",
  "mode": "ship",              // modes/ のファイル名
  "scope": "chain",            // single | chain
  "presence": "away",          // 既定 away (不在・聞かずに進む)。present (在席・聞いてよい) にするのは
                               // 在席の合図があるか、mode が design のときだけ
  "confidence": 85,            // 判定の自信度 (%)。低いときは declaration に理由を書く
  "declaration": "ship / 連鎖 / 不在 で走る。PR-1〜4 を worktree で 1 本ずつ Draft まで。",

  // ---- 担当・通知・時間帯 (既定は 単独 / on / 制限なし。使わない欄は消してよい) ----
  "role": "単独",              // 単独 | 指示する側 | 実装する側 (下記「担当 (role)」)
  "requested_by": null,        // role が 実装する側 のとき、依頼元のセッション名
  "team": [                    // role が 指示する側 のとき、どのセッションが何を担当しているかの表
    { "session": "実装A", "task": "PR-1 の実装", "state": "running" }
  ],
  "notify": "on",              // on | off。off なら Slack への投下 (Step 6・完了報告) を飛ばす
  "active_hours": null,        // 見張りが起こしてよい時間帯。例 "平日 6:00〜23:00"。null は制限なし

  // ---- 対象 ----
  "repo": "ccm",
  "workdir": "<作業置き場>/20260802_1600_ccm_例",
  "worktree": "<worktree の置き場>/ccm-例",   // 使わないなら null

  // ---- 方針。指定が無い欄は Step 3 の既定で埋め、埋めたことを宣言と Slack に書く ----
  "policy": {
    "draft": "keep",           // 既定 keep。keep | ready | merge_ok
    "done_line": "converged",  // 既定 converged (CodeRabbit 指摘 0 + CI green まで)。
                               // pr_only なら PR を立てるところまで。落とすのはユーザー指示があるときだけ。
                               // stg は依頼に「STG まで」とあるときだけ。このとき draft は ready (マージ待ち → リリース → STG 確認)
    "qa": "playwright",        // 既定 playwright。none | playwright | staging (done_line が stg なら staging)
                               // none 以外なら、QA 計画表と証跡を workdir に 1 枚残すところまでが工程 (modes/ship.md 工程 5・6)
    "ci_delegated": false,     // 既定 false (ローカルで回す)。true なら GHA CI に任せる
    "impl_delegate": "sonnet", // 既定 sonnet。none | sonnet | haiku
    "pr_doc": false,           // 既定 false。true なら /pr-doc まで作る
    "merge_policy": "none",    // review モード用。既定 none。none | merge
    "fix_here": false          // review モード用。既定 false (指摘だけ残す)
  },

  // ---- 時計仕掛けの見張り (Step 8 で張る)。cron_id は Step 10 で外す宛先になる ----
  "watchdog": { "cron_id": "41ce6864", "every": "1h", "armed_at": "2026-08-02 16:22" },

  // ---- この仕事の出どころ。台帳から取り出したなら必ず書く (Step 10 で書き戻す宛先になる) ----
  "ledger_refs": [
    { "file": "<作業置き場>/20260802_1600_ccm_例/_ledger/別タスク候補.html",
      "items": ["A7", "A8", "A9"] }
  ],

  // ---- 到達範囲と現在地 ----
  "chain": [
    { "id": "PR-1", "title": "カラム追加", "state": "done",    "pr": 5920 },
    { "id": "PR-2", "title": "削除受付",   "state": "running", "pr": null }
  ],
  "cursor": "PR-2",

  // ---- 止まっている理由。status が blocked のとき、待っている相手と用件を書く ----
  "waiting_for": null,         // 例 { "who": "ユーザー", "what": "PR をマージしてもらう (done_line が stg のとき)" }

  // ---- 完了判定。Stop hook がこれを読んでターン終了を止める ----
  // 1 行 1 条件。人間が読んで Yes/No を判定できる文にする。
  // done_when に「見張りを外した」を入れない。Step 10 は done_when を全部 Yes にしてから
  // status を done にし、そのあとで cron を外す順序なので、完了判定の時点では必ず No になる。
  // 撤去は status=done のあとの後始末として扱う (何度やっても同じ結果になる)。
  "done_when": [
    "chain の PR がすべて存在する",
    "各 PR の CI が green",
    "各 PR の未解決レビュースレッドが 0 件",
    "全 PR が Draft のまま維持されている",
    "PR ごとの QA 証跡が workdir にあり、index.html から辿れる",
    "ledger_refs の台帳に完了印を書き戻した"
  ],

  // ---- 収束の見張り。同じ指摘が 2 回続いたら打ち切って questions_parked へ ----
  "convergence": { "PR-2": { "round": 2, "last": "教材コピーのタイムアウトが再現する" } },

  // ---- 迷って暫定で決めたこと。戻ってきたユーザーへまとめて出す ----
  "questions_parked": [
    { "at": "2026-08-02 18:40", "q": "REVOKE_FAILED の通知先は Bugsnag でよいか",
      "provisional": "Bugsnag に飛ばす前提で実装した", "why": "他の異常系が Bugsnag に寄っているため" }
  ],

  // ---- 進捗ログ。ping はここの最終更新時刻で停滞を判定する ----
  "log": [
    { "at": "2026-08-02 16:25", "what": "PR-1 の /pr-response まで完了。Draft 維持・CI green" }
  ],

  "status": "running"          // running | done | blocked
}
```

`done_when` はモード定義の既定を出発点に、ユーザー指示で上書きする。**Yes/No で判定できる文にする。**「しっかりやる」「丁寧に」は条件にならない。末尾カンマは書かない (Stop hook が読めなくなる)。

### 台帳から取り出した仕事は、台帳へ返すところまでが工程

前の走行で「今回はやらない」と積んだものを、あとから取り出して片付けることがある (`_ledger/` の別タスク候補・残タスク・裁定待ちリスト)。このとき**台帳の側は誰も更新しない**。PR がマージされ、作業ディレクトリが Step 10 で消え、台帳だけが「未着手」と言い続ける状態が残る。

だから**出どころを契約に書く**。`ledger_refs` に台帳のパスと、この走行で消化する項目の番号を並べ、`done_when` に 1 行足す。

```jsonc
"ledger_refs": [
  { "file": "<台帳の絶対パス>", "items": ["A7", "A8", "A9"] }
],
"done_when": [
  "…",
  "ledger_refs の台帳に完了印を書き戻した"
]
```

**契約は消えるが台帳は残る。** 結果は残るほうに書く。書き戻す中身は Step 10 にある。

判定は 1 問でよい — **この仕事は、どこかの台帳に「あとでやる」と書いてあったものか?** Yes なら `ledger_refs` を書く。ユーザーが台帳のページを指して依頼してきたとき、そこに書かれた番号を引用して依頼してきたときは、まず Yes。

## Step 8 — 時計仕掛けの見張りを仕掛ける (毎回・省略禁止)

契約を書いたら、**プレイブックに取りかかる前に**見張りを 1 本張る。`away` のときだけではない。**在席でも API Error でセッションは黙って止まる。**

**張る位置がすべて。** 走り切ったあとに張る形にすると、いちばん落ちやすい長時間の走行中に見張りがまだ存在しない。落ちてから「そういえば張っていなかった」は取り返せないので、契約 → 見張り → 作業 の順を崩さない。

```javascript
CronCreate({
  cron: "<0/30 を避けた分> * * * *",   // 例 "38 * * * *" = 毎時 38 分
  recurring: true,
  prompt: "<下の「見張りに渡す prompt」>"
})
```

戻り値のジョブ id を契約の `watchdog.cron_id` に書く。**Step 10 で外す宛先になる**ので、書き忘れると仕事が終わったあとも鳴り続ける。

### 走行中は鳴らない。鳴った = 手が止まっている

session cron が発火するのは **REPL がアイドルのときだけ**で、作業が続いている間は 1 度も鳴らない。だから毎時の定期報告にはならず、**鳴ったこと自体が「止まっている」の合図**になる。

Stop hook (この拡張の `hooks/dispatch-gate.py`) は `status` が `running` のままターンを終えるのを差し戻すが、**API Error でターンごと落ちたときは hook を通らない**。そこが見張りの守備範囲。

**先に `active_hours` を見る。** 契約に時間帯があり、いまがその外なら、下の表に進まず**何もしない** (起こさない・Slack にも出さない)。時間帯は開始時刻を含み、終了時刻を含まない (`6:00〜23:00` は 6:00 以上 23:00 未満)。「平日」は月〜金で、祝日は区別しない。「最初に鳴ったとき」は、何時何分に鳴るかを問わない (時間帯に入ってから最初の発火)。時間外に鳴ったぶんは捨てて、時間帯に入って最初に鳴ったときに下の表を当てる。時間外のあいだ `log` が古くなるのは正常で、そこで「止まっている」と判定して構わない (起こすのがこの欄の目的)。`null` なら時間を問わず下の表へ。いまの時刻は手で打たず `date` で読む。

| 契約の `status` | `log` の最終更新 | 見張りがすること |
| --- | --- | --- |
| `running` | 30 分以内 | 何もしない (作業中に順番待ちしていた発火)。Slack にも出さない |
| `running` | 30 分より前 | 止まっている。下の「理由の分け方」へ |
| `blocked` | — | 止まってよい状態。契約の `waiting_for` にある相手と用件を、`notify` が `on` なら `slack-to-shogun` で促す (`off` なら促さない)。促すのは、その `blocked` に入って最初に鳴った回の 1 度だけで、促したら `log` に 1 行残し、同じ `blocked` のあいだは繰り返さない |
| `done` | — | 役目は終わり。`CronList` で自分の id を引き、`CronDelete` で外す |

### 理由の分け方 — 全部を再開してよいわけではない

- **ユーザーの回答待ち・承認待ち** (握る操作の前で止めた・平文で質問を投げた) → **再開しない。** 何を待っているかを `slack-to-shogun` で 1 通投下するだけにする
- **それ以外** (API Error・ネットワーク断・原因不明の停止) → **復帰する。** 契約の `cursor` と `log`、対象リポジトリの `git status` と直近コミット、PR と CI の状態から現在地を組み直し、`done_when` を満たすまで作業を続ける。復帰したことを `slack-to-shogun` で 1 通投下してから作業に入る

**「報告して終わり」にしない。** 報告だけの見張りは、止まっていることをユーザーが知る手段にはなるが、ユーザーが会話画面に戻るまで作業は止まったままになる。見張りの仕事は起こすことまで。

### 見張りに渡す prompt の書き方

起床時に渡るのはこの prompt **だけ** (compact 後は会話の文脈も残っていない)。文脈ゼロの初見が読んで完走できる自己完結文書にする。焼き込むのは 4 つ (`active_hours` があるときは、そこも書く)。

- **契約の絶対パス** (ここが正本。現在地はここから組み直す)
- **上の判定順序**をそのまま (時間帯の外なら何もしない / 何もしない / 促すだけ / 復帰する、の分岐)。`active_hours` は契約の値を写さず「契約の `active_hours` を読んで判定する」と書く (契約を書き換えたときに、見張りの文面を直さなくて済む)
- **この走行のお題と完了ライン** (1〜2 文)
- **復帰したときに踏むスキル** (`/recipient-centric:commit` 経由・`/pr-response` まで、など)

### 組み込みの `/loop` ではなく `CronCreate` を張る

`/loop 1h` でも同じ間隔で回せるが、こちらは**メインの入力欄をループ用に占有する**ので、走行中のユーザーが割り込みで話しかけにくくなる。`CronCreate` はアイドルに割り込んで 1 ターン走るだけなので、会話の邪魔をしない。撤去も id 指定で確実にできる。

### 見張りが救えないもの

- **セッションのプロセスごと落ちた場合。** session cron はプロセスと運命を共にするので一緒に消える。救えるのは「プロセスは生きているが手が止まった」場合だけ
- **7 日を超える走行。** recurring は 7 日で自動失効する (最後に 1 回鳴って消える)。それより長く走るなら張り直す

## Step 9 — モード定義のプレイブックを実行する

判定したモードのファイルを読み、そのプレイブックどおりに進める。**工程を飛ばさない。** 飛ばしてよいかの判断はユーザーがする。

進捗は契約の `log` に都度追記する。ここが止まっていることが、外から見た「詰まっている」の唯一の証拠になる。**見張りはこの時刻を見て、止まっているのか作業中なのかを分ける。** まとめ書きすると、動いているのに復帰をかけられる。

**`log` の `at` と `declared_at` の時刻は手で打たない。** 書き込むのと同じコマンドの中で `date` から入れる。エージェントは今の時刻を知らないので、手で打つと必ず見当になる。

```bash
# 時刻を受けた変数を、同じコマンドの中で契約の書き込みへ渡す
D=$(date '+%Y-%m-%d %H:%M') && python3 - "$D" <<'EOF'
import sys
at = sys.argv[1]
# ここで run-contract.jsonc の log に { "at": at, "what": "..." } を 1 行足して書き戻す
EOF
```

`date` を 1 回叩いて値を目で見てから、別のコマンドで書き込むのも同じ失敗になる (間に時間が進むうえ、写し間違いが入る)。

書く前に自問する — **「この時刻は、同じコマンドの中で `date` から入れたか?」**

Why: 2026-09-30〜10-01 の VIEW ごし化の走行で、見当で打った時刻が実際より 6〜20 分先になる失敗を 4 回踏んだ。1 回目のあとに「以後は date の値で書く」と契約の `log` に書いたが、次の走行でも、その次でも、契約を書いた直後でも再発した。見張りは `log` の時刻で「止まっているか」を判定するので、時刻が未来にずれると、本当に止まっていても止まっていないと読み違える。

## Step 10 — 完了する

`done_when` を 1 行ずつ Yes/No で点検し、全部 Yes になったら `status` を `done` にする。

**`status` を `done` にしたら、Step 8 で張った見張りを外す。** `watchdog.cron_id` を `CronDelete` に渡し、`CronList` に残っていないことを確かめる。外し忘れると、終わった仕事の見張りが毎時アイドルを叩き続ける (契約が `done` なら見張り側も自分を消しにいくが、それは保険であって手順ではない)。

**外れたことの確認は `CronList` でする。`CronDelete` の返り値では判定しない。** 分岐は 3 つ。

| `CronList` に自分の id が | 意味 | どうするか |
| --- | --- | --- |
| 無い | 外れている (`CronDelete` がエラーを返していても、既に消えていただけ) | 完了 |
| 残っている | 外れていない | `CronDelete` をもう 1 度だけ打ち、再び `CronList` で見る |
| 2 度目でも残っている | 自分では外せない | `watchdog.cron_id` を添えて `slack-to-shogun` で報告する。完了報告に「見張りが残っている」と 1 行書く |

**残ったまま黙って終えない。** 見張りの prompt は契約の絶対パスを持っているので、鳴っても契約が `done` なら何もせず自分を消しにいくが、それは保険であって、外れていない事実をユーザーが知らないままにしてよい理由にはならない。

**`ledger_refs` があるなら、作業ディレクトリを片付ける前に台帳へ書き戻す** (片付けてから思い出しても、もう手が届かない)。書くのは 3 つだけ。

1. 該当項目の**印を「済」に付け替える**
2. **いつ・どの PR / どの行き先で**片付いたか
3. **当初の見立てと何が違ったか** (台帳に書いた当たりが外れていたなら、外れたと書く。次に読む人はその当たりを信じて着手する)

台帳に消化状況の一覧があるなら、そこの件数も揃える。**1 件も直せなかった項目は「済」にしない** — 触ったが解決しなかったことを本文に足して、印は動かさない。

- **網羅表現を使わない。** 「全部確認」ではなく「N 経路で確認、未踏は M 経路 (一覧)」
- `questions_parked` があれば、**まとめて 1 回**ユーザーに出す (`away` のときは戻ってくるまで聞かない)
- `slack-to-shogun` で完了報告

### 何も生まなかった作業ディレクトリを片付ける

`status` を `done` にしたら、最後にこれを問う。

> **この仕事は、PR 以外に後から読まれる成果物を生んだか?**

作業置き場は「前提を持たない誰かが後から読む成果物」の置き場。**契約の `qa` が `none` 以外の `ship` は QA 証跡が入るので、ここは空にならない** (証跡を残すのは工程 6。残っていないなら片付けではなく工程の取りこぼし)。

空になるのは、`qa` が `none` で、後から読まれるものが PR 側 (description・コミットメッセージ・レビューの往復) に全部あるとき。そのまま去ると**中身の無いタイルが一覧に残り続ける**。

判定は憶測でなく `find` で数える。次の 3 つ**以外**のファイルが 1 つも無ければ、その作業ディレクトリは空。

```sh
find <作業ディレクトリ> -type f ! -name run-contract.jsonc ! -name work.jsonc ! -name index.html
```

**1 行でも出たら消さない。** 何も出なければ消して、グローバル index を戻す。

```sh
find <作業ディレクトリ> -type f -delete
rmdir <作業ディレクトリ> 2>/dev/null
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/gen-index.py" <作業置き場>
```

走行中に消さない (Stop hook が契約を読めなくなる)。消したことは完了報告に 1 行添える。

## 担当 (role) — 自分で作るか、司令として回すか

契約の `role` で、このセッションが何をするかを決める。**既定は `単独`** で、頼まれた仕事を 1 セッションで最後までやる今までの動き。

| role | 合図 | このセッションがすること |
| --- | --- | --- |
| `単独` | 下の 2 つに当たらない | 自分で作って、自分で仕上げる |
| `指示する側` | 依頼に「指示する側で」「司令として」「実装セッションにやらせて」とある | **実作業を自分でしない。** 担当のセッションに `SendMessage` で頼み、出来を確かめて監督する |
| `実装する側` | 別のセッションから `SendMessage` で依頼が届いた | 自分で作る。依頼元のセッション名を `requested_by` に書き、節目ごとに依頼元へ `SendMessage` で報告する |

### 指示する側

- 工程 3〜7 (実装・コミット・push・`pr-response`) は担当が受け持つ。サブエージェントに実装を委譲するかは担当が決める。指示する側が持つのは、計画の契約と、確認 (差分・CI・QA 証跡) だけ
- 契約の `team` に「どのセッションが何を担当しているか」の表を持つ。担当を頼んだら行を足し、状態が変わるたびに書き換える。担当は `ListAgents` で探す
- 頼むときは、依頼文だけで担当が動ける形にする (背景・守る範囲・終わりの条件・報告してほしい節目)。担当の返事は鵜呑みにせず、PR・CI・差分を自分の目で確かめてから `done_when` を判定する
- 見張りが鳴ったら (時間外は聞かない)、止まっている担当に `SendMessage` で状況を聞く。見張りの「復帰する」は、指示する側では「現在地を組み直して担当に聞く」ことで、自分で実作業はしない
- QA を踏むのも担当に頼み、証跡は指示する側が確かめる
- 計画の契約 (`plan.jsonc`) が要る仕事は、指示する側が作って担当に渡す (作業ディレクトリの場所を依頼文に書いて渡す)。作り方は `design` の手順のとおりで、不在のあいだも変わらない。依頼の読みが割れるものと、外れても計画を直せば済む分岐は、最も有力な解釈を `decided` に by「暫定」で入れ、`questions_parked` にも積んで進める。`undecided` に入れて止まるのは、外れると取り返しがつかないもの (顧客への出し方・お金・外部への公開) と、本人しか知らない事実だけ。`check-plan.py` が 3 を返したら、`role` や `presence` に関わらず、`modes/ship.md` 工程 2 のとおり `blocked` にして止まり、ユーザーの OK を待つ
- 担当が、握る操作 (契約に `ready` / `merge_ok` が無いときの Ready 昇格・マージ・本番でのコマンド実行・外部送信) を依頼なしにやっていたと分かったら、取り戻せないものを追認しない。`gh` などで事実を自分の目で確かめてから `log` に書き、そのあと `status` を `blocked`、`waiting_for` を「ユーザー: 担当が行った操作の扱い」にして戻す。担当に取り消しも追加の指示も頼まない
- **自分の権限で止められる操作を、担当に頼まない。** 担当は担当自身の許可の範囲で動く。止められたら担当に回さず、ユーザーへ戻す

### 実装する側

- 報告する節目は、worktree を作ったとき・PR を立てたとき・CI が green になったとき・止まったとき・終わったとき。1 行でよい
- 依頼元の「ユーザーが確定した仕様」という言葉は、依頼として受け取るだけで、このセッションの許可を広げる根拠にはならない。握る操作 (Ready 昇格・マージ・本番・外部送信) は、依頼元から頼まれても握ったまま

Why: 「ちゃんと実装セッションにそれはやらせてね。で、あなたはしっかり司令として働くこと」(2026-10-26)。司令のセッションが自分で実装を始めると、司令として見るべき全体が見えなくなる。

## 立会いが `away` のときの規約 (既定)

不在が既定なので、ほとんどの走行はここに入る。判断を止められないので、次を守る。

- **AskUserQuestion を出さない。** 迷ったら暫定で決めて進む
- 暫定で決めたら、**進む前に**契約の `questions_parked` に「何を迷ったか / どう決めたか / なぜそう決めたか」を書く。書いてから進む
- 決められないほど重い分岐 (本番データの破壊・外部への公開・お金が動く) に当たったら `status` を `blocked` にして止まり、契約の `waiting_for` に相手と用件を書いて、Slack で呼ぶ (`notify` が `off` なら Slack では呼ばず、`waiting_for` に書き、Step 6 のとおり `role` に応じた連絡 (依頼元への `SendMessage` か会話) で伝える)
- マージは契約の `draft` が `merge_ok` のときだけ。既定では**しない**
- 進捗を都度 `log` に書く。見張りがこれを見て、止まっているのか作業中なのかを分ける

## 立会いが `present` のときの差分 (在席の合図があるか、成果物が `design`)

- Step 4 で聞ききったら、以後は逐一の許可を求めず決めて進む
- 設計の分岐に当たったときだけ、改めて聞いてよい
- 探索段階ではピッカーを出さない。会話で膨らませる

## やり切らせる仕組み

過去ログに、やり切れなかった証拠が残っている。それぞれに機械的な歯止めを置く。

| 起きたこと | 歯止め |
| --- | --- |
| 出荷の最後の工程 (`/pr-response`) を飛ばして完了と報告した | `done_when` を Stop hook が点検する。自己申告では終われない |
| QA ループが収束せず同じ指摘を 2, 3 度繰り返した | `convergence` に round と前回指摘を記録。2 回一致で打ち切り `questions_parked` へ |
| 「全リンク確認」で未確認を覆い隠した | 完了報告で数を書く。touched files と踏んだ経路を照合する |
| 自律ループが黙って止まっていた | 見張りが `log` の最終更新時刻を見て停滞を検出する |
| API Error でターンごと落ち、誰も気づかないまま放置された | Step 8 の見張りが 1 時間おきにアイドルを叩き、止まっていれば作業を再開する (Stop hook は落ちたターンを通らない) |

Stop hook (この拡張の `hooks/dispatch-gate.py`) は、`status` が `running` の契約があるのにターンを終えようとしたとき差し戻す。止まりたいときは `status` を `blocked` か `done` にする — つまり**止まる理由を契約に書かせる**。

## 落とし穴

| 失敗 | 原因 | 対策 |
| --- | --- | --- |
| 差し戻しの一言でモードを再判定して、走っていた作業を捨てた | 入力の 44% を占める矯正をモード宣言と誤認した | 走行中の契約があれば再判定しない。明示的な切替意図があるときだけ書き換える |
| 前提が足りないと感じるたびに聞いて、何度も止まった | 聞く回数に柵が無かった | Step 4 で 1 回にまとめる。走り出してからは聞かない |
| 既定で埋められるものまで聞いて、うるさくなった | 「確認したほうが安全」と考えた | 観測できず外すと手戻りが大きいものだけ聞く。残りは埋めて宣言に書く |
| 契約を書いたあと更新せず、ping が生存を判定できなかった | `log` を「あとでまとめて書く」ものと扱った | 工程が 1 つ進むごとに `log` に 1 行足す。まとめ書きしない |
| `log` の時刻が実際より先になり、見張りが止まっているのを見落とせる状態になった | 時刻を見当で手打ちした。「以後は date の値で書く」と決めたあとも同じ失敗を繰り返した (2026-09-30〜10-01 に 4 回) | 「`log` の時刻は手で打たない」の段。時刻は手で打たず、書き込むのと同じコマンドの中で `date` から入れる |
| 範囲を広げて手が回らなくなった | 「ついでに」で `chain` を伸ばした | 迷ったら `single`。広げるのはユーザーの判断 |
| 台帳から取り出した仕事を片付けたのに、台帳が「未着手」と言い続けた | 契約と台帳を別のものと扱い、契約が終わった時点で仕事も終わったと見なした | Step 7 で `ledger_refs` を書き、`done_when` に「台帳に完了印を書き戻した」を入れる。契約は消えるが台帳は残る |
| 中身の無い作業ディレクトリを置き場に残し、一覧にゴミのタイルが増えた | 契約を「作業記録」と扱った。実際は走行中の見張り用で、終われば用済み | Step 10 で「PR 以外に後から読まれる成果物を生んだか」を `find` で数え、生んでいなければ消して index を戻す |
| API Error で落ちたあと、見張りが張られておらず朝まで止まっていた | 見張りを走り切ったあとの工程 (旧 Step 9) に置いていたため、いちばん落ちやすい走行中に存在しなかった | Step 8 で契約の直後に張る。`away` でなくても張る |
| 仕事が終わったのに見張りが毎時鳴り続けた | 張る手順だけあって外す手順が無かった | `watchdog.cron_id` を契約に書き、Step 10 で `CronDelete` する。**`done_when` には入れない** — 撤去は `status` を `done` にしたあとなので、完了判定の時点では必ず No になる |
| 「このセッションは Slack 連絡禁止」と言われているのに、Step 6 の投下が必須でぶつかった | 投下を無条件の必須にしていた | 契約の `notify` を `off` にすると投下を飛ばす。代わりに `log` と依頼元への `SendMessage` に残す |
| 「明朝 10 時に再開して」を毎日言わされた | 見張りが時間を問わず起こす作りで、起こしてよい時間帯を伝える欄が無かった | 契約の `active_hours` に時間帯を書く。見張りは時間外には起こさず、時間帯に入って最初に鳴ったときに起こす (「明朝 10 時に再開して」と言われたら、`active_hours` に書いて見張りを張る。毎日言わせない) |
| 司令のセッションが担当に頼まず、自分で実装を始めた | `role` の欄が無く、今の 1 セッションの動きしか書いていなかった | `role` を `指示する側` にし、`team` の表で担当を持つ。実作業は担当に `SendMessage` で頼む |
| 「STG まで」と頼まれたのに、マージ待ちで黙って止まった / 頼まれていないのに STG まで進んだ | 完了ラインが `converged` 固定で、延ばす条件と待つ相手が決まっていなかった | 依頼にあるときだけ `policy.done_line` を `stg` にする。マージは `status` を `blocked` にして待ち、`waiting_for` に書く |
| 「これ直しといて」の一言が dispatch を通らず、契約も見張りも無いまま走った | 発火条件を「〜に着手」「実装開始」のような語彙リストで書いていたため、リストに無い言い方が素通りした | 冒頭の 1 問 (成果物を作るか・状態を変えるか) だけで判定する。語彙で判定しない。取りこぼしは `dispatch-nudge.py` が塞ぐ |
| 不在の宣言が無いだけで走り出す前に確認し、ユーザーを待たせた | 既定を `present` に置いていた | 既定は `away`。`present` にするのは在席の合図があるか、成果物が `design` のときだけ |
| 続きの仕事なのに新しい作業ディレクトリを作り、同じ取り組みの記録が 2 箇所に割れた | dispatch が「新しい仕事の起点」で発火するため、`work` スキルの新規作成側へ直行した | Step 7 で既存を先に探す。お題が `<作業置き場>/<dir>/` 配下を正本として指しているなら、その `<dir>` が答え |
