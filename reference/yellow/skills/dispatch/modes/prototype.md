# prototype — 試作で確かめる

**捨てる前提でコードを書き、計画の「まだ分からない部分」を動かして確かめる。** 成果物は完成したコードではなく、計画の不確実性が減ったこと。

入口は 2 つ。ユーザーの依頼文に上の語が入っているときと、`design` の計画手順の「試作で確かめる」工程から呼ばれたとき。どちらから入っても、以下の工程は同じ。

## プレイブック

| # | 工程 | 中身 |
| --- | --- | --- |
| 1 | 確かめることを決める | 作業ディレクトリの計画の契約 `plan.jsonc` を読み、`undecided` (まだ決まっていないこと) のうち**動かせば分かるもの**だけを試作の問いにする。本人しか知らないこと・判断権限が要ることは問いにしない (工程 6 で design 側へ返す)。計画が無ければ、問いを 1 文ずつ書き出してから始める |
| 2 | 試作する | 必要な分は**全部**やる。ユーザーが範囲を狭めたときだけ狭める。ローカルで要るもの (テスト用ユーザー・データ) は聞かずに作る |
| 3 | 段ごとに 1 コミット | 粗くてよい。`/recipient-centric:commit` は通さない。push はする |
| 4 | 記録用の Draft PR を作る | 下記「PR」。マージしない |
| 5 | 端から端まで踏む | ローカルで計画どおりに通しで動くことを Playwright で踏み、スクショを証跡として作業ディレクトリに残す |
| 6 | 計画へ書き戻す | 下記「計画との往復」。試作の問いが `decided` / `rejected` に移っていなければ 1 に戻って再試作する。本人にしか答えられないものは `undecided` に残したまま design 側 (ユーザーへの確認) へ返す |

## 範囲 — 必要な分は全部やる

試作の範囲は、計画どおり端から端まで動くのに要る分すべて。「ここは目処が立っているから飛ばす」と自分で削らない。範囲を狭めるのはユーザーが言ったときだけ。

ローカルで要るもの (テスト用ユーザー・シードデータ・環境変数の仮置き) は、取り返せるうえ他人の時間が動かないので、**許可を求めずに作る。** マージ前に動かして確かめる検証環境 (ITG など) までは行かない。

## コミット — 段ごとに 1 コミット

段 (計画の 1 工程ぶんの動くまとまり) ごとに 1 コミットを積んで push する。

- `/recipient-centric:commit` は通さない。ルール準拠・コメント・用語・CodeRabbit の各ゲートは、捨てる前提のコードには要らない
- コミットメッセージは何の段かが分かる 1 行でよい

## PR — 記録用の Draft、マージしない

試作の経緯を残す記録用に Draft PR を作る。

- タイトルの先頭に `※マージしない[試作]` を付ける。利用者が通常の PR に付けている接頭辞は付けない
- 本文に `@coderabbitai ignore` を入れる (レビューを走らせない)
- Ready 昇格もマージもしない。`/yellow:pr-response` も通さない

## 終わりの条件 — 動くことを踏んで立証する

終わりは CodeRabbit の収束ではなく、**ローカルで、計画どおり端から端まで動くこと**。

- Playwright で通しの経路を実際に踏む。「動くはず」で終えない
- スクショは利用者の決めた置き場に撮り、**証跡に載せるものだけ**を作業ディレクトリへ移す。残りは片付ける (`playwright-cleanup` があれば使う)
- 踏めなかった経路は、何が足りなくて踏めなかったかを書く
- CodeRabbit の指摘 0 件・CI green は条件にしない

## 計画との往復 — 試作で分かったことを書き戻す

**試作と計画は行き来する。** 往復しないと不確実性が減らない。

試作で分かったことは、作業ディレクトリの計画の契約 `plan.jsonc` に書き戻す。

| 試作の結果 | 書き戻し先 |
| --- | --- |
| 動いた・分かった。採用が決まった | `decided` へ移す |
| 捨てた案 | `rejected` へ、理由つきで移す |
| 動かしてもまだ分からない | `undecided` に残す。もう一度動かせば分かりそうなら再試作の問いにする |
| 本人にしか答えられない (本人しか知らない・判断権限が要る) | `undecided` に残したまま、design 側 (ユーザーへの確認) へ返す。試作の問いにしない |

書き戻したあと、試作の問いにした項目が `decided` / `rejected` に移っていなければ、工程 1 に戻って再試作する。**終わりは「試作の問いが全部 `decided` / `rejected` に移ったとき」であって、`undecided` が 0 になったときではない。** 本人にしか答えられないものが `undecided` に残っていても、それは試作の終わりを止めない。`plan.jsonc` の書式の検査は `check-plan.py` が持つので、書き戻したら通す。

## 試作のコードを本実装に渡すとき

試作のコードを本実装 (`ship`) にどう渡すか (そのまま使う・切り直す・書き直す) は、このモードでは決めない。都度判断する。

## 落とし穴

| 失敗 | 原因 | 対策 |
| --- | --- | --- |
| 試作中に commit スキルを走らせ続け、「そんなのいま不要だよ」と止められた | 出荷の工程を試作にも当てはめた | 試作は `/recipient-centric:commit` を通さない。段ごとに 1 コミット |
| 動かさずに計画だけ書き足して終えた | 試作と計画の往復を工程として持っていなかった | 工程 6 で `plan.jsonc` に書き戻し、試作の問いが `decided` / `rejected` に移るまで再試作する |
| テスト用ユーザーを作っていいかを聞いて止まった | 取り返せる操作を許可待ちにした | ローカルで要るものは聞かずに作る |
| 記録用 PR に、通常の PR に付けている接頭辞を付けた、または `@coderabbitai ignore` を入れ忘れた | 通常の PR の規約をそのまま当てた | タイトル先頭は `※マージしない[試作]`、本文に `@coderabbitai ignore` |
| 本人にしか答えられない `undecided` が残ったまま、再試作が終わらなかった | `undecided` が 0 になるまで回す書き方だった | 試作の問いにするのは動かせば分かるものだけ。本人にしか答えられないものは `undecided` に残したまま design 側へ返す |

## Why

ユーザーの発言 (過去 5 セッションで約 30 回、ほぼ同じ文面で書き足されていた指示):

- 「あくまで試作なので、コミットはめちゃめちゃあらくていい、というか段ごとに１こみっとでいい」(同じ文が 4 回貼り直された)
- 「おーい、そんなのいま不要だよ」(試作中に commit スキルを走らせ続けたとき)
- 「試作と計画とを言ったり来たりしてほしいのよね。じゃないと不確実性が減らないので。」
- 「もうお前の方で勝手にユーザー作って勝手にやってくれていいんだよな」
