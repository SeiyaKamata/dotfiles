# review — 他人の PR をレビューする

自分の PR ではなく、**あなたがレビュアーに指名されている PR** を捌く。投稿という外向きの行為を伴うので、契約に明記されていない操作はしない。

## 実例 (実測ログより)

> 私がレビュアーになっている PR について、レビューワー作業を行ってほしい。指摘事項があればインラインコメントで。マージOKなら理由コメントを添えてApprove。いずれのコメントにもClaudeが自動操作していることを末尾に添えること。指摘事項があろうとなかろうと、必ずマージまで行うこと。

## プレイブック

| # | 工程 | 中身 |
| --- | --- | --- |
| 1 | 対象を確定する | どの PR が対象か、順番はどうか。契約の `chain` に並びを書く |
| 2 | 差分を読む | 生成物・コピー由来の差分と、本当に判断が要る差分を分ける |
| 3 | 投稿する | 指摘はインラインコメント、問題なければ理由を添えて Approve |
| 4 | マージ | 契約の `merge_policy` が `merge` のときだけ。`none` なら投稿までで止める |

### 投稿物に必ず添えるもの

**Claude が自動操作している旨を各コメントの末尾に書く。** 人間が書いたと誤解されると、レビュー品質の信頼度が誤って伝わる。

### 指摘への対応をどこでやるか

契約の `fix_here` が false なら、**この PR では直さない**。指摘だけ残し、対応はまとめて別ブランチでやる。実測ログの運用がこれ。

### Stacked PR のマージ

`gh stack` で作られた積み重ね PR は `gh pr merge` が拒否される。マージは GitHub の Web UI 専用で、**入れたい範囲の一番上の PR の Merge を押す**と下までまとめて畳める。エージェントは Web UI を操作できないので、`slack-to-shogun` でユーザーに依頼する。

## 完了判定

- 対象 PR すべてにコメントまたは Approve が投稿されている
- 各投稿の末尾に自動操作である旨が入っている
- 契約の `merge_policy` に到達している (`merge` ならマージ済み、`none` なら投稿済み)
- 終わったら `slack-to-shogun` で報告

## 落とし穴

| 失敗 | 原因 | 対策 |
| --- | --- | --- |
| Stacked PR を `gh pr merge` で畳もうとして弾かれた | CLI にも GraphQL にも手段が無い | Web UI 専用。一番上の PR の Merge をユーザーに依頼する |
| 指摘への修正をレビュー中の PR に混ぜた | 「ついでに直す」でスコープが広がった | `fix_here` が false なら指摘だけ残す |
