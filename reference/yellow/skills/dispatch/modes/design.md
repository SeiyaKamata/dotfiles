# design — 設計・計画をつくる

コードは書かない。**次の工程が迷わない状態**を作るのが成果物。

## 実例 (実測ログより)

> かなり込み入った話なので細部まで詰め切ってくれることを期待している。あらたに /work でディレクトリをつくってドキュメントにまとめてほしい。なお、新ドキュメントにおいて旧ドキュメントのリンク、参照等は絶対にしないこと。文字通りゼロベースで。
> 完成をイメージしづらい着手計画になっている。本番に影響がないように、だが、完成をイメージしやすいようにしたい。ようするにアウトサイドイン。可能な限りフロントエンドから着手をすすめたいんだ。

## プレイブック

**入口**: 実装の依頼はすべて、先に計画の契約を作る (規模を問わない)。作業ディレクトリは `work` スキルで作り、**同じ取り組みのものが既にあればそれを使い回す**。`ship` と判定された依頼も、`ship` の工程 2 でここへ来る (計画の契約があるか確かめ、無ければこの手順で作る)。`ship` から来たときの立会いは、その走行の立会いのまま (既定は `away`。聞かずに決め、決められないものは `undecided` に書く)。

| # | 工程 | 中身 |
| --- | --- | --- |
| 1 | 計画の契約を作る | `references/plan-contract.jsonc` を作業ディレクトリに `plan.jsonc` として写す。何を決めたいのかを 1 文にして `summary` に書き、**あるべき状態を 1 文で書いて、今回の変更をそこへの距離として説明する**。続けて**未確定の分岐を列挙する** (下記)。ずれたまま書くと全部やり直しになる |
| 2 | 未確定の分岐は `/yellow:grilling` | 列挙が 1 件以上なら `grilling` を走らせる。決まった分岐は契約の `decided` に書く |
| 3 | 事実の裏取り | 書く事実は実コード・実データで確認する。既存ドキュメントは過去の一時点の情報として扱う。外部の先行事例まで調べ、**他チームに聞く前に自分で答えを出せる問いを潰す**。今の経路・仕組みが本当に要るかを疑い、同じことをする既存の仕組みがリポジトリに無いかを探す (新しく作る前に既存を探す、という `priorities.md` の 3 位と同じ向き)。読んだブランチとコミットを契約の `current` に書く。**各結論に「実データで確認 / コードで確認 (file:line) / 未検証」のどれかを付ける。** 今の作りに違和感がある箇所を「既存だから」で温存せず、温存するなら理由を数字で書く。読める・測れるもの (コード・環境・ドキュメント・先行事例) は自分で読み、測って「確認済み」にする。読めない・測れないものは「未検証」「該当なし: 理由」と書き、数字を作らない。**足す処理の置き場 (`placement`) と、どう壊れうるか (`failure_modes`) もここで埋める** (下記「置き場と壊れ方を先に決める」) |
| 4 | 試作で確かめる | 不確かな欄が残っていれば、捨てる前提のコードで動かして規模も実測し、分かったことを契約と計画書に書き戻す。試作は `modes/prototype.md` の手順で行う |
| 5 | 優先順位で決める | `references/priorities.md` の順位で案を比べる。採用案だけでなく却下案を残し、却下理由は「優先順位のどれに負けたか」で `rejected` に書く |
| 6 | 分割と順番 | Outside-in。外側 (画面・API 契約) から着手できる順に割り、契約の `prs`・`release`・`impact` を埋める。最初の 1〜2 本で完成の形が画面や API として見える順にする。`impact` には、このあと控えている施策とぶつからないかも書く。`work` スキルの作法 (HTML、「要するに → 補足」、図は HTML+CSS) で計画書に書き、**書いたら `check-plan.py` を通す** (下記) |
| 7 | 初見のサブエージェントで点検 | 文脈を持たないサブエージェントに、契約の欄ごとに計画書を読ませる (委譲文は `agent-brief` の契約に従う)。小さな仕事でも省かない。省くのはサブエージェントを起こせない環境だけで、省いたことを走行の契約 (`run-contract.jsonc`) の `log` に書く |
| 8 | `undecided` が残れば止まる | 契約の検査が通り `undecided` が 0 件なら `ship` へ進む。1 件でも残っていれば、止まってユーザーの OK を待つ。`confidence` が 90 未満なら、まず自分で確かめて上げる (工程 3・4 に戻る)。結論に「未検証」が残っているうちは 90 以上を付けない。自分では確かめられないもの (本人しか知らない・外部の状態・判断権限が要る) だけを `undecided` に書く |

### このモードだけ立会いの既定が `present`

他のモードの既定は `away` (聞かずに走る) だが、**設計はユーザーの判断そのものが材料**なので、聞けない状態だと工程 2 の `grilling` が走らず成果物が空になる。だから `design` と判定した時点で `presence` は `present` にする (不在の宣言が明示されているときだけ `away`。そのときは `grilling` を走らせず、未確定の分岐をすべて `questions_parked` に積んで暫定で書き進める)。

### 工程 1 で未確定の分岐を列挙する

1 文にまとめただけでは、ずれていても誰も気づけない。**1 文の直後に、まだ決まっていない分岐を箇条書きで並べる。** 並べること自体は無条件でやる。

- 列挙が **1 件以上** → 工程 2 で `grilling` を走らせる。ラウンド制で判断だけを聞き、暗黙の前提が無くなるまで続ける。聞けないとき (不在) も、本人しか知らない・判断権限が要る分岐は暫定で決めず `undecided` に入れる (暫定で決めてよいのは、外れても計画を直せば済む分岐だけ)。**依頼の読み方が複数に割れるときも、止まらず仮に決めて進める**: コード・リポジトリから最も有力な解釈を選んで `decided` に by「暫定」で入れ、選ばなかった解釈と選んだ理由を書き、`run-contract.jsonc` の `questions_parked` にも積む。`undecided` に入れて止まるのは、外れると取り返しがつかないもの (顧客への出し方・お金・外部への公開) と、本人しか知らない事実だけ。依頼者の意図の解釈は、外れても計画を直せば済むなら `undecided` に入れない
- 列挙が **0 件** → 走らせない。「未確定の分岐は無かった」と 1 行書いて工程 3 へ進む

「込み入っていそうなら詰める」のような書き方にしない。**数えられる条件にしておく**ことで、判断がスキップされなくなる。

grilling は「事実はユーザーに聞かずサブエージェントが調べる」ので、工程 3 の裏取りの一部がここで前倒しに始まる。残りは工程 3 でそのまま続ける。

確定した決定と捨てた枝は `grilling` が決定ログとして書き出す。**工程 5 の却下案はそれを土台にする** — 同じ検討をもう一度やり直さない。

### 置き場と壊れ方を先に決める

レビューで差し戻される設計の指摘は、多くが「どこに置くか」と「どう壊れるか」の 2 つに集まる。実装してから指摘されると、置き場の移し替えとテストの書き直しが丸ごと手戻りになる。だから計画の段階で、契約の 2 つの欄に 1 行ずつ書く。欄ごとに何を当てるかはひな形のコメントが正本。

書く前に、次の 2 問を Yes/No で答える。

- **新しく足す処理・判断ごとに、同じ層の兄弟がどこに置いているかを数えたか? 同じ共有コードを通るほかの経路 (別の handler・別の worker など) に同じ問題が無いかを探したか?** (`placement`)
- **再配信・同時実行・順番の入れ替わり・途中の失敗・既定値への落ち込みを 1 つずつ当て、守りを何で固定するかまで書いたか?** (`failure_modes`)

どちらも、当たらない項目は最初のキー (`what` / `case`) に「該当なし: 理由」を書いた 1 行で残す (残りのキーは省いてよい)。空欄は `check-plan.py` が落とす。

0.5.0 からこの 2 欄は必須になった。それより前に作った `plan.jsonc` は、2 欄と計画書の節を足してから `check-plan.py` を通し直す。

Why: 2026-10-21〜29、atm (automated-training-service) の PR #2419 (配信結果の通知を読んで DB に記録する worker) のレビューで、指摘が次の 6 つに集まった。どれも計画の時点で答えられる問いだったのに、実装後に直したため、置き場の移し替えとテストの書き直しがまるごと手戻りになった。

- 兄弟の実行ファイルが 1 つも import していない層を借りていた
- 業務ルールが入口 (`main.go`) に置かれていた
- 同じ順序の問題が別の経路 (`/ses-event` の handler) にもあるのに、片方だけを守っていた
- 「既定値に委ねる」と書いたが、その既定値の意味を読んでいなかった。上流が実際に送る値も読んでいなかった
- 読んで判定してから書く処理が、トランザクションとロックの外にあった
- 兄弟プロダクトが同じ問題を逆の方針で扱っていた

### 計画の契約と検査

計画にも、走行中の契約 (`run-contract.jsonc`) と同じ形の契約 (`plan.jsonc`) を作業ディレクトリに置く。欄と書き方はひな形 `references/plan-contract.jsonc` が正本。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check-plan.py" <作業ディレクトリ>
```

次のどれかで非 0 で終わる。

- 空欄がある
- 「該当なし」と書いたのに理由が無い。`impact` は、利用者の設定にある連携先・兄弟プロダクトの名前が 1 つでも並んでいないと落ちる
- 計画書の HTML に、欄に対応する節が無い

終了コードは 0 (通った) / 1 (契約の不備) / 3 (埋まっているが `undecided` が残っている)。**PR 1 本の小さな仕事でも全部の欄を残す。** 小さい仕事は「該当なし: 理由」が多くなるだけで、数分で埋まる。作業ディレクトリに `plan.jsonc` があるとき、Stop hook (`dispatch-gate.py`) が同じ検査を走らせ、落ちていればターンを終わらせない。

### 工程 6 の分け方

PR を割る軸は、行数でもファイル数でもなく、**レビュワーが 1 本の筋として読めるか**。だから「細かく割れ」と「まとめろ」が両方出る。

- 各 PR を 1 文で説明したとき、「〜と〜」で 2 つの概念をつながずに言えるか (言えないなら割る)
- 同じ関心事を機械的に割っていないか (割りすぎなら、同じ関心事はまとめる)

出す順番 (`release`) の欄には、どの段で止めても既存挙動が壊れないか、逆にすると何が壊れるか、戻し方、途中で顧客に見えるものまで書く。判断の軸は `references/priorities.md` の 1 位。

### 「ゼロベースで」と言われたときの扱い

旧ドキュメントを参照しない。リンクも張らない。**読み直して引き写すのも参照にあたる。** 旧版は `_archive/` に退避するか `state: invalid` にして、新版から辿らせない。

### 探索段階ではピッカーを出さない

「どんな風になりそう?」の段階で選択肢ピッカー (AskUserQuestion) を出さない。会話で膨らませる。**方向が固まってから**選択肢にする。

### 曖昧語を書きそうになったら止まる

「想定」「要確認」「基本〜のはず」「意図的な曖昧性として残す」を書きそうになったら、書く前に確定させる。一次ソースで確認済みの記述 (例: npm registry を叩いて 404 だった) は例外。

**留保の言い回しも同じ扱い。**「実装時に確認すれば足りる」「骨格は変わらない」「実装時に判断」を書きそうになったら、そこで確定させる。骨格が変わらない論点でも先送りは通らない。

Why: 「残る論点は 6 点で、いずれも実装時の確認で足り、骨格を変えません」と書いて出したところ、**「そう言われていざ実装時にやったら手遅れみたいなのがなんどもあんだよ。あわせて今やれや」**と差し戻された (2026-07-25)。計画の価値は「実装が迷わない状態まで未確定を潰したか」で測られる。

潰しきれない項目だけを、なぜ自分では潰せないか (本人しか知らない / 外部システムの状態 / 判断権限が要る) を添えて、契約の `undecided` に入れる。

## 完了判定

- 作業ディレクトリに計画書と計画の契約 (`plan.jsonc`) がある
- `check-plan.py` が 0 件 (終了コード 0)。`undecided` が 0 件なら `ship` へ進み、残っていれば止まって OK を待つ
- 採用案と却下案が理由つきで書かれている (却下理由は優先順位のどれに負けたか)
- 次に着手する人が、そのドキュメントだけで着手できる
- 曖昧語・留保の言い回しが残っていない
- `gen-work-index.py --check` が 0 件

## 落とし穴

| 失敗 | 原因 | 対策 |
| --- | --- | --- |
| 表のセルに理由や経緯を詰め込んで読めなくなった | 表を説明の場所として使った | 表は索引、本文が「なぜ」の場所。動詞や因果が入ったら表から出す |
| 一発で完成させようとして品質が落ちた | 段階を踏まなかった | 依頼理解 → 裏取り → 見出し設計 → 本文、の順で作る |
| 日本語入りの SVG 図で文字がはみ出した | SVG の `<text>` は折り返さない | 図は HTML + CSS で組む。Playwright で PC 幅を実測する |
