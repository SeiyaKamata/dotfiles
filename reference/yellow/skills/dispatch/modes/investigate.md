# investigate — 事実を突き止める

実測 84 件で**最多**。本番ログと DB を突き合わせて「本当にそれが起きたか」を確定させる仕事が中心。

## 実例 (実測ログより)

> 3段階で確度を積み上げた: ①設定上リークし得る候補を抽出 → ②その中で実際に画面を開いた人をログで特定 → ③そのとき本当に他社データが返っていたかをデータベースで突合。推測ではなく実データで確認している。
> この流れは非常に良くない。なにが確実であるかをまずは見直そう。クリティカルなところでいうとまず候補は55名で間違いなかったか。そこから閲覧者を2名に絞れたのは間違いなかったか。ここらへんの裏取りから改めて行いたい。

## プレイブック

| # | 工程 | 中身 |
| --- | --- | --- |
| 1 | 問いを固定する | 何が分かれば答えになるのかを 1 文にする。ここがずれると全部やり直しになる |
| 2 | 確度の階段を設計する | 「候補を絞る → 実際に起きたか → 本当にその結果だったか」のように、段ごとに何で裏を取るかを先に決める |
| 3 | 素材を集める | ログ・SQL・スクリプトは作業ディレクトリに置いて育てる。一度きりの実行で終わらせない |
| 4 | 段ごとに確定させる | 各段の結論に**確度を明記する**。「実データで確認 (高)」「未検証」を混ぜない |
| 5 | 残す | 作業ディレクトリに HTML で残す。実行したコマンドはそのまま貼る |

### 確度の書き方

**「たぶん」「おそらく」で押し切らない。** 各結論に次のどれかを付ける。

- **実データで確認** — 何を叩いて何が返ったかを添える
- **コードで確認** — ファイルと行番号を添える
- **未検証** — 何を確かめれば確定するかを添える

確度が 90% に届かない結論は、届かせるために何が要るかを書く。自力で届かないなら (ユーザーしか知らない・外部システムの状態・判断権限) その旨と不足要素を列挙する。

### 段が崩れたら前に戻る

後段で矛盾が出たら、その場でつじつまを合わせない。**どの段の前提が崩れたかを特定して、その段からやり直す。** 実測ログでユーザーが差し戻したのはこの点。

## 完了判定

- 問いに対する答えが出ている (「分からなかった」も答えになる)
- 各結論に確度が付いている
- 未検証の項目が、隠されずに一覧になっている
- 使ったスクリプト・SQL・コマンドが作業ディレクトリに残っている

## 落とし穴

| 失敗 | 原因 | 対策 |
| --- | --- | --- |
| 段の途中で確度が落ちたのに、そのまま先へ進んだ | 各段で「ここは確実か」を止まって問わなかった | 段ごとに確度を書き、届かない段は先へ進まず前に戻る |
| 調査対象のディレクトリ・ロググループを取り違えた | 環境ごとの名前を毎回手探りしていた | `staging-qa` スキルの引き当て方に従う。ロググループ名は先に確定させる |
| スクリプトを使い捨てにして、同じ調査を最初からやり直した | 素材を作業ディレクトリに残していなかった | スクリプトは作業ディレクトリに置いて版を上げながら育てる |
