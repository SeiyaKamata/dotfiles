# ship — PR を出す

実測 121 件。あなたの指示のうち最も出荷に近く、最も「途中で止まりがち」なモード。

## 実例 (実測ログより)

> 改めてどんな変更を加えるべきかの裏取りを取り、しっかり計画を立て、実装を行う。コンテキストを節約するために実装はサブエージェント（Sonnet）にまかせること。実装が終わったら、レビューをし、プレイライトを用いてQAをしっかり行い、問題が見つかればその修正を行う。
> PR一つずつ確実に /commit -> /pr-create -> /pr-response で仕上げてから次のPRに着手すること。他セッションと衝突しないように必ずすべてworktreeで作業を行うこと。

## プレイブック

工程は 7 つ。**飛ばしてよい工程は無い。** スキップの判断はユーザーがする。

| # | 工程 | 中身 |
| --- | --- | --- |
| 1 | 裏取り | ドキュメント記載を鵜呑みにせず実コードで確認する (下記 5 点) |
| 2 | 計画 | **計画の契約 (`plan.jsonc`) があるか確かめ、無ければ `design` の手順で作る。** 検査 (`check-plan.py`) が 0 件で `undecided` が 0 件になってから実装に進む。何をどの順で変えるかは契約の `prs`・`release` が正本 (外側から積む) |
| 3 | 実装 | サブエージェント (Sonnet) に委譲する。委譲文は `agent-brief` の契約に従う |
| 4 | レビュー | 委譲結果を自分の目で見る。ワーカーの報告を鵜呑みにしない |
| 5 | QA 設計 | **踏む前に、何を踏めば壊れを捕まえられるかを決める。** 出力は QA 計画表 (下記) |
| 6 | QA 実行と証跡 | 計画表の経路を踏み、結果を作業ディレクトリに 1 枚残す。収束するまで 4 に戻る |
| 7 | 出荷 (収束まで) | `/recipient-centric:commit` → push → `/pr-create` → `/pr-response` を **CodeRabbit 指摘 0 + CI green になるまで**回す → (契約が求めれば) `/pr-doc` |

### 工程 1 の裏取りで見る 5 点

ロードマップ・spec・過去の PR description は**過去のある時点の情報**。着手前に実物で確認する。

1. **base ブランチの実態** — `git fetch && git log origin/<base>..HEAD` で本当に未マージか
2. **対象ファイルの現状** — ドキュメントが指す path に実ファイルがあるか、中身が想定通りか
3. **テストフレームワーク / lint / path alias** — プロジェクトごとに揺れる (vitest / jest / playwright)
4. **既存 helper・関数の有無** — 「新規追加」と書かれていても既に類似実装があることがある
5. **兄弟プロジェクトとの差** — 写経対象がある場合、実装パターンが揺れていないか

想定と食い違いを見つけたら、着手せず計画を先に直す。「着手 → 食い違い発見 → 後戻り」より速い。

### 工程 2 の計画の契約 — 実装の依頼はすべてここを通る

「実装して」と言われても、いきなり書き始めない。作業ディレクトリ (既に同じ取り組みのものがあれば、それを使い回す) に `plan.jsonc` があり、次を満たしているかを見る。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check-plan.py" <作業ディレクトリ>   # 0 なら進める。1 は契約の不備、3 は未確定が残っている
```

- 無い → `modes/design.md` の手順で作る (規模を問わない。PR 1 本でも全部の欄を残す)
- 有って 0 → 実装へ
- 有って 1 → 欄を直す
- 有って 3 → 止まってユーザーの OK を待つ (`status` を `blocked` にし、`undecided` を `questions_parked` に写して報告する)

### 実装をサブエージェントに委譲する理由

メインの文脈を実装コードで埋めないため。**メイン側が持つのは判断** (レビュー・git 操作・CodeRabbit 対応・QA)、**委譲するのはコードを書く手** という分業にする。この分担は実測ログで繰り返し明示されている。

### scope: single のとき

1 本の PR を 1〜7 まで通して終わり。worktree は任意 (他セッションと競合しないなら不要)。

### scope: chain のとき

- **worktree は必須。** 別セッションとの衝突を避けるため。`git -C <path>` を使い、`cd` を並列に投げない
- **1 本ずつ完結させてから次に着手する。** 前の PR が 7 まで終わる前に次を始めない
- ブランチは直前の PR のブランチから切る (Stacked)。`gh-stack` スキルを使う
- test / lint はローカルで回さず GHA の CI で代替してよい (契約の `ci_delegated` が true のとき)
- 契約の `chain` に PR の並びを、`cursor` に現在地を書く。1 本終えるごとに `cursor` を進める
- **QA 証跡は PR ごとに 1 枚。** 連鎖の最後にまとめて書こうとすると、どの PR で何を踏んだかが混ざって書けなくなる

### 工程 5 — 何を踏むかを先に決める

**踏みながら考えると、手数は増えるのに穴が残る。** 実機 QA は 1 経路あたりの費用が高い (docker 起動・ログイン・データの用意)。だから、どこに手数を割くかを先に決める。

#### まず経路を数える (これが後で分母になる)

`git diff --name-only <base>...HEAD` で触ったファイルを並べ、そこから**ユーザーが踏む経路**へ翻訳する。ファイル単位ではなく経路単位で数える。

ここで作った一覧が、完了報告の「N 経路で確認、未踏は M 経路」の**分母**になる。分母を後から作ると、踏んだ経路の数がそのまま分母になり、未踏が消えて「全部確認」になる。

#### 何で捕まえるかを、この 3 つに振り分ける

| 変更の性質 | 何で捕まえるか | 実機で踏むか |
| --- | --- | --- |
| 型・命名・分岐の抜け・規約違反 | 型検査 / lint / CodeRabbit / `rule-check` | 踏まない (工程 4 で終わっている) |
| 変換・集計・判定のロジック | 自動テストを足す | 踏まない (テストの方が速く何度でも回る) |
| 表示・遷移・権限・非同期・外部連携・経路の発火 | **実機でしか出ない** | 踏む |

**工程 4 までで捕まるものを実機でもう一度踏むのが、いちばん多い無駄。** 逆に「経路が発火しない」「権限で弾かれない」「待ちが足りず空に見える」は静的なレビューを何周しても出てこない。実機の手数はこちらに寄せる。

センシティブ領域 (認証 / IP 制限 / Bearer 注入 / セッション / middleware の auth check / 401・403・404 の遷移動線) に触っていたら `sensitive-flow-qa` を使う。通常操作では踏めないので、経路を強制的に発火させる手が要る。

#### 手数を減らす 3 手

1. **1 回の操作で複数経路を踏めるデータを選ぶ。** 添付や設問を持つデータを題材にすると、その裏のテーブルまで検証範囲に入る
2. **起動コストを束ねる。** ログイン 1 回・docker 1 回で連続して踏める順に経路を並べる。画面を行き来する順ではなく、**状態が育つ順**に並べる
3. **期待値が「変わらないこと」の経路を混ぜる。** 全部を「変わること」の確認にすると、やり過ぎ (消しすぎ・出しすぎ・権限の開けすぎ) を検出できない

#### 出力は QA 計画表

決めた内容を表にする。**この表は工程 6 で結果欄が埋まり、そのまま証跡になる。** 証跡を別に作り直さない。

| # | 経路 | 操作 | 期待値 | 実機で踏む理由 | 結果 |
| --- | --- | --- | --- | --- | --- |
| 1 | (固有名で書く) | (1 行 1 操作) | (前後の数字で書く) | (工程 4 で捕まらない理由) | (工程 6 で埋める) |

**踏まないと決めた経路も、理由つきで表に残す** (「自動テストで覆われている」「今回の変更が届かない」)。消すと、未踏なのか判断済みなのかを後から区別できない。

#### 共通の関数を変えたら、呼び出し元を分母に入れる

触ったファイルから経路へ翻訳するとき、**変更した関数の呼び出し元を `git grep` で列挙し、呼び出し元ごとに経路を 1 行ずつ表に入れる。** 画面 1 つの変更に見えても、共通の検索関数や repository を変えていれば、別の画面・ジョブ・CSV が同じ関数を通る。自問は 1 つ — **「この関数を呼ぶ場所を全部数え、踏んだか未踏かを 1 行ずつ書いたか?」**

STG や本番のような共有環境で踏むときは、**自分が流した操作のログだけを突き合わせない。** QA の時間帯の遅い処理のログ (RDS のスロークエリログなど) を全部取り、処理の形で分類して、自分の経路以外の形が出ていないかを証跡に 1 節として残す。自問 — **「ログは自分の操作の分だけでなく、その時間帯の全部を形で分類して読んだか?」**

Why: 2026-10-22 ev2 (elearning-service)。一覧の検索関数を相関 EXISTS の形に書き換えた PR の QA で、受講履歴の画面だけを踏んだ。同じ関数を通る受講者本人の受講記録の検索 (受講者全員が通る) が会社の全行を読む形になり、本番で 1 日 6,819 本・最大 12.8 秒のスロークエリになった。STG のスロークエリログには QA の時間帯に同じ形が 7 本 (10.5〜14.7 秒) 出ていたが、自分が流した一覧の SQL だけを突き合わせていたので、本番に出るまで気づかなかった。

### 工程 6 — 踏んだ結果を証跡として残す

QA は「やった」と言えれば終わりではない。**後から読む人が、何が確認済みで何が未確認かを言える状態**までが工程。

置き場は契約の `workdir`。**ここはユーザーに聞かない** (Step 7 で確定しているため。`staging-qa` は聞く手順になっているが、dispatch 経由ではその答えが先に出ている)。工程 5 の計画表に結果を埋めたものを HTML 1 枚にする。

- ファイル名の採番と `index.html` への登録は `work` スキルが正本。書いたら `gen-work-index.py --check` を通す (登録を忘れると、置いてあっても誰も辿り着けない)
- スクリーンショットは撮るときは `_capture/` 配下の絶対パス (CLAUDE.md のルール)。**証跡に載せるものだけ作業ディレクトリへ移し**、残りは `playwright-cleanup` で片付ける
- 前後の対比で書く (「0 件でした」ではなく「40,892 件 → 0 件」)
- **網羅表現を使わない。** 「N 経路で確認、未踏は M 経路 (一覧)」
- 踏めなかった経路は、**何が足りなくて踏めなかったか**を書く。契約の `questions_parked` にも積む

中身の書き方の詳細は `staging-qa` の §8 が正本。ここに書き写さない。

### QA の収束

QA は「問題が出なくなるまで」回すが、**同じ指摘が 2 回続いたら収束不能と判定する**。契約の `convergence` に round 数と前回指摘の要約を書き、2 回一致したらそれ以上回さず `questions_parked` に積んで次へ進む。

実測ログに「全然収束せず、2, 3 度繰り返した」という記録がある。無限ループはこの仕組みで止める。

### 工程 7 の完了ライン — PR を立てて終わりではない

**指示が無いときの終わりは「CodeRabbit 指摘 0 + CI green」** (`dispatch/SKILL.md`「完了ラインの既定」)。PR が立った時点では終わっていない。そこへ至る往復 (指摘対応 → `/recipient-centric:commit` → push → 再レビュー → CI 確認) は、途中で許可を取らずに回し切る。

- **コミットと push で止まらない。** 許可を待つ操作ではない (Step 3 の 2 問表: 取り返せる / 他人が動かない)
- **CI が落ちたら直して push し直す。** 「CI が落ちたので見てください」で止めない。ただし同じ原因で 2 回落ちたら収束不能として `convergence` に記録し、打ち切って報告する
- **CodeRabbit がレート制限のときは飛ばさない。** 15 分おきに PR の URL と `@coderabbitai review` を Slack へ投下してユーザーに投稿してもらい、レビューが返るまで回す
- **Ready 昇格とマージだけは既定で握る。** (`done_line` が `stg` のときの Ready 昇格は、依頼がマージまでを含むので握らない。下の「完了ラインが STG のとき」) `policy.draft` が `keep` の間は、Draft のまま収束させるところまでが仕事

### 完了ラインが STG のとき — マージを待ち、リリースから STG での確認まで

契約の `policy.done_line` が `stg` のとき (依頼に「STG まで」「STG で確認まで」とあったときだけ。`dispatch/SKILL.md`「STG での確認まで走らせる」) は、上の `converged` に着いたところから先が続く。

1. **`converged` まで進める。** 上の完了ラインのとおり。Ready 昇格もここで済ませる (`policy.draft` が `ready` なので `pr-response` 手順5 のとおり昇格する。Draft のままではマージを頼めない)
2. **マージを頼んで待つ。** PR の URL をつけて「マージしてください」と頼む (走り出す前の進め方の投下とは別の 1 通)。`notify` が `on` なら `slack-to-shogun`、`off` なら `role` に応じて依頼元への `SendMessage` か会話で頼む。契約の `status` を `blocked` にし (止まってよい状態なので Stop hook は通す。待ちは下の `Monitor` が起こす)、`waiting_for` に `{ "who": "ユーザー", "what": "PR のマージ" }` と書く
3. **5 分おきに PR の状態を見る。** `gh pr view <PR> --repo <owner>/<repo> --json state,mergedAt`。マージされていなければ何もせず次の 5 分を待つ。マージされずに閉じられたら、そこで止まって報告する。5 分おきの待ちは、`Monitor` の until ループ (5 分間隔) で持つ。1 時間おきの見張りは止まりの検出が仕事なので、この待ちには使わない。待っている間に見張りが鳴ったら、`blocked` の行 (`waiting_for` を 1 度だけ促す) に当たるだけで、再開はしない。マージを確認したら `status` を `running` に戻し、`waiting_for` を `null` にして 4 へ進む
4. **マージされたら、STG 確認のスキルを呼ぶ。** (`policy.qa` が `staging` でも、ローカルでの実機確認は、PR を収束させる前の工程 5・6 で済ませてあるもので、飛ばさない。マージ後にやり直す必要は無い。STG での確認はそれに加えて行う) `dispatch.json` の `stg_check_skill` を読み、あればそのスキルを Skill ツールで呼ぶ。リリースを作る・STG へのデプロイを見届ける・STG で確認する、の順をそのスキルの手順で進める。リリースを作ってよいかも、そのスキルとリポジトリごとの許可に従う (許可が無ければ作らず、`blocked` で止まって報告する。許可が出たら (ユーザーの返事が会話か依頼元からの `SendMessage` で届いたとき) `status` を `running` に戻して続ける。許可を求める相手はユーザーで、`waiting_for` には `{ "who": "ユーザー", "what": "リリース作成の許可" }` と書く)。空なら「STG 確認の手順を持つスキルが設定されていない」と報告して `blocked` で止まる。確認の結果は QA 証跡と同じ形で `workdir` に残し、完了報告には「N 経路で確認、未踏は M 経路 (一覧)」と数で書く
5. **STG で問題が見つかったら、直す PR を立てて、1 から同じ流れを回す。** 直す PR も通常の ship と同じ工程 2 以降 (実装・ローカルでの実機確認・証跡) を省かない。契約は同じものを使い、`log` に直す PR を足し、マージ待ちになったらまた `blocked` にする。同じ問題が 2 回続けて出たら収束不能として `convergence` に記録し、打ち切って報告する
6. **本番には何もしない。** 本番へのリリース反映・本番でのコマンド実行・本番での確認は、依頼にあっても、この完了ラインの外

**例外: 依頼に「マージまで任せる」とあるときだけ**、契約の `policy.draft` を `merge_ok` にして、2 と 3 を飛ばし、マージも自分でする。CI が green で CodeRabbit の指摘が 0 件に収束していない PR はマージしない。

### 実装中に迷ったとき・止まったとき

相談せずに適用してよい。

#### 環境・検証で止まったとき

**「制約上できません」は結論ではなく、探索が足りていないサイン。** 報告する前に迂回路を 2 つ試す。数えるのは試行回数ではなく、**動かした軸の数**。同じ軸の中で値を変えただけのものは 1 つと数える。

> サブエージェントが 529 Overloaded で落ち続けたとき、種類を general-purpose → Explore と変えて計 7 回落とした。「3 通り試した」と数えていたが、動かした軸は「エージェントの種類」1 つだけだった。モデルという別の軸に触れたら 1 回で通った (2026-08-24)。

止まったら、試した手を軸ごとに並べ直す。**同じ列に 2 つ以上並んでいたら、まだ 1 つしか試していない。**

| 迷い | 既定 |
| --- | --- |
| テスト DB が汚れている / drift している | 再生成・リセットの経路を探す (別コンテナで軽いテストを 1 本流すとリセットされる等) |
| ローカル環境が立たない | キャッシュ削除・完全再起動・別の起動経路を試してから報告する |
| ライブラリ制約でできない | 制約の中で成立する別の形を 2 つ以上探す |
| 別セッションと競合しそう | `git worktree`。実機 QA が要るときは Playwright がプロファイルを共有するので、`scope` が `single` のときだけメインで作業してよい (`chain` は worktree 必須) |
| ローカルでテストを回すと重い / 競合する | 契約の `policy.ci_delegated` を `true` にしてから CI に委ねる。既定は `false` なので、宣言なしに省略しない |
| コンフリクトを解消する | マージコミットを作ってから解消する (解消ポイントが履歴で分かるように) |
| サブエージェントが 529 Overloaded で落ちる | モデルを変える。エージェントの種類を横に動かしても同じ壁に当たる |
| コミットが大きくなった | 作り直す。`commit-planner` の計画を自己判断で簡略化しない |

#### レビュー指摘

| 迷い | 既定 |
| --- | --- |
| 指摘に納得できない | 妥当性を判断してよい |
| Nitpick レベル | よっぽど出ない限り無視でよい |
| 指摘対応で PR が膨らむ | 別 PR に切り、指摘対応リストとして残す |
| CodeRabbit がレート制限 | 飛ばさない。15 分おきに PR の URL と `@coderabbitai review` を Slack に投下してユーザーに投稿してもらい、レビューが返るまで潰し切る (`pr-response` 手順4) |
| 自分の提案が否定された | 鵜呑みにせず裏取りして反論してよい |

#### 委譲の境界

コードを書く手は下位モデルに渡すが、**検証と判断は渡さない**。動機は品質ではなく**メインの文脈を実装コードで埋めないこと**なので、判断を手放す意味ではない。

## 完了判定

契約の `done_when` は既定で次のとおり。Stop hook がこれを見てターン終了を止める。

- 契約の `chain` に挙げた PR が**すべて存在する**
- 各 PR の CI が green
- 各 PR の CodeRabbit 指摘が 0 件 (inline の未解決スレッド + review 本文の折りたたみ。`pr-response` 手順5 の 3 条件)。**折りたたみのうち純粋な好みの指摘 (`Nitpick comments`) だけは、拾わない判断を PR に書き残していれば 0 でなくてよい** (同手順 条件3 の表)
- `policy.draft` に従った状態になっている (`keep` なら Draft のまま、`ready` なら Ready へ昇格済み、`merge_ok` ならマージ済み)。`done_line` が `stg` のときは `ready` (または `merge_ok`) で、下の `stg` 用の条件が加わる
- **QA 証跡が契約の `workdir` に存在し、`index.html` から辿れる** (契約の `qa` が `none` のときを除く)
- **`policy.done_line` が `stg` のとき**は、上に加えて次の 2 つ。PR がマージ済みであること (ユーザーがマージした、または `merge_ok` で自分でマージした)。STG にデプロイされたことを確認し、STG での確認の結果が `workdir` に残っていること。マージ待ちと、STG 確認のスキルが無いときは `blocked` で止まるので、`done` にはならない

**「だいたい終わった」で終えない。** 未踏の経路があるなら「N 経路で確認、未踏は M 経路 (一覧)」と数で書く。「全部」「全件」は使わない。

## 落とし穴

| 失敗 | 原因 | 対策 |
| --- | --- | --- |
| `/pr-response` を飛ばして「完了」と報告した | 出荷工程の最後が一番だれる。PR が立った時点で達成感が出る | 完了判定に「未解決レビュースレッド 0 件」を機械条件として入れる |
| 収束待ちを `/pr-response` に通さず、待ち方をその場で自作して永久に待った | 工程 7 の往復を「待つだけ」と見なし、手順書を開かなかった。知識はあったのに開いていないので使えなかった | 収束待ちに入る前に `/pr-response` を開く。待ち方の正本は手順4-1 で、完了は状態遷移シグナルの OR。**新規レビューが立つことにも特定文字列にも賭けない** (2026-08-31 PR#392。CodeRabbit は指摘 0 件のとき新規レビューを作らず walkthrough コメントを書き換えるだけなので、レビュー API の `submitted_at` を見張る自作 watcher は原理的に検知できなかった) |
| 「STG まで」と頼まれたのにマージ待ちで黙って止まった、または頼まれていないのに STG まで進んだ | 完了ラインを延ばす条件と、マージを待つ相手・待ち方が決まっていなかった | 依頼にあるときだけ `stg`。マージは `blocked` で待ち、5 分おきに PR の状態を見る。STG の確認手順は入れてもらったスキルを呼び、リリースを作ってよいかもそのスキルに従う |
| push・コミットの前で手が止まり、ユーザーの許可待ちになっていた | 完了ラインが宣言されておらず、「どこまでやってよいか」を毎回ユーザーに書かせていた | 既定の完了ラインは収束まで (指摘 0 + CI green)。握るのは Ready 昇格とマージだけ (2026-08-27 矯正) |
| QA ループが収束せず何度も同じ指摘が出た | 収束したかどうかを誰も数えていなかった | `convergence` に round と前回指摘を記録し、2 回一致で打ち切る |
| 並列 `cd` で意図しないリポジトリに commit した | Bash tool は cwd をコール間で共有する | 複数リポは必ず `git -C <path>`。`cd` を含むコマンドは並列に投げない |
| 網羅表現 (「全リンク確認」) で未確認を覆い隠した | 踏んだ経路を数えていなかった | touched files を列挙し、踏んだ経路と未踏を数で書く |
| 実機で踏んだのが、自動テストや型検査で既に覆われている場所ばかりだった | 何で捕まえるかを振り分けず、目に付いた画面から踏み始めた | 工程 5 で 3 分類に振り分ける。工程 4 までで捕まるものは実機で踏まない |
| 共通の関数を変えたのに、変更が見える画面 1 つだけを踏み、別の呼び出し元の遅さが本番で出た | 経路の分母を「触った画面」で作り、関数の呼び出し元を数えていなかった。共有環境のログも自分が流した操作の分しか読んでいなかった | 工程 5 で呼び出し元を `git grep` で列挙して表に入れる。QA の時間帯のスロークエリログを形で分類して全部読む (2026-10-22 ev2 の本番障害) |
| QA の結果が会話の中だけで消え、次に同じ場所を触るとき前回の確認範囲が分からなかった | QA を「その場で確かめる行為」と扱い、証跡の置き場を決めていなかった | 工程 6 で `workdir` に 1 枚残す。`done_when` に入れて Stop hook に見張らせる |
