# 迷ったときの優先順位

案が割れたら、上から順に当てる。`design` モードの工程 5 (優先順位で決める) と、計画の契約の `rejected` (却下理由を「どの順位に負けたか」で書く) が参照する。

1. **止めずに、途中を見せずに出せる**
   - メンテナンス時間を作らない
   - 途中の PR まで入った状態で、顧客の画面と動作が今と変わらない (変わるのは機能を開放したときだけ)
   - 複数リポジトリの同時リリースを求めない。順番さえ守れば、間を何日空けてもよい
   - どの段で止めても既存挙動が壊れない順に割る。動き出すと困る定期ジョブは、稼働させる工程を最後に置く
   - 長く開いたままの PR を作らない (コンフリクトを産む)。こまめに出せる形に割る

   Why: Seculio の NOT NULL 化 (PR #9143) を実装したが revert した。型変換が要り、マイクロサービス 2 つとのほぼ同時リリースが必要になって、メンテナンス時間を設けざるを得なくなったため。差し戻し時の言葉は「メンテナンスは嫌なので、順番さえまもれば時間を開けても問題ないような作業計画にしたい」(2026-07-25)。
2. **長期の保守性**
   - 本命を最初から選ぶ。「まず軽い案、困ったら本命」を推奨にしない
   - 今の作りに違和感がある箇所を「既存だから」で温存しない。温存するなら、理由を数字で言う
   - 対症療法より根本を直す (範囲が広くても。ただし PR は分ける)
   - 共通の置き場は新設する。「1 定数のためには重い」は理由にならない
   - NULL を「未設定」に使わない (NOT NULL + デフォルト値)、状態で分けず一本化、アーキ原則は実装都合に勝つ
   - 過剰な安全策で保守性が落ちるなら、保守性を取る
   - 業務ルールは、判断材料を全部持っている型 (値オブジェクト・エンティティ・ドメインのサービス) に置く。入口 (main・handler) に置かない
   - 守らないと壊れる前提 (「トランザクションの中で呼ぶこと」など) は、コメントではなく型やシグネチャで守る
3. **既存の作法に倣う**
   - 同種の機能の作り方と名前の付け方に揃える。既存の置き場があるなら素直に足す
   - 名前を略さない。曖昧な語を使わない
   - マジックナンバーを見つけたら、定数があれば置き換え、無ければ作る
   - 新規に発明する前に、兄弟リポ・類似機能・共通の置き場を探す
   - 層をまたいで借りるときは、同じ層の兄弟が同じものを借りているかを数える。0 件なら、借りずに兄弟と同じ形にする
4. **要らないことはしない**
   - 実際には踏めない経路への防御コードは足さない
   - 起きない事象への対策を足さない

## 順位とは別の決まり

**工数は案を比べる材料にしない。** 計画書に工数も日付も書かない。順位に入れると「ほかが同じなら工数で選ぶ」と読めてしまうので、順位の外に置く。

コストを理由に小さい案を推したくなったら、数字を添える。添えられないなら、その主張をしない。

## 聞くときの決まり

- 聞くのは、この順位を当てても本当に割れたときだけ
- 聞く前に、順位に照らした自分のベスト案を書く
- 選べる案が実質 1 つなら、聞かずに決めて宣言する
