# Claude Code 設定

## ユーザーへの質問スタイル

ユーザーに確認・選択を求めるときは、すぐに回答できる形式にする：

- **2択**: `y/n` または `はい/いいえ`
- **多択**: 番号付きリスト
  ```
  1: ...
  2: ...
  3: ...
  ```
- 自由記述が必要な場合でも、典型的な選択肢を番号で並べて「その他」を最後に置く

開放的な質問（「どうしますか？」など）は避ける。

## コミット

コミットする際は必ず `/commit` スキルを使う。直接 `git commit` を実行しない（実行するのは `/commit` が起動する `committer` エージェントのみ）。

## force push

force push は **draft PR のみ**許可する。Ready for review 済み（open）の PR には行わない
（レビュースレッドと CI 履歴が壊れ、復旧が効かない）。stacked PR の rebase 伝播で必要に
なった場合も、対象 PR が open なら push 前に確認する。

## ガード・ブロックの扱い

フックや権限で操作がブロックされたら、それは**「止まって確認する」シグナル**。別手段
（Bash のリダイレクト・別コマンド）で同じ書き込みを試して迂回しない。ユーザーに確認する。
配置場所・要否・方式を相談している最中も同じで、承認を得るまで成果物を作らない・変更しない。

`.specs/` 配下の Markdown の部分書き換え（チェックボックスの `[ ]`→`[x]` など）は **Edit ツール**で
行う。`sed -i` / `perl -i` の in-place 編集は、macOS の `-i ''` の空引数がパスとして解釈されて
`restrict-edits.sh` にブロックされる。件数が多くても Edit を必要回数呼ぶ。

## Bash の作業ディレクトリ

`settings.json` の `env.CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1` により、Bash コマンドの
作業ディレクトリは呼び出しごとにプロジェクトルートへリセットされる。`cd` しても次の呼び出しに
持ち越されないため、cwd の意図しない持ち越しは起きない。ディレクトリを指定したいときは
絶対パスか `git -C` / `make -C` / `npm --prefix` のようなオプションを使う。

## 実行していないことを書かない

ツールを実際に呼ばずに実行結果や tool_use を地の文で生成しない。サブエージェントについても
「起動した」と述べるだけで終わらせず、必ず Agent ツールを実呼び出しする。

## 訂正・摩擦の扱い

ユーザーから訂正・注意・却下を受けたとき、**または自分が作業中に摩擦にぶつかったとき**、その気づきを
**改善提案に切り出す**。恒久ルール（`CLAUDE.md`）へ自己判断で追記しない — 再発判定は
`/proposals-sweep`、恒久化するかは人が判断する。

- **摩擦とは次のもの**（曖昧な違和感は含めない）: フックや権限で操作がブロックされて迂回や往復が
  発生した／同じ確認をユーザーに 2 回以上した／上流工程の成果物（要件・設計・タスク）の不備を
  見つけた／スキルの手順どおりに進められなかった／その工程が本来 catch すべきだった逸脱に気づいた
- **起票したら完了カードに載せる**: カードの外に別文で書かず、「やったこと」の 1 行として出す
  （例: `- 💡 提案 1 件発行: <claim>`）

- **行き先を選ぶ（この節が振り分けの正本。各スキルはここを参照する）**:
  - **skill / パイプラインの改善** → `/propose`。改善提案の唯一の入口。一行のルールに落ちるか
    構成規模かは propose が内部で判定する（構成規模は `kind: backlog` として記録し、着手は
    dotfiles で `/spinoff` で詳細化する）。
  - **今のタスクを完了させるのに別 PJ の変更が必要** → `/handoff`。ブロッカーなので依頼元
    `tasks.md` の `## 事前セットアップ` の `S<n>` で**追跡する**。
  - **投げなくても今のタスクは完了する** → `/spinoff`。棚上げなので**追跡記録を残さない**。
- **敷居**: その場限りのタイポ・パス違いなど再発しない訂正は切り出さない。
- **タイミング**: その場で割り込まず、**作業の区切り**（工程の終わり）に回す。
- **起票は無確認・着手は人**: 提案ファイル・`seed.md` の作成は確認を取らずに実行し、結果を事後
  報告する（`/propose`・`/spinoff`・`/handoff`）。handoff だけは依頼先 PJ が一意に決まらないとき
  に宛先を確認する。起票した内容の**着手**（実装の開始）は自動で始めず、人が起動する。

## 前提が覆ったとき

spec の前提（スコープ・依存・外部条件）が途中で覆ったら、覆った前提の**キーワードで
`.specs/<feature>/` 配下を grep** し、requirements.md / design.md / tasks.md に残る古い記述を
すべて更新する。**1 ファイルだけ直して終わらせない** — spec ファイルは相互参照が多く、新旧の
前提が並存すると読んだ人の判断が割れる（矛盾したドキュメントは無いより悪い）。編集モードの
再入で担保されるのは構造的な整合だけで、別の節に残った古い文言は引っかからない。
どの工程から再入するかは `/orchestrator`「工程一覧」の「共通: 実装中の変更」（前進カスケード）に従う。

## 担当 feature のスコープ

成果物の書式は**担当スキルの出力フォーマットにだけ従う**。書式や判断の前例を探す目的で
他 feature の `.specs/` を読まない（スキルに規定が無いなら前例で埋めず、規定不足として報告する）。

## 用語集（開発パイプライン）

スキル間で用語を統一する。特に「フェーズ」と「工程」を混同しない。

| 用語 | 意味 |
|---|---|
| **工程 (stage)** | パイプラインの各段階＝各スキル（spec / design / tasks / impl / test / review / qa / commit / sync-to-remote / …）。「工程に戻す」「工程を推定する」はこの意味。 |
| **フェーズ (phase)** | **実装後に `/sync-to-remote` が確定する PR 単位**（ブランチ `pN` = 1 PR）。分割が要らなければフェーズは現れず単一 PR になる。**実装前には存在しない**（`/impl` はフェーズを持たない）。 |
| **大タスク / サブタスク** | tasks.md の 2 階層。**大タスクは関心のグルーピング**（PR 単位ではない）、その配下がサブタスク（実装の最小単位）。 |
| **stacked PR** | 分割したフェーズを積み上げるブランチ運用（`pN` を `p(N-1)` にスタック）。`/sync-to-remote` が実装後のコミット列から切り出す。 |
| **実装ブランチ** | `/impl` が**実装の最初に**切る `<feature>` 1 本。目的は**実装の隔離**（捨てる・作り直すのを安全にする）で、PR の単位ではない。 |
| **フェーズブランチ** | `/sync-to-remote` が**分割時に**コミット境界から切る `<feature>-pN`。**PR の単位**。分割しなければ作られない。 |
| **Step** | スキル内部の手順見出し。工程・フェーズとは別物。 |

## PR / ブランチ命名

全 PR タイトルは固定 prefix `【鎌田QA】` で始める。形式の詳細（フェーズ番号の付け方・`seed.md` frontmatter の使い方）は `/sync-to-remote` に一元化されている（`seed.md` の `pr_title` を直接読み、`/tasks` は経由しない）。

## PR 運用の有無

repo が PR を運用するかは**リポジトリの性質**であって工程の性質ではない。判定条件はこの節に一元化し、各スキルは自前の判定を持たずここを参照する。

判定材料は**プロジェクト（repo ルート）側の `CLAUDE.md`** のブランチ・PR 運用に関する記述（この global 設定は材料にしない）。

| 判定値 | 確定条件 |
|---|---|
| `あり` | ブランチ・PR 運用の記述が無い（`CLAUDE.md` 自体が無い場合を含む）／stacked PR・PR 前提の運用が記述されている |
| `なし` | 「ブランチを切らない」「デフォルトブランチへ直接コミット / 直接 push する」「PR を作らない」「PR 運用を勧めない」のいずれかに相当する記述がある |

**`不明`（記述が混在する・条件付きでどちらとも決まらない）なら安全側の `あり` を採る。** PR を余分に作っても閉じれば済むが、レビューを求める repo で黙ってデフォルトブランチを進めると戻せない。

**判定を読むのは `/sync-to-remote` だけ**。`あり` なら draft PR を作り、`なし` なら実装ブランチをデフォルトブランチへ取り込んで push する。

他の工程は運用差を持たず、**常に PR 前提で動く**：

- `/tasks` — PR タイトルには関与しない。素材（`seed.md` の `pr_title`）から分割・最終的なタイトルの確定まで `/sync-to-remote` が一貫して行う
- `/impl` — 常に実装ブランチ `<feature>` を 1 本切る（実装を隔離しておけば捨てる・作り直すのが安全）
- `/commit` — 判定しない（コミットは可逆で push もしないため）

## PR 分割の判定

**PR を何本に割るかは実装後に決める。** 判定するのは `/sync-to-remote` だけで、材料はコミット済みの diff とコミット列（実物）。

実装前の見積りで割ると、量が少ないのに stacked にされる。**既定は単一 PR**で、分割は理由を要する例外として扱う（判定基準の詳細は `/sync-to-remote`）。`/tasks` と `/impl` は分割を決めない。

## Notion 連携

Notion に触れるのは `/notion-import`（入力）と `/notion-export`（出力）の 2 つだけ。他工程は Notion を知らず、`.specs/<feature>/` のファイルだけを読む。これで Notion 連携の可否の分岐がパイプライン全体に広がらない。**どちらも人が明示的に実行する**（`/orchestrator` の自走パイプラインには組み込んでいない）。
