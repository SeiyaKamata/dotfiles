# Claude Code 設定

## ユーザーへの質問スタイル

選択肢を提示するツール、AskUserQuestionは使わない。
情報が足りない場合は、妥当な仮定を置いて回答し、その仮定を冒頭で明示する。
どうしても必要な確認は本文中に1つだけ書き、すぐに回答できる形式にする：

- 2択: `y/n` または `はい/いいえ`
- 多択: 番号付きリスト
  ```
  1: ...
  2: ...
  3: ...
  ```
- 自由記述が必要な場合でも、典型的な選択肢を番号で並べて「その他」を最後に置く

上記のいずれの形式にも当てはまらない、選択肢を示さない聞き方は避ける。

## 出力する文章のスタイル

- 丸括弧を使わないでください。
- 丸括弧を使うと可読性が下がりユーザーの負担になるためです。
- ユーザーと会話する感じでお願いします。

## 実行していないことを書かない

ツールを実際に呼ばずに実行結果や tool_use を地の文で生成しない。
サブエージェントについても「起動した」と述べるだけで終わらせず、必ず Agent ツールを実呼び出しする。

## コードコメントの書き方

コメントは基本的に書きません。
消したときに後で読む人が困るかどうかで判断し、困らないなら書きません。
コードを読めば分かることや命名・型で表現できることはコメントで重複させず、コードそのものを直します。
変更の経緯はコミットメッセージやPR説明に書きます。

書いてよいのは、コードを読むだけでは復元できない情報だけです。
実装を選んだ制約、一見不要に見えるが必要な理由、外部要因の判断がこれに当たります。

実装後は書いたコメントを1つずつ見直し、判定に迷ったら消す方に倒します。

## コミット

コミットする際は必ず `/commit` スキルを使う。
直接 `git commit` を実行しない。
実行するのは `/commit` が起動する `committer` エージェントのみです。

## force push

force push は draft PR のみ許可する。
Ready for review 済み、つまり open の PR には行わない。
レビュースレッドと CI 履歴が壊れ、復旧が効かないためです。
stacked PR の rebase 伝播で必要になった場合も、対象 PR が open なら push 前に確認する。

## 作業の退避

ブランチを切り替えて別の作業に戻る必要があるとき、未コミットの変更は `git stash` ではなく WIP コミットで退避する。
stash はブランチの外側の状態で、他の無関係な stash と混ざって見失いやすく、`git log` やブランチの状態からも気づけない。

- WIP コミットは `git log` から常に見え、`git reset --soft HEAD~<N>` で戻せる。
- コミットメッセージに `WIP:` などの接頭辞を付け、未整理である旨を明記する。
- 退避先のブランチから戻ったら、このコミットを起点に続けるか `/commit` 相当の整理で分割し直す。

## ガード・ブロックの扱い

フックや権限で操作がブロックされたら、それは「止まって確認する」シグナル。
Bash のリダイレクトや別コマンドのような別手段で同じ書き込みを試して迂回しない。
ユーザーに確認する。
配置場所・要否・方式を相談している最中も同じで、承認を得るまで成果物を作らない・変更しない。

## Markdown の部分書き換え

`.specs/` 配下の Markdown の部分書き換え、チェックボックスの `[ ]`→`[x]` などは Edit ツールで行う。
`sed -i` / `perl -i` の in-place 編集は、macOS の `-i ''` の空引数がパスとして解釈されて `restrict-edits.sh` にブロックされる。
件数が多くても Edit を必要回数呼ぶ。

## Bash の作業ディレクトリ

`settings.json` の `env.CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1` により、Bash コマンドの作業ディレクトリは呼び出しごとにプロジェクトルートへリセットされる。
`cd` しても次の呼び出しに持ち越されないため、cwd の意図しない持ち越しは起きない。
ディレクトリを指定したいときは絶対パスか `git -C` / `make -C` / `npm --prefix` のようなオプションを使う。

## 開発パイプラインの用語集

スキル間で用語を統一する。
特に「フェーズ」と「工程」を混同しない。

| 用語 | 意味 |
|---|---|
| 工程 stage | パイプラインの各段階で、各スキル spec / design / tasks / impl / test / review / qa / commit / sync などを指す。「工程に戻す」「工程を推定する」はこの意味。 |
| フェーズ phase | 実装後に `/sync` が確定する PR 単位。ブランチ `pN` が 1 PR に対応する。分割が要らなければフェーズは現れず単一 PR になる。実装前には存在せず、`/impl` はフェーズを持たない。 |
| 大タスク / サブタスク | tasks.md の 2 階層。大タスクは関心のグルーピングで PR 単位ではなく、その配下がサブタスクで実装の最小単位。 |
| stacked PR | 分割したフェーズを積み上げるブランチ運用。`pN` を `p(N-1)` にスタックする。`/sync` が実装後のコミット列から切り出す。 |
| 実装ブランチ | `/impl` が実装の最初に切る `<feature>` 1 本。目的は実装の隔離で、捨てる・作り直すのを安全にするため。PR の単位ではない。 |
| フェーズブランチ | `/sync` が分割時にコミット境界から切る `<feature>-pN`。PR の単位で、分割しなければ作られない。 |
| Step | スキル内部の手順見出し。工程・フェーズとは別物。 |

## 前提が覆ったとき

spec の前提、スコープ・依存・外部条件が途中で覆ったら、覆った前提のキーワードで `.specs/<feature>/` 配下を grep し、requirements.md / design.md / tasks.md に残る古い記述をすべて更新する。
1 ファイルだけ直して終わらせない。
spec ファイルは相互参照が多く、新旧の前提が並存すると読んだ人の判断が割れる。
どの工程から再入するかは `/orch` の「工程一覧」にある「共通: 実装中の変更」の前進カスケードに従う。

## Notion 連携

Notion に触れるのは入力を担う `/notion-import` と出力を担う `/notion-export` の 2 つだけ。
他工程は Notion を知らず、`.specs/<feature>/` のファイルだけを読む。
これで Notion 連携の可否の分岐がパイプライン全体に広がらない。
どちらも人が明示的に実行する。
`/orch` の自走パイプラインには組み込んでいない。

## 内省ログの記録

会話の中でユーザー自身の内省・思考パターン・行動の癖・感情の動き・判断の癖などの気づきや、ユーザーにとって新しく得た学び・知見になりそうなログ情報を見つけたら、確認を挟まず自分の判断で `nikki` コマンドを使って保存する。
**主語は常にユーザー。**

- 保存形式: `nikki -n <要約した内容>`
- 機密情報、個人情報・認証情報・非公開の内部情報は絶対に載せない。
- 要点だけを短く要約する。

## 訂正・摩擦の扱い

ユーザーから訂正・注意・却下を受けたとき、または自分が作業中に摩擦にぶつかったとき、その気づきを改善提案に切り出す。
恒久ルール、`CLAUDE.md`、へ自己判断で追記しない。
恒久化するかは人が判断する。

### 訂正直後のチェック

ユーザーから訂正・注意・フラストレーションの表明を受けたら、謝罪・修正・次の作業などの対応を始める前に、その場で次の2つを明示的に自問する。

- 内省ログに残すべき気づきか →`nikki -n` で保存する
- 改善提案に切り出すべき摩擦か → 下記の判定基準・行き先に従う

この2つは Slack 投稿の Stop hook のような外部の強制チェックを持たず、完全に能動的な判断に委ねられている。
「直す」対応に意識が向くとこの確認自体が抜け落ちやすいため、訂正を受けた直後という決まったタイミングで必ず立ち止まる。

### 摩擦の判定基準

摩擦とは次のもの。
曖昧な違和感は含めない。
フックや権限で操作がブロックされて迂回や往復が発生した／同じ確認をユーザーに 2 回以上した／上流工程の成果物、要件・設計・タスクの不備を見つけた／スキルの手順どおりに進められなかった／その工程が本来 catch すべきだった逸脱に気づいた／初見では分からず、かつ次回も同じ状況になりうる再現性があるそのリポジトリ固有の手順・制約・回避策を試行錯誤の末に突き止めた。

その場限りのタイポ・パス違いなど再発しない訂正は摩擦に含めず切り出さない。

### 行き先の判定

この節が振り分けの正本で、各スキルはここを参照する。

#### 一行のルールに落ちる改善

ファイルへ自動記録せず、工程の終わりに完了カードでユーザーへ直接提案する。
`CLAUDE.md` への反映要否は人が判断する。

#### 構成規模の改善

複数ステップの追加・ファイルの新設・スキル本体の修正が要るものは、キューに積まず直接実装する。
カレントが dotfiles ならこのセッションで直接編集し、PJ セッションからなら `ListAgents` で稼働中の dotfiles セッションを探し `SendMessage` で依頼する。
現状は開発途上のため即時反映を優先し、後回しにしない。

#### PJ 固有の運用知識の発見

skill やパイプライン自体の不備ではなく、そのリポジトリに固有の手順・制約・回避策は、そのリポジトリの `CLAUDE.local.md` に用途ごとの節を立てて追記する。
グローバル `CLAUDE.md` や他 PJ には波及させない。
`/test` の「テストコマンドが分かったら `CLAUDE.local.md` の `## テスト` 節に書き戻す」仕組みの一般化にあたる。

#### 別 PJ の変更が必要

今のタスクを完了させるのに別 PJ の変更が必要なら、セッションを跨いで直接対応する。
相手 PJ に `claude` セッションが立っているか `ListAgents` で確認し、無ければ人に起動を頼んだうえで `SendMessage` で状況を伝え、会話しながら詰める。
ブロッカーなので依頼元 `tasks.md` の `## 事前セットアップ` の `S<n>` で追跡する。
解決したら人が `[x]` を付ける。

#### 棚上げで今のタスクは完了する

投げなくても今のタスクは完了するなら `/spinoff` に切り出す。
棚上げなので追跡記録を残さない。

### 起票の作法

一行のルールの提案は完了カードの「やったこと」に 1 行で載せる。
カードの外に別文で書かず、ファイルへの自動記録もしない。
`- 💡 提案: <claim>` の形式で書き、反映要否の判断は人に委ねる。

その場で割り込まず、工程の終わりという作業の区切りに回す。

`/spinoff` の下書き `requirements.md` 作成、構成規模の直接実装は確認を取らずに実行し、結果を事後報告する。
`/spinoff`・直接実装のいずれも同様。
