# Claude Code 設定

## ユーザーへの質問スタイル

選択肢を提示するツール、AskUserQuestionは使わない。

プロンプトの意図が理解できないときだけ質問する。
理解できれば、仮定を置かずそのまま進める。

ユーザーにコマンドの実行を頼むとき、`!` プレフィックスは案内しない。
別ペインで実行してもらい、コマンドの先頭に `Notify` をつけて案内する。
Notify がコマンドを実行し、成功と失敗の別、失敗時は終了コードと出力のログパスを claude に送る。
依頼は 1 回につき 1 コマンドにする。
複数の手順が要るときは 1 コマンドずつ頼み、結果を受けてから次を頼む。
`&&` やパイプは、それ無しでは成立しない単純なものに限り、その場合は `Notify sh -c '...'` の形にする。
Notify のコマンドは、別ペインが repo のルートディレクトリにいる前提で組み立てる。
`cd` や絶対パス、`git -C` のような cwd 指定を付けず、ルートからの相対パスで書く。
node や npm を使うコマンドを頼むとき、`.nvmrc` があれば先に `nvm use` する。
`nvm` はシェル関数なので `Notify sh -c '...'` ではなく `Notify zsh -ic '...'` の形にする。
依存インストールは社内ルールで Claude が実行しない。必要になったら止めて、1 コマンドで人に依頼する。

## 出力する文章のスタイル

丸括弧は使わない。
可読性が下がりユーザーの負担になるため。
ユーザーと会話する感じで書く。

進めた結果に対して、提案や次のステップに勝手に進まない。
聞かれたことにだけ答える。

## 実行していないことを書かない

ツールを実際に呼ばずに実行結果や tool_use を地の文で生成しない。
サブエージェントについても「起動した」と述べるだけで終わらせず、必ず Agent ツールを実呼び出しする。

## コードコメントの書き方

コメントは基本的に書かない。
消したときに後で読む人が困るかどうかで判断し、困らないなら書かない。
コードを読めば分かることや命名・型で表現できることはコメントで重複させず、コードそのものを直す。
変更の経緯はコミットメッセージやPR説明に書く。

書いてよいのは、コードを読むだけでは復元できない情報だけ。

- 実装を選んだ制約
- 一見不要に見えるが必要な理由
- 外部要因の判断

実装後は書いたコメントを1つずつ見直し、判定に迷ったら消す方に倒す。

## Bash の作業ディレクトリ

`settings.json` の `env.CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1` により、Bash コマンドの作業ディレクトリは呼び出しごとにプロジェクトルートへリセットされる。
`cd` しても次の呼び出しに持ち越されないため、cwd の意図しない持ち越しは起きない。
Claude 自身が実行する Bash でディレクトリを指定したいときは絶対パスか `git -C` / `make -C` / `npm --prefix` のようなオプションを使う。

## 会社設定で禁止されているコマンド

`~/.claude/remote-settings.json` の `permissions.deny` が正本。
Bash を組み立てる前に、`curl` `wget` `npm install` 系 `rm -rf` `docker` などが入っていないか意識する。
疎通確認は `curl` ではなく Playwright のブラウザ操作で行う。
deny 一覧は会社が更新しうるので、内容を写さずファイルを指す。

## 開発フロー

### コミット

コミットする際は必ず `/commit` スキルを使う。
`/commit` の外で直接 `git commit` を実行しない。

### force push

force push は draft PR のみ許可する。
Ready for review 済み、つまり open の PR には行わない。
レビュースレッドと CI 履歴が壊れ、復旧が効かないためです。

### 作業の退避

ブランチを切り替えて別の作業に戻る必要があるとき、未コミットの変更は `git stash` ではなく WIP コミットで退避する。
stash はブランチの外側の状態で、他の無関係な stash と混ざって見失いやすく、`git log` やブランチの状態からも気づけない。

- WIP コミットは `git log` から常に見え、`git reset --soft HEAD~<N>` で戻せる。
- コミットメッセージに `WIP:` などの接頭辞を付け、未整理である旨を明記する。
- 退避先のブランチから戻ったら、このコミットを起点に続けるか `/commit` 相当の整理で分割し直す。

### ガード・ブロックの扱い

目的の操作そのものがフックや権限でブロックされたら、それは「止まって確認する」シグナル。
Bash のリダイレクトや別コマンドのような別手段で同じ書き込みを試して迂回しない。
ユーザーに確認する。
配置場所・要否・方式を相談している最中も同じで、承認を得るまで成果物を作らない・変更しない。

読み取りだけの確認や補助コマンドがブロックされたら、同じ目的を満たす別の読み取り手段に切り替えて続行する。
この場合は止まらない。

### 開発パイプラインの用語集

スキル間で用語を統一する。

| 用語 | 意味 |
|---|---|
| 工程 stage | パイプラインの各段階で、各スキル spec / plan / impl / test / review / qa / commit / sync などを指す。「工程に戻す」「工程を推定する」はこの意味。 |
| 実装ブランチ | `/impl` が実装の最初に切る、`branch_name` のブランチ 1 本。目的は実装の隔離で、捨てる・作り直すのを安全にするため。`/land` がこのブランチから 1 本の PR を作り、追加 push は `/sync` が担う。 |
| Step | スキル内部の手順見出し。工程とは別物。 |

### HTML の生成

`.specs/` の jsonc を Write か Edit で書くと、`settings.json` の PostToolUse フックが `render.py` を呼び、同じディレクトリの jsonc すべての HTML を作り直す。
skill は `render.py` を呼ばない。
jsonc が壊れていると、フックが失敗の内容を返すので、jsonc を直す。

### 前提が覆ったとき

spec の前提、スコープ・依存・外部条件が途中で覆ったら、覆った前提のキーワードで `.specs/` 配下を grep し、requirements.jsonc / plan.jsonc に残る古い記述をすべて更新する。
1 ファイルだけ直して終わらせない。
spec ファイルは相互参照が多く、新旧の前提が並存すると読んだ人の判断が割れる。
どの工程から再入するかは `/orch` の「前進カスケード」に従う。

### 作業中の割り込み事項の扱い

ハーネスの改善ではなく、今のタスクの進め方に関わる割り込み事項の振り分け。

#### 別 PJ の変更が必要

今のタスクを完了させるのに別 PJ の変更が必要なら、セッションを跨いで直接対応する。
相手 PJ に `claude` セッションが立っているか `ListAgents` で確認し、無ければ人に起動を頼んだうえで `SendMessage` で状況を伝え、会話しながら詰める。
ブロッカーなので依頼元 `plan.jsonc` の `setup` の `S<n>` で追跡する。
解決したら人が `done` を `true` にする。

#### 棚上げで今のタスクは完了する

投げなくても今のタスクは完了するなら `/feature` に切り出す。
棚上げなので追跡記録を残さない。
下書き `feature.jsonc` の作成は確認を取らずに実行し、結果を事後報告する。
