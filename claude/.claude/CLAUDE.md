# Claude Code 設定

## ユーザーへの質問スタイル

ユーザーに確認・選択を求めるときは、すぐに回答できる形式にする：

- 2択: `y/n` または `はい/いいえ`
- 多択: 番号付きリスト
  ```
  1: ...
  2: ...
  3: ...
  ```
- 自由記述が必要な場合でも、典型的な選択肢を番号で並べて「その他」を最後に置く

上記のいずれの形式にも当てはまらない、選択肢を示さない聞き方は避ける。

## AskUserQuestionの禁止
選択肢を提示するツール、AskUserQuestionは使わないでください。
情報が足りない場合は、妥当な仮定を置いて回答し、その仮定を冒頭で明示してください。
どうしても必要な確認は本文中に1つだけ書いてください。

## 出力する文章のスタイル
- 丸括弧を使わないでください。丸括弧を使うと可読性が下がりユーザーの負担になるためです。ユーザーと会話する感じでお願いします。

## 実行していないことを書かない

ツールを実際に呼ばずに実行結果や tool_use を地の文で生成しない。サブエージェントについても
「起動した」と述べるだけで終わらせず、必ず Agent ツールを実呼び出しする。

## コードコメントの書き方

コメントは基本的に書きません。判断基準は一つで、そのコメントを消したときに後で読む人が困るかどうかです。困らないなら書きません。

コードを読めば分かることは、コード自体が同じ情報をより正確に伝えるので、コメントで重複させません。命名や型で表現できることも、コメントで補うのではなく命名や型そのものを直します。変更の経緯や理由はコードの中に残しても後から実態とずれていくので、コミットメッセージやPR説明に書きます。

書いてよいのは、コードを読むだけでは復元できない情報だけです。なぜその実装を選んだかという制約、一見不要または遠回りに見えるが実は必要な理由、コード上に痕跡が残らない外部要因の判断。これらは消すと失われる情報なので残します。

実装の後に、書いたコメントを1つずつ「消しても後で読む人が困らないか」で見直し、判定に迷ったら消す方に倒します。

## コミット

コミットする際は必ず `/commit` スキルを使う。直接 `git commit` を実行しない。実行するのは `/commit` が起動する `committer` エージェントのみです。

## force push

force push は draft PR のみ許可する。Ready for review 済み、つまり open の PR には行わない。
レビュースレッドと CI 履歴が壊れ、復旧が効かないためです。stacked PR の rebase 伝播で必要に
なった場合も、対象 PR が open なら push 前に確認する。

## 作業の退避

ブランチを切り替えて別の作業に戻る必要があるとき、未コミットの変更は `git stash` ではなく WIP
コミットで退避する。stash はブランチの外側にある状態で、セッションが変わって戻ってきたとき
`stash list` に他の無関係な stash、別ブランチ・別セッションのものが複数溜まっており、どれが
今回の作業分かを見失うリスクがある。`git log` やブランチの状態を見ただけでは存在にも気づけない。

- WIP コミットは `git log` やブランチの状態から常に見え、後から `git reset --soft HEAD~<N>` で
  戻せる。stash よりも「どこに行ったか」が追跡しやすい
- コミットメッセージには `WIP:` 等の接頭辞を付け、セルフレビュー中や分割未完了などまだ整理
  されていない旨を明記する
- 退避先のブランチに戻ってきたら、この WIP コミットを起点に作業を続ける。そのまま残すか、後で
  `/commit` 相当の整理を経て分割し直すかは状況次第

## ガード・ブロックの扱い

フックや権限で操作がブロックされたら、それは「止まって確認する」シグナル。Bash のリダイレクトや
別コマンドのような別手段で同じ書き込みを試して迂回しない。ユーザーに確認する。
配置場所・要否・方式を相談している最中も同じで、承認を得るまで成果物を作らない・変更しない。

## Markdown の部分書き換え

`.specs/` 配下の Markdown の部分書き換え、チェックボックスの `[ ]`→`[x]` などは Edit ツールで
行う。`sed -i` / `perl -i` の in-place 編集は、macOS の `-i ''` の空引数がパスとして解釈されて
`restrict-edits.sh` にブロックされる。件数が多くても Edit を必要回数呼ぶ。

## Bash の作業ディレクトリ

`settings.json` の `env.CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1` により、Bash コマンドの
作業ディレクトリは呼び出しごとにプロジェクトルートへリセットされる。`cd` しても次の呼び出しに
持ち越されないため、cwd の意図しない持ち越しは起きない。ディレクトリを指定したいときは
絶対パスか `git -C` / `make -C` / `npm --prefix` のようなオプションを使う。

## 完了カードの共通仕様

各スキルの最終 Step は、この形式で完了カードを出力して終わる。個別の見出し名・生成物・
次の一手の中身はスキルごとに決め、この節では繰り返さない。

- コードフェンス自体は出さず中身だけそのまま出力する。前後に作業サマリ・所感・補足を足さない
- カードは**〈完了系の見出し〉**・**要確認**・**次の一手**の 3 ブロックに分ける。混ぜない
- 見出しの 1 行目は一言サマリ。主要な結果は `- ` 箇条書きで**最大 3 行**。無ければ行ごと省略する
- 生成物は 1 件 1 行。変更ファイルの一覧や委譲先エージェントの報告詳細は列挙しない
- 要確認: 仕様に根拠が無くスキル側やエージェント側が自分で決めた点を挙げる。無ければブロックごと省略する
- 次の一手: 次工程への具体的なコマンド。次工程の起動そのものは完了条件に含めない

**中断時**: 同じブロック構成で見出しを `〈完了系の見出し〉` → `〈中断系の見出し〉` に差し替える。
一言サマリに中断理由。次の一手に復帰コマンドを出す。

## 開発パイプラインの用語集

スキル間で用語を統一する。特に「フェーズ」と「工程」を混同しない。

| 用語 | 意味 |
|---|---|
| 工程 stage | パイプラインの各段階で、各スキル spec / design / tasks / impl / test / review / qa / commit / sync-to-remote などを指す。「工程に戻す」「工程を推定する」はこの意味。 |
| フェーズ phase | 実装後に `/sync-to-remote` が確定する PR 単位。ブランチ `pN` が 1 PR に対応する。分割が要らなければフェーズは現れず単一 PR になる。実装前には存在せず、`/impl` はフェーズを持たない。 |
| 大タスク / サブタスク | tasks.md の 2 階層。大タスクは関心のグルーピングで PR 単位ではなく、その配下がサブタスクで実装の最小単位。 |
| stacked PR | 分割したフェーズを積み上げるブランチ運用。`pN` を `p(N-1)` にスタックする。`/sync-to-remote` が実装後のコミット列から切り出す。 |
| 実装ブランチ | `/impl` が実装の最初に切る `<feature>` 1 本。目的は実装の隔離で、捨てる・作り直すのを安全にするため。PR の単位ではない。 |
| フェーズブランチ | `/sync-to-remote` が分割時にコミット境界から切る `<feature>-pN`。PR の単位で、分割しなければ作られない。 |
| Step | スキル内部の手順見出し。工程・フェーズとは別物。 |

## herdr によるセッション分離

複数リポジトリにまたがる開発でセッションをどう分けるかの方針。

### どこで分けるか

- `/spec`〜`/tasks` は 1 セッションに集約する。命名統一など横断的な決定がこの区間に集中する
  ため、複数リポジトリが絡んでもここは分割しない。
- `/impl` 以降はリポジトリごとに herdr で物理的に独立したセッションへ分離する。実装は各
  リポジトリの実装ブランチに閉じるため、リポジトリを跨いだ集約は不要になる。

### herdr の役割の限定

herdr の役割はセッションの配置だけに限定する。配置後の対話・完了待ちは herdr ではなく
`ListAgents` + `SendMessage` に一本化する。`SendMessage` は `notify_when_idle: true` を
付けて完了通知を受ける。`herdr agent send` は対象セッションの入力欄へ文字を送るだけで
Enter 相当の送信を伴わないことを実測で確認済みのため、対話・指示出しの手段として使わない。

### 実装中の設計変更

実装途中で設計変更が必要になった場合は、herdr で分離した実装セッションから `/spec`〜`/tasks`
を集約したメインセッションへ `SendMessage` で差し戻し、合意を取り直してから実装セッション側に
反映する。再入先の判断自体は `/orch` の「共通: 実装中の変更」の前進カスケードに従う。

## 前提が覆ったとき

spec の前提、スコープ・依存・外部条件が途中で覆ったら、覆った前提のキーワードで
`.specs/<feature>/` 配下を grep し、requirements.md / design.md / tasks.md に残る古い記述を
すべて更新する。1 ファイルだけ直して終わらせない。spec ファイルは相互参照が多く、新旧の
前提が並存すると読んだ人の判断が割れる。矛盾したドキュメントは無いより悪い。編集モードの
再入で担保されるのは構造的な整合だけで、別の節に残った古い文言は引っかからない。
どの工程から再入するかは `/orch` の「工程一覧」にある「共通: 実装中の変更」の前進カスケードに従う。

## 担当 feature のスコープ

成果物の書式は担当スキルの出力フォーマットにだけ従う。書式や判断の前例を探す目的で
他 feature の `.specs/` を読まない。スキルに規定が無いなら前例で埋めず、規定不足として報告する。

## PR 運用

### ブランチ・タイトル命名

全 PR タイトルは固定 prefix `【鎌田QA】` で始める。形式の詳細はフェーズ番号の付け方や `seed.md` の frontmatter の使い方を含めて `/sync-to-remote` に一元化されている。`seed.md` の `pr_title` を直接読み、`/tasks` は経由しない。

### 運用の有無の判定

repo が PR を運用するかはリポジトリの性質であって工程の性質ではない。判定条件はこの節に一元化し、各スキルは自前の判定を持たずここを参照する。

判定材料は repo ルート側のプロジェクト `CLAUDE.md` にあるブランチ・PR 運用に関する記述。この global 設定は材料にしない。

| 判定値 | 確定条件 |
|---|---|
| `あり` | ブランチ・PR 運用の記述が無い、`CLAUDE.md` 自体が無い場合を含む／stacked PR・PR 前提の運用が記述されている |
| `なし` | 「ブランチを切らない」「デフォルトブランチへ直接コミット / 直接 push する」「PR を作らない」「PR 運用を勧めない」のいずれかに相当する記述がある |

記述が混在する・条件付きでどちらとも決まらない `不明` の場合は安全側の `あり` を採る。PR を余分に作っても閉じれば済むが、レビューを求める repo で黙ってデフォルトブランチを進めると戻せない。

判定を読むのは `/sync-to-remote` だけ。`あり` なら draft PR を作り、`なし` なら実装ブランチをデフォルトブランチへ取り込んで push する。

他の工程は運用差を持たず、常に PR 前提で動く：

- `/tasks` — PR タイトルには関与しない。素材となる `seed.md` の `pr_title` から分割・最終的なタイトルの確定まで `/sync-to-remote` が一貫して行う
- `/impl` — 常に実装ブランチ `<feature>` を 1 本切る。実装を隔離しておけば捨てる・作り直すのが安全
- `/commit` — 判定しない。コミットは可逆で push もしないため

### 分割の判定

PR を何本に割るかは実装後に決める。判定するのは `/sync-to-remote` だけで、材料はコミット済みの diff と実物のコミット列。

実装前の見積りで割ると、量が少ないのに stacked にされる。既定は単一 PR で、分割は理由を要する例外として扱う。判定基準の詳細は `/sync-to-remote` を参照。`/tasks` と `/impl` は分割を決めない。

## Notion 連携

Notion に触れるのは入力を担う `/notion-import` と出力を担う `/notion-export` の 2 つだけ。他工程は Notion を知らず、`.specs/<feature>/` のファイルだけを読む。これで Notion 連携の可否の分岐がパイプライン全体に広がらない。どちらも人が明示的に実行する。`/orch` の自走パイプラインには組み込んでいない。

## 訂正・摩擦の扱い

ユーザーから訂正・注意・却下を受けたとき、または自分が作業中に摩擦にぶつかったとき、その気づきを
改善提案に切り出す。恒久ルール、`CLAUDE.md`、へ自己判断で追記しない。恒久化するかは人が判断する。

### 摩擦の判定基準

摩擦とは次のもの。曖昧な違和感は含めない。フックや権限で操作がブロックされて迂回や往復が
発生した／同じ確認をユーザーに 2 回以上した／上流工程の成果物、要件・設計・タスクの不備を
見つけた／スキルの手順どおりに進められなかった／その工程が本来 catch すべきだった逸脱に気づいた。

その場限りのタイポ・パス違いなど再発しない訂正は摩擦に含めず切り出さない。

### 行き先の判定

この節が振り分けの正本で、各スキルはここを参照する。

- skill / パイプラインの改善で、一行のルールに落ちるもの → `/propose` でキューに記録する。
- skill / パイプラインの改善で、構成規模のもの。複数ステップの追加・ファイルの新設・スキル
  本体の修正が要るもの → キューに積まず直接実装する。カレントが dotfiles ならこのセッションで
  直接編集し、PJ セッションからなら `ListAgents` で稼働中の dotfiles セッションを探し
  `SendMessage` で依頼する。現状は開発途上のため即時反映を優先し、後回しにしない。
- 今のタスクを完了させるのに別 PJ の変更が必要 → セッションを跨いで直接対応する。相手 PJ に
  `claude` セッションが立っているか `ListAgents` で確認し、無ければ人に起動を頼んだうえで
  `SendMessage` で状況を伝え、会話しながら詰める。ブロッカーなので依頼元 `tasks.md` の
  `## 事前セットアップ` の `S<n>` で追跡する。解決したら人が `[x]` を付ける。
- 投げなくても今のタスクは完了する → `/spinoff`。棚上げなので追跡記録を残さない。

### 起票の作法

起票したら完了カードに載せる。カードの外に別文で書かず、「やったこと」の 1 行として出す。
例: `- 💡 提案 1 件発行: <claim>`

その場で割り込まず、工程の終わりという作業の区切りに回す。

提案ファイル・`seed.md` の作成、構成規模の直接実装は確認を取らずに実行し、結果を事後報告する。
`/propose`・`/spinoff`・直接実装のいずれも同様。
