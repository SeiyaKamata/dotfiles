# Claude Code 設定

## ユーザーへの質問スタイル

ユーザーに確認・選択を求めるときは、すぐに回答できる形式にする：

- **2択**: `y/n` または `はい/いいえ`
- **多択**: 番号付きリスト
  ```
  1: ...
  2: ...
  3: ...
  ```
- 自由記述が必要な場合でも、典型的な選択肢を番号で並べて「その他」を最後に置く

開放的な質問（「どうしますか？」など）は避ける。

## コミット

コミットする際は必ず `/commit` スキルを使う。直接 `git commit` を実行しない。

## force push

force push は **draft PR のみ**許可する。Ready for review 済み（open）の PR には行わない
（レビュースレッドと CI 履歴が壊れ、復旧が効かない）。stacked PR の rebase 伝播で必要に
なった場合も、対象 PR が open なら push 前に確認する。

## ガード・ブロックの扱い

フックや権限で操作がブロックされたら、それは**「止まって確認する」シグナル**。別手段
（Bash のリダイレクト・別コマンド）で同じ書き込みを試して迂回しない。ユーザーに確認する。
配置場所・要否・方式を相談している最中も同じで、承認を得るまで成果物を作らない・変更しない。

## 実行していないことを書かない

ツールを実際に呼ばずに実行結果や tool_use を地の文で生成しない。サブエージェントについても
「起動した」と述べるだけで終わらせず、必ず Agent ツールを実呼び出しする。

## 訂正の扱い

ユーザーから訂正・注意・却下を受けたら、その気づきを**改善提案に切り出す**。恒久ルール
（`CLAUDE.md`）へ自己判断で追記しない — 再発判定は `/proposals-sweep`、恒久化するかは人が判断する。

- **成果物の種類で選ぶ**: 一行のルールに落ちる（`CLAUDE.md` か対象スキルに 1 行足せば次回以降
  防げる）なら `/propose`。手順・構成の変更が要る（複数ステップ・ファイルの新設・コードの修正）なら
  `/spinoff`（今いる PJ で直せる）・`/handoff`（別 PJ 側の変更が要る）。スキル・パイプライン本体の
  穴は dotfiles 宛（dotfiles で作業中なら `/spinoff`）。
- **敷居**: その場限りのタイポ・パス違いなど再発しない訂正は切り出さない。
- **タイミング**: その場で割り込まず、**作業の区切り**（工程の終わり）に回す。
- 自動起動しない。切り出し先を提示して実行は人に委ねる。

## 用語集（開発パイプライン）

スキル間で用語を統一する。特に「フェーズ」と「工程」を混同しない。

| 用語 | 意味 |
|---|---|
| **工程 (stage)** | パイプラインの各段階＝各スキル（spec / design / tasks / impl / test / review / qa / commit / create-pr / …）。「工程に戻す」「工程を推定する」はこの意味。 |
| **フェーズ (phase)** | 実装を PR 単位に割った塊。**大タスク = フェーズ = ブランチ `pN` = 1 PR**。複数フェーズ = stacked PR。 |
| **大タスク / サブタスク** | tasks.md の 2 階層。**大タスク ≡ フェーズ**（1 PR）、その配下がサブタスク（実装の最小単位）。 |
| **stacked PR** | フェーズ（大タスク）を積み上げるブランチ運用（`pN` を `p(N-1)` にスタック）。 |
| **Step** | スキル内部の手順見出し。工程・フェーズとは別物。 |

## PR / ブランチ命名

全 PR タイトルは固定 prefix `【鎌田QA】` で始める。形式の詳細（フェーズ番号の付け方・`seed.md` frontmatter の使い方）は `/tasks`（PR タイトル確定）と `/create-pr`。

## Notion 連携

Notion に触れるのは `/notion-import`（入力）と `/notion-export`（出力）の 2 つだけ。他工程は Notion を知らず、`.specs/<feature>/` のファイルだけを読む。これで Notion 連携の可否の分岐がパイプライン全体に広がらない。**どちらも人が明示的に実行する**（`/orchestrator` の自走パイプラインには組み込んでいない）。
