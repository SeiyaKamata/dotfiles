# 新規PR着地スキル

## 役割
コミット後の変更を初めて draft PR としてリモートへ着地させる。

PR を何本に割るかを判定するのはこの工程だけで、判定材料は実装後のコミット済みの実物、diff とコミット列にする。
既存 PR への追加コミットの push は扱わず、「まだ PR を持たないブランチの初回」と「次のフェーズを新しい PR にする」ときだけを担う。
既に PR があるブランチ・マージ済みのブランチはスキップするので、何度呼んでも同じ結果になる。

## 判断が割れる点の扱い
ベースブランチはデフォルトブランチを自動採用し、聞かない。
分割の判定に迷えば単一 PR に倒し、倒した判断は完了カードの要確認に出す。
rebase のコンフリクトや push の拒否は自動解決せず、中断カードで人に委ねる。

## PR 分割の基準
既定は単一 PR で、次の 4 つのいずれかに該当するときだけ stacked を検討する。

| 理由 | 内容 |
|---|---|
| (a) レビュー負荷 | 1 つの機能として完結し feature を分けられないが、1 PR に収めるとレビュアーが一度に見る量が過大 |
| (b) リスク分離 | 破壊的マイグレーション・広範なリネームのような危険な変更を、安全な変更から切り離して先に着地させたい |
| (c) 着地の緊急度差 | 一部を先に本番へ出したい |
| (d) レビュアーが違う | 領域ごとに別の人が見る |

分割しない側に働く力も判定材料にする。
- 前のフェーズに修正が入るたび、次のフェーズを作る前に実装ブランチを載せ直す手間が要り、コンフリクトすれば人を呼ぶ
- 同じコードが PR の本数ぶん CI で回る
- 後続 PR が着地までブロックされる
- force push が draft PR に限られる

割ってはいけないもの。
- 1 つの契約を共有するコミット群。出力側と読み取り側の両端を変える修正のように、片側だけ着地すると壊れる
- 量だけを理由にした分割。変更行数・ファイル数は理由 (a) の材料に留め、閾値で機械的に決めない

分割点はコミットの境界から選び、1 つのコミットを複数の PR に分けない。
各分割点は「そこまでをデフォルトブランチにマージして放置しても、既存挙動が壊れず、機能が中途半端な状態で止まらないか」の着地テストを通す。
そのフェーズだけでは動かず未使用のコードが増えるだけなら通し、そこまででは妥当か判断できない状態なら落とす。
どの分割点も落ちれば単一 PR にする。

stacked でも全 PR を一斉には作らない。
一斉に作ると `p1` に返ってきた指摘の修正が全スタックへの rebase 伝播を要求し、自走で安全に行えない。
1 本ずつ閉じてから次を作れば、修正は常に先端で完結する。

## PR のタイトルと本文
タイトルは固定 prefix `【鎌田QA】` で始め、`<pr_title>` は `.specs/<feature>/requirements.md` の frontmatter から取る。
無ければコミットメッセージから主題を作る。

- 単一 PR: `【鎌田QA】<pr_title>`
- stacked: `【鎌田QA】<pr_title>：<フェーズ内容>（PR<N>/<M>）`
  - `<フェーズ内容>` はそのフェーズのコミット列から 1 行で書く

```markdown
@coderabbitai ignore

## Summary
[変更の概要を 1〜3 行。stacked なら冒頭に `stacked PR 2/3 — base: <feature>-p1` の形で位置と base]

## 変更内容
[そのフェーズの git diff だけをもとに、変更ファイルと変更内容を箇条書き。前フェーズの変更を含めない]

## このPRをマージした後の状態
[着地テストで言語化した状態を 1 行。単一 PR では省略してよい]
```

本文の書き方。
- IT・ビジネスの専門用語を避け、読んだ人が知識に関わらず理解できる言葉で書く
  - リファクタリング・マイグレーション・エンドポイント・スキーマ・デプロイ・バリデーションは、コードの整理・テーブル構造の変更・API の受け口・データの形式・本番環境への反映・入力値の確認と言い換える
- 今日チームに入ったばかりの人が 1 度読み通すだけで、何が変わったか・なぜ必要か・なぜ安全かを掴めるかを自問し、Summary の 1 文を専門用語ゼロで言い切れないなら書き直す
- PR の git diff に出るファイルだけに言及し、`.gitignore` 配下のファイルには触れない
- 別 PR / 別チケットへのリンクは付けてよいが、リンク先を読まないと理解が成立しない書き方は避ける
- 箇条書きは太字の見出しを項目にし、空行 + 2 スペースインデントで詳細を段落として落とす
- フローに変更があれば Mermaid 図を Before / After 並置か `★新規` / `★変更` / `★削除` の差分ラベルで書き、図だけ見て何が変わったかが 1 文で言えなければ作り直す
- `gh pr create --body` の HEREDOC は `<<'EOF'` の literal mode にし、バッククォートを escape しない
  - escape すると backslash がそのまま渡って表示が崩れる

## 進め方

### Step 1: 未コミットの変更確認

`git status` で確認し、あれば `/commit` を起動して完了後に続行する。

### Step 2: 対象ブランチの解決

```
DEFAULT=$(git default-branch)
CURRENT=$(git branch --show-current)
```

`CURRENT` が `<feature>` とも `<feature>-pN` とも一致しなければ、`git branch --list "<feature>-p*"` で探して `git switch` する。
- 1 件 → そのフェーズブランチへ
- 0 件 → `<feature>` へ。存在しなければ実装ブランチが無い旨を Step 7 の中断カードで報告する
- 2 件以上 → 1 周を閉じきってから次を作る前提が崩れているので、Step 7 の中断カードで報告する

switch 後の `CURRENT` で呼ばれ方を判定する。
- `<feature>-pN` → 再呼び出し。`gh pr view --json statusCheckRollup,reviewThreads` で CI green かつ未返信の未解決コメントなしを確認する
  - 満たしていなければこのフェーズは閉じきっていないので、Step 7 の中断カードで報告する
  - 満たしていれば分割の方針は決まっているので Step 3 を飛ばし Step 4 へ
  - 実装ブランチ `<feature>` に未反映のコミットが残っていなければ「全フェーズ着地済み」として Step 7 へ
- それ以外 → 初回。Step 3 へ

feature 名は `-p<数字>` を除いて求める。

### Step 3: 分割の判定

```
git fetch origin "+refs/heads/$DEFAULT:refs/heads/$DEFAULT"
git log "$DEFAULT"..HEAD --oneline
git diff "$DEFAULT"...HEAD --stat
```

「PR 分割の基準」で単一か stacked かを決め、stacked なら分割点と総 PR 数 `M` を確定して `p1` だけを切る。

```
git branch <feature>-p1 <分割点1のコミット>
```

残りの分割点は Step 4 の載せ直しで SHA が変わるので、「どのコミットまでを次のフェーズに入れるか」をコミットの内容で完了カードに報告する。

### Step 4: 前のフェーズの先端へ載せ直す

再呼び出しのときだけ。
`p1` を閉じる過程で積まれた修正コミットを実装ブランチは持っていないので、そのまま次を切ると差分に前の修正の打ち消しが現れる。

```
git checkout <feature>
git rebase <feature>-pN
git branch <feature>-p(N+1)
```

実装ブランチは push しないので、この rebase は他人が見ているブランチを書き換えない。
コンフリクトが出たら `git rebase --abort` で戻し、衝突ファイルを Step 7 の中断カードに出す。
載せ直した結果、次のフェーズに入れる差分が空なら前のフェーズの修正で吸収されたので、そのフェーズは作らず「全フェーズ着地済み」として Step 7 へ。

### Step 5: 対象の絞り込み

- 単一 → `<feature>` 1 本
- stacked → その周の 1 フェーズだけ。初回なら `p1`、再呼び出しなら Step 4 で作った `p(N+1)`

`gh pr list --head "<対象ブランチ>" --state all --json number --jq '.[].number'` が空でなければ既に PR があり、`git branch --merged "$DEFAULT"` に含まれていればマージ済みなので、どちらもスキップする。
対象が 0 件なら既存 PR の URL を Step 7 で報告して終了する。

### Step 6: draft PR を作る

単一でカレントブランチがデフォルトブランチと同じなら、コミット内容から命名したブランチを `git checkout -b` で作ってから進む。
push を実行するのはこのスキルなので、デフォルトブランチのまま push しないための最終防波堤になる。
stacked ではフェーズブランチが既にあるので新規作成しない。

`gh label list` でラベルを取得し、未 push なら `git push -u origin <対象ブランチ>` してから、「PR のタイトルと本文」で作成する。

```
gh pr create --draft --base <base> --head <対象ブランチ> --title "<タイトル>" --body "<本文>" --assignee @me --label "<ラベル>"
```

base は単一ならデフォルトブランチ、stacked なら 1 つ下のフェーズで `p1` はデフォルトブランチ。
残りのフェーズはここでは作らず、この PR が CI green + 未返信の未解決コメントなしになってから `<feature>-pN` で `/land` を再度呼ぶ。

`gh pr create` が「head branch is the same as base branch」で失敗したら、base と head が同じになっていないかを確認する。

### Step 7: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### draft PR 作成中断` にし、1 行目に中断理由を書き、作成できた PR があれば生成物の行を残し、次の一手は復帰に必要な操作だけにする。

```markdown
### draft PR 作成完了
<作成した PR の構成、単一 / stacked N/M、と分割した場合は採用した理由 (a)〜(d) を 1 行>

生成物: <作成した PR の URL。既存でスキップした PR は URL の後に（既存）を添え、1 PR 1 行>

### 要確認
- <分割点の取り方と、未作成の後続フェーズの本数。この PR が green + 全件返信済みになったら `<feature>-pN` に switch して `/land` を再実行>
<無ければこのブロックを省略>

### 次の一手
- CI を監視する: `/watch-ci`
```
