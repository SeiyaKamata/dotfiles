# PRコメント選別スキル

## 役割
自分の PR に付いた未解決のレビューコメントを収集し、要件照合と裏取りを行った上で、対応方針の提案を `comment-report.md` にまとめる。
コード修正・返信・スレッド対応は行わない。
対応する/しないの判断は人の領分なので、ここでは提案するだけで確定させない。

人への確認は 1 件ずつの対話では行わない。
全件の提案をレポートとして出力し、承認は人がレポートを読んで書き込む非同期の形にする。
これにより `orch` のような自走スキルから呼んでも、対話の同期待ちを発生させずに次工程へ進める。

対応中にレビュアーの恒常的な好みや PJ の規約などの摩擦に気づいたら、`claude/CLAUDE.md`「ハーネスの自己強化」の「PJ 固有の運用知識の発見」に従い、そのリポジトリの `CLAUDE.local.md` に書き戻す。

## 入出力
- 入力:
  - PR 番号。
    引数で指定するか、未指定ならカレントブランチの PR を使う。
  - その PR のコメント。インライン + 会話
  - `.specs/<feature>/requirements.md`
- 出力:
  - `.specs/<feature>/comment-report.md`。対応方針の提案と、人間が承認を書き込む欄

## 用語（前提）
用語は `claude/CLAUDE.md`「用語集」に従う。

## コメントの属性
コメントごとに次の属性を持ち回る。`classification` は Step 5、`verification` は Step 6、`proposal` は Step 7 で埋まる：

| 属性 | 値域 |
|---|---|
| `classification` | `整合` \| `矛盾` \| `スコープ外` \| `無関係` \| `未照合` |
| `verification` | `成立` \| `不成立` \| `未検証` \| `対象外` |
| `proposal` | `対応する` \| `対応しない` |

`proposal` は提案であって確定ではない。
確定した `policy` は人間が `comment-report.md` の承認欄に書き込む。

`verification` の `対象外` は「矛盾／スコープ外と分類した」「人間の指摘」「質問・議論系」など**裏取りを実施しなかった**ケース。
`未検証` は**裏取りを実施したが成立・不成立を判定できなかった**ケースだけに使う。
この 2 つを混同すると要確認の件数が意味を失う。

対象コメントは全 author、人間 + CodeRabbit。
author で絞り込まない。

## 除外基準
収集したコメントから対応対象を絞り込む基準。
Step 2 で適用する。

**解決済みスレッドの除外:**
収集したインラインコメントには解決済みも含まれる。
未解決スレッドを reviewThreads で取得し、`path` + `line` + 本文で突き合わせて、解決済みのものを対象から外す：
```
gh pr view <PR番号> --json reviewThreads \
  --jq '[.reviewThreads[] | select(.isResolved == false) | {path, line, body: .comments[0].body}]'
```

**選別済みの除外:**
author を絞らず全コメントを対象にするため、再収集で同じコメントを何度もレポートに載せないよう必要。
既存の `.specs/<feature>/comment-report.md` があれば読み込み、そこに載っているコメントは `id` で突き合わせて対象から外す。
ただし承認欄が空のまま残っている項目は再提示の対象として残す。

インラインは収集済みの全コメント、ルート + 返信、をそのまま使う。
追加の取得は不要。

会話コメントはスレッド構造を持たないため、`comment-report.md` に記録済みの `id` の集合と突き合わせて除外する。

**nitpick の除外:**
レビュー bot が軽微・任意、nitpick、と分類した指摘は対応対象から外す。
bot 自身が「対応しなくてよい」と申告しているものに要件照合・裏取りのフル手順を回すのは費用に見合わない。
除外した件数は Step 8 の「要確認」に出し、拾うかは人に委ねる。

**除外の順序:** 解決済みスレッドの除外 → 選別済みの除外 → nitpick の除外。
すべてを通ったものが対象になる。

## 引用の基準
Step 7 でレポートに根拠を書くときの基準。
`sync` が返信を組み立てる際にそのまま引用できる形にする。

**根拠はファイルパスではなく文言の引用で示す。**
`.specs/` は gitignore されており PR の diff にも GitHub 上にも出ないため、レビュアーはそのファイルを開けない。
CodeRabbit も同様。
ファイル名・パスを書かず、該当する受け入れ条件・「含まない」項目の文言を転記する。

| ケース | 引用 |
|---|---|
| 矛盾 | `本 feature の要件「<要件名>」の受け入れ条件「<該当行を転記>」と矛盾する` |
| 矛盾。要件側を直すべき | 上記に加えて「ご指摘の方が妥当。要件そのものの見直しが必要」の旨 |
| スコープ外 | `「含まない」と定めた項目「<該当項目を転記>」に該当する。理由: <理由>` |
| 要件の意図への回答 | `要件「<要件名>」/ スコープの「<項目を転記>」を根拠に<結論>` |
| 根拠が見つからない | `要件を確認したが該当する記述が見つからなかった。確認した範囲: <範囲>` |

## 進め方
各 Step は順番に実行する。
**完了ゲート**を通過するまで次へ進まない。

### Step 1: 対象PRの特定

常に 1 PR だけを対象にする。
他フェーズの PR には踏み込まないため、rebase 伝播は発生しない。
上から順に判定し、最初に当たったもので確定する。

1. PR 番号が渡されている → その 1 本：
```
gh pr view <PR番号> --json number,title,url,headRefName
```

2. 渡されていない場合は既定でカレントブランチの PR を使う：
```
gh pr view --json number,title,url,headRefName
```

PR を特定できなければ中断する。
PR 番号を渡して再実行するよう復帰コマンドに書く。
特定できた場合は確認を求めず先へ進む。

**完了ゲート:** 対象 PR と feature 名を確定したか。
feature 名は head ブランチが `<feature>-pN` なら `<feature>`、それ以外はブランチ名をそのまま feature 候補とする。

### Step 2: コメント収集

インラインのコメントだけ見ると会話コメントを取りこぼすため、2 種類とも集める。
レビュー総評は総括であり個別コメントへの対応ではないため対象に含めない。

① インラインのレビューコメント。フィルタなしで全件、ルート + 返信を 1 回で取得する
```
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments \
  --jq '[.[]] | sort_by(.path, .line)'
```
ここからルートコメントだけを抜くには `.in_reply_to_id == null` でフィルタする。
`line != null` でフィルタするとファイル全体へのコメント、line: null、が漏れるので使わない。

② PR 会話タブの一般コメント
```
gh api repos/{owner}/{repo}/issues/<PR番号>/comments --jq '.[] | {id, user: .user.login, body}'
```

収集できたら「## 除外基準」に従って対象を絞り込む。

**完了ゲート:** 2 種類を取得し、解決済み・選別済み・nitpick を除外した対象コメント一覧ができたか。

### Step 3: 0件チェック

一覧が空なら Step 4 以降、要件読込・要件照合・裏取り、を**いずれも実行しない**。
未解決コメントが無いことを報告して終了する。
既存の `comment-report.md` に承認待ちの項目が残っていれば、その件数もあわせて報告する。

**完了ゲート:** 空なら終了を確定して報告したか。
空でなければ次へ進む。

### Step 4: 照合基準の読込

Step 1 で確定した feature 名を入力に、対象 PR の `requirements.md` を特定して読み込む。

所在特定。上から順に試す:
```
# 1. 直接ヒットを試す
test -f .specs/<feature>/requirements.md

# 2. 外れたら .specs 配下を列挙し、ブランチ名に最も近いものを選ぶ
find . -path './.git' -prune -o -name 'requirements.md' -print | grep '\.specs/'
```
- 単一ヒット → それを使う。
  複数ヒットして選べない → ユーザーに確認する。
  0 件 → 特定失敗
- **Read のみで扱う。Edit / Write はしない**

読み込んで保持する照合基準:
- 「## スコープ」節の「含む」「含まない」の各項目。「含まない」は理由込み
- 各 `### Requirement N` の受け入れ条件

**特定失敗時のフォールバック:** 要件照合を行わず、実コードでの裏取りだけで続行する。
**中断しない**。
Step 8 で「要件未照合」を報告する。

**完了ゲート:** requirements.md を読み込めたか、または特定失敗を確定してフォールバックに進んだか。

### Step 5: 要件照合

requirements.md を読み込めた場合、対象コメント全件を照合し、次の 4 分類のいずれか 1 つに分類する。
裏取りより先に行う。
「矛盾」「スコープ外」と判定した指摘はコードを触らない提案になるため、裏取りには進まない。

| 分類 | 判定基準 | 裏取り |
|---|---|---|
| 整合 | 指摘に従うと受け入れ条件を満たす方向に近づく | 裏取りに委ねる |
| 矛盾 | 指摘に従うと受け入れ条件を破る | しない |
| スコープ外 | 「含まない」いずれかの項目に該当する | しない |
| 無関係 | requirements.md が言及していない領域。スタイル・実装品質など | 裏取りに委ねる |

「整合」「無関係」は照合結果を理由に提案を変えず、裏取りの結果に従う。

矛盾のサブ分岐: 指摘の方が妥当で要件側を直すべきと判断した場合も、「矛盾」と同じ扱いとし、要件の見直しが必要と判断した旨をレポートに含める。
requirements.md はこの場で書き換えない。

判定に迷うケース:
- 「整合」か「無関係」で迷う → どちらでも提案は変わらないので、どちらかに寄せて先へ進む
- 「矛盾」か「スコープ外」で迷う → 「含まない」項目への該当を優先して判定する
- 確信が持てない → 迷った旨と根拠をレポートに記録し、暫定の分類のまま先へ進む

**完了ゲート:** 対象コメント全件が 4 分類のいずれかに分類されたか。

### Step 6: 裏取り

「整合」「無関係」と分類した AI 指摘、実質的には CodeRabbit の指摘だけを対象に、提案を決める前に実コードで裏を取る。
AI レビューは誤検知を含み、鵜呑みで直すと問題のないコードを壊す。

指摘された箇所を開き、その条件が実際に成立しうるかを確認する。
呼び出し元・型・既存のガード節・テストの有無まで辿り、影響範囲も確認する。
不成立と判断したら「対応しない」の提案とし、確認した根拠を添える。
成立とも不成立とも確認できない場合は `verification = 未検証` のまま確認した範囲を記録し、Step 8 の要確認に回す。

人間の指摘・質問議論系コメントには裏取りを行わない。
`verification = 対象外`。

**完了ゲート:** 整合・無関係に分類した AI 指摘全件に、成立 / 不成立 / 未検証のいずれかが付いたか。

### Step 7: レポート作成

`.specs/<feature>/comment-report.md` を Write する。
既存ファイルがあれば、承認欄が埋まっていない項目を維持しつつ、新規コメントを追記する。

```markdown
---
fixed: false
pr: <PR番号>
branch: <headRefName>
head: <HEAD SHA>
---

# コメント対応レポート: PR #<PR番号>

<総件数> 件。各項目の「承認」欄に `対応する` / `対応しない` / `保留` のいずれかを記入してください。
空欄のままだと次の工程で拾われません。

## [1/<総件数>] <path>:<line>、投稿者: <author>

<コメント本文>

要件照合: <分類>。根拠: <引用>
裏取り: <成立 / 不成立 / 未検証 / 対象外>
提案: <対応する / 対応しない>。理由: <理由>

承認: <未記入>

---

## [2/<総件数>] ...
```

`id` を HTML コメントで埋め込み、次回実行時の選別済み除外に使う：
```
<!-- comment-id: <id> -->
```

**完了ゲート:** 対象コメント全件がレポートに記載され、`comment-report.md` を Write したか。

### Step 8: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。
人に確認を求めず、ここで工程を終える。

```markdown
### コメント選別完了
<提案件数を 1 行>
- <主要な提案 最大 3 行>

生成物: `.specs/<feature>/comment-report.md`

### 要確認
- 未検証 <n> 件。裏取りで成立・不成立を判定できなかった指摘
- スコープ外 <n> 件 → /spinoff
- 要件の見直しが必要 <n> 件 → /spec <feature>
- nitpick 除外 <n> 件。bot が軽微と分類し、レポートに載せていない
- 要件未照合。requirements.md を特定できず

### 次の一手
- レポートの承認欄を確認する: `.specs/<feature>/comment-report.md`
- 承認後に修正する: `/fix <feature>`
```

- やったこと: 主要な提案は無ければ行ごと省略する。
  コメントごとの指摘・提案内容はカードに列挙せず、レポートに寄せる。
- 要確認: `/spinoff` `/spec` は**提示のみで自動起動しない**。

**中断時**: 同じブロック構成でヘッダを `### コメント選別中断` に差し替える。

- やったこと: 一言サマリに中断理由を書く。
- 次の一手: 復帰コマンド。

**完了ゲート:** カードを出力したか。

## 完了条件
- 対象コメント全件が分類・裏取りされ、`comment-report.md` に提案として記録された
- 人に確認を求めず終了した
