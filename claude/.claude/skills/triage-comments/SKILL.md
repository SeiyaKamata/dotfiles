# PRコメント選別スキル

## 役割
自分の PR に付いた未解決のレビューコメントを収集し、要件照合と裏取りを行った上で、対応方針の提案を `.specs/<feature>/comment-report.md` にまとめる。
コード修正・返信・スレッド対応は行わず、対応する / しないの確定は人がレポートの承認欄に書き込む。

対応中にレビュアーの恒常的な好みや PJ の規約に気づいたら、そのリポジトリの `CLAUDE.local.md` に書き戻す。

## 判断が割れる点の扱い
途中でユーザーに質問も承認も求めず、全件の提案をレポートに出して人が非同期に承認する形にする。
自走スキルから呼ばれても対話の同期待ちが発生しない。
分類に確信が持てなければ迷った旨と根拠をレポートに記録し、暫定の分類のまま進める。

## コメントの属性
コメントごとに次の属性を持ち回る。

| 属性 | 値域 | 埋まる Step |
|---|---|---|
| 要件照合 | `整合` / `矛盾` / `スコープ外` / `無関係` / `未照合` | Step 4 |
| 裏取り | `成立` / `不成立` / `未検証` / `対象外` | Step 5 |
| 提案 | `対応する` / `対応しない` | Step 6 |

裏取りの `対象外` は裏取りを実施しなかったコメントで、`未検証` は実施したが成立・不成立を判定できなかったコメントだけに使う。
混同すると要確認の件数が意味を失う。

## 除外基準
収集したコメントから次の順で除外し、すべてを通ったものを対象にする。
author では絞り込まず、人間と CodeRabbit の両方を対象にする。

1. 解決済みスレッド
   - 未解決スレッドを `gh pr view <PR番号> --json reviewThreads --jq '[.reviewThreads[] | select(.isResolved == false) | {path, line, body: .comments[0].body}]'` で取り、`path` + `line` + 本文で突き合わせて解決済みを外す
2. 選別済み
   - 既存の `comment-report.md` に載っているコメントを `id` で突き合わせて外す
   - `[x]` は対応済み、`[ ]` で承認欄が埋まっている項目は下流の処理待ちで、どちらも再提示しない。承認欄が空のまま残っている項目だけ再提示する
3. nitpick
   - レビュー bot が軽微・任意と分類した指摘は外し、件数を要確認に出す
   - bot 自身が「対応しなくてよい」と申告しているものにフル手順を回すのは費用に見合わない

## 要件照合の分類

| 分類 | 判定基準 | 裏取り |
|---|---|---|
| 整合 | 指摘に従うと受け入れ条件を満たす方向に近づく | する |
| 矛盾 | 指摘に従うと受け入れ条件を破る | しない。提案は `対応しない` |
| スコープ外 | 「含まない」いずれかの項目に該当する | しない。提案は `対応しない` |
| 無関係 | requirements.md が言及していない領域。スタイル・実装品質など | する |

- 「整合」か「無関係」で迷う → どちらでも提案は変わらないので、どちらかに寄せて進む
- 「矛盾」か「スコープ外」で迷う → 「含まない」項目への該当を優先する
- 矛盾だが指摘の方が妥当で要件側を直すべき → 「矛盾」と同じ扱いにし、要件の見直しが必要な旨をレポートに書く。`requirements.md` はこの場で書き換えない

## 引用の基準
レポートの根拠は、返信にそのまま使えるよう、ファイルパスではなく文言の引用で示す。
`.specs/` は PR の diff にも GitHub 上にも出ないので、レビュアーはそのファイルを開けない。

| ケース | 引用 |
|---|---|
| 矛盾 | `本 feature の要件「<要件名>」の受け入れ条件「<該当行を転記>」と矛盾する` |
| 矛盾。要件側を直すべき | 上記に加えて「ご指摘の方が妥当。要件そのものの見直しが必要」の旨 |
| スコープ外 | `「含まない」と定めた項目「<該当項目を転記>」に該当する。理由: <理由>` |
| 要件の意図への回答 | `要件「<要件名>」/ スコープの「<項目を転記>」を根拠に<結論>` |
| 根拠が見つからない | `要件を確認したが該当する記述が見つからなかった。確認した範囲: <範囲>` |

## comment-report.md のフォーマット
既存ファイルがあれば既存の項目をチェック状態ごと全部維持し、新規コメントを末尾に追記する。
項目は削除せず、対応済みは `[x]` のまま履歴として残す。

```markdown
---
fixed: false
pr: [PR番号]
branch: [headRefName]
head: [HEAD SHA]
---

# コメント対応レポート: PR #[PR番号]

未対応 [件数] 件。各項目の「承認」欄に `対応する` / `対応しない` / `保留` のいずれかを記入してください。
空欄のままだと次の工程で拾われません。
`[x]` は返信または issues.md への記録まで済んだ項目です。

- [ ] [path]:[line]、投稿者: [author] <!-- comment-id: [id。次回の選別済み除外に使う] -->
  - コメント: [コメント本文]
  - 要件照合: [分類]。根拠: [「引用の基準」に従った引用]
  - 裏取り: [成立 / 不成立 / 未検証 / 対象外]
  - 提案: [対応する / 対応しない]。理由: [理由]
  - 承認: [未記入のまま]
```

## 進め方

### Step 1: 対象 PR の特定

常に 1 PR だけを対象にする。
- `$ARGUMENTS[0]` があれば `gh pr view <PR番号> --json number,title,url,headRefName`
- 無ければ `gh pr view --json number,title,url,headRefName` でカレントブランチの PR

特定できなければ Step 8 の中断カードで報告する。
feature 名は head ブランチが `<feature>-pN` なら `<feature>`、それ以外はブランチ名をそのまま使う。

### Step 2: コメント収集

インラインと会話の 2 種類を集める。
レビュー総評は個別コメントへの対応ではないので含めない。

- インライン: `gh api repos/{owner}/{repo}/pulls/<PR番号>/comments --jq '[.[]] | sort_by(.path, .line)'`
  - ルートコメントは `.in_reply_to_id == null` で抜く
  - `line != null` で絞るとファイル全体へのコメントが漏れるので使わない
- 会話: `gh api repos/{owner}/{repo}/issues/<PR番号>/comments --jq '.[] | {id, user: .user.login, body}'`

「除外基準」で対象を絞り込む。
対象が 0 件なら Step 3〜6 を飛ばし、Step 8 で未解決コメントが無いことと、既存の `comment-report.md` に残る承認待ちの件数を報告して終了する。

### Step 3: 照合基準の読込

`.specs/<feature>/requirements.md` を Read する。
無ければ `find . -path './.git' -prune -o -name 'requirements.md' -print | grep '\.specs/'` で列挙し、ブランチ名に最も近いものを選ぶ。
0 件、または複数ヒットして選べなければ特定失敗とし、要件照合を `未照合` にして裏取りだけで続行する。
候補のパスは要確認に列挙する。

保持する照合基準は「## スコープ」の「含む」「含まない」の各項目と、各 Requirement の受け入れ条件。

### Step 4: 要件照合

対象コメント全件を「要件照合の分類」で分類する。

### Step 5: 裏取り

「整合」「無関係」の AI 指摘だけを対象に、指摘された箇所を開いて条件が実際に成立しうるかを確認する。
呼び出し元・型・既存のガード節・テストの有無まで辿り、影響範囲も確認する。
人間の指摘・質問議論系コメントは `対象外` にする。

### Step 6: 提案

裏取りが `不成立` なら `対応しない` とし、確認した根拠を添える。
`未検証` は確認した範囲を記録し、要確認に回す。

### Step 7: レポート作成

「comment-report.md のフォーマット」で `.specs/<feature>/comment-report.md` を Write する。

### Step 8: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
要確認の `/spinoff` `/spec` は提示のみで自動起動しない。
中断時は見出しを `### コメント選別中断` にし、1 行目に中断理由を書き、生成物の行を省き、次の一手は復帰に必要な操作だけにする。

```markdown
### コメント選別完了
<提案件数を 1 行>

生成物: `.specs/<feature>/comment-report.md`

### 要確認
- 未検証 <n> 件。裏取りで成立・不成立を判定できなかった指摘
- スコープ外 <n> 件 → /spinoff
- 要件の見直しが必要 <n> 件 → /spec <feature>
- nitpick 除外 <n> 件。bot が軽微と分類し、レポートに載せていない
- 要件未照合。requirements.md を特定できず。複数ヒットなら候補のパスを添える
<該当しない行と、無ければブロックごと省略>

### 次の一手
- レポートの承認欄を確認する: `.specs/<feature>/comment-report.md`
- 承認後に修正する: `/fix <feature>`
```
