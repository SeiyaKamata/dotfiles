# レビュースキル

## 役割
実装されたコード（デフォルトブランチとの git 差分）を、仕様・設計との整合性とコード品質の観点でレビューする。会話ではなく git と `.specs` から入力を得る。

## 入出力
- **入力**: `.specs/<feature>/` の requirements / design / tasks と、デフォルトブランチとの git 差分（導出は Step 2）
- **出力**: `.specs/<feature>/review.md`

## 引数
- `$ARGUMENTS[0]`: feature 名（必須）

## 対話方針
判定と保存を済ませて完了カードを出す。途中でユーザーに何も聞かない。**NG の戻し先は呼び出し元が判断する**。このスキルは判定と記録までを担う。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`(feature) が未指定なら「使い方: /review <feature>」を表示して終了

### Step 2: 対象確定とレビュー範囲の導出

起動時に対象 feature と実行コンテキストを次の手順で確定する。

1. feature の確定 — 第 1 引数。未指定なら使い方を表示して終了する。
2. ブランチの確定 — カレントブランチが実装ブランチ `<feature>` でなければ、まず自分で switch を試みる：
   ```
   git switch <feature>
   ```
   - switch できた → 実装ブランチ `<feature>` にいる。想定どおり
   - `<feature>` ブランチが存在しない → 現在のブランチをそのまま採用する（PR を作らない運用で直接コミットしているとみなす）
   - 未コミットの変更があって switch できない → 報告して中断する（stash などの作業ツリー操作はしない）
   - detached HEAD のまま `<feature>` も無い → `branch: none` として続行する（レポートは書けるが、後で `/fix` が行う branch 照合の材料が減る）
3. 実行コンテキストの確定 — `feature` / `branch` / `head`（`git rev-parse HEAD`）を確定する。収集コマンド（macOS の BSD `date` は `-Iseconds` 非対応なのでフォーマット指定を使う）:
   ```bash
   git branch --show-current                       # branch
   git rev-parse HEAD                              # head
   date +"%Y-%m-%dT%H:%M:%S%z"                     # ran_at
   ```
   `phase` キーは持たない。`/review` はフェーズを持たず実装ブランチ 1 本の上で 1 回ずつ回るためで、対象の同一性は `branch` と `head` で判定できる。

確定したら、レビュー対象の差分を **git から導出**する：

- base は**常にデフォルトブランチ**。レビュー対象 = `git diff origin/<デフォルトブランチ>`。コミット前でも後でも同じコマンドで feature の変更全体が得られる

保存先は `.specs/<feature>/review.md`（feature 単位の単一パス）。

### Step 3: レビュー

**3-1 仕様整合性**

差分が `requirements.md` / `design.md` と整合しているかを確認する。

**3-2 コード品質（AI コードレビュー）**

`code-review` skill を `Skill` ツールで起動してコード品質をレビューさせる。効果レベルは指定せず既定に従う。導入済みなら `coderabbit:code-review` などの専用レビュー skill に差し替えてよい。**この工程ではレビュー結果を受け取るだけで、PR へのコメント投稿・修正の適用（`--comment` / `--fix`）はしない** — 判定と記録だけを担うため。

**3-3 指摘の裏取り**

AI コードレビューの指摘は**誤検知を含む**。指摘をそのまま判定・修正指示に流すと、問題のないコードを壊す変更や不要な NG 差し戻しが発生する。重大と報告された指摘は、判定に使う前に**該当箇所を実コードで開いて裏を取る**。**判定は曲げない** — 「未検証」の指摘を NG に倒したり OK に丸めたりせず、未検証のまま記録して人に渡す：

- 指摘されたファイル・行を読み、その条件が**実際に成立しうるか**を確認する。呼び出し元・型・既存のガード節・テストの有無まで辿る
- 影響範囲を確認する。指摘が別の層で既に担保されている／到達しないコードなら、指摘は成立しない
- 検証結果は「確認済み（成立）」「不成立（理由）」で書き分ける。**不成立の指摘は NG の根拠にしない**
- 実コードで成立とも不成立とも確認できない指摘は「未検証」として残す

**3-4 判定**

| 条件 | 判定 |
|---|---|
| 仕様・設計との不整合がある | NG |
| **実コードで成立を確認できた**重大な問題（バグ・セキュリティ・クラッシュ）がある | NG |
| AI コードレビューの指摘がスタイル・軽微な改善のみ | OK — 指摘は記録する |
| AI コードレビューが重大と報告したが検証で不成立だった | NG にしない — 理由つきで記録する |
| 実装は仕様どおりだが、仕様（`requirements.md` / `design.md`）の記述が実コードと食い違っている | OK — 実装をやり直させない。食い違いを「推奨対応」に上流 doc の記述修正として列挙し、完了カードの「要確認」にも出す |

### Step 4: 書き出し
既存の `review.md` があれば、上書きする前に前回の判定（OK/NG）と `count` を読む。今回が NG かつ既存レポートも NG だったなら `count` を既存値 +1、それ以外（OK・既存レポート無し・既存レポートが OK）なら `count: 1` にする。`fixed` は常に `false` を書く（`/fix` だけが `true` に変える）。

Step 2 で決めた保存先に次のフォーマットで書く。指摘の一覧はここに寄せ、ターミナルには列挙しない。

```markdown
---
feature: <feature>
branch: <feature>                      # detached・照合不可時は none
head: 4f8c1e9b2a...                    # 取得不能時は none
ran_at: 2026-07-28T22:45:00+0900
fixed: false                           # 直前に /fix が対象コードを修正していたか
count: 1                               # NG が何回連続か（OK なら 1 にリセット）
---

### 判定
OK / NG

### 仕様整合性
- 指摘内容と該当箇所

### AI コードレビューの指摘
- 指摘内容と該当箇所 — 重大度 + 検証結果: 成立 / 不成立（理由） / 未検証

### 推奨対応
- 対応方針
```

### Step 5: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### レビュー完了
<判定と対象範囲を 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/review.md`

### 要確認
- <未検証の指摘> — 該当: <ファイル:行>

### 次の一手
- 動作確認する: `/qa <feature>`
```

カードは 3 ブロックに分ける。**レビュー完了**、続けて**要確認**、最後に**次の一手**。

- レビュー完了: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**。無ければ行ごと省略する。レビュー指摘の一覧は review に書き、カードには列挙しない。生成物は Step 2 で決めたパスをそのまま出す。
- 要確認: **「未検証」の指摘を全部ここに挙げる**。成立とも不成立とも確認できなかったもの。判定には使っていないので、拾うかどうかは人が決める。無ければブロックごと省略する。
- 次の一手: **判定は確定しているので該当する道だけ**を出す。NG なら戻し先（`- 設計を直す: /design <feature>` / `- 実装を直す: /fix <feature>`）に差し替える。**qa は review の次の工程なので、判定 OK ならここで出す**。単体で試すときだけ `/qa <feature>` を添えてよい。

**中断時**: 同じブロック構成で見出しを `### レビュー中断` に差し替える。

- レビュー中断: 一言サマリに中断理由。review 未生成なら生成物の行は省略する。
- 次の一手: 復帰コマンド。判定が出ていないまま `/commit` へ進む道は出さない。

## 完了条件
仕様・設計との整合とコード品質をレビューし、OK / NG を判定してレポートに記録したら完了。**判定がどちらでも完了**。NG は中断ではない。次工程の起動は完了条件に含めない。
