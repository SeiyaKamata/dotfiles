# レビュースキル

## 役割
実装されたコード（デフォルトブランチとの git 差分）を、仕様・設計との整合性とコード品質の観点でレビューする。会話ではなく git と `.specs` から入力を得る。

## 入出力
- **入力**: `.specs/<feature>/` の requirements / design / tasks と、デフォルトブランチとの git 差分（導出は Step 2）
- **出力**: `.specs/<feature>/review.md`

**コンテキストフリー**: このスキルは会話履歴に依存しない。入力はすべて `.specs/<feature>/` と git から得るので、コールドで `/review <feature>` を叩いても同じ対象に到達する。

## 引数
- `$ARGUMENTS[0]`: feature 名（必須）

## モード
判定と保存を済ませて完了カードを出す。途中でユーザーに何も聞かない。**NG の戻し先は呼び出し元が判断する**。このスキルは判定と記録までを担う。

どちらも**判定を曲げない**。「未検証」の指摘を NG に倒したり OK に丸めたりせず、未検証のまま記録して人に渡す。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`(feature) が未指定なら「使い方: /review <feature>」を表示して終了

### Step 2: 対象確定とレビュー範囲の導出
`/orchestrator`「工程一覧」の `/review` の「対象確定」の手順 1〜3 に従い、feature・対象ブランチを確定する。`/review` は差分なくすべて実行する。

確定したら、レビュー対象の差分を **git から導出**する：

- base は**常にデフォルトブランチ**。レビュー対象 = `git diff origin/<デフォルトブランチ>`。コミット前でも後でも同じコマンドで feature の変更全体が得られる
- **PR 分割はまだ行われていない**。`/sync-to-remote` が review より後に判定する。だから review が見るのは常に feature の全変更で、フェーズ単位の差分を切り出す必要がない
- フェーズブランチ `<feature>-pN` 上で呼ばれた場合も base はデフォルトブランチのまま。分割後に再レビューする運用は取らない。同じコードを二度見ることになる

保存先は `.specs/<feature>/review.md`（feature 単位の単一パス）。

### Step 3: レビュー

**3-1 仕様整合性**

差分が `requirements.md` / `design.md` と整合しているかを確認する。

**3-2 コード品質（CodeRabbit）**

`coderabbit:code-review` を起動してコード品質をレビューさせる。

**3-3 指摘の裏取り**

CodeRabbit（および他の AI レビュー）の指摘は**誤検知を含む**。指摘をそのまま判定・修正指示に流すと、問題のないコードを壊す変更や不要な NG 差し戻しが発生する。重大と報告された指摘は、判定に使う前に**該当箇所を実コードで開いて裏を取る**：

- 指摘されたファイル・行を読み、その条件が**実際に成立しうるか**を確認する。呼び出し元・型・既存のガード節・テストの有無まで辿る
- 影響範囲を確認する。指摘が別の層で既に担保されている／到達しないコードなら、指摘は成立しない
- 検証結果は「確認済み（成立）」「不成立（理由）」で書き分ける。**不成立の指摘は NG の根拠にしない**
- 実コードで成立とも不成立とも確認できない指摘は「未検証」として残し、NG にはせず判断を人に渡す

**3-4 判定**

| 条件 | 判定 |
|---|---|
| 仕様・設計との不整合がある | NG |
| **実コードで成立を確認できた**重大な問題（バグ・セキュリティ・クラッシュ）がある | NG |
| CodeRabbit の指摘がスタイル・軽微な改善のみ | OK — 指摘は記録する |
| CodeRabbit が重大と報告したが検証で不成立だった | NG にしない — 理由つきで記録する |
| 実装は仕様どおりだが、仕様（`requirements.md` / `design.md`）の記述が実コードと食い違っている | OK — 実装をやり直させない。食い違いを「推奨対応」に上流 doc の記述修正として列挙し、完了カードの「要確認」にも出す |

### Step 4: 書き出し
Step 2 で決めた保存先に次のフォーマットで書く。指摘の一覧はここに寄せ、ターミナルには列挙しない。

```markdown
---
feature: <feature>
branch: <feature>                      # detached・照合不可時は none
head: 4f8c1e9b2a...                    # 取得不能時は none
dirty: true
ran_at: 2026-07-28T22:45:00+0900
---

### 判定
OK / NG

### 仕様整合性
- 指摘内容と該当箇所

### CodeRabbit の指摘
- 指摘内容と該当箇所 — 重大度 + 検証結果: 成立 / 不成立（理由） / 未検証

### 推奨対応
- 対応方針
```

frontmatter の値の仕様は `/orchestrator`「工程一覧」の `/test` の「実行コンテキスト frontmatter」（`/review` も同じ書式を使う）を参照する。

### Step 5: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### レビュー完了
<判定と対象範囲を 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/review.md`

### 要確認
- <未検証の指摘> — 該当: <ファイル:行>

### 次の一手
- 動作確認する: `/qa <feature>`
```

カードは 3 ブロックに分ける。**レビュー完了**、続けて**要確認**、最後に**次の一手**。

- レビュー完了: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**。無ければ行ごと省略する。レビュー指摘の一覧は review に書き、カードには列挙しない。生成物は Step 2 で決めたパスをそのまま出す。
- 要確認: **「未検証」の指摘を全部ここに挙げる**。成立とも不成立とも確認できなかったもの。判定には使っていないので、拾うかどうかは人が決める。無ければブロックごと省略する。
- 次の一手: **判定は確定しているので該当する道だけ**を出す。NG なら戻し先（`- 設計を直す: /design <feature>` / `- 実装を直す: /impl <feature>`）に差し替える。**qa は review の次の工程なので、判定 OK ならここで出す**。単体で試すときだけ `/qa <feature>` を添えてよい。

**中断時**: 同じブロック構成で見出しを `### レビュー中断` に差し替える。

- レビュー中断: 一言サマリに中断理由。review 未生成なら生成物の行は省略する。
- 次の一手: 復帰コマンド。判定が出ていないまま `/commit` へ進む道は出さない。

## 出力規律
実行中の逐次ナレーション（「〜します」「〜しました」）は出さない。ツール実行はターミナルに表示されるため二重になる。ただし `coderabbit:code-review` へ委譲して表示が止まる区間の開始時だけ、次の 1 行を出す（1 区間 1 回）。

⏳ review: CodeRabbit のレビューを実行中…

## 完了条件
仕様・設計との整合とコード品質をレビューし、OK / NG を判定してレポートに記録したら完了。**判定がどちらでも完了**。NG は中断ではない。次工程の起動は完了条件に含めない。
