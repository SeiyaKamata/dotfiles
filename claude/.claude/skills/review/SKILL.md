# レビューエージェント

## 役割
実装されたコード（対象フェーズの git 差分。下記「入力」で導出）を、仕様・設計との整合性とコード品質の観点でレビューする。会話ではなく git と `.specs` から入力を得る。

## 設計方針: コンテキストフリー
このスキルは会話履歴に依存しない。入力はすべて `.specs/<feature>/` と git から得る。コールドで `/review <feature> [pN]` を叩いても同じ対象に到達する。

## 自走モード（`auto` 引数）
起動引数のいずれかが `auto` の場合は自律モード（ブロック抑制）とする。末尾の完了カードを出さず、確定した遷移先を 1 行の簡易ログのみ残す。引数なしの単体起動では完了カードを表示する。

## 引数
- `$ARGUMENTS[0]`: feature 名（必須）
- `$ARGUMENTS[1]`: `pN`（省略可。対象フェーズの明示指定）
- `auto`: `pN` の有無に関わらず、引数のいずれかに含まれていれば自律モード

## 入力
- `.specs/<feature>/requirements.md`
- `.specs/<feature>/design.md`
- `.specs/<feature>/tasks.md`（対象確定に使うフェーズ構成。無ければフェーズ照合をスキップする）
- 実装コード差分（git から取得。**stacked 対応**。会話でなく git から導出する）:
  - 対象ブランチ = Step 2 の対象確定で確定したフェーズのブランチ（＝カレントブランチ。対象確定でブランチ照合済み）。
  - その base を `.specs/<feature>/tasks.md` の各フェーズ見出し（`ブランチ: X（base: Y）`）から引く。単一フェーズなら base = デフォルトブランチ。
  - このフェーズの変更 = `git diff <base>`（base の先端 → 作業ツリー）。コミット前でも後でも同じコマンドで**このフェーズ分だけ**が得られる。
  - **`git diff <デフォルトブランチ>` で固定しない**。stacked では base が `p(N-1)` なので、デフォルトブランチと比べると下位フェーズの変更まで巻き込みレビュー範囲が壊れる。
  - `ブランチ: なし` 運用（tasks.md 不在時を含む）ではフェーズのブランチが無いため、従来どおりカレントブランチとデフォルトブランチの差分（`git diff <デフォルトブランチ>`）を取る。

## 保存先
Step 2 で確定した `phase` が `pN` なら `.specs/<feature>/review.pN.md`、`none`（`tasks.md` 不在／`ブランチ: なし` 運用）なら従来どおり `.specs/<feature>/review.md`。複数フェーズが並行して走っても、フェーズ別パスに分かれるため上書きされない。

## 進め方
1. `$ARGUMENTS[0]` が未指定なら「使い方: /review <feature> [pN] [auto]」を表示して終了
2. `/orchestrator`「対象確定（工程共通）」の手順 1〜6（`/test` `/review` は差分なくすべて実行）に従い、feature・対象フェーズ・対象ブランチを確定する。前提が破れた場合（フェーズ指定の形式不正・範囲外・推定不能・ブランチ不一致）は中断する
3. 「入力」の手順で対象フェーズの差分を導出し、仕様・設計との整合性を確認する
4. `coderabbit:code-review` を起動してコード品質をレビューさせる
5. **CodeRabbit の指摘を実コードで裏取りする**（下記「AI レビュー指摘の検証」）。鵜呑みにして判定に流さない
6. 検証を通った指摘と仕様整合性の確認結果を合わせて OK/NG を判定する
7. 結果を「保存先」節のパスに保存する。先頭に実行コンテキストの frontmatter（`feature` / `phase` / `branch` / `head` / `dirty` / `ran_at`。値の仕様は `/orchestrator`「対象確定（工程共通）」の「実行コンテキスト frontmatter」参照）を置く
8. 末尾「完了カード」のブロックを出力して終了する（指摘の一覧は review に寄せ、ターミナルには列挙しない）

## AI レビュー指摘の検証
CodeRabbit（および他の AI レビュー）の指摘は**誤検知を含む**。指摘をそのまま判定・修正指示に流すと、
問題のないコードを壊す変更や不要な NG 差し戻しが発生する。重大と報告された指摘は、判定に使う前に
**該当箇所を実コードで開いて裏を取る**：

- 指摘されたファイル・行を読み、その条件が**実際に成立しうるか**を確認する（呼び出し元・型・
  既存のガード節・テストの有無まで辿る）。
- 影響範囲を確認する。指摘が別の層で既に担保されている／到達しないコードなら、指摘は成立しない。
- 検証の結果は review.md に「確認済み（成立）」「不成立（理由）」で書き分ける。**不成立の指摘は
  NG の根拠にしない**。
- 実コードで成立とも不成立とも確認できない指摘は「未検証」として review.md に残し、NG にはせず
  判断を人に渡す（自律モードでは未検証として報告する）。

## OK/NG の判定基準
- 仕様・設計との不整合がある → NG
- **実コードで成立を確認できた**重大な問題（バグ・セキュリティ・クラッシュ）がある → NG
- CodeRabbit の指摘がスタイル・軽微な改善のみ → OK（指摘は review.md に記録する）
- CodeRabbit が重大と報告したが検証で不成立だった → NG にしない（理由つきで review.md に記録する）

## 出力フォーマット
```
---
feature: <feature>
phase: p2                              # 未確定時は none
branch: <feature>-p2                   # 未確定時は none
head: 4f8c1e9b2a...                    # 取得不能時は none
dirty: true
ran_at: 2026-07-28T22:45:00+0900
---
```

### 判定
OK / NG

### 仕様整合性
- 指摘内容と該当箇所

### CodeRabbit の指摘
- 指摘内容と該当箇所（重大度 + 検証結果: 成立 / 不成立（理由） / 未検証）

### 推奨対応
- 対応方針

## 完了条件
仕様・設計との整合とコード品質をレビューし、結果を報告できたら完了。
次工程は、フェーズループ本流では review OK → `/commit`（qa は全フェーズ後に 1 回だけ回す）。単体起動で試すときだけ `/qa` に繋ぐこともあるが、orchestrator 経由の本流の next は commit。NG の戻し先（設計の根本問題は design／それ以外は impl）は orchestrator が判断する。

工程を終える際、この工程が本来 catch すべきだった逸脱に気づいたら**改善提案に切り出す**。切り出し先の
判定は `CLAUDE.md`「訂正の扱い」に従う（判定基準をここに重複させない）。確認を取らずに実行し、結果を
完了カードの主要な結果に 1 行載せる。

## 出力規律
実行中の逐次ナレーション（「〜します」「〜しました」）は出さない（ツール実行はターミナルに表示されるため二重になる）。ただし `coderabbit:code-review` へ委譲して表示が止まる区間の開始時だけ、次の 1 行を出す（1 区間 1 回）。

⏳ review: CodeRabbit のレビューを実行中…

## 完了カード
判定と保存が済んだら、次の完了カードを**コードフェンスで囲まず**プレーンテキストで出力して終了する。カードの前後に作業サマリ・所感・補足を足さない。次スキルは自動起動せずユーザーの実行を待つ。一言サマリは 1 行、主要な結果は **最大 3 行**（無ければ行ごと省略）で、レビュー指摘の一覧は review に書きカードには列挙しない。▶ 行は完了時点で確定した分岐 1 つだけを出す。📄 行は「保存先」節で決まったパスをそのまま出す（フェーズ確定時は `review.pN.md`、未確定時は `review.md`）。

✅ レビュー完了
<判定と対象範囲を 1 行>
- <主要な結果 最大 3 行>
📄 .specs/<feature>/review.pN.md（フェーズ未確定時は review.md）
▶ OK（QAあり）：/qa <feature>
▶ OK（QAなし）：/commit <feature>
▶ NG（設計の問題）：/design <feature>
▶ NG（実装の問題）：/impl <feature>

完了条件を満たせずに終了するときは、同じ構成でヘッダを `⚠ レビュー中断` に差し替え、一言サマリに中断理由、▶ 行に復帰コマンドを書く（review 未生成なら 📄 行は省略する）。

自律モード（起動引数に `auto` を含む）では完了カードを出さず、確定した遷移先を 1 行の簡易ログだけ残す（例: `次: /qa <feature>`）。次スキルの起動は呼び出し元（orchestrator）が行う。
