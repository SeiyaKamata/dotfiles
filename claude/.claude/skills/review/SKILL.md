# レビュースキル

## 役割
実装されたコード、デフォルトブランチとの git 差分を、仕様・設計との整合性とコード品質の観点でレビューする。
このスキルは判定と記録までを担う。
NG の戻し先は呼び出し元が判断する。

## 入出力
- 入力:
  - `.specs/<feature>/requirements.md`
  - `.specs/<feature>/design.md`
  - `.specs/<feature>/tasks.md`
  - デフォルトブランチとの git 差分
- 出力: `.specs/<feature>/review.md`

## 引数
- `$ARGUMENTS[0]`: feature 名。必須

## 対話方針
判定と保存を済ませて完了カードを出す。
途中でユーザーに何も聞かない。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]` feature が未指定なら「使い方: /review <feature>」を表示して終了

### Step 2: ブランチの確定
カレントブランチが実装ブランチ `<feature>` でなければ、報告して中断する。
switch などのブランチ操作はしない。

### Step 3: 実行コンテキストの確定
`feature` / `branch` / `head` を確定する。
`head` は `git rev-parse HEAD` で取る。
収集コマンドは次のとおり。
macOS の BSD `date` は `-Iseconds` 非対応なのでフォーマット指定を使う:
```bash
git branch --show-current                       # branch
git rev-parse HEAD                              # head
date +"%Y-%m-%dT%H:%M:%S%z"                     # ran_at
```

### Step 4: 並列レビュー
`Agent` ツールで次の 2 つを並列に起動する。
いずれも fresh な general-purpose agent とし、レビュー対象は自分で読ませる。

- 仕様整合性reviewer:
  - `.specs/<feature>/requirements.md` を読ませる。
  - `.specs/<feature>/design.md` を読ませる。
  - `.specs/<feature>/tasks.md` を読ませる。
  - `git diff origin/<デフォルトブランチ>` を読ませる。
  - 差分が仕様・設計と整合しているかを確認させ、指摘一覧を返させる。
- コード品質reviewer:
  - `coderabbit:code-review` skill が導入済みならそちらを `Skill` ツールで起動させる。
  - 未導入なら `code-review` skill にフォールバックさせる。
  - 効果レベルは指定せず既定に従う。
  - `--comment` / `--fix` は使わせない。判定と記録だけを担うため。

両エージェントの完了を待ってから次に進む。

### Step 5: 指摘の裏取り
仕様整合性reviewer・コード品質reviewerの指摘はどちらも誤検知を含む。
指摘をそのまま判定・修正指示に流すと、問題のないコードを壊す変更や不要な NG 差し戻しが発生する。
重大と報告された指摘は、判定に使う前に該当箇所を実コードで開いて裏を取る。
「未検証」の指摘を NG に倒したり OK に丸めたりせず、未検証のまま記録して人に渡す：

- 指摘されたファイル・行を読み、その条件が実際に成立しうるかを確認する。
  - 呼び出し元・型・既存のガード節・テストの有無まで辿る。
- 影響範囲を確認する。
  - 指摘が別の層で既に担保されている、または到達しないコードなら、指摘は成立しない。
- 検証結果は「確認済み。成立」「不成立。理由」で書き分ける。
  - 不成立の指摘は NG の根拠にしない。
- 実コードで成立とも不成立とも確認できない指摘は「未検証」として残す。

### Step 6: 判定

| 条件 | 判定 |
|---|---|
| **裏取りで成立を確認できた**仕様・設計との不整合がある | NG |
| **裏取りで成立を確認できた**バグ・セキュリティ・クラッシュなど重大な問題がある | NG |
| コード品質reviewerの指摘がスタイル・軽微な改善のみ | OK — 指摘は記録する |
| 重大と報告されたが裏取りで不成立だった | NG にしない — 理由つきで記録する |
| 実装は仕様どおりだが、`requirements.md` / `design.md` の記述が実コードと食い違っている | OK |

最後の行は実装をやり直させない特殊ケース。
食い違いは「推奨対応」に上流 doc の記述修正として列挙し、完了カードの「要確認」にも出す。

### Step 7: 書き出し
既存の `review.md` があれば、上書きする前に前回の判定 OK/NG と `count` を読む。
今回が NG かつ既存レポートも NG だったなら `count` を既存値 +1、それ以外なら `count: 1` にする。
それ以外とは OK・既存レポート無し・既存レポートが OK のいずれか。
`fixed` は常に `false` を書く。

入出力に定めた `.specs/<feature>/review.md` に次のフォーマットで書く。
指摘の一覧はここに寄せ、ターミナルには列挙しない。
対象の同一性は `branch` と `head` で判定できる。

```markdown
---
feature: <feature>
branch: <feature>
head: 4f8c1e9b2a...                    # 取得不能時は none
ran_at: 2026-07-28T22:45:00+0900
fixed: false                           # 直前に /fix が対象コードを修正していたか
count: 1                               # NG の連続回数。OK なら 1 にリセットする
---

### 判定
OK / NG

### 仕様整合性
- 指摘内容と該当箇所

### AI コードレビューの指摘
- 指摘内容と該当箇所 — 重大度 + 検証結果: 成立 / 不成立（理由） / 未検証

### 推奨対応
- 対応方針
```

### Step 8: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### レビュー完了
<判定と対象範囲を 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/review.md`

### 要確認
- <未検証の指摘> — 該当: <ファイル:行>

### 次の一手
- 動作確認する: `/qa <feature>`
```

- レビュー完了: 主要な結果は無ければ行ごと省略する。
- 要確認: 「未検証」の指摘を全部ここに挙げる。判定には使っていないので、拾うかどうかは人が決める。
  - 無ければブロックごと省略する。
- 次の一手: 判定は確定しているので該当する道だけを出す。
  - NG なら戻し先、`- 設計を直す: /design <feature>` / `- 実装を直す: /fix <feature>`、に差し替える。
  - qa は review の次の工程。単体で試したいときは NG でも添えてよい。

**中断時**: 同じブロック構成で見出しを `### レビュー中断` に差し替える。

- レビュー中断: 一言サマリに中断理由。
  - review 未生成なら生成物の行は省略する。
- 次の一手: 復帰コマンド。
  - 判定が出ていないまま `/commit` へ進む道は出さない。

## 完了条件
- 差分が `requirements.md` / `design.md` と整合しているかを確認した
- コード品質を AI コードレビューでレビューした
- OK / NG を判定して `.specs/<feature>/review.md` に記録した
  - 判定はどちらでも完了する。NG は中断ではない。
