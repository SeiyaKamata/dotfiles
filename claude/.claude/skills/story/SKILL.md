# ユーザーストーリースキル

## 役割
機能要望をPdM・ステークホルダーが読めるユーザーストーリー形式でまとめる。
技術的な詳細は書かず、**ビジネス価値とユーザー体験**に焦点を当てる。

## 出力先
`.specs/<feature>/stories.md`

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]` が未指定なら「使い方: /story <feature>」を表示して終了
- feature 名を確定する

### Step 2: コンテキスト収集
- 既存の `.specs/<feature>/stories.md` があれば読み込む
- `.specs/<feature>/requirements.md` があれば参照する

### Step 3: ヒアリング
ユーザーの要望を受け取り、以下を質問して詰める：
- **誰が使うか**: ユーザーの役割・属性
- **何をしたいか**: 達成したいゴール
- **なぜ必要か**: ビジネス上の価値・背景
- **完了の基準**: どうなれば「できた」と言えるか

技術的な実装方法は聞かない。

### Step 4: ユーザーストーリー作成
ドラフトを作成してユーザーに確認を取る。

### Step 5: 保存
承認されたら `.specs/<feature>/stories.md` に保存する。
`.specs/<feature>/` ディレクトリがなければ作成する。

## 出力フォーマット

```markdown
# ユーザーストーリー: [機能名]

## ストーリー

### [ストーリー名]
**As a** [ユーザーの役割],
**I want** [やりたいこと],
**so that** [得られる価値・目的].

**受け入れ条件:**
- [ ] [条件1]
- [ ] [条件2]
- [ ] [条件3]

**優先度:** 高 / 中 / 低
**スコープ:** 今回含む / 将来対応

---

### [ストーリー名2]
...
```

## 完了条件
承認され `.specs/<feature>/stories.md` に保存できたら完了。
次に `/spec <feature>` を使うと、このストーリーを元に要件を詳細化できる。

## 完了カード
stories.md の保存が済んだら、次の完了カードを**コードフェンスで囲まず**プレーンテキストで出力して終了する。カードの前後に作業サマリ・所感・補足を足さない。次スキルは自動起動せずユーザーの実行を待つ。

- 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。ストーリー本文・受け入れ条件は stories.md に書き、カードには列挙しない。
- ▶ 行は該当する分岐だけを出す。

✅ ユーザーストーリー作成完了
<何本のストーリーをまとめたかを 1 行>
- <主要な結果 最大 3 行>
📄 .specs/<feature>/stories.md
▶ OK：/spec <feature>

完了条件を満たせずに終了するときは、同じ構成でヘッダを `⚠ ユーザーストーリー作成中断` に差し替え、一言サマリに中断理由、▶ 行に復帰コマンドを書く（成果物が未生成なら 📄 行は省略する）。
