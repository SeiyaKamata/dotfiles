# QAスキル

## 役割
アプリを実起動した状態でブラウザ操作をなぞり、要件どおり動くかを確認する**最終受け入れゲート**。

ブラウザ操作は一切行わず、**`qa-browser` サブエージェントに委譲する**。Playwright はメインで触らない。このスキルは検証環境の起動と停止・シナリオの受け渡し・結果の集約を担う。

**`/qa` は feature 全体のゲート**で、**フェーズ引数を取らない**。実装ブランチ 1 本の上で 1 回だけ回す。`/review` の後・`/commit` の前に走るので、**PR がまだ存在しない**。分割は `/sync-to-remote` が後で判定する。

## 入出力
- **入力**: `.specs/<feature>/qa.md`（`/tasks` が生成した QA シナリオ）
- **出力**:
  - `.specs/<feature>/qa.md`（チェックボックス更新）
  - `.specs/<feature>/qa-report.md` — `/fix` が読む失敗の内訳。毎回上書きする
  - ファイル以外に **Docker の稼働状態**が変わる（自分で起動した分は Step 6 で元に戻す）

**コンテキストフリー**: このスキルは会話履歴に依存しない。入力はすべて `.specs/<feature>/` から得るので、コールドで `/qa <feature>` を叩いても同じ対象に到達する。

## モード
判定を完了カードで報告する。

**環境は落ちている前提で始め、起動した分は自分で片付ける。** 検証には自分の worktree のコードが載った環境が要るので、`/qa` は起動ステップ（Step 3）と停止ステップ（Step 6）を自分で持つ。`/swws -loop` は**別 worktree を奪わず**空くまで待つので、他セッションの作業を壊さない。

**停止するのは自分が起動したときだけ。** 開始時点で自分の worktree が既に起動していたら、それは人か別セッションが用意したものなので触らない。`/swws` の「起動＝占有 / 停止＝解放」に合わせ、他人の占有を勝手に解放しない。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`(feature) が未指定なら「使い方: /qa <feature>」を表示して終了

### Step 2: 対象確定

`/orchestrator`「対象確定（工程共通）」の手順 1〜3 を実施する（feature の確定・ブランチの確定・実行コンテキストの確定）。続けて `.specs/<feature>/qa.md` の存在を確認する。無ければ「入力 `.specs/<feature>/qa.md` がありません（`/tasks` が生成します）」として中断する。この時点では何も起動していないので停止は不要。

**完了ゲート:** feature を確定し、`qa.md` の存在を確認したか。

### Step 3: 環境起動

**到達性を起動済みの証拠として使わない。** compose プロジェクトは 1 リポジトリに 1 つしかないため、**別 worktree の環境が起動していてもベース URL には到達できてしまう**。`curl` が通ったことを根拠に進むと、別ブランチのコードを検証して PASS を出す。だから「何が起動しているか」から確認する。

**3-1 現在のマウント先を確認する**

```
swws status
```

`status` は稼働中コンテナのラベルを読むだけで切り替えないので、直接叩いてよい（切り替え系は `/swws` skill を使う）。

**3-2 状態に応じて起動する**

`git rev-parse --show-toplevel` で得た自分の worktree と照合し、次のとおり分岐する。**起動・切り替えを行ったかどうかを覚えておく**。Step 6 で停止するかの判断材料。以下これを「起動フラグ」と呼ぶ。

| `swws status` の状態 | 動作 | 起動フラグ |
|---|---|---|
| 何も起動していない | `/swws <profile>` で起動する | **立てる** |
| 自分の worktree が起動中 | そのまま使う（触らない） | 立てない |
| 別 worktree が起動中 | `/swws -loop <profile>` で空くのを待って切り替える | **立てる** |
| `⚠️ 混在:`（複数 worktree が同居） | `/swws stop` で全停止してから `/swws <profile>` で起動し直す | **立てる** |

プロファイルは既定 `web`。別プロファイルが要るなら対象リポジトリの `CLAUDE.md` に従う。

`-loop` は最大 25 分待ちうるので **`run_in_background` で**実行する。`-loop` は**別 worktree を奪わない**ので事故にならない。

**3-3 到達性を確認する**

起動後、ベース URL に到達できるか確認する（`curl -sSf <baseURL>` など）。数秒間隔で再確認してよい。

到達できたら Step 4 へ。**起動できない／到達しない／`-loop` が空かずに失敗したとき**は `BLOCKED`（起動不可）として扱う。qa は回さず、**起動フラグが立っていれば Step 6 で停止してから**中断する。人間承認は待たない。

**完了ゲート:** 自分の worktree の環境に到達できたか。できなければ BLOCKED を確定し、起動フラグを控えたか。

### Step 4: シナリオ実行の委譲
`.specs/<feature>/qa.md` を読み、`qa-browser` を Agent で起動する。**全シナリオを 1 回の委譲で**渡す（ブラウザセッション共有・メインのコンテキスト消費最小）。

渡す入力: ベース URL / シナリオ配列（qa.md の該当ブロックそのまま）/ スクリーンショット保存先ディレクトリ（スクラッチパッド等の git 管理外）。

`qa-browser` からは `S<n>: pass|fail` ＋原因 1 行＋スクショパスの配列だけを受領する。

**完了ゲート:** `qa-browser` が全シナリオの結果を返したか。

### Step 5: 書き出し

1. 結果配列で `.specs/<feature>/qa.md` のチェックボックスを更新する（pass → `[x]` / fail → `[ ]` のまま）
2. `git branch --show-current` / `git rev-parse HEAD` / `git status --porcelain` で `branch` / `head` / `dirty` を確定し、`ran_at` を書き出し時点で記録する
3. **最新の結果を `.specs/<feature>/qa-report.md` に必ず書き出す**。これが下流 `/fix` の入力源になり、失敗原因を会話に依存させない（`/test` の `test-report.md` と同じパターン）
4. スクショは PR 添付用に保持し、保存先パスを qa-report.md に記録する

`/qa` は feature 単位のゲートなので、保存先は `.specs/<feature>/qa-report.md` の固定パス。

```markdown
---
feature: <feature>
branch: <カレントブランチ>              # 取得不能時は none
head: 4f8c1e9b2a...                    # 取得不能時は none
dirty: true
ran_at: 2026-07-28T22:45:00+0900
---

# QA結果: [機能名]

## サマリ
- 判定: PASS / FAIL / BLOCKED（BLOCKED=環境を起動できず検証未実施）
- シナリオ数 / pass / fail: N / N / N

## 失敗シナリオ（FAIL のとき）
- S<n> [タイトル]: [原因] — スクショ: <path>
  - _Requirements: N_
```

frontmatter の値の仕様は `/orchestrator`「対象確定（工程共通）」の「実行コンテキスト frontmatter」を参照する。

**完了ゲート:** `qa.md` のチェックボックスを更新し、`qa-report.md` を書き出したか。

### Step 6: 環境停止

**起動フラグが立っているときだけ**停止する：

```
/swws stop
```

- **立っている**（Step 3 で起動・切り替えた） → 停止して解放する
- **立っていない**（開始時点で自分の worktree が既に起動していた） → **何もしない。** 人か別セッションが用意した環境なので、勝手に解放しない

**判定に関わらず実行する。** PASS でも FAIL でも、Step 3 の BLOCKED による中断でも、起動した分は必ず片付ける。FAIL の原因調査で環境が要るなら `/fix` 側で起動し直す。これで次に `/qa` を回すときも「環境は落ちている」前提が成り立つ。

書き出し（Step 5）より**後**に置くのは、`qa-report.md` を残してから環境を落とすため。停止に失敗しても判定は確定しているので、失敗は要確認に載せるだけで中断しない。

**完了ゲート:** 起動フラグに従って停止したか。フラグが立っていなければ何もしないことを確認したか。

### Step 7: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### QA 完了 — PASS
<シナリオ数と判定を 1 行>
- <主要な結果 最大 3 行>

生成物:
- `.specs/<feature>/qa.md`
- `.specs/<feature>/qa-report.md`

### 要確認
- <シナリオに書かれておらず、実行時に判断で補った点> — 該当: S<n>

### 次の一手
- コミットする: `/commit`
```

カードは 3 ブロックに分ける。**QA 完了**、続けて**要確認**、最後に**次の一手**。

- QA 完了: 見出しの末尾に判定（PASS / FAIL）を付ける。**検証を実施して確定した判定だけがこちら側**で、検証そのものを実施できなかった BLOCKED は中断カード側に出す。一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**。無ければ行ごと省略する。失敗シナリオの内訳・スクショパスは qa-report.md に寄せ、カードには列挙しない。生成物は 1 件 1 行（qa-report.md 未生成ならその行を省略）。
- 要確認: シナリオの手順が曖昧で `qa-browser` が解釈で補った点、環境依存で結果が変わりうる点を挙げる。**Step 6 の停止に失敗したときは必ずここに書く**。環境が上がったまま残るので、次の作業に影響する。無ければブロックごと省略する。
- 次の一手: **判定は確定しているので該当する 1 行だけ**を出す。FAIL なら `- 失敗を直す: /fix <feature>` に差し替える。fix は qa-report.md を読んで原因を特定する。設計起因なら `/design`・`/impl` へ。

**中断時**（**BLOCKED を含む**）: 同じブロック構成で見出しを `### QA 中断` に差し替える。

- QA 中断: 一言サマリに中断理由。`qa.md` が無い・環境を起動できず検証を実施できないなどが該当する。成果物が未生成なら生成物の行は省略する。**中断時も Step 6 は実行済み**。起動フラグが立っていれば停止してから中断する。
- 次の一手: 復帰コマンド。BLOCKED なら `- 復帰: /qa <feature>`。**`/qa` は自分で環境を起動するので「アプリを起動してから」とは案内しない。** 判定が出ていないまま `/commit` へ進む道は出さない。

## 出力規律
実行中の逐次ナレーション（「〜します」「〜しました」）は出さない。ツール実行はターミナルに表示されるため二重になる。ただし表示が止まる区間の開始時だけ、次の 1 行を出す（1 区間 1 回）。ユーザーへの確認は対話なのでこの制限の対象外。

⏳ qa: qa-browser で <n> シナリオを検証中…

`-loop` で別 worktree が空くのを待つ区間（最大 25 分）も同様に 1 行出す。

⏳ qa: 別 worktree が使用中のため空くのを待機中…

## 完了条件
全シナリオを実行して PASS / FAIL を判定し、`qa.md` のチェックボックス更新と `qa-report.md` の書き出しを済ませ、**自分が起動した環境を停止したら**完了。**判定がどちらでも完了**。FAIL は中断ではない。検証を実施できなかった BLOCKED だけが未完了。次工程の起動は完了条件に含めない。

**環境の後始末は完了条件に含む。** 起動フラグが立っているのに停止していなければ未完了。停止コマンドが失敗した場合は、要確認に記録すれば完了扱いとしてよい。
