# QAスキル

## 役割
アプリを実起動した状態でブラウザ操作をなぞり、要件どおり動くかを確認する最終受け入れゲート。

ブラウザ操作は一切行わず、`browser-tester` サブエージェントに委譲する。
Playwright はメインで触らない。
`disallowed-tools` の名前空間は `browser-tester` の `tools` が指す実際の Playwright MCP の名前空間と対にする。
起動方式が変わって名前空間が変わったときは両方を揃えて直す。
このスキルは検証環境の起動と停止・シナリオの受け渡し・結果の集約を担う。

## 入出力
- 入力: `.specs/<feature>/qa.md` の `## ローカルQAシナリオ`。`/tasks` が生成した QA シナリオ。
  `qa.md` にはデプロイ後でないと検証できない `## デプロイ環境QAシナリオ` も含まれるが、これはローカル環境では検証できないので `/qa` は読まない
- 出力:
  - `.specs/<feature>/qa.md` — チェックボックス更新
  - `.specs/<feature>/qa-report.md` — `/fix` が読む失敗の内訳。毎回上書きする
  - ファイル以外に Docker の稼働状態が変わる。Step 8 で必ず元に戻す

## 対話方針
途中でユーザーに何も聞かず、判定を完了カードで報告する。
QA中にデータが足りなくて、QAできない場合、追加してQAの完遂を目指す。
QAで使用する環境は、専用の環境なので、不要なデータを生成しようが問題ありません。

## 環境の扱い
環境は落ちている前提で始め、開始時点の状態に関係なく検証が終わったら常に片付ける。
検証には自分の worktree のコードが載った環境が要るので、`/qa` は起動ステップ Step 4 と停止ステップ Step 8 を自分で持つ。
「自分が起動した分だけ停止する」という条件はメモリ上の判定、起動フラグに依存し、追跡を一度誤ると環境が起動しっぱなしのまま残る。
`swws stop` は未起動の状態に対しても安全に呼べるため、無条件に呼んで構わない。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]` feature が未指定なら「使い方: /qa <feature>」を表示して終了

### Step 2: 対象確定

起動時に対象 feature と実行コンテキストを次の手順で確定する。

1. feature を第 1 引数から確定する。
2. ブランチの確定。
   カレントブランチが実装ブランチ `<feature>` でなければ、まず自分で switch を試みる：
   ```
   git switch <feature>
   ```
   - switch できた → 実装ブランチ `<feature>` にいる。想定どおり。
   - `<feature>` ブランチが存在しない → 現在のブランチをそのまま採用する。
   - 未コミットの変更があって switch できない → 作業ツリー操作はせず、報告して中断する。
   - detached HEAD のまま `<feature>` も無い → `branch: none` として続行する。
3. 実行コンテキストの確定。
   - `feature` / `branch` / `head` を確定する。
   - `head` は `git rev-parse HEAD` で取る。
   - `phase` キーは持たない。

`/qa` はフェーズを持たず実装ブランチ 1 本の上で 1 回ずつ回るためで、対象の同一性は `branch` と `head` で判定できる。

続けて `.specs/<feature>/qa.md` の存在を確認する。
無ければ「入力 `.specs/<feature>/qa.md` がありません。`/tasks` が生成します」として中断する。
この時点では何も起動していないので停止は不要。

**完了ゲート:** feature を確定し、`qa.md` の存在を確認したか。

### Step 3: 環境起動プロファイルの確認とマウント先確認

到達性を起動済みの証拠として使わない。
compose プロジェクトは 1 リポジトリに 1 つしかないため、別 worktree の環境が起動していてもベース URL には到達できてしまう。
`curl` が通ったことを根拠に進むと、別ブランチのコードを検証して PASS を出す。
だから「何が起動しているか」から確認する。

起動プロファイルは `CLAUDE.local.md` の `## 環境起動` 節から採用する。
記載が無ければ推測せず、Step 9 の中断カードで記載を促して中断する。
誤ったプロファイルで起動すると、検証対象と違うサービス構成を PASS と誤判定しかねない。

```
swws status
```

`status` は稼働中コンテナのラベルを読むだけで切り替えないので、直接叩いてよい。

### Step 4: 状態に応じて起動する

`git rev-parse --show-toplevel` で得た自分の worktree と照合し、次のとおり分岐する。
`<profile>` は Step 3 で確定したプロファイル。

| `swws status` の状態 | 動作 |
|---|---|
| 何も起動していない | `swws <profile>` で起動する |
| 自分の worktree が起動中 | そのまま使う。触らない |
| 別 worktree が起動中 | `swws -loop <profile>` で空くのを待って切り替える |
| 混在。複数 worktree が同居 | `swws stop` で全停止してから `swws <profile>` で起動し直す |

`-loop` は長時間ブロッキングしうるので `run_in_background` で実行する。

### Step 5: 到達性を確認する

起動後、ベース URL に到達できるか確認する。
`curl -sSf <baseURL>` などを使う。
数秒間隔で再確認してよい。

到達できたら Step 6 へ。
起動できない・到達しない・`-loop` が空かずに失敗したときは BLOCKED、起動不可として扱う。
qa は回さず、Step 8 で停止してから中断する。
人間承認は待たない。

**完了ゲート:** 自分の worktree の環境に到達できたか。できなければ BLOCKED を確定したか。

### Step 6: シナリオ実行の委譲
`.specs/<feature>/qa.md` の `## ローカルQAシナリオ` を読み、`browser-tester` を Agent で起動する。
全シナリオを 1 回の委譲で渡す。
ブラウザセッション共有・メインのコンテキスト消費最小のため。
`## デプロイ環境QAシナリオ` と `## 自動QA対象外` は対象外で渡さない。

渡す入力はベース URL、シナリオ配列、スクリーンショット保存先ディレクトリの3つ。
シナリオ配列は `## ローカルQAシナリオ` のブロックそのまま。
保存先ディレクトリはスクラッチパッド等の git 管理外にする。

`browser-tester` からは `S<n>: pass|fail` と原因1行とスクショパスの配列だけを受領する。

**完了ゲート:** `browser-tester` が全シナリオの結果を返したか。

### Step 7: 書き出し

1. 結果配列で `.specs/<feature>/qa.md` の `## ローカルQAシナリオ` のチェックボックスを更新する。
   - pass は `[x]`、fail は `[ ]` のままにする。
2. `git branch --show-current` / `git rev-parse HEAD` で `branch` / `head` を確定し、`ran_at` を書き出し時点で記録する
3. 既存の `qa-report.md` があれば、上書きする前に前回の判定と `count` を読む。
   - 判定は PASS / FAIL / BLOCKED のいずれか。
   - 非 PASS とは FAIL または BLOCKED を指す。
   - 今回が非 PASS かつ既存レポートも非 PASS だったなら `count` を既存値 +1、それ以外なら `count: 1` にする。
   - それ以外とは PASS・既存レポート無し・既存レポートが PASS のいずれか。
   - `fixed` は常に `false` を書く。
   - `/fix` だけが `true` に変える。
4. 最新の結果を `.specs/<feature>/qa-report.md` に必ず書き出す。
   - これが下流 `/fix` の入力源になり、失敗原因を会話に依存させない。
5. スクショは PR 添付用に保持し、保存先パスを qa-report.md に記録する

`/qa` は feature 単位のゲートなので、保存先は `.specs/<feature>/qa-report.md` の固定パス。

```markdown
---
feature: <feature>
branch: <カレントブランチ>              # 取得不能時は none
head: 4f8c1e9b2a...                    # 取得不能時は none
ran_at: 2026-07-28T22:45:00+0900
fixed: false                           # 直前に /fix が対象コードを修正していたか
count: 1                               # 非 PASS の連続回数。PASS なら 1 にリセットする
---

# QA結果: [機能名]

## サマリ
- 判定: PASS / FAIL / BLOCKED。BLOCKED は環境を起動できず検証未実施を指す
- シナリオ数 / pass / fail: N / N / N

## 失敗シナリオ、FAIL のとき
- S<n> [タイトル]: [原因] — スクショ: <path>
  - _Requirements: N_
```

**完了ゲート:** `qa.md` のチェックボックスを更新し、`qa-report.md` を書き出したか。

### Step 8: 環境停止

```
swws stop
```

FAIL の原因調査で環境が要るなら `/fix` 側で起動し直す。
これで次に `/qa` を回すときも「環境は落ちている」前提が成り立つ。

書き出し、Step 7、より後に置くのは、`qa-report.md` を残してから環境を落とすため。
停止に失敗しても判定は確定しているので、失敗は要確認に載せるだけで中断しない。

**完了ゲート:** `swws stop` を実行したか。

### Step 9: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### QA 完了 — PASS
<シナリオ数と判定を 1 行>
- <主要な結果 最大 3 行>

生成物:
- `.specs/<feature>/qa.md`
- `.specs/<feature>/qa-report.md`

### 要確認
- <シナリオに書かれておらず、実行時に判断で補った点> — 該当: S<n>

### 次の一手
- コミットする: `/commit`
```

- QA 完了: 見出しの末尾に判定、PASS または FAIL、を付ける。
  - 検証を実施して確定した判定だけがこちら側で、検証そのものを実施できなかった BLOCKED は中断カード側に出す。
  - 主要な結果は無ければ行ごと省略する。
  - 失敗シナリオの内訳・スクショパスは qa-report.md に寄せ、カードには列挙しない。
  - qa-report.md 未生成なら生成物の行を省略する。
- 要確認: シナリオの手順が曖昧で `browser-tester` が解釈で補った点、環境依存で結果が変わりうる点を挙げる。
  - Step 8 の停止に失敗したときは必ずここに書く。
  - 環境が上がったまま残るので、次の作業に影響する。
  - 無ければブロックごと省略する。
- 次の一手: 判定は確定しているので該当する 1 行だけを出す。
  - FAIL なら `- 失敗を直す: /fix <feature>` に差し替える。
  - fix は qa-report.md を読んで原因を特定する。
  - 設計起因なら `/design`・`/impl` へ。

**中断時**: BLOCKED を含む。
同じブロック構成で見出しを `### QA 中断` に差し替える。
環境を起動済みなら Step 8 を実行してから中断する。
`CLAUDE.local.md` にプロファイルが無く起動前に中断したときは、まだ何も起動していないので Step 8 は不要。

- QA 中断: 一言サマリに中断理由。
  - `qa.md` が無い・環境起動プロファイル未検出・環境を起動できず検証を実施できないなどが該当する。
  - 成果物が未生成なら生成物の行は省略する。
- 次の一手: 復帰コマンド。
  - プロファイル未検出のときは `- CLAUDE.local.md に \`## 環境起動\` 節を追加し、環境起動プロファイルを1行で記載する` と `- 記載後に再実行する: /qa <feature>` の2行にする。
  - それ以外の BLOCKED のときは `- 復帰: /qa <feature>` にする。
  - `/qa` は自分で環境を起動するので「アプリを起動してから」とは案内しない。
  - 判定が出ていないまま `/commit` へ進む道は出さない。

## 完了条件
検証を実施できなかった BLOCKED だけが未完了。

- 全シナリオを実行して PASS / FAIL を判定した
- Step 7・Step 8 の完了ゲートを満たした
