# 棚上げ案件の切り出しスキル

## 役割
スコープ外として棚上げされた指摘を、その場で要件化せずに独立 feature の下書き `.specs/<新feature>/requirements.md` として切り出す。
追跡記録は残さず、元 feature に「切り出し済み」のマーキングもしない。
今のタスクを止めるブロッカーは依頼元 `plan.md` の `S<n>` で追跡し、ここで扱うのは投げなくても今のタスクが完了する案件だけ。

## 判断が割れる点の扱い
途中でユーザーに質問も承認要求もしない。
どれを切り出すか・分割かまとめか・スラッグ名は自分で確定し、完了カードで事後報告する。
指摘の中身で不足している情報は下書きに「TODO: /spec で詳細化」と書き、質問で埋めない。

## requirements.md のフォーマット

既知の情報だけを書き、EARS 形式の受け入れ条件は書かない。
詳細化は `/spec` が読んだときに行い、そこで `status: confirmed` に引き上げる。

```markdown
---
status: draft
---

# [何をしたい変更か 1 行で]

## 背景・目的
[なぜこの変更が要るか。専門用語・内部用語は本文で説明する]

## やりたいこと
[何を実現したいか。挙動・体験のレベルで書き、実装方法は指定しない]

## 対象範囲・既知の手がかり
[実コードで確認した対象ファイルや該当箇所。詳細化の起点にする参考情報で、不足は「TODO: /spec で詳細化」と書く]

## 制約・前提
[外せない条件、やってほしくないこと、既存仕様との整合]

## 拾い方
この下書きは未着手。`/spec <新feature>` を実行して requirements 詳細化から始める。
```

## 進め方

### Step 1: 受付判定

持ち込まれた案件がこのスキルの担当かを確認し、違うものは切り出さずに正しい行き先を案内して Step 5 の中断カードで終了する。
振り分けの正本は `claude/CLAUDE.md`「ハーネスの自己強化」。

| 案件の性質 | 行き先 |
|---|---|
| それが無いと今のタスクが完了しない。別 PJ の変更待ちなど | 別 PJ セッションと会話しながら詰める。ここで棚上げすると追跡されないまま埋もれる |
| skill / pipeline 本体の改善で、今のリポジトリが dotfiles | このスキルの担当。Step 2 へ |
| skill / pipeline 本体の改善で、今のリポジトリが別 PJ | `ListAgents` で稼働中の dotfiles セッションを探し `SendMessage` で `/spinoff` の実行を依頼する |
| 投げなくても今のタスクは完了する | このスキルの担当。Step 2 へ |

### Step 2: 入力の特定

- `$ARGUMENTS[0]` があれば `.specs/<元feature>/review.md` を探し、見つかれば読む
- プロンプトで指摘が直接渡されていれば、それも候補に含める
- 元 feature もプロンプトの指摘も無ければ「使い方: /spinoff <feature>」を表示して終了
- review も無くプロンプトの指摘も無ければ「切り出せるスコープ外指摘が無い」として Step 5 の中断カードで終了

review にはスコープ外を示す公式マーカーが無いので機械的に絞り込まず、全件を候補として Step 3 に渡す。

### Step 3: ルーティングの確定

どの指摘を切り出すか、独立した複数の下書きに分割するか 1 つにまとめるかを確定する。
根拠が薄いときは指摘ごとに個別の下書きへ分割する側に倒す。まとめて後戻りしにくくなるより、後で `/spec` 側で統合を判断できる方が安全。

### Step 4: 書き出し

切り出し先ごとにスラッグを決め、「requirements.md のフォーマット」で `.specs/<採用名>/requirements.md` を書く。

- スラッグは入力内容から kebab-case・3〜5 語程度で作り、引数で明示されていればそれを使う
- 既に `.specs/` に同名があれば区別がつく別名にし、衝突を理由に中断しない
  - 1 回の実行で複数生成するときは、採用済みの名前も既存として扱う
- 複数の下書きを一括生成するとき、1 件が失敗しても他は生成し、部分成功を報告する

### Step 5: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### 切り出し中断` にし、1 行目に中断理由を書き、生成できた下書きがあれば生成物の行は残し、次の一手には Step 1 で判定した行き先を書く。

```markdown
### 切り出し完了
<何件をどの feature に切り出したかを 1 行>

生成物:
- `.specs/<新feature1>/requirements.md`
- `.specs/<新feature2>/requirements.md`

### 要確認
- <切り出すか迷った指摘・分割かまとめかの判断>

### 次の一手
- 要件に落とす: `/spec <新feature>`
```

要確認は無ければブロックごと省略し、次の一手は下書きが複数なら 1 件 1 行で出す。
