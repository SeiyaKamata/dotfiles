# スコープ外指摘の切り出し（spinoff）

## 役割

`/review` 等でスコープ外として棚上げされた指摘や、**投げなくても今のタスクが完了する棚上げ
案件**を、その場で議論・要件化せずに独立 feature の"種"文書 `.specs/<新feature>/seed.md` として
切り出す。切り出しは非対話を基本とし、ルーティング（どれを切り出すか・分割/まとめ・スラッグ名）
も含めて自分で確定する。

**handoff との境界**: 対象は「投げなくても今のタスクが完了する」ものに限る。相手PJの完了を
待たないと今のタスクが完了しないブロッカーは `/handoff` の対象であり、本スキルは扱わない。
本スキルは**追跡記録を残さない**（元 feature に切り出し済みのマーキングをしない。Step 5）。
これが「追跡する」handoff との決定的な違い。

**位置づけ**: seed.md は「機能要望」であって requirements.md ではない。切り出し先 feature で
`/spec` に渡すと、質問しながら requirements.md に詳細化され、その後 design → tasks → impl と
正規フローに乗る。よって本スキルは実装手順・受け入れ条件・EARS 要件を先回りして書かない
（spec→design→tasks が生成する）。書くのは「何を・なぜ・どこまで」に絞る。

**非対話原則**:
- 指摘の中身について要件詳細化のための質問はしない。
- 不足している情報は seed.md 内に「TODO: /spec で詳細化」と明記するだけで、質問で埋めない。
- EARS 形式の `requirements.md` は生成しない（詳細化は `/spec` の責務）。
- **ルーティング（どれを切り出すか・分割orまとめ・スラッグ名）もユーザーに問わず自分で確定する**
  （無確認実行）。確定した内容は事後報告（完了カード）に載せる。既存 feature との衝突は上書き
  せず連番で回避し、連番の上限（`-99`）まで空きが無ければ生成せず中断して別名の指定を促す
  安全弁は維持する（下記スラッグ採番手順）。

## 引数

- 第1引数: 元 feature 名（`.specs/<feature>/review.md` および `.specs/<feature>/review.p*.md` からスコープ外指摘を拾う）
- プロンプトで指摘内容を直接渡すこともできる（review と併用可）

## 進め方

### Step 1: 入力の特定

- `$ARGUMENTS[0]`（元 feature）があれば `.specs/<feature>/review.md`（フェーズ未確定・単一フェーズ運用）と `.specs/<feature>/review.p*.md`（フェーズ別。`/review` がフェーズ確定時にこの形で保存する）を `ls`/`Glob` で探し、見つかったものをすべて読む。複数見つかった場合はフェーズ番号の昇順（`review.p1.md` → `review.p2.md` → …。フェーズ未確定の `review.md` があれば先頭）で全件を候補として列挙する（取りこぼしを防ぐため、一部だけ読んで終わらない）。
- プロンプトで指摘が直接渡されていれば、それも切り出し対象の候補に含める。
- **`.specs/proposals/` 配下の backlog 提案ファイルのパスが渡された場合**、それを Read して
  切り出し候補に含める（`/propose` の完了カードが案内する `dotfiles で /spinoff <パス>` の導線を
  受ける入口）。提案ファイルの `target`・`claim`・本文をそのまま切り出し候補の内容として扱う。
- 元 feature が未指定かつプロンプトの指摘も無ければ「使い方: /spinoff <feature>」を表示して終了する。
- review.md も review.p*.md も存在せず、プロンプトの指摘も無ければ「切り出せるスコープ外指摘が無い」旨を伝えて終了する。

**完了ゲート:** 切り出し対象の候補（review.md 由来 / プロンプト由来）が確定したか。

### Step 2: 候補の抽出

- Step 1 で読んだ review（`review.md` / `review.p*.md` の全件）から指摘（`### CodeRabbit の指摘` / `### 推奨対応` 等の記録項目）を候補として列挙する。複数フェーズの review があればフェーズをまたいで全件を候補にする。
- review にはスコープ外を示す公式マーカーが無いため、ここで機械的に絞り込まず、Step 3 の
  確認でユーザーに対象を選ばせる。
- 指摘の中身についての質問はしない。要件詳細化はここでは行わない。

### Step 3: ルーティングの確定（非対話）

以下をユーザーに問わず自分で確定する（`AskUserQuestion` は使わない）。指摘内容の議論・
要件化ではなく振り分けの確定であり、無確認実行の対象:

1. 切り出す指摘（複数候補があるとき、どれを切り出すか）
2. 「独立した複数 seed に分割」か「1つの seed にまとめる」か

判断の根拠が薄いときは、指摘ごとに個別 seed へ分割する側に倒す（まとめて後戻りしにくくなる
より、個別に分けて後で `/spec` 側で統合を判断できる方が安全なため）。確定した内容
（切り出した指摘・分割方針）は Step 6 の完了カードで事後報告する。

**完了ゲート:** 切り出し対象・分割方針を自分で確定したか。

### Step 4: seed 生成

確定した切り出し先ごとに以下を行う:

1. 下記「スラッグ採番手順」で切り出し先の feature スラッグを採用する。
2. 採用した名前で `.specs/<採用名>/seed.md` を下記フォーマットで Write する。既知情報のみ記述し、
   不足は「TODO: /spec で詳細化」と明記する。
3. `requirements.md` は生成しない。

複数 seed を一括生成する場合、1 件だけ連番の上限を超えて中断しても他は生成する（部分成功を報告）。

**完了ゲート:** 採番して seed.md を Write したか。

### スラッグ採番手順

`/spinoff` `/handoff` `/notion-import` 共通の手順。feature スラッグは他の feature と区別さえつけば
よい識別子なので、ユーザーに確認せず以下の順で決めて生成まで通す。

1. **候補を決める**（優先順）:
   1. 引数で明示されたスラッグ
   2. Notion の `Branch Name` の最終セグメント（`/notion-import` のみ）
   3. 入力内容から作った kebab-case の短い名前（3〜5 語程度）
2. **既存一覧を取る**: `ls <出力先ルート>/.specs/` で既存の feature ディレクトリ名を得る。
3. **空き名を採る**: 候補名が一覧に無ければそのまま採用する。既存なら `<候補>-2` `<候補>-3` … と
   連番を上げ、最初に空いている名前を採用する。明示指定でも自動命名でも扱いは同じで、衝突を
   理由に中断しない。
4. **上限**: `-99` まで空きが無ければ生成せず中断し、別名の指定を促す。
5. **生成**: 採用した名前で `<出力先ルート>/.specs/<採用名>/seed.md` を Write する（3 で空きを
   採っているため既存 seed.md の上書きは起きない）。
6. 採番の可否はユーザーに確認しない。採用した名前は完了カードの 📄 行のパスで分かるので、
   「自動命名した」「連番になった」旨の説明行は足さない。

1 回の実行で複数の seed を生成するときは、生成のたびに採用済みの名前を既存一覧に足してから
次の採番を行う（同一実行内で候補が重複しても、先に生成した側が残り後続が連番になる）。

### Step 5: 元 feature には何も書かない

元 feature の `review.md` などに切り出しの追跡記録は残さない。これは明示的な設計であり、
「切り出し済み」のマーキングや戻り値を書き込む処理は行わない。**これが `handoff`（依頼元
`tasks.md` の `H<n>` にチェックを付けて追跡する）との境界**であり、spinoff は棚上げを追跡しない。

### Step 6: 導線提示

生成した各 `seed.md` のフルパスと、次に `/spec <新feature>` を実行する導線を提示する。
`/spec` は自動起動しない。末尾の `## 完了カード` で示す。

## seed.md フォーマット（統一テンプレート）

`/spinoff` `/handoff` `/notion-import` が出力する共通フォーマット。EARS 要件ではなく「機能要望」の
粒度で書く。実装手順・受け入れ条件は書かない（`/spec`→`design`→`tasks` が生成する）。
（`/notion-import` だけは命名メタの frontmatter を先頭に付ける。`/spinoff` では付けない。）

```markdown
# <タイトル: 何をしたい変更か 1 行で>

## 背景・目的
なぜこの変更が要るか。専門用語・内部用語は本文で説明する。

## やりたいこと
何を実現したいか。挙動・体験のレベルで書く（実装方法は指定しない）。

## 対象範囲・既知の手がかり
実コードで確認した対象ファイルや該当箇所（参考情報。詳細化の起点）。
不足している情報は「TODO: /spec で詳細化」と明記し、質問で埋めない。

## 制約・前提
外せない条件、やってほしくないこと、既存仕様との整合など。

## 拾い方
この種文書は未着手。`/spec <新feature>` を実行して requirements 詳細化から始める。
```

## 完了条件

切り出し対象の feature ごとに `.specs/<採用名>/seed.md` を Write し、
元 feature 側には追跡記録を残さず、`/spec <採用名>` への導線を報告したら完了。

## エラー処理

- 元 feature 未指定かつプロンプトの指摘も無い → 「使い方: /spinoff <feature>」を表示して終了
- review.md も無くプロンプト指摘も無い → 「切り出せるスコープ外指摘が無い」旨を伝えて終了
- `-99` まで空きが無い → 生成せず中断し別名の指定を促す
  （他の切り出し先は生成を続行する）

## 完了カード
seed の生成が済んだら、次の完了カードを**コードフェンスで囲まず**プレーンテキストで出力して終了する。カードの前後に作業サマリ・所感・補足を足さない。`/spec` は自動起動せずユーザーの実行を待つ。

- 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。指摘の中身は seed.md に書き、カードには列挙しない。
- 📄 行は生成した `seed.md` を **1 件 1 行**で生成数ぶん出す（行数上限は主要な結果にだけ課す）。

✅ 切り出し完了
<何件をどの feature に切り出したかを 1 行>
- <主要な結果 最大 3 行>
📄 .specs/<新feature1>/seed.md
📄 .specs/<新feature2>/seed.md
▶ OK：/spec <新feature>

完了条件を満たせずに終了するときは、同じ構成でヘッダを `⚠ 切り出し中断` に差し替え、一言サマリに中断理由（切り出せる指摘が無い・連番の上限に達したなど）、▶ 行に復帰コマンドを書く（生成できた seed.md があれば 📄 行は残す）。
