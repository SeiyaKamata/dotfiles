# 棚上げ案件の切り出しスキル

## 役割
スコープ外として棚上げされた指摘を、その場で議論・要件化せずに独立 feature の"種"文書 `.specs/<新feature>/seed.md` として切り出す。

**追跡記録を残さない。** 元 feature に「切り出し済み」のマーキングをしない。これが `/handoff`（依頼元 `tasks.md` の `S<n>` にチェックを付けて追跡する）との決定的な違い。

## 入出力
- **入力**: `.specs/<元feature>/review.md` および `review.p*.md` / プロンプトで直接渡された指摘 / `.specs/proposals/` の backlog 提案ファイル（`/propose` からの導線）
- **出力**: `.specs/<新feature>/seed.md`（1 件以上）

## 判断ポリシー
**非対話**: 指摘の中身について要件詳細化のための質問はしない。**ルーティング（どれを切り出すか・分割かまとめか・スラッグ名）もユーザーに問わず自分で確定する**（無確認実行）。確定した内容は完了カードで事後報告する。

不足している情報は seed.md 内に「TODO: /spec で詳細化」と明記するだけで、質問で埋めない。**EARS 形式の requirements.md は生成しない**（詳細化は `/spec` の責務）。

## 進め方

### Step 1: 受付判定
持ち込まれた案件がこのスキルの担当かを確認する。**違うものは切り出さず、正しい行き先を案内して中断する**（振り分けの正本は `claude/CLAUDE.md`「訂正・摩擦の扱い」）。

| 案件の性質 | 行き先 |
|---|---|
| **それが無いと今のタスクが完了しない**（別 PJ の変更待ちなど） | `/handoff`（**追跡が要る**ため。ここで棚上げすると追跡されないまま埋もれる） |
| skill / pipeline 本体の改善 | `/propose` |
| 投げなくても今のタスクは完了する | **このスキルの担当**。Step 2 へ |

**完了ゲート:** 担当案件だと確認できたか（違えば案内して中断したか）。

### Step 2: 入力の特定と候補の抽出

- `$ARGUMENTS[0]`（元 feature）があれば `.specs/<feature>/review.md`（フェーズ未確定・単一フェーズ運用）と `.specs/<feature>/review.p*.md`（フェーズ別）を `ls`/`Glob` で探し、**見つかったものをすべて読む**。複数あればフェーズ番号の昇順（`review.md` があれば先頭）で全件を候補に挙げる（一部だけ読んで終わらない）
- プロンプトで指摘が直接渡されていれば、それも候補に含める
- **`.specs/proposals/` 配下の backlog 提案ファイルのパスが渡された場合**は Read して候補に含める（`/propose` の完了カードが案内する導線の受け口）。提案ファイルの `target`・`claim`・本文をそのまま候補の内容として扱う
- 元 feature が未指定かつプロンプトの指摘も無ければ「使い方: /spinoff <feature>」を表示して終了
- review も無くプロンプトの指摘も無ければ「切り出せるスコープ外指摘が無い」旨を伝えて終了

review にはスコープ外を示す公式マーカーが無いため、**ここで機械的に絞り込まない**。全件を候補として Step 3 に渡す。

**完了ゲート:** 切り出し対象の候補が確定したか。

### Step 3: ルーティングの確定
次をユーザーに問わず自分で確定する（指摘内容の議論・要件化ではなく振り分けの確定であり、無確認実行の対象）：

1. どの指摘を切り出すか
2. 独立した複数 seed に分割するか、1 つの seed にまとめるか

**判断の根拠が薄いときは、指摘ごとに個別 seed へ分割する側に倒す**（まとめて後戻りしにくくなるより、個別に分けて後で `/spec` 側で統合を判断できる方が安全）。

**完了ゲート:** 切り出し対象・分割方針を自分で確定したか。

### Step 4: 書き出し

切り出し先ごとに feature スラッグを決めて `.specs/<採用名>/seed.md` を Write する。

**スラッグ**: 入力内容から kebab-case の短い名前（3〜5 語程度）を作る。引数で明示されていればそれを使う。既に `.specs/` に同名があれば区別がつく別名にする（**衝突を理由に中断しない**）。1 回の実行で複数生成するときは、採用済みの名前も既存として扱う。採番の可否はユーザーに確認せず、採用した名前は完了カードの生成物の行のパスで分かるので「自動命名した」旨の説明行は足さない。

**書式**: 既知情報のみ記述し、不足は「TODO: /spec で詳細化」と明記する（「判断ポリシー」参照）。

```markdown
# <タイトル: 何をしたい変更か 1 行で>

## 背景・目的
なぜこの変更が要るか。専門用語・内部用語は本文で説明する。

## やりたいこと
何を実現したいか。挙動・体験のレベルで書く（実装方法は指定しない）。

## 対象範囲・既知の手がかり
実コードで確認した対象ファイルや該当箇所（参考情報。詳細化の起点）。
不足している情報は「TODO: /spec で詳細化」と明記し、質問で埋めない。

## 制約・前提
外せない条件、やってほしくないこと、既存仕様との整合など。

## 拾い方
この種文書は未着手。`/spec <新feature>` を実行して requirements 詳細化から始める。
```

**元 feature には何も書かない。** `review.md` などに切り出しの追跡記録を残さない（明示的な設計。「切り出し済み」のマーキングも戻り値の書き込みもしない）。

複数 seed を一括生成する場合、1 件が失敗しても他は生成する（部分成功を報告する）。

**完了ゲート:** seed.md を Write し、元 feature に何も書いていないか。

### Step 5: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。`/spec` は自動起動せずユーザーの実行を待つ。

```markdown
### 切り出し完了
<何件をどの feature に切り出したかを 1 行>
- <主要な結果 最大 3 行>

生成物:
- `.specs/<新feature1>/seed.md`
- `.specs/<新feature2>/seed.md`

### 要確認
- <切り出すか迷った指摘・分割の判断>（無確認で確定したので事後に見てもらう）

### 次の一手
- 要件に落とす: `/spec <新feature>`
```

カードは**やったこと**・**要確認**・**次の一手**の 3 ブロックに分ける。混ぜない。

- やったこと: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。指摘の中身は seed.md に書き、カードには列挙しない。生成物の行は生成した seed.md を **1 件 1 行**（行数上限は主要な結果にだけ課す）。
- 要確認: **ルーティングを無確認で確定している**ので、迷った判断（切り出さなかった指摘・分割かまとめか）をここに出す。無ければブロックごと省略する。
- 次の一手: 生成した seed が複数なら 1 件 1 行で出す。

**中断時**: ヘッダを `### 切り出し中断` に差し替え、一言サマリに中断理由（担当外だった・切り出せる指摘が無いなど）、次の一手に行き先（`- 依頼を投げる: /handoff`、`- 改善提案にする: /propose`）を書く（生成できた seed.md があれば生成物の行は残す）。

## 完了条件
切り出し対象ごとに `.specs/<採用名>/seed.md` を Write し、元 feature 側に追跡記録を残していなければ完了。次工程の起動は完了条件に含めない。
