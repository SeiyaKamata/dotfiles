# QAシナリオ生成スキル

## 役割
`requirements.md` の受け入れ条件から `/qa` が実行する QA シナリオを導出し、`.specs/<feature>/qa.md` に書き出す。
シナリオは検証できる環境ごとに振り分け、受け入れ条件の全網羅は目的にしない。

## 判断が割れる点の扱い
途中でユーザーに質問も承認要求もしない。
判断が割れる点は最も素直な解釈を採って進め、採った解釈は該当するシナリオの行に `【要確認: 理由】` を付記する。

## qa.md の構成

`qa.md` は検証できる環境ごとに 3 節に分け、ID は節ごとの連番にする。

- `## ローカルQAシナリオ`: `/qa` がローカル起動したアプリをブラウザ操作して検証する。ID は `Q<n>`
- `## デプロイ環境QAシナリオ`: デフォルトブランチへマージ・デプロイした後でなければ観測できない確認。ID は `V<n>`
- `## 自動QA対象外`: どちらの環境でも検証できず、検証手段を手動確認 / CI / 別途に委ねるもの。ID なし

### 振り分けの基準

振り分けは「ブラウザで観測できるか」で決める。
画面遷移・表示内容・フォームの送信結果・入力エラーの表示のように観測できるものは `## ローカルQAシナリオ` へ。
メールの実送信・外部 API の実通信・cron 実行のようにブラウザの外で起きるものでも、結果が UI に現れるならその表示を期待値にしてローカルへ入れる。
UI に一切現れないものだけを次の 2 つに分ける。

- マージ・デプロイ後になら検証できる → `## デプロイ環境QAシナリオ`
  - マージを起点にした自動処理・デフォルトブランチでしか発火しないワークフローが該当する
  - 常に feature 全体のマージ後に実施するので、実施タイミングや変更単位との対応は書かない
- マージ後にも検証できない → `## 自動QA対象外`
  - 実時間の経過待ち・本番専用インフラ依存が該当する

結果が UI に現れるかは `plan.md` の「失敗の可視性」の判断に従い、`plan.md` が無いときは既存の画面の挙動に従う。

## qa.md のフォーマット

該当が無い節は省略する。
チェックは各節を消費する工程が付ける。

```markdown
# QAシナリオ: [機能名]

## ローカルQAシナリオ
- [ ] Q1. [シナリオタイトル]
  - 前提: [開始状態]
  - 手順: 1.[操作] 2.[操作] 3.[操作]
  - 期待: [ブラウザ画面上で観測できる期待結果]
  - _Requirements: [対応する要件番号]_
- [ ] Q2. ...

## デプロイ環境QAシナリオ
- [ ] V1. [マージ後に何を確認するか 1 行]
  - 手順: [どう実施するか]
  - 期待: [合格と判定できる結果]
  - _Requirements: [対応する要件番号]_

## 自動QA対象外
- [どちらの環境でも検証できない受け入れ条件]。_Requirements: [対応する要件番号]_。検証手段: [手動確認 / CI / 別途]
```

## 進め方

### Step 1: 入力の確認と開始 Step の判定

- `$ARGUMENTS[0]` が無ければ「使い方: /scenarios <feature>」を表示して終了
- `.specs/<feature>/requirements.md` を読む。無ければ Step 6 の中断カードで報告して終了
- `.specs/<feature>/plan.md` があれば読む

`.specs/<feature>/qa.md` の有無で分岐する:
- **無い**: 新規作成。Step 2 から書き起こす
- **有る**: 編集。現在の `requirements.md` / `plan.md` と突き合わせ、シナリオの無い受け入れ条件・削除された要件のシナリオの残存のようなズレと変更要望に該当する箇所だけを Step 2〜3 で直す
  - どちらも無ければ Step 2〜5 を飛ばし、Step 6 で「変更なし」と報告して終了

### Step 2: 手順の手がかりの特定

シナリオの `手順` に書く画面・操作の手がかりを確定する。
- `plan.md` がある → `## 影響範囲` と `## 付録:` の画面に関する記述を使う
- `plan.md` が無い → 要件が触る既存の画面を Grep / Glob で探し、その画面の操作を使う

### Step 3: QAシナリオの導出

`requirements.md` の受け入れ条件から `qa.md` のシナリオを起こす。
節への振り分けは「振り分けの基準」に従う。
各シナリオに対応する要件番号を `_Requirements:_` で記す。

### Step 4: 書き出し

Step 3 の内容を「qa.md のフォーマット」で `.specs/<feature>/qa.md` に書く。
編集では上書きする。

### Step 5: 点検

書き出した `qa.md` を次の観点で見直し、外れていれば直してから Step 6 へ進む。
- 各シナリオに前提・手順・期待が揃い、期待がブラウザ画面上で観測できる形になっている
- 各シナリオが `_Requirements:_` で受け入れ条件に対応している
- 「qa.md の構成」を満たす

### Step 6: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### QAシナリオ生成中断` にし、1 行目に中断理由を書き、生成物の行は書き出し前なら省き、次の一手は `/spec <feature>` と `/scenarios <feature>` だけにする。

```markdown
### QAシナリオ生成完了
<ローカル・デプロイ環境・対象外の件数を 1 行>

生成物: `.specs/<feature>/qa.md`

### 要確認
<件数>件。無ければこのブロックを省略

### 次の一手
- 実装に進む: `/impl <feature>`
- シナリオを直す: `/scenarios <feature>`
```
