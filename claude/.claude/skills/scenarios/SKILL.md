# QAシナリオ生成スキル

## 役割
`requirements.md` の受け入れ条件から `/qa` が実行する QA シナリオを導出し、`.specs/<feature>/qa.md` に書き出す。
シナリオの手順は画面構成に依存するため、`design.md` があればそれを、無ければ既存コードの画面を手がかりにする。

## 入出力
- 入力:
  - `.specs/<feature>/requirements.md`
  - `.specs/<feature>/design.md`、あれば
  - `.specs/<feature>/qa.md`、あれば
  - 既存コードの画面。`design.md` が無いとき、手順の手がかりとして Grep / Glob で探す
- 出力:
  - `.specs/<feature>/qa.md` — 詳細は下記「qa.md の構成」

## モード
`qa.md` の有無で、新規作成モードと編集モードのどちらで動くかが決まる。
判定は Step 2 で行い、以降の Step はここを参照する。

| 対象 | 分かれ目 |
|---|---|
| 新規作成 | `qa.md` が無い |
| 編集 | `qa.md` がある |

書き切ったら完了カードを出して終わり、修正は編集モードで `/scenarios <feature>` を再実行して受ける。

## 対話方針
途中でユーザーに何も聞かない。
判断が割れる点は止まらずに安全側を採り、該当するシナリオの行に `【要確認: 理由】` を付記する。

## QAシナリオ設計の原則
受け入れ条件を無理に全網羅しようとしない。
網羅は `tasks.md` 側の責務。

## qa.md の構成
節の定義はここが正本。
`qa.md` は検証できる環境ごとに次の3節に分ける：

- `## ローカルQAシナリオ`
  - ID: `Q<n>`
  - 検証環境・タイミング: `/qa` が Playwright を使う `browser-tester` でローカル起動したアプリをブラウザ操作して検証する
  - 消費する工程: `/qa` が結果でチェックを更新する
- `## デプロイ環境QAシナリオ`
  - ID: `V<n>`
  - 検証環境・タイミング: デフォルトブランチへマージ・デプロイした後でなければ実施・観測できない確認
  - 消費する工程: デプロイ後の QA 工程が消費する。`/impl` は読まないので完了条件を妨げない
- `## 自動QA対象外`
  - ID: なし
  - 検証環境・タイミング: どちらの環境でも検証できない
  - 消費する工程: 記録するだけ。検証手段は手動確認 / CI / 別途に委ねる

`tasks.md` の `_Depends:_` は `V<n>` を参照先にしない。
サブタスクがデプロイ後の検証結果を前提にすると、「マージには実装の完了が必要で、完了にはマージが必要」という循環になる。

### 振り分けの基準
振り分けは「ブラウザで観測できるか」で決める。
画面遷移・表示内容・フォームの送信結果・バリデーション表示のように観測できるものは `## ローカルQAシナリオ` へ。
メールの実送信・外部 API の実通信・cron 実行のようにブラウザの外で起きるものでも、結果が UI に現れるならその表示を期待値にしてローカルへ入れる。
UI に一切現れないものだけを除外し、行き先を 2 つに分ける：

- マージ・デプロイ後になら検証できる → `## デプロイ環境QAシナリオ` の `V<n>`。
  - マージを起点にした自動処理・デフォルトブランチでしか発火しないワークフローなどが該当する。
  - 実施タイミングは書かない。
  - 常に feature 全体のマージ後に実施するため、個別の変更単位に紐づける欄を持たない
- マージ後にも検証できない → `## 自動QA対象外`。
  - 実時間の経過待ち・本番専用インフラ依存などが該当する

結果が UI に現れるかは `design.md` の「失敗の可視性」の判断に従う。
`design.md` が無いときは既存の画面の挙動に従う。

### 番号体系
`Q<n>` / `V<n>` は節ごとの連番。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`、feature が未指定なら「使い方: /scenarios <feature>」を表示して終了

### Step 2: コンテキスト収集とモード判定
**読み込む**:
- `.specs/<feature>/requirements.md` — 必須。無ければ `/spec` を案内して終了
- `.specs/<feature>/design.md` — あれば読む
- `.specs/<feature>/qa.md` — あれば読む

**モード判定**、`qa.md` の有無で分岐する:
- **無い → 新規作成モード**: Step 3 へ。
- **有る → 編集モード**: 既存の `qa.md` をベースに、まず現在の `requirements.md` / `design.md` と突き合わせてズレを洗い出す。
  - シナリオの無い受け入れ条件、削除された要件のシナリオが残存、などが該当する。
  - ズレとユーザーの変更要望に該当する箇所だけを Step 3〜4 で直し、白紙に戻さない。
  - どちらも無ければ Step 3〜5 を飛ばして Step 6 へ。
  - レビューの指摘を受けて再実行される場合も同じ。

### Step 3: 手順の手がかりの特定
シナリオの `手順` に書く画面・操作の手がかりを確定する。
- `design.md` がある → `## API/インターフェース設計` と `## アーキテクチャ` の画面に関する記述を使う
- `design.md` が無い → 要件が触る既存の画面を Grep / Glob で探し、その画面の操作を使う。
  `/quick` ルートは新規の画面構成を伴わないと判定済みなので、既存の画面だけで手順が書ける

### Step 4: QAシナリオの導出
`requirements.md` の受け入れ条件から `qa.md` のシナリオを起こす。
節への振り分けは上記「qa.md の構成」の「振り分けの基準」に従う。
各シナリオに対応する要件番号を `_Requirements:_` で記す。

### Step 5: 書き出し
Step 4 の内容を次のフォーマットで `.specs/<feature>/qa.md` に書く。
編集モードでは上書きする。

```markdown
# QAシナリオ: [機能名]

## ローカルQAシナリオ
- [ ] Q1. <シナリオタイトル>
  - 前提: <開始状態>
  - 手順: 1.<操作> 2.<操作> 3.<操作>
  - 期待: <ブラウザ画面上で観測できる期待結果>
  - _Requirements: <対応する要件番号>_
- [ ] Q2. ...

## デプロイ環境QAシナリオ
- [ ] V1. [マージ後に何を確認するか 1 行]
  - 手順: [どう実施するか]
  - 期待: [合格と判定できる結果]
  - _Requirements: 5_

## 自動QA対象外
- <どちらの環境でも検証できない受け入れ条件> — _Requirements: N_ — 検証手段: <手動確認 / CI / 別途>
```

チェックは各節を消費する工程が付ける。
該当が無い節は省略してよい。
`## ローカルQAシナリオ` が無い場合、`/qa` は環境を起動せず PASS で抜ける。

**完了ゲート:** 次を満たして書き出したか。
- 各シナリオに前提・手順・期待が揃い、期待がブラウザ画面上で観測できる形で書かれている
- 各シナリオが `_Requirements:_` で受け入れ条件に対応している
- 「QAシナリオ設計の原則」「qa.md の構成」の規定を満たしている

### Step 6: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### QAシナリオ生成完了
<ローカル・デプロイ環境・対象外の件数を 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/qa.md`

### 要確認
<件数>件、本文の `【要確認】` を参照

### 次の一手
- <ルートに応じて 1 行目を差し替える>
- シナリオを直す: `/scenarios <feature>`
```

- QAシナリオ生成完了: 主要な結果は無ければ行ごと省略する。
- 要確認: 件数と「本文を見よ」の一言だけ。
  - 内容の列挙はしない。
  - 無ければブロックごと省略する。
- 次の一手: 1 行目は `tasks.md` の有無で分岐する。
  - 有る → `- 実装に進む: /impl <feature>`。
  - 無い → `- 直接実装する: /quick <feature>`。

**中断時**: 同じブロック構成で見出しを `### QAシナリオ生成中断` に差し替える。

- QAシナリオ生成中断: 一言サマリに中断理由。
  - `requirements.md` が無い、などが該当する。
  - 書き出し前に止まったなら生成物の行は省略する。
- 次の一手: 復帰コマンド。
  - `- 要件を作る: /spec <feature>` など。
  - 未完成のシナリオのまま `/impl`・`/quick` へ進む道は出さない。

## 完了条件
- 受け入れ条件から導出した QA シナリオが `.specs/<feature>/qa.md` に書き出せた
