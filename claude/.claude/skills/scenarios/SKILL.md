# QAシナリオ生成スキル

## 役割
`requirements.jsonc` の受け入れ条件から `/qa` が実行する QA シナリオを導出し、`.specs/qa.jsonc` に書き出し、同じ内容から `.specs/qa.html` を生成する。
シナリオは検証できる環境ごとに振り分け、受け入れ条件の全網羅は目的にしない。

## 判断が割れる点の扱い
途中でユーザーに質問も承認要求もしない。
判断が割れる点は最も素直な解釈を採って進め、採った解釈と理由は該当するシナリオの `question` に書く。

## qa.jsonc の構成

`qa.jsonc` は検証できる環境ごとに 3 つの配列に分け、ID は配列ごとの連番にする。

- `local`: `/qa` がローカル起動したアプリをブラウザ操作して検証する。ID は `Q<n>`
- `deploy`: デフォルトブランチへマージ・デプロイした後でなければ観測できない確認。ID は `V<n>`
- `excluded`: どちらの環境でも検証できず、検証手段を手動確認 / CI / 別途に委ねるもの。ID なし

### 振り分けの基準

振り分けは「ブラウザで観測できるか」で決める。
画面遷移・表示内容・フォームの送信結果・入力エラーの表示のように観測できるものは `local` へ。
メールの実送信・外部 API の実通信・cron 実行のようにブラウザの外で起きるものでも、結果が UI に現れるならその表示を期待値にして`local` へ入れる。
UI に一切現れないものだけを次の 2 つに分ける。

- マージ・デプロイ後になら検証できる → `deploy`
  - マージを起点にした自動処理・デフォルトブランチでしか発火しないワークフローが該当する
  - 常に feature 全体のマージ後に実施するので、実施タイミングや変更単位との対応は書かない
- マージ後にも検証できない → `excluded`
  - 実時間の経過待ち・本番専用インフラ依存が該当する

結果が UI に現れるかは `plan.jsonc` の `decisions` にある「失敗の可視性」の判断に従い、`plan.jsonc` が無いときは既存の画面の挙動に従う。

## qa.jsonc のフォーマット

該当が無い配列は空配列にする。
`done` は各配列を消費する工程が `true` にする。
書式の誤りと、存在しない要件番号への参照は、書いた直後にフックが指摘して返す。

```jsonc
{
  "local": [
    {
      "id": "Q1",
      "title": "[シナリオタイトル]",
      "done": false,
      "precondition": "[開始状態]",
      "steps": ["[操作]", "[操作]", "[操作]"],
      "expect": "[ブラウザ画面上で観測できる期待結果]",
      "requirements": [1],
      "question": "[判断で埋めたときだけ採った解釈と理由。無ければ空文字]"
    }
  ],
  "deploy": [
    {
      "id": "V1",
      "title": "[マージ後に何を確認するか 1 行]",
      "done": false,
      "steps": ["[どう実施するか]"],
      "expect": "[合格と判定できる結果]",
      "requirements": [1],
      "question": ""
    }
  ],
  "excluded": [
    { "text": "[どちらの環境でも検証できない受け入れ条件]", "requirements": [1], "method": "[手動確認 / CI / 別途]" }
  ]
}
```

## 進め方

### Step 1: 入力の確認と開始 Step の判定

- `.specs/requirements.jsonc` を読む。無ければ結果に理由を書き、次の一手を `/spec` にして終了する
- `.specs/plan.jsonc` があれば読む

`.specs/qa.jsonc` の有無で分岐する:
- **無い**: 新規作成。Step 2 から書き起こす
- **有る**: 編集。現在の `requirements.jsonc` / `plan.jsonc` と突き合わせ、シナリオの無い受け入れ条件・削除された要件のシナリオの残存のようなズレと変更要望に該当する箇所だけを Step 2〜3 で直す
  - どちらも無ければ Step 2〜5 を飛ばし、Step 6 で「変更なし」と報告して終了

### Step 2: 手順の手がかりの特定

シナリオの `手順` に書く画面・操作の手がかりを確定する。
- `plan.jsonc` がある → `appendix` の画面に関する記述を使う
- `plan.jsonc` が無い → 要件が触る既存の画面を Grep / Glob で探し、その画面の操作を使う

### Step 3: QAシナリオの導出

`requirements.jsonc` の受け入れ条件から `qa.jsonc` のシナリオを起こす。
節への振り分けは「振り分けの基準」に従う。
各シナリオに対応する要件番号を `requirements` に書く。

### Step 4: 書き出し

Step 3 の内容を「qa.jsonc のフォーマット」で `.specs/qa.jsonc` に書く。
編集では上書きする。

### Step 5: 点検

書き出した `qa.jsonc` を次の観点で見直し、外れていれば直してから Step 6 へ進む。
- 各シナリオの期待がブラウザ画面上で観測できる形になっている
- 「qa.jsonc の構成」を満たす

### Step 6: 出力

次を出して終了する。
- 結果: ローカル・デプロイ環境・対象外の件数
- 詳細: `.specs/qa.html`
- 次の一手: `/impl`
