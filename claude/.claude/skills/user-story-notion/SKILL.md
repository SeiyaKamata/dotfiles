# ユーザーストーリーを書く

US を書く精度と速度を上げていくためのスキル。**書くたびにこのページを直す。** 差し戻された箇所は落とし穴表へ、うまくいった書き方は `references/style.md` へ足す。

## 初めて使う人へ

**一言でいうと**: Notion の US ページの URL を渡すと、素材集め・コードでの裏取り・下書き・点検をこの順で進め、合意が取れてから Notion へ書き込むスキル。

| 項目 | 内容 |
| --- | --- |
| 要るもの | Notion MCP (US の DB に書き込める権限)。現状をコードで確かめるので、対象のリポジトリを手元に clone しておく |
| 一緒に使うスキル | `agent-brief` (素材集めをサブエージェントに頼むときの依頼の型)。無くても動くが、そのときは出典 URL を付けて返すよう依頼文に書く |
| 環境の前提 | 下書きや作業記録の置き場として、作業ディレクトリ (`_work`) を持っている前提で書いてある。持っていなければ、下書きは会話に出すだけでよい |
| 育て方 | 取った人の手元で、落とし穴表と `references/style.md` に書き足していく前提。良い追記はこのリポジトリへ戻す |

## 置き場とテンプレート

| もの | 在り処 |
| --- | --- |
| US の DB | data source `collection://0d30efba-f801-48f8-89ce-e6579b4a2ae1` |
| 新テンプレート | https://app.notion.com/p/lrm-corp/38a442af606f80a5beb2feab1482db93 |
| お手本 (PdM 片岡 秀公さんの US) | PdM担当 = `user://242d872b-594c-816b-89ea-000253441478` で絞り込む |
| 書き方の型 | 同ディレクトリの `references/style.md` |

**書き方の正本はこのスキル (`references/style.md` を含む)。** Notion のテンプレートは、更新されたと聞いたときだけ読み直し、変わった点をこのスキルへ書き戻す。

## 手順

### 1. 対象ページと周辺を読む

対象の US ページを fetch し、次を控える。

- プロパティ: 主要顧客 / 機能名 / タスク / 期 / 炎
- 本文に残っている古い記述 (旧テンプレート・過去記述のトグル)
- 似た US (同じ主要顧客・同じ機能名・タイトルの語が重なるもの)。特に**同じ課題の別解** (例: 手動入力に対する自動翻訳) が別の US に切り出されていないか

### 2. 素材を集める (サブエージェントに委譲)

`agent-brief` の契約で、読み取り専用のサブエージェントに次を集めさせる。**全事実に出典 URL を付け、推測は「推測:」と分けさせる。**

- ひも付くタスク全件 (タイトル・ステータス・要旨・PR)
- ページのコメント (discussion)
- 方針を決めた会議の議事録 (見積もり会・定例など。タスクの親や、ユーザーが指したページ)
- 主要顧客ごとの要望の原文 (目安箱・商談議事録)

ユーザーが「ここに情報がある」とページを指したら、そこを最優先で読む。**方針の正本はたいてい議事録にあり、タスクの本文は空のことが多い。** Slack のやりとりやスクショを貼られたら、それも一次情報として扱う。

社外のサービスとの連携が題材なら、相手の公開資料 (API リファレンス・ヘルプ・競合との連携の説明) も集めさせる。WebFetch はフックで止められることがあり、そのときは WebSearch の要約が根拠になる。**要約が根拠の事実は、原文を読めていないと下書きの補足に書き添える。**

### 3. 現状を一次ソースで確かめる

Problem に「〜できない」「〜しかない」と書く事柄は、**書く前に実コードか実画面で確かめる。** タスク名・古い記述・議事録の言い回しから推測しない。

- 例: 「この通知は文面を編集できるか」→ 対象リポジトリで通知種別とその編集画面のコントローラを grep する
- **作業ツリーではなく `origin/main` を見る** (`git -C <repo> grep ... origin/main`)。手元がプロトタイプのブランチにチェックアウトされていると、まだ出ていない機能が「ある」と読める。`git branch -a | grep -i <語>` と `git log --all --grep=<語>` でプロトタイプを探し、見つかったらコミットメッセージで範囲を読んで達成条件のプロトタイプ欄に書く (2026-10-02 SCORM で、ev2 (elearning-service) の手元が spike ブランチのままだった)
- 確かめられないものは下書きに書かず、手順 4 でユーザーに聞く
- 「できない」の裏を取るついでに、**回避策になりうる既存の機能**も探す (例: TE は配信開始後に対象者を足せるので、管理者だけで始めて後から残りを足せば作り直さずに済む)。顧客の声に出てこない回避策は、Problem に書くかを確認したいことに回す

### 4. 目指す姿をユーザーから一言で聞く

素材が揃ったら、下書きの前にユーザーに**「端的に言うと、今まで何が面倒で、何ができるようになるのか」**を聞く。素材からの推測より、この一言のほうが Problem の芯を正確に言い当てる。在席でないなら素材から書き、Problem の「代わりにしていること」を `questions_parked` に積んでおく。

聞き方は、白紙で聞くより**自分の理解を 3〜4 文の言い直しにして見せ、「合っているか」を選択肢で聞く**ほうが速い。選択肢には「その理解で合っている」「芯は別の側面 (例: 協業・営業の都合)」「両方」を並べる。Who と Problem の芯がこの 1 問で決まる。

### 5. 型に沿って下書きする

`references/style.md` の型で、Who → Goal → Problem → Benefit → 達成条件 → 要望元 → サマリの順に書く (サマリは最後)。下書きは会話に出し、まだ Notion には書かない。

### 6. 点検する

`references/style.md` の「テンプレートの書けたら確認」と、末尾の点検リストを Yes/No で通す。加えて次の 2 問。

- Problem・要望元に書いた事実は、すべて手順 2 の出典か手順 3 の確認に戻れるか?
- 要望元の顧客ごとに、ヒアリング由来か推測かを書いたか?

### 7. 合意してから Notion へ書き込む

ユーザーの合意が取れた欄だけを書き込む。

- 直前に fetch し直し、`update_content` で**欄ごとにテンプレートの灰色の注記を丸ごと本文へ差し替える**。注記は残さない (片岡さんのページも消している)。画像や議論の付いた古い記述を壊さないよう、`replace_content` でページ全体を書き直すことはしない
- 古い記述は消さず、折りたたみ (見出しの例: 「過去記述」) に入れて残す
- タイトルは `update_properties` で「ユーザーストーリー」プロパティを書き換える
- 書いたあと fetch し直し、全欄が入っていることと入れ子が崩れていないことを確かめる。USステータス などのほかのプロパティは、頼まれない限り触らない

### ユーザーが不在のとき

手順 4 の一言は聞けないので、素材から芯を決めて下書きし、迷った分岐を「確認したいこと」として下書きの末尾に並べる。下書きは作業ディレクトリに HTML で置き、**Notion には書き込まない** (手順 7 の合意が取れていないため)。戻ってきたら、確認したいことに答えてもらってから書き込む。

## 旧テンプレートのページを書き直すとき

古い型 (What / Why / Other、Acceptance Criteria の欄があるもの) のまま残っている US もある (例: 2026-10-02 の TE 複数配信設定)。

- **新テンプレートの見出しがページに無いので、手順 7 の欄ごとの差し替えはできない。** 新しい本文をテンプレートの並びでページの先頭に入れ、元の本文は「過去記述」の折りたたみへ移す。同期ブロック (synced block) は中身を写さず、ブロックごと移す
- この組み替えは `replace_content` 1 回で済む。新しい本文のあとに `# 🗂 過去記述 {toggle="true" color="gray_bg"}` を置き、元の本文を 1 段字下げして入れる。同期ブロックは fetch で返った `<synced_block_reference url="...">` をタグごと字下げして入れれば、同じ参照のまま折りたたみへ移る (2026-10-02 TE 複数配信設定で確認)
- **「元の記述を踏襲して」と言われたら**、元の Who・Goal・Problem・ニーズを 1 項目ずつ新しい欄へ割り振る。外した項目は、外した理由を下書きに書く (例: 時差は別の US が受け持つので外した)。タイトルも元のまま残す
- 元の記述にあるニーズでも、顧客の原文が見つからないものは要望元に「推測」と書く (元の記述を書いた人の見立てかもしれないため)
- ページのコメントに「〜を US に追加する」とあれば、芯の候補として扱う

## 社内の開発者向けの US を書くとき

目的が「開発者体験向上」で主要顧客が「なし」の US もある (例: 2026-10-02 の DBまたぎをVIEW越しでやる)。型は同じで、材料の置き場が変わる。

- **要望元は顧客ではなく、実際に起きた事故と、起票した人の動機。** 親タスクの本文 (動機が数行で書かれていることが多い)・作業置き場 (`_work`) の診断や説明資料・別の開発者が立てた Issue から拾い、要望元には「事故が起点。ヒアリングではない」と書く
- **Who は「変える人」と「困る人」がずれやすい。** 例: テーブルの列を変える開発者 (作業する人) と、そのテーブルを読む他のアプリの開発者 (壊れて困る人)。親タスクの動機がどちらの側の守りを言っているかで芯を決め、もう片方は Problem の「代わりにしていること」にケースとして並べる
- **進行中の US は、フェーズを実績と残りで書く。** 済んだフェーズは PR 番号と日付、残りは何が止まっているか (未決の論点・待っている相手) を書く
- 守り・安全の利点 (読めてはいけない列に届かなくなる等) は、開発者の困りごとから外れるなら Benefit の「（その先）」に置く

## 完了済みの US を後追いで書くとき

開発が終わってから US を書く依頼もある (例: 2026-10-02 のサブドメイン認証)。手順は同じだが、素材と書き方が少し変わる。

- **素材の正本はリリース情報と作業記録。** US にひも付く「リリース情報」ページに、顧客から見える変化と「前提/課題」が書かれていることが多い。計画の変遷は作業置き場 (`_work`) の計画書にある
- **達成条件は、実際に出したものを Must に書く。** フェーズは計画ではなく実績 (PR 番号・本番リリース日) で書き、まだ済んでいない後片付けや後続は Want に置く
- **リリース情報と計画書の食い違いを探す。** リリース情報は計画段階の言い回しのまま残っていることがある (例: 未着手の機能が「変わります」と書かれていた)。食い違いは確認したいことに回す
- **顧客の声が、この US ではなく後続の課題を指していないか確かめる。** 記録に残っている要望が、別の壁 (例: 同じメールアドレスでの複数所属) の話であることがある

## 落とし穴

| 失敗 | 原因 | 対策 |
| --- | --- | --- |
| 「新規登録・パスワード再設定の通知は文面を編集できない」と書いて差し戻された (2026-10-01) | タスク名「〜の文面を編集可能に」から現状を推測した。実際は Seculio (自社のセキュリティ教育サービス) の `user_email_templates` で編集できた | 手順 3。「できない」と書く前にコードで確かめる |
| 片岡さんの US を 3 本だけ読んで型をまとめ、量が足りないと指摘された (2026-10-01) | 手近な新しいものだけで足りると判断した | お手本は全件読む (サブエージェントに委譲)。型は `references/style.md` に蓄積し、次からはそこを読む |
| 確認したいことを 1 行ずつの見出しだけで並べて聞き、短すぎて何を聞かれているか分からないと差し戻された (2026-10-01) | 下書きを書いた自分の文脈を、読み手も持っている前提で聞いた | 1 問ごとに「何が分かっていて、何が分からないか」「答えで US のどの欄が決まるか」を書き、選択肢を付けて聞く。コードで確かめられる問いは聞かずに確かめる |
| 複数の US を並べて下書きしたあとの「両方 Notion に書いて良し」を、1 本の確認したいこと (Who を 1 人か 2 人か) への答えと読み、書き込んでから戻した (2026-10-02) | 「両方」が何を指すかを、開いていた 1 本の文脈だけで決めた | 回答待ちの US が複数あるときは、まず「両方 / 全部」を US の本数と照らす。確認したいことへの答えと読めるときも、各 US の暫定がそのまま通ったと読むのが先 |
| フェーズを「教材から完了を受け取る」「点数・続きからの再開、SCORM 2004、複製…」と仕組みの名前と機能名の羅列で書き、phase2・phase3 で何が変わるのか伝わらなかった (2026-10-02 SCORM) | 自分が仕様を知っている前提で、出すものの名前だけを書いた。Want の項目を寄せ集めて 1 つのフェーズにした | 各フェーズは「Who や受講者の操作の流れがどう変わるか」で書き、前のフェーズで残った不便が何で消えるかを 1 行添える。仕組みの説明が要るなら「しくみ:」として分ける。互いに関係の無い Want はフェーズにまとめない |
| 顧客が「1 問テストで可」と言っているのに、「教材を終えたら完了 (テスト不要)」を Must の phase2 に置き、誰の困りごとを解くフェーズなのかを問われた (2026-10-02 SCORM) | 仕様 (SCORM は完了を知らせてくる) から「できたほうが良いこと」を組み立て、Who の痛みかを確かめなかった | フェーズを Must に置く前に「このフェーズで消える不便を、要望元の誰かが言っているか」を問う。言っていなければ Want に置き、Must に上げる条件 (どんな声が出たら上げるか) を添える |
| 回避策を素材 (議事録の 1 社の運用) から組み立て、実際の面倒さ (送るたびに文面を書き換えて保存し直す) を外した (2026-10-01) | 下書きの前にユーザーに目指す姿を聞かなかった | 手順 4 |
