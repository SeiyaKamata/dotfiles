# 提案キュー棚卸しスキル

## 役割
`.specs/proposals/` に積み上がった提案を走査し、**再発シグナル**（`kind: rule` の近接クラスタ）と**着手待ち一覧**（`kind: backlog`）を報告したうえで、**`open` を 1 件ずつトリアージして決着させる**。

`/propose` が「1 件発行するだけで再発を見ない」のと対になっていて、**過去を見る役割はこちらが一手に持つ**。

**キューは腐る。** 提案が発行された後にスキル本体が変わり、別解で解決済みになったり前提が崩れたりする。だから報告だけを返して人に丸投げしない — **各件を実コードに当てて照合し、判断材料を揃えてから聞く**（Step 4-1）。反映するか落とすかを決めるのは人で、決まった内容の適用はこのスキルが実行する。

提案ファイルの frontmatter スキーマの正本は `/propose` の「提案ファイルのスキーマ」。ここでは再掲しない。

## 入出力
- **入力**: `<dotfiles>/.specs/proposals/*.md`（`README.md` を除く）
- **出力**:
  - 報告（再発シグナル / backlog 一覧 / 保留件数 / 不正ファイル）
  - `status` の更新（`applied` / `deferred` / `dropped`）
  - 人が「反映する」と決めた提案の**スキル本体・`CLAUDE.md` への適用**

## モード
**手動スイープ**として人が起動する。引数は取らない。

`status` の書き換えと成果物の変更は、**Step 4 で人が選んだ結果としてのみ**行う。勝手に反映しない・勝手に落とさない（例外は Step 2-2 の寿命管理）。

## 進め方

### Step 1: キューの解決と対象の抽出

**1-1 QUEUE_DIR**

```bash
QUEUE_DIR="$(dirname "$(dirname "$(dirname "$(readlink -f ~/.claude/skills)")")")/.specs/proposals"
```

`readlink -f` が失敗する、`QUEUE_DIR` が存在しない、中身が空（`README.md` 以外の提案ファイルが無い）場合は「提案なし」と報告して終了する。

**1-2 frontmatter の一括読み取り**

`$QUEUE_DIR/*.md`（`README.md` を除く）の frontmatter を**全件**読む（`awk` で frontmatter だけを抜く。`cat` でファイル全体を出さない）。

```bash
for f in "$QUEUE_DIR"/*.md; do
  b=$(basename "$f"); [ "$b" = "README.md" ] && continue
  echo "===== $b"
  awk 'NR==1 && $0!="---"{print "NO_FRONTMATTER"; exit} NR==1{next} /^---$/{exit} {print}' "$f"
done
```

**`status` で捨てない。** 全件を読むのは、`applied` / `dropped` / `deferred` も**再発の証拠**として数えるため（2-1）。

**1-3 集合の確定**

| 区分 | 判定 |
|---|---|
| **トリアージ対象** | `status: open` のもの |
| **証拠のみ** | `status: applied` / `dropped` / `deferred`（クラスタのカウントには入るが、トリアージ・寿命管理の対象外） |
| **不正集合** | `kind` が `rule` / `backlog` 以外の値／`target` `claim` `date` `status` のいずれか欠落。**すべての判定から外し**、Step 3 でファイル名を添えて報告する |

`kind` の正規化（メモリ上のみ。**ファイルは書き換えない**）:

| 読み取った `kind` | 正規化結果 |
|---|---|
| `rule` | rule 集合 |
| `backlog` | backlog 集合 |
| フィールド無し | **rule 集合**（フォールバック） |

**完了ゲート:** トリアージ対象・証拠のみ・不正集合の 3 つが確定したか。

### Step 2: 判定

**2-1 クラスタ検出（rule 集合のみ）**

`target` が完全一致し `claim` が近似するもの同士でグルーピングする。近似判定は AI が行う（**表現の揺れは吸収するが、無関係な claim を混ぜない**）。

- **カウントには `status` を問わず全件を入れる。** `dropped` にした過去の同一指摘も再発の証拠として数える（落とした後に再発したなら、落とした判断が誤りだったということ）
- 同一クラスタが **3 件以上** かつ **`open` メンバーが 1 件以上** → **再発シグナル**として報告対象
- 全メンバーが `applied` のクラスタは報告しない（既に手当て済み）

`kind: backlog` はグルーピング・再発件数のカウントに**含めない**。

**2-2 寿命管理（rule 集合の `open` のみ）**

`date`（`YYYY-MM-DD`）を epoch に変換し、現在時刻との差が `90*86400` 秒を超えるかを判定する（macOS/BSD 前提。ロケール非依存にするため `-j -f` を使う）：

```bash
date -j -f "%Y-%m-%d" "<date>" "+%s"
now=$(date +%s)
```

- **90 日超の `open` singleton**（2-1 のグルーピングでクラスタを構成していないもの）だけを `status: dropped` に `Edit` で更新し、トリアージ対象から外す
- **クラスタを構成しているメンバーは 90 日超でも drop しない**（生きた再発シグナルとして残す）
- `kind: backlog` は**経過日数に依らず drop しない**
- `deferred` は寿命管理の対象にする（90 日超の singleton なら `dropped` へ）

**完了ゲート:** クラスタが確定し、90 日超 singleton を `dropped` に更新したか。

### Step 3: 全体報告

トリアージに入る前に全体像を出す。**再発シグナル**（rule クラスタ・3 件以上ごと）:

```
## 再発シグナル

### target: <target>
- 代表 claim: <claim>
- 件数: N（open M / applied A / dropped D）
- ファイル:
  - <path1>
  - <path2>
```

クラスタが 1 つも無ければ「再発クラスタなし」と報告する。

**backlog の別枠棚卸し**（**3 件閾値は rule 専用の概念なので backlog には適用しない。1 件から出す**）:

```
## dotfiles backlog（着手待ち）

- target: <target> ｜ <claim>
  - 発行日: <date>
  - ファイル: <path>
```

open な backlog が 1 件も無ければ「着手待ちの backlog なし」と**明示的に報告する**（節を黙って省略しない）。

続けて 1 行ずつ添える。

- **保留中**: `status: deferred` の件数（0 件なら省略）
- **不正な提案ファイル**: あればファイル名を列挙

**完了ゲート:** 再発シグナル・backlog 一覧・保留件数・不正ファイルを（0 件でも明示して）報告したか。

### Step 4: トリアージ（1 件ずつ）

`open` を**発行日の古い順**に 1 件ずつ決着させる。クラスタを構成しているものは**まとめて 1 回で扱う**（同じ判断が複数件に及ぶため）。

冒頭で選択肢の形式を 1 回だけ示す：

```
1: 反映する   → 成果物に適用し status: applied
2: 落とす     → status: dropped
3: 保留する   → status: deferred（次回のトリアージ対象から外す）
4: 判断しない → open のまま次へ
```

**4-1 照合（提示の前に必ず行う）**

提案を読んだだけで提示しない。**先に実物を当たる。** 最低限これを確認する。

| 確認 | 手段 |
|---|---|
| **既に対応済みか** | `target` のスキル本体・`CLAUDE.md` を `grep`。claim のキーワードと**言い換え**の両方で引く |
| **前提が崩れていないか** | 提案が前提にした構造が今もあるか。`git log --oneline -- <対象ファイル>` で提案日以降の変更を見る。別解で解決されていることが多い |
| **仕様の裏取りが要るか** | claim が外部仕様（Claude Code の frontmatter キー・ツールの挙動など）に依存するなら `WebFetch` で公式ドキュメントを確認する。**実測だけを根拠に「無効」と断定しない** |
| **提案の記述が現状と合っているか** | 対象ファイル・件数が提案本文どおりか（統合・改名で消えていることがある） |

照合で分かった食い違いは**提示に必ず含める**（「既に別解で解決済み」「仕様上は有効」「対象が存在しない」など）。

**4-2 提示**

1 件につき次を出す。

- **見出し**: `N/M — <ファイル名>`
- **メタ**: `target` / `kind` / 発行日 / `source_feature`
- **claim** と**背景**（提案本文の要約）
- **照合結果**（4-1 で分かったこと）
- **価値判断**: 次の 4 軸で評価し、**推奨（1〜4）を先に述べる**

| 軸 | 見るもの |
|---|---|
| **再発性** | 構造的な動機があるか。偶発の 1 回きりか。クラスタなら件数と間隔 |
| **被害の非可視性** | **気づかず後工程に流れるか。** diff や出力を見れば人が即座に気づくものは優先度が低い。成果物に紛れて下流が引きずるものほど一行を置く価値が高い |
| **コスト/副作用** | 一行で済むか。正当な動作まで止めないか。**既存の設計思想と衝突しないか** |
| **重複** | 他の変更で既に塞がっていないか（4-1 の結果） |

**判断を求める前に、文面案を出す。** `rule` なら追記する実文と**追記先**（グローバル `claude/.claude/CLAUDE.md` か、プロジェクト `CLAUDE.md` か、対象スキル本体か）を示す。追記先は**そのルールが発火する範囲**で選ぶ — dotfiles での作業でしか起きないなら プロジェクト側に置く。

**4-3 適用**

人が選んだとおりに実行する。

- **反映**: 文面を成果物に適用し、`status: applied` に更新する。既存の同種表現の掃除まで行うかは別に聞く（提案本文が適用範囲を限定していることがある）
- **落とす / 保留**: `status` だけ更新する
- **判断しない**: 何もしない

**書き換えは frontmatter の `status` だけを狙う。** 提案本文が他の提案の `status` を引用している場合があるので、`Edit` の `old_string` には直前の行（`source_feature:` など）を含めて一意にする。

**完了ゲート:** `open` 全件について 1〜4 のいずれかに決着したか。中断する場合は残件数を報告する。

### Step 5: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの後に作業サマリ・所感・補足を足さない。

```markdown
### 提案キュー棚卸し完了
<走査件数・クラスタ数・トリアージ結果の内訳を 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/proposals/<status を更新した提案ファイル>`

### 要確認
- <不正な提案ファイル>（`kind` が不正・frontmatter 欠落）

### 次の一手
- <残件があれば再開方法／無ければ着手待ち backlog の提示>
```

カードは**やったこと**・**要確認**・**次の一手**の 3 ブロックに分ける。混ぜない。

- やったこと: 一言サマリは 1 行（走査件数・反映/落とす/保留の内訳）。主要な結果は `- ` の箇条書きで**最大 3 行**。生成物の行は `status` を書き換えた提案ファイルを **1 件 1 行**（更新が無ければ行ごと省略。行数上限は主要な結果にだけ課す）。**成果物を変更した場合はそのファイルも生成物の行に出す。**
- 要確認: 不正な提案ファイルを挙げる（**すべての判定から外している**ので、放置すると永久に棚卸しされない）。無ければブロックごと省略する。
- 次の一手: 1 行に留める。

**中断時**: ヘッダを `### 提案キュー棚卸し中断` に差し替え、一言サマリに中断理由と**残件数**、次の一手に `- /proposals-sweep で再開（open の古い順から続く）` を書く。`applied` / `dropped` / `deferred` に落としたぶんは次回のトリアージ対象から自動で外れるので、再開位置の記録は要らない。

## エラー処理
- **`QUEUE_DIR` が解決できない／空** → 「提案なし」で終了する
- **frontmatter が壊れている**（`target` / `claim` / `date` / `status` の欠落）→ すべての対象から外し、ファイル名を添えて報告する
- **`kind` の値が `rule` / `backlog` のいずれでもない** → 同様に不正扱いとし、対象から外して報告する
- **`kind` フィールドが欠落している場合だけは不正扱いにしない** → Step 1-3 の正規化に従い `rule` にフォールバックし、**ファイルは書き換えずに**従来どおり扱う
- **照合で外部ドキュメントが取れない**（`WebFetch` 失敗）→ 裏取りできなかった事実を提示に書く。**推測で「有効」「無効」を断定しない**

## 完了条件
- `.specs/proposals/` を走査し、rule の 3 件以上クラスタ（`status` を問わずカウント）をすべて報告できた
- 90 日超の `open` rule singleton を `status: dropped` に更新できた（**クラスタメンバーは対象外**）
- `kind: backlog` を別枠の一覧として報告できた（**0 件なら明示的に報告**）
- **`open` 全件を 1 件ずつトリアージし、照合結果と推奨を添えて提示した**（中断時は残件数を報告した）
- **人が「反映する」と決めた提案を成果物に適用し、`status` を更新した**
- 不正な提案ファイルをすべての対象から除外し、ファイル名を添えて報告できた
