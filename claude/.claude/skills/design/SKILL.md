# 技術設計スキル

## 役割
要件から、実装者が迷わずコードを書けるレベルの技術設計を作る。
設計判断のうち人間の承認が要るものは `design.md` の `## レビューポイント` に集め、それ以外の節は実装者だけが読む前提で書く。

## 判断が割れる点の扱い
途中でユーザーに質問も承認要求もしない。
判断が割れる点は最も素直な案を採って進め、採った案は `design.md` の `## レビューポイント` に挙げる。

## 判断基準

### 既存を踏襲する
同種の処理が repo に既にあるなら、その構成・命名・レイヤ分け・エラー処理・テストの置き方をそのまま採る。

- 設計を組む前に、近い責務のコードを Grep / Glob で探して踏襲元を特定する
- 逸脱は要件が既存の形で満たせないときだけにする
  - 踏襲元と違う形にした点と理由を控える
- 踏襲元が無いときだけ新しく決める
  - repo 全体で優勢なパターンに合わせ、比較した代替案とその却下理由を控える

### コンポーネントの境界を明確にする
各コンポーネントについて、担当するファイル・責務と、隣接するコンポーネントの責務に踏み込まない範囲を決める。
複数のコンポーネントが同じファイル・同じ責務を担当する重なりがあれば、どちらか一方に寄せるか 1 つに統合する。
feature が複数リポジトリにまたがるときは、各コンポーネントが担当するリポジトリも決める。

## レビューポイントの書き方

`## レビューポイント` の 4 カテゴリはこの順で並べ、該当が無いカテゴリは見出しごと省略する。

| カテゴリ | 判定基準 |
|---|---|
| 1. 仕様に影響する変更 | 要件の記述から挙動・記録粒度・可視性が変わる。コンポーネント境界の引き方が要件と矛盾する場合もここ |
| 2. 技術判断としての逸脱 | 踏襲元と違う形にしたが、要件は満たす。対象・逸脱内容・理由を書く |
| 3. 未検証の断言 | 根拠を示さず影響を打ち消す記述。「〜のため発生しない」「〜に収まる」「実質〜」が目印 |
| 4. 確認質問 | 答えが設計を変える。最大 5 個 |

1 と 2 はどちらも逸脱だが、承認を求める相手が仕様の持ち主とコードの読み手で違うので分ける。
全体を 1〜2 画面に収め、超えるなら 1 項目 1〜2 行に圧縮する。

### 未検証の断言の拾い方

設計本文から漏れなく拾い、各項目に確認方法を 1 つ添える。

| 確認方法 | 使う場面 |
|---|---|
| 実測する | 件数・時間・サイズなど数で決まるもの |
| 該当コードを読む | 既存実装の挙動を前提にしているもの |
| 仕様の持ち主に聞く | 運用・業務上の前提を置いているもの |

断言によって実際に回避される事象と、形を変えて残るコストを分けて書く。

## design.md のフォーマット

該当しない節は節ごと省略し、空節を並べない。
ただし `## レビューポイント` と `## 付録: 要件対応表` は常に置く。
`## レビューポイント` と `## アーキテクチャ` と `## データ設計` を合わせて 2 画面を超えたら、決定だけを残して説明は削るか付録へ送る。

```markdown
# 技術設計: [機能名]

## 概要
[設計の方針・アプローチを 2〜3 文で]

## レビューポイント
[該当が無いサブ見出しは省略する]

### 仕様に影響する変更
- [何がどう変わるか]。要件は[元の記述]、設計では[採った形]。[なぜ変えたか。誰の承認が要るか]

### 技術判断としての逸脱
- [対象]: [踏襲元と違う点]。踏襲元は `path/to/file`。[理由]

### 未検証の断言
- 「[本文中の断言をそのまま引く]」。該当は[節名]。確認方法: [確認方法]

### 確認質問
1. [答えが設計を変える質問。最大 5 個]

## アーキテクチャ

### コンポーネント構成
[主要コンポーネントとその責任]

### コンポーネント境界
[コンポーネントごとに担当するファイル・責務と担当しない範囲。複数リポジトリにまたがるときは `リポジトリ: <repo名>` を添える]

### データフロー
[データの流れ。Mermaid 図を使うならノード ID は英数字とアンダースコアだけにし、ラベルに `()` `[]` `"` `/` `@` を含めない。装飾はせず素の構造だけ書く]

## データ設計
[DB スキーマ、データ構造、型定義]

## API/インターフェース設計
[エンドポイント、関数シグネチャ、入出力形式]

## テスト方針
[TDD を採るか、レイヤーごとのテスト種別、モックの使用方針。踏襲元があればその配置・命名・フレームワークに合わせる]

## 実装上の注意事項
[実装者向けの技術メモだけを置く。レビューポイントに上げた項目はここに重複させない]

## 付録: 設計サマリ
| 設計対象 | 採った形 | 踏襲元 | 検討した代替案 |
|---|---|---|---|
| [何を決めたか] | [採用した構成・ライブラリ・データ構造] | `path/to/file` | 該当なし |
| [...] | [...] | 該当なし。合わせた repo 全体のパターン: [パターン] | [候補]。却下理由: [理由] |

## 付録: ディレクトリ構成
[新規作成・変更するファイルの一覧]

## 付録: 要件対応表
| Requirement | 対応するコンポーネント/実装 |
|---|---|
| Requirement 1 | ... |
| Requirement 2 | ... |

## 付録: [その他の表題]
[擬似コードなど、実装者だけが読む長い記述。無ければ節ごと省略]
```

## 進め方

### Step 1: 開始条件の確認とモード判定

- `$ARGUMENTS[0]` が未指定なら「使い方: /design <feature>」を表示して終了
- `.specs/<feature>/requirements.md` が無ければ `/spec <feature>` を案内して終了

`.specs/<feature>/design.md` の有無で分岐する:
- **無い**: 新規作成モード。Step 2 へ
- **有る**: 編集モード。既存 `design.md` と現在の `requirements.md` を突き合わせ、新要件の未反映・削除された要件の残存のようなズレと変更要望に該当する箇所だけを Step 2〜5 で直す
  - どちらも無ければ Step 2〜7 を飛ばし、Step 8 で「変更なし」と報告して終了

### Step 2: 踏襲元の特定

「判断基準: 既存を踏襲する」に従って踏襲元を探す。
探す範囲はモードに応じて変える:
- **編集モード**: 直す箇所の周辺だけ
- **既存機能の拡張**: 統合ポイントを Grep で洗い、その周辺の実装の形に合わせる
  - 新しい層・新しい命名体系は持ち込まない
- **新規機能**: まず repo 内に近い責務のコードを探し、無いことを確認してからアーキテクチャパターン・依存ライブラリを調査する
  - 必要なら WebSearch を使い、ライブラリは repo に既に入っているものを優先する

### Step 3: コンポーネント境界の確定

「判断基準: コンポーネントの境界を明確にする」に従って確定する。

### Step 4: 外部環境の確認

- **別 PJ の実装状況・挙動**: `requirements.md` に「実装済み」のような記載があれば、その PJ のデフォルトブランチを worktree に展開し、Read / Grep で確認する
  - bare repo は自分の bare repo `git rev-parse --git-common-dir` と同じ親ディレクトリにある `<リポジトリ名>` を採り、`git -C <bare repo> rev-parse --is-bare-repository` が `true` でなければ確認を諦めて `## レビューポイント` に出す
  - `git -C <bare repo> fetch origin` で最新化してから `dest=$(mkworktree <bare repo> <リポジトリ名>-<feature>)` で切る。同名の worktree が既にあればそれを使う
  - 依頼元の作業ツリーは remote に載っているとは限らないので、デフォルトブランチのコードを正とする
  - 食い違いは `## 実装上の注意事項` に書き、`requirements.md` 側の修正要否を `## レビューポイント` に挙げる
- **環境変数・設定値の導入**: ローカル・各デプロイ環境の投入先ファイルを実リポジトリで特定してから設計する
  - 「インフラ側で対応」とスコープ外に出す前にデプロイ定義の有無を確認し、特定できなければ `## レビューポイント` に出す

### Step 5: 固定チェックリストの適用

組んだ設計に対して次を、要件に書かれていなくても確認する。
該当したものは `## レビューポイント` に書き、該当しなければ何も書かない。

- **テナント / 認可スコープ**: 親の ID をスコープとして受け取っているのに、子のクエリでその条件を付けずに引いていないか
  - ジョブ引数・キュー経由の値は永続化されて後から再実行されうるので、投入時に整合していても実行時に整合しているとは限らない
- **リトライの有無**: 例外の catch や握り潰しでフレームワークのリトライを殺していないか
  - 殺すなら明示的な決定としてレビューポイントに書く
- **失敗の可視性**: 「処理は成功と表示され、実際には何も実行されていない」が成立する経路が無いか
  - 結果が履歴・ログに残らない設計は特に見る
- **非可逆な操作**: 削除・外部送信・課金・マイグレーションを含むか
  - 外部送信はメール・通知・Webhook を含む
- **新規依存の追加**: repo にまだ無いライブラリ・外部サービスを持ち込むか
- **宣言とコードの食い違い**: 設計本文で参照しないと宣言したデータを、クエリ側の `includes` / `select` / join に残していないか

### Step 6: 書き出し

Step 2〜5 の内容を「design.md のフォーマット」で `.specs/<feature>/design.md` に書く。
編集モードでは上書きする。

### Step 7: 点検

書き出した `design.md` が次を満たしているか見直し、外れていれば直してから Step 8 へ進む。
- 全 Requirement が `## 付録: 要件対応表` で追える
- インターフェース・データフローが実装者が推測せずに書ける具体度になっている
- 「判断基準」「レビューポイントの書き方」「Step 5 の固定チェックリスト」を満たしている

### Step 8: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### 技術設計中断` にし、1 行目に中断理由を書き、書き出し前なら生成物の行を省き、次の一手は `/design <feature>` と `/spec <feature>` だけにする。

```markdown
### 技術設計完了
<何を設計したかを 1 行>

生成物: `.specs/<feature>/design.md`

### 要確認
<件数>件。`## レビューポイント` を参照。無ければこのブロックを省略

### 次の一手
- タスク分割に進む: `/tasks <feature>`
- 設計を直す: `/design <feature>`
```
