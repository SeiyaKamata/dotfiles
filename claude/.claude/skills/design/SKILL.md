# 技術設計スキル

## 役割
要件を受け取り、実装者が迷わずコードを書けるレベルの技術設計を作る。
要件が「何を作るか」を、ここでの設計が「どう作るか」を担う。

## 入出力
- **入力**:
  - `.specs/<feature>/requirements.md`
  - `.specs/<feature>/design.md`(あれば)
- **出力**:
  - `.specs/<feature>/design.md`

## モード
`design.md` の有無で、新規作成モードと編集モードのどちらで動くかが決まる。
判定は Step 2 で行い、以降の Step はここを参照する。

| 対象 | 分かれ目 |
|---|---|
| 新規作成 | `design.md` が無い |
| 編集 | `design.md` がある |

書き切ったら完了カードを出して終わり、修正は編集モードで `/design <feature>` を再実行して受ける。

## 対話方針
途中でユーザーに何も聞かない。判断が割れる点は止まらずに最も素直な案を採り、
完了カードの「要確認」に挙げる。

## 設計方針

### 既存を踏襲する

**既存コードは踏襲元**として扱う。
同種の処理が repo に既にあるなら、その構成・命名・レイヤ分け・エラー処理・テストの置き方を**そのまま採る**。
設計だけ新しい形にすると repo 全体の一貫性が落ちる。

- **設計を組む前に踏襲元を特定する**: 近い責務のコードを Grep / Glob で探し、見つけたものを
  `design.md` の `## 付録: 設計サマリ` の踏襲元列にファイルパスで明記する。`/impl` がここを読んで
  `implementer` に渡す。
- **逸脱は要件が既存の形で満たせないときだけ**。逸脱した点と理由を `## レビューポイント` の
  「技術判断としての逸脱」に書き、完了カードの「要確認」に挙げる。
- **踏襲元が無いときだけ新しく決める**。そのときも repo 全体で優勢なパターン、ディレクトリの
  切り方・命名規則・依存の向きに合わせる。

### コンポーネントの境界を明確にする

**コンポーネントは「何を所有し、何を所有しないか」を持つ。** 責務が曖昧なまま「連携する」とだけ書くと、
どのコンポーネントがどのファイルを触るかが `/tasks` の時点で決まらず、大タスクの境界も曖昧になる。

- 各コンポーネントについて、**担当するファイル・責務**と、**担当しない範囲**（隣接するコンポーネントの
  責務に踏み込まない境界）を `## アーキテクチャ` の `### コンポーネント境界` に書く
- 複数のコンポーネントが同じファイル・同じ責務を担当してしまう重なりが無いか確認する。重なりが見つかったら、
  どちらか一方の責務に寄せるか、コンポーネントを1つに統合する
- **feature が複数リポジトリにまたがるとき**は、各コンポーネントが担当するリポジトリも明記する。
  `### コンポーネント境界` の項目に `リポジトリ: <repo名>` を添える。`/tasks` はこれを根拠に
  大タスクの単位をリポジトリ境界と一致させる
- これは実装者向けの情報であり、`## レビューポイント` には上げない。境界の引き方自体が要件と矛盾する
  （例: 要件が求める権限分離が守れない）場合だけ「技術判断としての逸脱」に書く

## 出力の構成

### 読み手の分離: 人間が読むのは `## レビューポイント` だけ

`design.md` には読み手が 2 種類いる。**冒頭の `## レビューポイント` は人間用**で、ここだけ読めば
レビューが終わる状態にする。それ以外の節は `/tasks` と `implementer` が実装のために読むもので、
人間は普段開かない。

**信号を雑音に埋めない。** 踏襲元の一覧・要件対応表・ディレクトリ構成・擬似コードといった調査の証跡は
量が多いうえ、人間には正しさを検証できない。間違っていれば impl とテストで落ちる。これらと、
セキュリティ境界・非可逆な劣化・未検証の断言といった事故につながる決定を同じ粒度・同じ重みで並べると、
後者が読み飛ばされる。**証跡は付録へ送り、決定はレビューポイントへ上げる。**

### レビューポイントに載せるもの
次の順で並べる。**全体で 1〜2 画面に収める**。超えるなら 1 項目 1〜2 行に圧縮する。

1. **仕様に影響する変更** — 挙動・記録粒度・可視性が要件の記述から変わるもの。**仕様の持ち主の
   承認が要る**ので最初に出す。例えば、失敗の記録粒度がアドレス単位から一括単位に落ちる、など
2. **技術判断としての逸脱** — 踏襲元と違う形にした点。対象・逸脱内容・理由を書く
3. **未検証の断言** — 下記「〜なので問題ない」形の記述
4. **確認質問** — **最大 5 個**。答えが設計を変えるものだけ書く

**1 と 2 は必ず分ける。** どちらも「逸脱」だが承認を求める相手が違う。1 は仕様の持ち主、2 は
コードの読み手が相手になる。同じ見出しに同じ重みで並べると、承認が要る仕様変更が技術的な好みの話に見える。

該当が無いカテゴリは**見出しごと省略する**。

### 「〜なので問題ない」は全部列挙する
検証せずに「問題ない」と結論づけた記述を設計本文から**漏れなく拾い**、レビューポイントに並べる。
断言の形を禁じるのではなく、**まとめて出して人間が確認できる状態にする**のが目的。

拾う言い回し: 「〜のため発生しない」「〜なので害はない」「〜に収まる」「大半は〜なのでほぼ〜しない」
「〜なので無視できる」「実質〜」。

各項目に**確認方法**を 1 つ添える：

| 確認方法 | 使う場面 |
|---|---|
| 実測する | 件数・時間・サイズなど数で決まるもの |
| 該当コードを読む | 既存実装の挙動を前提にしているもの |
| 仕様の持ち主に聞く | 運用・業務上の前提を置いているもの |

**「SQL は出ない」と「コストがゼロ」を混同しない。** 断言を拾うときは、避けられたのが何で残るのが何かを
分けて書く。例えば、UPDATE は発生しないが `save` の呼び出しとバリデーションのコストは残る、というように。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`(feature) が未指定なら「使い方: /design <feature>」を表示して終了

### Step 2: コンテキスト収集とモード判定
読み込む：
- `.specs/<feature>/requirements.md` — 必須。無ければ `/spec <feature>` を案内して終了
- `.specs/<feature>/design.md`(あれば)

`design.md` の有無で分岐する：
- **無い → 新規作成モード**: Step 3 へ。
- **有る → 編集モード**: 既存 `design.md` をベースに、まず現在の `requirements.md` と突き合わせてズレを洗い出す。
  新要件が設計に未反映、削除された要件の設計が残存、などが該当する。
  ズレとユーザーの変更要望に該当する箇所だけを Step 3 で直す。どちらも無ければ Step 3・Step 4 を飛ばして Step 5 へ。
  - **再起動されたときは白紙に戻さない。** 既存の `design.md` をベースに、渡された変更要望に該当する箇所だけを直す。
    レビューの指摘を受けて再実行される場合も同じ。

### Step 3: 設計

**3-1 踏襲元の特定と設計**

まず「設計方針: 既存を踏襲する」節に従って**踏襲元を探す**。踏襲元の探し方はモードに応じて変える：
- **新規作成・単純な追加**: 同種の既存実装を 1 つ特定し、その形をそのまま複製する前提で組む
- **新規作成・既存機能の拡張**: 統合ポイントを Grep で洗い、**その周辺の実装の形に合わせる**。新しい層・新しい命名体系は持ち込まない
- **新規作成・新規機能**: まず repo 内に近い責務のコードが無いかを探す。**無いことを確認してから**アーキテクチャパターン・依存ライブラリを調査する。必要なら WebSearch を使う。ライブラリは repo に既に入っているものを優先する
- **編集モード**: 直す箇所の周辺だけ調べる

設計時に次も確認する：
- **別 PJ の実装状況・挙動**（`seed.md` に「実装済み」「この形式で比較する」などの記載がある場合）: 依頼元は自分の
  未コミット作業ツリーを見て書くため、remote に載っているとは限らない。その PJ を `git fetch` してデフォルトブランチの
  コードを読んで確認する。食い違いは design.md の「実装上の注意事項」に書き、`requirements.md` 側の修正要否を Step 5
  の「要確認」に挙げる
- **環境変数・設定値を導入する feature**: ローカルとプロジェクトが持つ各デプロイ環境それぞれの**投入先ファイルを実
  リポジトリで特定**してから設計する。「インフラ側で対応」とスコープ外に出す前に、デプロイ定義がその repo に
  無いかを確認する。未設定時にフォールバックする設計は投入先の誤りを隠すので、特定できなければ Step 5 の
  「要確認」に出す
- **要件に書かれていない判断**（ライブラリ選定・データ構造・エラー時の挙動など）: 「設計方針」の既存踏襲と
  「対話方針」に従う

**3-2 固定チェックリストの適用**

設計が組めたら、次を**組んだ設計に対して明示的に確認する**。要件に書かれていなくても見る。
該当したものは `## レビューポイント` に書き、**該当しなければ何も書かない**。項目は今後増えるので、末尾に追記していく。

- **テナント / 認可スコープ** — 親の ID を受け取っているのに、子を無条件に引いていないか。
  例えば親の ID をスコープとして渡されているのに、子のクエリではその条件を付けずに全件から引く、というように。特に
  **ジョブ引数・キュー経由の値は信頼しない** — 永続化されて後から再実行されうるので、投入時に
  整合していても実行時に整合しているとは限らない
- **リトライの有無** — 例外の catch や握り潰しでフレームワークの
  リトライを殺していないか。殺すなら**明示的な決定として**レビューポイントに書く
- **失敗の可視性** — 失敗したとき誰がどこで気づくか。「処理は成功と表示され、実際には何も
  実行されていない」が成立する経路が無いか。結果が履歴・ログに残らない設計は特に見る
- **非可逆な操作** — 削除・外部送信（メール・通知・Webhook）・課金・マイグレーション
- **新規依存の追加** — repo にまだ無いライブラリ・外部サービスを持ち込むか

**「見ない」と書いたものを読み込んでいないかも確認する。** 設計本文で参照しないと宣言したデータを
クエリ側（`includes` / `select` / join）に残すと、宣言とコードが食い違う。

### Step 4: 書き出し
Step 3 の内容を次のフォーマットで `.specs/<feature>/design.md` に書く。編集モードでは上書きする。

```markdown
# 技術設計: [機能名]

## 概要
[設計の方針・アプローチを2〜3文で]

## レビューポイント
[人間がレビューする唯一の節。1〜2 画面に収める。該当が無いサブ見出しは省略する]

### 仕様に影響する変更
- [何がどう変わるか]。要件は[元の記述]、設計では[採った形] — [なぜ変えたか。誰の承認が要るか]

### 技術判断としての逸脱
- [対象]: [踏襲元と違う点]。踏襲元は `path/to/file` — [理由]

### 未検証の断言
- 「[本文中の断言をそのまま引く]」。該当は[節名] — 確認方法: [実測する / 該当コードを読む / 仕様の持ち主に聞く]

### 確認質問
1. [答えが設計を変える質問。最大 5 個]

## アーキテクチャ

### コンポーネント構成
[主要コンポーネントとその責任]

### コンポーネント境界
[コンポーネントごとに「担当するファイル・責務（所有するもの）」と「担当しないもの（他コンポーネントの責務に
踏み込まない範囲）」を明記する。複数コンポーネントが同じファイル・責務を担当してしまう重なりが無いか確認する。
`/tasks` がタスクを大タスク単位に割るときの根拠になる。feature が複数リポジトリにまたがるときは
`リポジトリ: <repo名>` も明記する。単一リポジトリの feature では省略する]

### データフロー
[データの流れを説明。必要ならMermaid図で。ノードIDは英数字とアンダースコアのみにし、ラベルに
`()` `[]` `"` `/` `@` などの記号を含めない（strict modeで構文エラーになる）。装飾はせず素の構造だけ書く]

## データ設計
[DBスキーマ、データ構造、型定義など]

## API/インターフェース設計
[エンドポイント、関数シグネチャ、入出力形式]

## テスト方針
[TDD を採るか、レイヤーごとにどの種類のテスト（ユニット/統合/E2E）を書くか、モックの使用方針など。
踏襲元があれば、そのテスト方針（配置・命名・フレームワーク）に合わせる]

## 実装上の注意事項
[実装者向けの技術メモだけを置く。レビューポイントに上げた項目はここに重複させない]

## 付録: 設計サマリ
| 設計対象 | 採った形 | 踏襲元 |
|---|---|---|
| [何を決めたか] | [採用した構成・ライブラリ・データ構造] | `path/to/file`（構成・命名・エラー処理） |
| [...] | [...] | 該当なし（新規） — 合わせた repo 全体のパターン: ... |

## 付録: ディレクトリ構成
[新規作成・変更するファイルの一覧]

## 付録: 要件対応表
| Requirement | 対応するコンポーネント/実装 |
|-------------|--------------------------|
| Requirement 1 | ... |
| Requirement 2 | ... |

## 付録: [その他の表題]
[擬似コードなど、実装者だけが読む長い記述をここに置く。無ければ節ごと省略]
```

**読み手が読む必要のあるものだけを残す：**

- **本文と付録は「人間が読む必要があるか」で分ける**（基準は「出力の構成」節の通り）。行数では切らない。
  本文には2種類ある。人間用のレビューポイントと、実装者が判断に使うアーキテクチャ・データ設計・
  API/インターフェース設計・実装上の注意事項。**設計サマリ（踏襲元）・ディレクトリ構成・要件対応表・
  擬似コードは付録**へ送る。
- **付録は削除ではなく移動。** 要件対応表が担う網羅性の担保は変わらない。`/tasks` と `implementer` は
  付録も読む。
- **`## レビューポイント` と `## 付録: 要件対応表` は常に置く**。前者は人間のレビュー、後者は要件の
  網羅を追う唯一の手段。レビューポイントに該当が無いときはサブ見出しを省略する。
- **該当しない節は節ごと省略する。** DB を持たない feature に
  「## データ設計」は要らず、外部インターフェースを足さない feature に「## API/インターフェース設計」は
  要らない。空節が並ぶと、中身のある節がその中に埋もれる。
- **`## レビューポイント` + `## アーキテクチャ` + `## データ設計` が 2 画面を超えたら圧縮する。**
  超えるのは決定と説明が混ざっているサイン — 決定だけを残し、説明は削るか付録へ送る。
- **擬似コードを本文に置かない。** implementer は付録を読み、人間はコードレビューで実物を見る。

**完了ゲート:** 次を満たして書き出したか。
- 全要件（Requirement 1, 2, ...）が設計に対応していて、`## 付録: 要件対応表` で追える
- インターフェース・データフローが具体的で、実装者が推測せずに書ける
- 拡張性・保守性（SOLID）を踏まえている
- 「設計方針」（既存を踏襲する・コンポーネントの境界を明確にする）
- 「出力の構成」（レビューポイントに載せるもの・「〜なので問題ない」の列挙・読み手が読む必要のあるものだけを残す）
- Step 3-2 の固定チェックリスト（テナント / 認可スコープ・リトライ・失敗の可視性・非可逆な操作・新規依存）

要件に根拠が無いまま決めた判断は、書きながら控えておき Step 5 の「要確認」に挙げる。**確認が要るものの置き場は
`## レビューポイント` の 1 箇所**で、アーキテクチャやデータ設計の節に「※要確認」の注記を散らさない。
散らすと、レビューポイントを読んだだけでは足りない doc になる。

### Step 5: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### 技術設計完了
<何を設計したかを 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/design.md`

### 要確認
- <仕様に影響する変更> — 該当: <節名>
- <要件に根拠が無く、こちらの判断で決めた点・踏襲元からの逸脱> — 該当: <節名>
- <未検証の断言> — 該当: <節名>、確認方法: <実測する / 該当コードを読む / 仕様の持ち主に聞く>
- <確認質問> — 該当: <節名>

### 次の一手
- タスク分割に進む: `/tasks <feature>`
- 設計を直す: `/design <feature>`
```

カードは 3 ブロックに分ける。**技術設計完了**、続けて**要確認**、最後に**次の一手**。

- 技術設計完了: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**。無ければ行ごと省略する。
  生成物のパスは見出しブロックの末尾に 1 行で添える。
  設計判断の根拠や検討経緯は design.md に書き、カードには出さない。
- 要確認: 聞かずに書き切るぶん、確認が要るものを全部ここに挙げる。「レビューポイントに載せるもの」の4分類（仕様に影響する変更 → 技術判断としての逸脱 → 未検証の断言 → 確認質問）と**同じ順・同じ名称**で並べる。
  design.md のどこを見ればいいか該当箇所を添える。無ければブロックごと省略する。無理に絞らず、有るものは全部出す。
- 次の一手: `- <何をするか>: <コマンド>` の形で、選べる道を全て出す。どれを選ぶかはこのカードを受け取った側（人間 / `/orch`）の判断に委ねる。

**中断時**: 同じブロック構成で見出しを `### 技術設計中断` に差し替える。

- 技術設計中断: 一言サマリに中断理由。`requirements.md` が無い・要件から設計を確定できない、などが該当する。
  書き出し前に止まったなら生成物の行は省略する。
- 次の一手: 復帰コマンド。`- 設計を作り直す: /design <feature>`・`- 要件を作る: /spec <feature>` など。
  未完成の設計のまま `/tasks` へ進む道は出さない。

## 完了条件
全要件をカバーする設計が `.specs/<feature>/design.md` に書き出せたら完了。
