# 実装スキル

## 役割
`.specs/<feature>/tasks.md` の `## タスク一覧` を実装する。
コードは `implementer` サブエージェントに書かせ、自分はコーディネーターとして配布・ビルド確認・進捗更新だけを行う。
仕様だけで実装が通るかを確かめるため、自分ではコードを書かない。

## 判断が割れる点の扱い
途中でユーザーに質問も承認も求めない。
未完了の事前セットアップ・implementer の blockers・ビルド失敗のように実装を続けられない事態では止まり、中断カードを出して分岐を呼び出し元に委ねる。
推測で埋めると誤った実装がそのまま積み上がる。

## 配布の単位
大タスクごとに `implementer` を 1 体、依存順に逐次呼ぶ。
同じ作業ツリーへの Write が衝突するので並列には配布しない。
大タスクが大きすぎても impl 側で分割せず、タスク分解の側を直す。

## 進め方

### Step 1: 引数の確認
- `$ARGUMENTS[0]` が無ければ「使い方: /impl <feature> [task-numbers]」を表示して終了
- `$ARGUMENTS[1]` に `1.1` や `1,2` の形でサブタスク番号があれば手動モードにし、指定サブタスクだけを実装する

### Step 2: コンテキスト収集
配布と確認に要るものだけを集め、`requirements.md` と `design.md` は読まない。
仕様の裏取りは `implementer` が自分で行う。

- `.specs/<feature>/tasks.md` の `## タスク一覧` から、サブタスクの説明・完了条件・`_Requirements:_`・`_Depends:_`・`_Repo:_`
- `design.md` の `## 付録: 設計サマリ` の踏襲元列
- ビルド設定ファイルから読み取ったテスト・ビルドコマンド

対象タスクの `_Depends:_` に `## 事前セットアップ` の未チェックの `S<n>` があれば、人の作業待ちなので Step 7 の中断カードで止まる。

### Step 3: 実装ブランチの確定
実装ブランチ `<feature>` 1 本の上で全タスクを実装する。
実装を隔離しておけば、途中で捨てる・作り直すのが安全になる。
HEAD の状態で分岐する:
- `<feature>` ブランチが既にある → checkout して前回の実装を再開する
- detached HEAD → `git checkout -b <feature>` で今の HEAD から切る
  - worktree はデフォルトブランチの先端に detached で作られているので、これが起点になる
- ブランチ上 → デフォルトブランチを最新化し、その先端から切る

```
DEFAULT=$(git default-branch)
git fetch origin "+refs/heads/$DEFAULT:refs/heads/$DEFAULT"
git checkout -b <feature> "$DEFAULT"
```

### Step 4: 配布対象の決定

大タスクに `_Repo:_` があるときは feature が複数リポジトリにまたがっているので、現在の作業ディレクトリのリポジトリ名と一致する大タスクだけを配布対象にする。
一致しない大タスクが 1 つ以上あれば、まだ呼んでいなければここで一度だけ `dispatch <feature>` を `Skill` ツールで呼び、他リポジトリの実装を並列に走らせる。
`dispatch` の完了は待たず、自分のリポジトリ分をそのまま続ける。

- 手動モードでなければ、配布対象の大タスクのうち未完了の最初の 1 つ
- 手動モードなら指定サブタスクだけ
- `- [ ]*` の印が付いたタスクも含める
  - 後回しにできるテストとして印が付いたもので、既定では実装する

### Step 5: implementer に配布

プロンプトに渡すもの:
- feature 名
- `## タスク一覧` から転記したサブタスクの説明・完了条件・`_Requirements:_`・`_Depends:_`
- `design.md` の `## 付録: 設計サマリ` の踏襲元列があれば、そのパスと踏襲する点をそのまま渡し、その形に合わせて書く旨を明示する
- 「tasks.md に書かれた順に実装し、git・tasks.md・テストとビルドの実行には触れず、報告フォーマットで返す」旨
  - `implementer` 側にも定義済みだが明示する

### Step 6: 報告の取り込みとビルド確認

`implementer` の報告が返ったら次を順に行う。
1. `変更ファイル`・`タスクごとの確認` を確認する
2. Step 2 で確定したビルドコマンドでビルドを実行する。コマンドが無いリポジトリでは飛ばす
3. 完了と報告されたサブタスクの `[ ]` を `## タスク一覧` で `[x]` にする。`## 事前セットアップ` の `S<n>` は人が付けるので触らない
4. `blockers` があるサブタスクはチェックせず、次で分ける
   - 軽微なら追加指示を添えて同じ大タスクを再配布する
   - 上流の工程の問題なら Step 7 の中断カードで止め、戻し先は呼び出し元に委ねる
   - `- [ ]*` のタスクは未完了でも中断せず要確認に回す
5. `自分で決めた判断` を控え、Step 7 の要確認に出す

ビルドが通らないまま次の大タスクを配布しない。
壊れた土台を渡すと、既存コードに合わせて書く次の `implementer` がそれに引きずられる。
ビルドエラーを添えて同じ大タスクを再配布し、それでも通らなければ Step 7 の中断カードで止める。

手動モードでなく `## タスク一覧` に未完了の大タスクが残っていれば Step 4 に戻り次を配布し、残っていなければ Step 7 へ進む。

### Step 7: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### 実装中断` にし、1 行目に中断理由を書き、`[x]` を 1 つも付けていなければ生成物の行を省き、次の一手は復帰に必要な操作だけにする。
`S<n>` 待ちの中断では、1 行目に当該項目の内容と `種別:` をそのまま引き写し、「別 PJ の変更待ち」に丸めない。
次の一手は `種別:` で分ける。
- `別 PJ 依頼:` なら相手 PJ のセッションと `ListAgents` / `SendMessage` で会話しながら詰める
- `repo 内セットアップ` なら当該項目を実施してから `/impl <feature>` を再実行する

```markdown
### 実装完了
<何タスクを実装したかを 1 行>

生成物: `.specs/<feature>/tasks.md` のチェックボックス更新

### 要確認
- <implementer の報告の `自分で決めた判断` をそのまま> — 該当: <タスク番号 / ファイル>
<無ければこのブロックを省略>

### 次の一手
- テストを回す: `/test <feature>`
  <テストコマンドが無いリポジトリなら `- レビューに進む: /review <feature>` に差し替える>
- 仕様を直す: `/spec` `/design` `/tasks` のいずれかを再実行
  <要確認があるときだけ>
- 他リポジトリの完了は notify_when_idle の通知で確認する
  <Step 4 で dispatch を呼んだときだけ>
```
