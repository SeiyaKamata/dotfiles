# 実装スキル（コーディネーター）

## 役割
`.specs/<feature>/tasks.md` の `## タスク一覧`を**実装ブランチ 1 本で**実装する。

実装そのものは **`implementer` サブエージェントに委譲**し、このスキル（メイン）は**コーディネーターに徹する**。これによりメインの context を実装のトークンで汚さず、仕様（requirements/design/tasks）だけで実装が通るか＝**仕様の自己完結性**も検証できる。

- **メインが握るもの**: git 操作（ブランチ作成・checkout）、tasks.md のチェックボックス更新、大タスクごとのビルド確認、リポジトリ全体の最終テスト、詰まったときの判断
- **implementer に任せるもの**: コード実装だけ。git・tasks.md・テストとビルドの実行には触らせない。`implementer` 側の制約に定義済み
- **メインでコードを直接書かない**

## 入出力
- **入力**: `.specs/<feature>/tasks.md` の `## タスク一覧`と `## 事前セットアップ`（依存チェック用）＋ `design.md` の `## 付録: 設計サマリ` の踏襲元列だけ。Step 4-1 で implementer に渡す。`requirements.md` と `design.md` の残りは**メインで読まない**（implementer が自分で読む）
- **出力**: 実装コード＋`.specs/<feature>/tasks.md` の `## タスク一覧` のチェックボックス更新

## 引数
- `$ARGUMENTS[0]`: feature 名（必須）
- `$ARGUMENTS[1]`: 手動モード（省略可）
  - 省略: `## タスク一覧` の全大タスクのサブタスクを実装する
  - タスク番号（例: `1.1`, `1,2`）: 指定サブタスクのみ実行

## モード
途中でユーザーに何も聞かない。ただし未完了の事前セットアップ・implementer の blockers・大タスクのビルド失敗・
最終テストの失敗継続という**実装を続けられない事態では止まる** — 推測で埋めると誤った実装がそのまま積み上がるため。
止まったら中断カードを出し、分岐は呼び出し元に委ねる。

## 用語
前提として、用語の定義は `claude/CLAUDE.md`「用語集」に従う。特にこのスキルでは：
- **ブランチは `<feature>` 1 本。** 実装を隔離するためのもので、リモートへの反映の形（変更をどう束ねるか）は `/sync-to-remote` が実装後に決める。
- **大タスクは PR 単位ではなく関心のグルーピング**。1 回の `/impl` 呼び出しで全大タスクを実装する。
  tasks が単一サブタスクを昇格させた、サブタスクを持たない大タスクは、サブタスクと同じ配布単位として扱う。
- タスクの分割・粒度は **tasks の責務**。impl は tasks.md に**書かれたとおりに実装する**。大タスクが大きすぎても impl 側で分割しない。それは tasks がおかしいということなので、`/tasks` を編集モードで再入して直す。
- **配布は大タスク単位。** 大タスク（1., 2., ...）ごとに `implementer` を 1 体呼び、依存順に逐次で回す（Step 4-1）。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`(feature) が未指定なら「使い方: /impl <feature> [task-numbers]」を表示して終了
- 手動タスク番号が渡されていれば確定する

### Step 2: コンテキスト収集
メインが軽量に実施する。実装のためではなく**配布と最終確認のため**に、最小限だけ集める。
**ブランチを切る前に行う**。ここで止まる場合、空のブランチを残さない。

- `.specs/<feature>/tasks.md` の **`## タスク一覧`** — 全大タスクのサブタスク一覧・完了条件・`_Requirements:_`・`_Depends:_`
- **事前セットアップ依存** — 対象タスクの `_Depends:_` に `S<n>`（`## 事前セットアップ` の項目）があり、それが未チェック（`[ ]`）なら**人の作業待ちで実装できない**。配布せず中断する。`S<n>` はコーディングタスクではないので implementer には渡さない
  - 中断カードには**当該 `S<n>` の項目内容（1 行目と `種別:`）をそのまま引き写す**。待ち内容を「別 PJ の変更待ち」に丸めない。`S<n>` には GUI 操作・Secrets 登録など別 PJ と無関係のものも入る
- **`qa.md` は読まない** — `## デプロイ環境QAシナリオ`（`V<n>`）はデプロイ後に実施する項目で、配布対象でも完了条件でもない。`_Depends:_` から `V<n>` が参照されることも無い。参照があれば tasks 側の誤りなので、中断して `/tasks` の編集モード再入に回す
- テスト・ビルドコマンド（`package.json`, `Makefile`, `go.mod`, `pyproject.toml` などから）
- `git status --porcelain` でベースライン

### Step 3: ブランチ準備
メインが実施する。**PR 運用の有無に関わらず、常にブランチを切る。** 実装を隔離しておけば、途中で捨てる・作り直すのが安全になる。PR を作らない repo でも同じで、その場合は `/sync-to-remote` がデフォルトブランチへ取り込む。

**ブランチは `<feature>` 1 本だけ**をデフォルトブランチから切る。

```
DEFAULT=$(git remote show origin | sed -n 's/.*HEAD branch: //p')
git fetch origin "$DEFAULT"
git checkout -b <feature> "origin/$DEFAULT"
```

既に `<feature>` が存在する場合、前回の実装を再開するので、新規作成せずそれに checkout する。

### Step 4: 実装

**4-1 implementer に配布**

`## タスク一覧` のサブタスクを `implementer`（Agent）に配布する。**配布するのは `## タスク一覧` のサブタスクだけ**で、`## 事前セットアップ`（`S<n>`）は渡さない。人が実施する。プロンプトに渡すもの：
- feature 名（specs のパスを含む）
- `## タスク一覧` から転記したサブタスクの説明・完了条件・`_Requirements:_`・`_Depends:_`
- `design.md` の `## 付録: 設計サマリ` の踏襲元列(あれば) — 踏襲元のパスと踏襲する点をそのまま渡し、**その形に合わせて書く**旨を明示する
- 「tasks.md に書かれた順に実装し、git・tasks.md・テストとビルドの実行には触れず、報告フォーマットで返す」旨を伝える。`implementer` 側にも定義済みだが明示する

**配布の単位は大タスク。** `## タスク一覧` の大タスク（1., 2., ...）ごとに `implementer` を 1 体呼び、**依存順に逐次**で回す。

- `/tasks` の定義どおり大タスクは**関心の単位**でまとまっているので、そのまま 1 体に渡せる範囲になる
- 配下のサブタスクをさらに分けて別々の `implementer` に渡さない。同じ関心の実装が分断される
- **各回の報告を Step 4-2 で取り込み、ビルドが通ってから次の大タスクを配布する**。`_Depends:_` の前提が満たされ、かつ壊れていない土台を渡すため
- `/tasks` が単一サブタスクを昇格させた、サブタスクを持たない大タスクも 1 体に渡す 1 単位として扱う
- 1 つの大タスクが `implementer` の context に収まらないほど大きい場合は、**tasks の粒度がおかしい**ので `/tasks` を編集モードで再入して割り直す。impl 側で刻まない

**並列配布はしない。** 複数の `implementer` を同時に走らせると、同じ作業ツリーへの Write が衝突して互いの変更を壊す。git で分離されていないので復旧手段も無い。分けるとしても**必ず逐次**で、前の報告を取り込んでから次を配布する。

> 並列化が要る場面は「1 つの feature の中でタスクを並列に処理する」ことではなく、**worktree を分けて複数の feature のパイプラインを同時に回す**こと（`claude/CLAUDE.md` の worktree 運用）。これはパイプラインの外側で人が行うので、`/impl` は関与しない。

**`- [ ]*` のタスク:** 配布対象に含める。既定では実装する。ただし `implementer` が完了できなかった場合、**それを理由に中断しない**。後回しにできるテストとして tasks が印を付けたもの。未完了のまま Step 5 の「要確認」に挙げる。

手動モード（タスク番号指定）では、指定サブタスクだけを 1 つの implementer に配布する。

**4-2 報告の取り込みとビルド確認**

`implementer` の報告が返ったら：
1. `変更ファイル`・`タスクごとの確認` を確認する
2. **ビルドを実行する**。Step 2 で確定したビルドコマンドを使う。ビルドコマンドが無いリポジトリではスキップする
3. **完了と報告されたサブタスクの `[ ]` を `[x]` に更新**する（`.specs/<feature>/tasks.md` の `## タスク一覧`）。`## 事前セットアップ`（`S<n>`）のチェックボックスは更新しない — 人が実施したときに人が付ける
4. `blockers` があるサブタスクはチェックせず、「例外処理」に従う。`- [ ]*` のタスクは除く。未完了でも中断せず「要確認」に回す
5. `自分で決めた判断` は控えておき、Step 5 の「要確認」に出す

**ビルドが通らないまま次の大タスクを配布しない。** 検証のためではなく、**次の `implementer` への入力を壊さない**ため。implementer は毎回使い捨てで、既存コードを読んで周囲のパターンに合わせて書くので、壊れた土台を渡すとそれに引きずられる。自分が書いていない箇所のビルドエラーを見て判断を誤りもする。

**ここで回すのはビルドだけで、テストは回さない。** 大タスクは関心のグルーピングであって単体で着地する単位ではないので、この時点のテスト失敗には後続の大タスクで解消されるものが混じる。テストの判定は `/test` が feature 全体に対して 1 回行う。

**4-3 最終確認**

- リポジトリ全体のテスト・ビルドを実行する。最終確認はメインが 1 回まとめて行う
- 対象サブタスクが完了条件・関連要件（`_Requirements:_`）を満たしているか確認する

### Step 5: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### 実装完了
<何タスクを実装したかを 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/tasks.md` — `## タスク一覧` のチェックボックス更新

### 要確認
- <仕様に根拠が無く implementer が自分で決めた点> — 該当: <タスク番号 / ファイル>

### 次の一手
- テストを回す: `/test <feature>`
- 仕様を直す: 変更する工程を編集モードで再入(/spec・/design・/tasks)
```

カードは 3 ブロックに分ける。**実装完了**、続けて**要確認**、最後に**次の一手**。

- 実装完了: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**。無ければ行ごと省略する。
  変更ファイルの一覧や implementer の報告詳細は列挙せず、tasks.md と git 差分に寄せる。
- 要確認: implementer の報告の `自分で決めた判断` をそのまま出す。仕様に書かれておらず実装側で決めた点を全部挙げる。既定値・エラー時の挙動・命名などが該当する。無ければブロックごと省略する。
- 次の一手: テストが無いリポジトリなら 1 行目を `- レビューに進む: /review <feature>` に差し替える。Step 2 でテストコマンドの有無が分かっている。

**中断時**: 同じブロック構成で見出しを `### 実装中断` に差し替える。

- 実装中断: 一言サマリに中断理由。未完了の事前セットアップ・blockers・大タスクのビルド失敗・最終テスト失敗などが該当する。**`S<n>` 待ちで止まった場合は当該項目の内容を引き写す**。「別 PJ の変更待ち」に丸めない。途中まで `[x]` を付けたなら生成物の行は残す。
- 次の一手: 復帰コマンド。`S<n>` 待ちなら `種別:` に応じて出す。`別 PJ 依頼:` なら `- 依頼を投げる: /handoff`、`repo 内セットアップ` なら `- <S<n> の内容> を実施してから /impl <feature> を再実行`。仕様の問題なら `- 仕様を直す: /spec・/design・/tasks を編集モードで再入`。未完成のまま `/test` へ進む道は出さない。

## 例外処理
- `implementer` が、仕様の曖昧さ・設計の穴・大タスクが大きすぎる等の `blockers` を報告 → メインで判断する。
  - 軽微なら追加指示を添えて `implementer` を再配布する
  - 仕様・設計・タスク分割の問題なら上流工程（`/spec`・`/design`・`/tasks`）への編集モード再入が要るため、中断カードを出して止める。戻し先の判断は呼び出し元に委ねる
- 大タスクのビルドが通らない（Step 4-2）→ ビルドエラーを添えて同じ大タスクを `implementer` に再配布する。再配布しても通らなければ中断する。次の大タスクは配布しない
- 最終テストが失敗し続ける場合 → 根本原因を調査し、該当タスクを `implementer` に再配布して最小限の修正を試みる。それでも通らなければ中断する

## 出力規律
実行中の逐次ナレーション（「〜します」「〜しました」）は出さない。ツール実行はターミナルに表示されるため二重になる。ただし implementer へ委譲して表示が止まる区間の開始時だけ、次の 1 行を出す。1 区間 1 回、委譲が複数回あれば区間ごとに 1 回。

⏳ impl: implementer に <n> タスクを委譲中…

## 完了条件
**`## タスク一覧`** の対象サブタスク（手動モードでなければ全サブタスク）が `[x]` になり、リポジトリ全体のテスト・ビルドがパスしたら完了。次工程の起動は完了条件に含めない。
