# 実装スキル

## 役割
`.specs/<feature>/tasks.md` の `## タスク一覧`を実装ブランチ 1 本で実装する。

実装そのものは **`implementer` サブエージェントに委譲**し、メインはコーディネーターに徹してコードを直接書かない。これによりメインの context を実装のトークンで汚さず、requirements・design・tasks の仕様だけで実装が通るか＝仕様の自己完結性も検証できる。

implementer に任せるのはコード実装だけで、git・tasks.md・ビルドの実行には触らせない。`implementer` 側の制約に定義済み。

## 入出力
- **入力**:
  - `.specs/<feature>/tasks.md` の `## タスク一覧` と、依存チェック用の `## 事前セットアップ`
  - `design.md` の `## 付録: 設計サマリ` の踏襲元列 — Step 5 で implementer に渡す
  - `requirements.md` と `design.md` の残りは**メインで読まない** — implementer が自分で読む
- **出力**:
  - 実装コード
  - `.specs/<feature>/tasks.md` の `## タスク一覧` のチェックボックス更新

## 引数
- `$ARGUMENTS[0]`: feature 名。(必須)
- `$ARGUMENTS[1]`: 手動モード。(省略可)
  - 省略: `## タスク一覧` の全大タスクのサブタスクを実装する
  - タスク番号を指定: 指定サブタスクのみ実行。形式は `1.1` や `1,2`

## 自律方針
途中でユーザーに何も聞かない。ただし未完了の事前セットアップ・implementer の blockers・大タスクのビルド失敗という
**実装を続けられない事態では止まる** — 推測で埋めると誤った実装がそのまま積み上がるため。
止まったら中断カードを出し、分岐は呼び出し元に委ねる。

## 用語
前提として、用語の定義は `claude/CLAUDE.md`「用語集」に従う。特にこのスキルでは：
- 大タスクが大きすぎても impl 側で分割しない。それは tasks がおかしいということなので、`/tasks` を編集モードで再入して直す。
- **配布は大タスク単位。** `1.`, `2.` と番号が振られた大タスクごとに `implementer` を 1 体、依存順に**逐次**呼ぶ。配布と実行は Step 4・Step 5。**並列配布はしない** — 同じ作業ツリーへの Write が衝突するため。

## 進め方

### Step 1: 引数チェック
- feature 名 `$ARGUMENTS[0]` が未指定なら「使い方: /impl <feature> [task-numbers]」を表示して終了
- 手動タスク番号が渡されていれば確定する

### Step 2: コンテキスト収集
メインが軽量に実施する。実装のためではなく配布と最終確認のために、最小限だけ集める。

- `.specs/<feature>/tasks.md` の `## タスク一覧` — 全大タスクのサブタスク一覧・完了条件・`_Requirements:_`・`_Depends:_`・`_Repo:_`
- **事前セットアップ依存** — 対象タスクの `_Depends:_` に `## 事前セットアップ` の項目 `S<n>` があり、それが未チェック `[ ]` のままなら人の作業待ちで実装できない。配布せず中断する。`S<n>` はコーディングタスクではない。配布対象外の扱いは Step 4 参照
  - 中断カードには**当該 `S<n>` の項目内容、1 行目と `種別:` をそのまま引き写す**。待ち内容を「別 PJ の変更待ち」に丸めない。`S<n>` には GUI 操作・Secrets 登録など別 PJ と無関係のものも入る
- テスト・ビルドコマンド — `package.json`、`Makefile`、`go.mod`、`pyproject.toml` などから読み取る

### Step 3: ブランチ準備
メインが実施する。**常にブランチを切る。** 実装を隔離しておけば、途中で捨てる・作り直すのが安全になる。

**ブランチは `<feature>` 1 本だけ**をデフォルトブランチから切る。

```
DEFAULT=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null); DEFAULT=${DEFAULT##*/}
[ -z "$DEFAULT" ] && { git remote set-head origin --auto >/dev/null; DEFAULT=$(git symbolic-ref --short refs/remotes/origin/HEAD); DEFAULT=${DEFAULT##*/}; }
git fetch origin "$DEFAULT"
git checkout -b <feature> "origin/$DEFAULT"
```

`git remote show origin | sed` を使わないのは、`sed` がパイプ経由で権限の allowlist に無く承認待ちで止まるため。

既に `<feature>` が存在する場合、前回の実装を再開するので、新規作成せずそれに checkout する。

### Step 4: 配布対象の決定

`## タスク一覧` のサブタスクを `implementer` Agent への配布対象とする。**配布するのは `## タスク一覧` のサブタスクだけ**で、`## 事前セットアップ` の `S<n>` は渡さない。人が実施する。

**大タスクに `_Repo:_` があるとき**は、feature が複数リポジトリにまたがっている。`_Repo:_` が現在の
作業ディレクトリのリポジトリ名と**一致する**大タスクだけを配布対象にする。一致しない大タスクが 1 つ以上
あれば、まだ呼んでいなければ Step 3 の直後に一度だけ `dispatch <feature>` を `Skill` ツールで呼ぶ。
他リポジトリでの実装を並列に走らせる委譲で、詳細は `dispatch/SKILL.md` を参照。`dispatch` の完了は
待たず、自分のリポジトリ分の配布・実装をそのまま続ける。

- `$ARGUMENTS[1]` を省略した全大タスク実行時: `## タスク一覧` の大タスク、`1.`, `2.` ... のうち、まだ完了していない最初の 1 つ。`_Repo:_` で対象外にしたものは除く。
  - `/tasks` の定義どおり大タスクは関心の単位でまとまっているので、そのまま 1 体に渡せる範囲になる。配下のサブタスクをさらに分けて別々の `implementer` に渡さない
  - 大タスクが `implementer` の context に収まらないほど大きい場合は、tasks の粒度がおかしいとして `/tasks` 再入で直す。impl 側で刻まない。「用語」節に従う
- タスク番号指定の手動モード時: 指定サブタスクのみ
- `- [ ]*` の印が付いたタスクも配布対象に含める。後回しにできるテストとして tasks が印を付けたもので、既定では実装する

### Step 5: implementer に配布

プロンプトに渡すもの:
- feature 名。specs のパスを含む
- `## タスク一覧` から転記したサブタスクの説明・完了条件・`_Requirements:_`・`_Depends:_`
- `design.md` の `## 付録: 設計サマリ` の踏襲元列があれば、そのパスと踏襲する点をそのまま渡し、その形に合わせて書く旨を明示する
- 「tasks.md に書かれた順に実装し、git・tasks.md・テストとビルドの実行には触れず、報告フォーマットで返す」旨を伝える。`implementer` 側にも定義済みだが明示する

### Step 6: 報告の取り込みとビルド確認

`implementer` の報告が返ったら次を行う:
- `変更ファイル`・`タスクごとの確認` を確認する
- Step 2 で確定したビルドコマンドでビルドを実行する。コマンドが無いリポジトリではスキップする
- 完了と報告されたサブタスクの `[ ]` を `.specs/<feature>/tasks.md` の `## タスク一覧` で `[x]` に更新する。`## 事前セットアップ` の `S<n>` は人が実施したときに人が付けるので更新しない
- `blockers` があるサブタスクはチェックせずメインで判断する。`- [ ]*` のタスクは除き、未完了でも中断せず「要確認」に回す。軽微なら追加指示を添えて `implementer` を再配布する。仕様・設計・タスク分割の問題なら `/spec`・`/design`・`/tasks` への編集モード再入が要るため、中断カードを出して止める。戻し先の判断は呼び出し元に委ねる
- `自分で決めた判断` は控えておき Step 7 の「要確認」に出す

**ビルドが通らないまま次の大タスクを配布しない。** 次の `implementer` への入力を壊さないため — implementer は毎回使い捨てで既存コードのパターンに合わせて書くので、壊れた土台を渡すとそれに引きずられ、自分が書いていない箇所のビルドエラーで判断を誤りもする。ビルドエラーを添えて同じ大タスクを `implementer` に再配布し、再配布しても通らなければ中断する。次の大タスクは配布しない。

**完了ゲート:** 次を終えたか。
- 報告を確認した
- ビルドを実行した
- チェックボックスを更新した
- blockers を処理した
- `自分で決めた判断` を控えた

省略時、`## タスク一覧` に未完了の大タスクが残っていれば Step 4 に戻り次を配布する。残っていなければ、対象サブタスクが完了条件・関連要件 `_Requirements:_` を満たしていれば Step 7 へ進む。手動モードなら配布した 1 回で必ずここに該当する。

### Step 7: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### 実装完了
<何タスクを実装したかを 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/tasks.md` — `## タスク一覧` のチェックボックス更新

### 要確認
- <仕様に根拠が無く implementer が自分で決めた点> — 該当: <タスク番号 / ファイル>

### 次の一手
- テストを回す: `/test <feature>`
- 仕様を直す: /spec・/design・/tasks を編集モードで再入
```

カードは 3 ブロックに分ける。**実装完了**、続けて**要確認**、最後に**次の一手**。

- 実装完了: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**。無ければ行ごと省略する。
  変更ファイルの一覧や implementer の報告詳細は列挙せず、tasks.md と git 差分に寄せる。
- 要確認: implementer の報告の `自分で決めた判断` をそのまま出す。仕様に書かれておらず実装側で決めた点を全部挙げる。既定値・エラー時の挙動・命名などが該当する。無ければブロックごと省略する。
- 次の一手: テストが無いリポジトリなら 1 行目を `- レビューに進む: /review <feature>` に差し替える。Step 2 でテストコマンドの有無が分かっている。Step 4 で `dispatch` を呼んでいたら `- 他リポジトリの完了は notify_when_idle の通知で確認する` を追加する。

**中断時**: 同じブロック構成で見出しを `### 実装中断` に差し替える。

- 実装中断: 一言サマリに中断理由。未完了の事前セットアップ・blockers・大タスクのビルド失敗などが該当する。**`S<n>` 待ちで止まった場合は当該項目の内容を引き写す**。「別 PJ の変更待ち」に丸めない。途中まで `[x]` を付けたなら生成物の行は残す。
- 次の一手: 復帰コマンド。`S<n>` 待ちなら `種別:` に応じて出す。
  - `別 PJ 依頼:` → `- 相手 PJ のセッションと会話しながら詰める（ListAgents/SendMessage）`
  - `repo 内セットアップ` → `- <S<n> の内容> を実施してから /impl <feature> を再実行`
  - 仕様の問題 → `- 仕様を直す: /spec・/design・/tasks を編集モードで再入`
  - 未完成のまま `/test` へ進む道は出さない

## 完了条件
`## タスク一覧` の対象サブタスクが `[x]` になり、リポジトリ全体のビルドがパスしたら完了。手動モードでなければ全サブタスクが対象。
