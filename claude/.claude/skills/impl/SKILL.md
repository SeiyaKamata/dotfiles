# 実装スキル（コーディネーター）

## 役割
`.specs/<feature>/tasks.md` の**単一フェーズ（大タスク）**を実装する。

実装そのものは **`implementer` サブエージェントに委譲**し、このスキル（メイン）は**コーディネーターに徹する**。これによりメインの context を実装のトークンで汚さず、仕様（requirements/design/tasks）だけで実装が通るか＝**仕様の自己完結性**も検証できる。

- **メインが握るもの**: git 操作（ブランチ作成・checkout）、tasks.md のチェックボックス更新、リポジトリ全体の最終テスト、詰まったときの判断
- **implementer に任せるもの**: 対象フェーズのコード実装と、タスク単位の確認だけ（git・tasks.md には触らせない。`implementer` 側の制約に定義済み）
- **1 フェーズ = 1 implementer**。サブタスクを分割・並列化しない
- **メインでコードを直接書かない**

## 入出力
- **入力**: `.specs/<feature>/tasks.md`（対象フェーズ）。`requirements.md` / `design.md` は**メインで読まない**（implementer が自分で読む）
- **出力**: 実装コード＋`.specs/<feature>/tasks.md` のチェックボックス更新

## 引数
- `$ARGUMENTS[0]`: feature 名（必須）
- `$ARGUMENTS[1]`: フェーズ指定または手動モード
  - 省略: 単一フェーズ構成の feature でそのフェーズを実行
  - `p1`, `p2`, ...: 指定フェーズ（大タスク）を実行
  - タスク番号（例: `1.1`, `1,2`）: 手動モードで指定サブタスクのみ実行

## モード
途中でユーザーに何も聞かない。ただし**実装を続けられない事態（未依頼の handoff・implementer の blockers・最終テストの失敗継続）では止まる** — 推測で埋めると誤った実装がそのまま積み上がるため。止まったら中断カードを出し、分岐は呼び出し元に委ねる。

## 用語（前提）
用語の定義は `claude/CLAUDE.md`「用語集」に従う。特にこのスキルでは：
- **フェーズ = 大タスク = ブランチ = 1 PR**。tasks.md は大タスク（1., 2., ...）を 1 フェーズに 1:1 で対応させて出力する。複数フェーズ = stacked PR。
- 1 回の `/impl` 呼び出しが扱うのは**単一フェーズ（＝単一の大タスク）**のみ。マルチフェーズは orchestrator が `/impl <feature> p1`, `/impl <feature> p2`, ... と別々に呼ぶ。
- タスクの分割・粒度は **tasks の責務**。impl は tasks.md に**書かれたとおりに実装する**。大タスクが大きすぎても impl 側で分割しない（それは tasks がおかしいということなので、`/tasks` を編集モードで再入して直す）。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`（feature）が未指定なら「使い方: /impl <feature> [pN|task-numbers]」を表示して終了
- フェーズ／手動タスク番号を確定する

### Step 2: コンテキスト収集（メインが軽量に実施）
実装のためではなく**配布と最終確認のため**に、最小限だけ集める。**ブランチを切る前に行う**（ここで止まる場合、空のブランチを残さない）。

- `.specs/<feature>/tasks.md` — 対象フェーズのサブタスク一覧・完了条件・`_Requirements:_`・`_Depends:_`
- **他 PJ への handoff 依存** — 対象フェーズのタスクの `_Depends:_` に `H<n>`（`## 他 PJ への handoff` の項目）があり、それが未チェック（`[ ]`）なら**別 PJ の変更待ちで実装できない**。配布せず中断する（`/handoff` で依頼を投げる必要がある）。`H<n>` はコーディングタスクではないので implementer には渡さない
- テスト・ビルドコマンド（`package.json`, `Makefile`, `go.mod`, `pyproject.toml` などから）
- `git status --porcelain` でベースライン
- **prototype コードの有無** — `git rev-parse --verify <feature>-proto` が通れば、Step 4 で「参照して昇格」を指示する

### Step 3: ブランチ準備（メインが実施）
**PR 運用の有無に関わらず、常にブランチを切る。** 実装を隔離しておけば、途中で捨てる・作り直すのが安全になる。PR を作らない repo でも同じで、その場合は `/sync-to-remote` がデフォルトブランチへ取り込む。

tasks.md のブランチ名ルールに従う：

| 対象 | ブランチ名 | 作成元 |
|---|---|---|
| 単一フェーズ（指定なし） | `<feature>` | デフォルトブランチ |
| フェーズ p1 | `<feature>-p1` | デフォルトブランチ |
| フェーズ pN（N > 1） | `<feature>-pN` | `<feature>-p(N-1)`（stacked） |

**デフォルトブランチから作成する場合:**
```
DEFAULT=$(git remote show origin | sed -n 's/.*HEAD branch: //p')
git fetch origin "$DEFAULT"
git checkout -b <ブランチ名> "origin/$DEFAULT"
```

**pN（N > 1）の場合:** 現在のブランチが `<feature>-p(N-1)` であることを確認してから作成する。一致しなければ中断する（スタックの土台がずれたまま積むと差分が壊れるため）：
> `<feature>-pN` を作成するには `<feature>-p(N-1)` ブランチにいる必要があります。現在のブランチ: `<現在のブランチ名>`

```
git checkout -b <ブランチ名>
```

### Step 4: 実装

**4-1 implementer に配布**

対象フェーズを **1 つの `implementer`（Agent）に丸ごと配布**する。プロンプトに渡すもの：
- feature 名（specs のパスを含む）
- 対象フェーズの番号と、tasks.md から転記したサブタスクの説明・完了条件・`_Requirements:_`・`_Depends:_`
- リポジトリのテスト／ビルドコマンド
- 既存コードの関連パターンの手がかり（あれば）
- prototype がある場合の「参照して昇格」指示（下記）
- 「tasks.md に書かれた順に実装し、git・tasks.md には触れず、報告フォーマットで返す」旨（`implementer` 側にも定義済みだが明示する）

手動モード（タスク番号指定）では、指定サブタスクだけを 1 つの implementer に配布する。

**参照して昇格（`<feature>-proto` が存在する場合のみ）**

prototype 工程が `<feature>-proto` ブランチに動く参考実装を残している。implementer に次を指示する：
- 白紙から書き起こさず、prototype コードを**読んで流用**する。参照は**読み取り専用の git** で行う（ブランチ切り替え・作業ツリー変更をする git 操作は implementer に禁止されているため使わない）：
  - ファイル一覧: `git diff --stat $(git merge-base HEAD <feature>-proto) <feature>-proto`
  - 中身の参照: `git show <feature>-proto:<path>`
  - 流用は「参照して自分で書く」＝ `git show` で読んだ内容を Write/Edit で現ブランチに書き起こす（`git checkout -- <path>` 等での取り込みはしない）
- prototype コードは**品質を問わない捨て実装**なので、そのまま写さない。**本番品質に整形して昇格**する（命名・責務分割・エラーハンドリング・型・テスト・本リポジトリのコード規約に合わせる）
- **正典は `design.md`**。prototype コードと design.md が食い違う場合は design.md を優先する
- 対象フェーズのサブタスクに対応する範囲だけを流用・整形する（フェーズ外は取り込まない）

**4-2 報告の取り込み**

`implementer` の報告が返ったら：
1. `変更ファイル`・`タスクごとの確認` を確認する
2. **完了と報告されたサブタスクの `[ ]` を `[x]` に更新**する（`.specs/<feature>/tasks.md`）
3. `blockers` があるサブタスクはチェックせず、「例外処理」に従う
4. `自分で決めた判断` は控えておき、Step 5 の「要確認」に出す

**4-3 最終確認**

- リポジトリ全体のテスト・ビルドを実行する（最終確認はメインが 1 回まとめて行う）
- 対象フェーズの各サブタスクが完了条件・関連要件（`_Requirements:_`）を満たしているか確認する

### Step 5: 出力

次の完了カードを**コードフェンスで囲まず**プレーンテキストで出力して終了する。カードの前後に作業サマリ・所感・補足を足さない。

✅ フェーズ実装完了
<どのフェーズの何タスクを実装したかを 1 行>
- <主要な結果 最大 3 行>
📄 .specs/<feature>/tasks.md（チェックボックス更新）

要確認:
- <仕様に根拠が無く implementer が自分で決めた点>（該当: <タスク番号 / ファイル>）

次の一手:
▶ テストを回す：/test <feature>
▶ 仕様を直す：変更する工程を編集モードで再入（/spec・/design・/tasks）

カードは**やったこと**（`✅` 〜 `📄`）・**要確認**・**次の一手**の 3 ブロックに分ける。混ぜない。

- やったこと: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。変更ファイルの一覧や implementer の報告詳細は列挙せず、tasks.md と git 差分に寄せる。
- 要確認: implementer の報告の `自分で決めた判断` をそのまま出す。仕様に書かれておらず実装側で決めた点（既定値・エラー時の挙動・命名など）を全部挙げる。無ければブロックごと省略する。
- 次の一手: テストが無いリポジトリなら 1 行目を `▶ レビューに進む：/review <feature>` に差し替える（Step 2 でテストコマンドの有無が分かっている）。

**中断時**: 同じブロック構成でヘッダを `⚠ フェーズ実装中断` に差し替える。

- やったこと: 一言サマリに中断理由（未依頼の handoff・blockers・最終テスト失敗など）。途中まで `[x]` を付けたなら 📄 行は残す。
- 次の一手: 復帰コマンド（`▶ 依頼を投げる：/handoff`、`▶ 仕様を直す：/spec・/design・/tasks を編集モードで再入` など）。未完成のまま `/test` へ進む道は出さない。

## 例外処理
- `implementer` が `blockers`（仕様の曖昧さ・設計の穴・大タスクが大きすぎる等）を報告 → メインで判断する。
  - 軽微なら追加指示を添えて `implementer` を再配布する
  - 仕様・設計・タスク分割の問題なら上流工程（`/spec`・`/design`・`/tasks`）への編集モード再入が要るため、中断カードを出して止める（戻し先の判断は呼び出し元に委ねる）
- 最終テストが失敗し続ける場合 → 根本原因を調査し、対象フェーズを `implementer` に再配布して最小限の修正を試みる。それでも通らなければ中断する

## 出力規律
実行中の逐次ナレーション（「〜します」「〜しました」）は出さない（ツール実行はターミナルに表示されるため二重になる）。ただし implementer へ委譲して表示が止まる区間の開始時だけ、次の 1 行を出す（1 区間 1 回。委譲が複数回あれば区間ごとに 1 回）。

⏳ impl: implementer に <n> タスクを委譲中…

## 完了条件
対象フェーズの全サブタスクが `[x]` になり、リポジトリ全体のテスト・ビルドがパスしたら完了。次工程の起動は完了条件に含めない。
