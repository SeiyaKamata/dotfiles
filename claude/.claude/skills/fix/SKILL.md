# 修正スキル

## 役割
テスト失敗、およびコード品質・実装ミスに起因するレビュー NG の**根本原因を診断し、最小限の修正**を行う。実装バグ・テストの期待値ずれは直す。

**新機能の追加や設計変更は行わない** — それが必要なら `/design` を編集モードで再入し、前進カスケードに委ねる。

## 入出力
- **入力**: すべて `.specs/` と実行から得る。会話に依存しない。
  - `.specs/<feature>/test-report.md` — `/test` が書いた失敗レポート
  - `.specs/<feature>/qa-report.md` — `/qa` 起点で呼ばれたとき
  - `.specs/<feature>/bug-report.md` — `/bughunt` 起点で呼ばれたとき
  - `.specs/<feature>/review.md` — `/review` NG 起点で呼ばれたとき
  - `.specs/<feature>/{requirements,design,tasks}.md` — 「実装バグか設計の穴か」を判断する文脈
- **出力**: コード修正。起点になったレポートの `fixed` を `true` に書き換える以外、レポートの判定内容は更新しない。それ以外のファイル成果物は持たない。修正の確認は呼び出し元が起動する下流のスキル `/test` / `/qa` / `/review` に委ねる

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]` は feature 名。未指定なら「使い方: /fix <feature>」を表示して終了

### Step 2: 存在確認

レポートが存在しなければ**中断する**。復帰コマンドはそのレポートを生成するスキル。4種類のレポート共通のルール。

- `test-report.md` → `/test <feature>`
- `bug-report.md` → `/bughunt <feature>`
- `qa-report.md` → `/qa <feature>`
- `review.md` → `/review <feature>`

### Step 3: 着手判定

`fixed` を見る。4種類のレポート共通。

- `fixed: true` → 既に `/fix` が着手済みで、まだ下流の再検証を経ていない状態。下流の再検証とは `/test` / `/qa` / `/review` を指す。重ねて修正すると二重作業になるので、branch/head を見るまでもなく**中断する**。復帰コマンドは Step 2 の対応表と同じ
- `fixed: false` → まだ `/fix` が着手していない、または前回の修正が効かず差し戻された状態。Step 4 へ進む

### Step 4: 対象確認

`test-report.md` / `qa-report.md` / `review.md` は `branch` / `head` をカレントブランチ・`git rev-parse HEAD` と照合する。`bug-report.md` は `branch`/`head` を持たないためこの照合は無い。

不一致は「`/fix` が見ているコードとレポートが指す対象がズレている」ことを意味するので**中断する**。復帰コマンドは Step 2 の対応表と同じ。

レポートの中身は判定・指摘ともそのまま信頼して使う。自分でテストを再実行して観測し直すことはしない。時間の無駄になる。

一致すれば Step 5 へ進む。

### Step 5: 根本原因の診断

レポート・`.specs/<feature>/` の仕様・失敗に関連するコードを読み、原因を分類する。`/bughunt` 起点では `test-report.md` が未生成なので `bug-report.md` を起点にする：

| 分類 | 進み先 |
|---|---|
| **実装バグ** | Step 6 で最小修正 |
| **テストの期待値ずれ** | requirements.md の仕様と照合してから Step 6 で修正 |
| **設計の問題** | **コードを触らず** `/design <feature>` を編集モードで再入する。前進カスケードで design→tasks→impl→test を回し直す |
| **環境・依存関係の問題** | 報告して止まる |

`review.md` 起点では、その「仕様整合性」「CodeRabbit の指摘」のうち成立と判定された指摘を対象に同じ分類を適用する。仕様・設計との不整合はここでも「設計の問題」として扱い、コードを触らず差し戻す。

### Step 6: 最小修正
特定した原因に対し、**問題を解消する最小限の変更のみ**を加える。新機能・設計変更・リファクタは行わない。

修正を適用したら、Step 3 で読んだ起点のレポートの `fixed` を `true` に書き換える。**判定内容・他のフィールドは変更しない**。これが `/fix` の唯一のレポート更新。

**修正後の確認はここでは行わない。**

### Step 7: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### fix 完了
<原因と修正結果を 1 行>
- <修正内容 最大 3 行>

### 要確認
- <仕様に根拠が無く判断で決めた修正> — 該当: <ファイル>

### 次の一手
- テストで再ゲート: `/test <feature>`
```

カードは**やったこと**・**要確認**・**次の一手**の 3 ブロックに分ける。混ぜない。

- やったこと: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**とし、無ければ行ごと省略する。何をどう直したか、原因の分類・修正した箇所を載せる。診断の詳細・失敗の内訳は起点のレポート `test-report.md` 等に寄せる。fix は**ファイル成果物を持たない**ので生成物の行は出さない。
- 要確認: 期待値ずれをどちらに寄せたか、仕様に書かれていない挙動を決め打ちした箇所などを挙げる。無ければブロックごと省略する。
- 次の一手: **診断結果は確定しているので該当する 1 行だけ**を出す。設計が原因でコードを触らなかった場合は `- 設計を直す: /design <feature>` に差し替える。

**中断時**: 同じブロック構成でヘッダを `### fix 中断` に差し替える。

- やったこと: 一言サマリに中断理由を書く。環境や依存の問題、レポートが存在しない、対象がズレている、`fixed: true` で二重着手、などが該当する。
- 次の一手: 復帰コマンド。次工程へ進む道は出さない。レポート起点に応じて次から選ぶ。
  - `- テストを回し直す: /test <feature>`
  - `- QA を回し直す: /qa <feature>`
  - `- レビューを回し直す: /review <feature>`
  - `- 調査し直す: /bughunt <feature>`

## 完了条件
次のいずれかに達したら完了。次工程の起動は完了条件に含めない。

- **実装バグ・テストの期待値ずれ・review 指摘のうち設計以外の原因と診断した場合**: 最小修正を適用した。確認は下流の `/test` / `/qa` / `/review` に委ねる。`/fix` 自身は確認しない
- **設計が原因と診断した場合**: コードを修正せず差し戻しを報告した。診断も成果物
