# バグ調査スキル

## 役割
ユーザーからのバグ報告を起点に、再現確認と原因の一次特定を行い、`.specs/<feature>/bug-report.md` に記録する。
コード修正・回帰テスト・レビュー・コミットは行わず、この工程は何も直さない。

## 判断が割れる点の扱い
症状の聞き取りだけは Step 2 で質問する。
入力が人からしか得られないためで、調査結果や記録内容の確認はしない。
再現できなければ原因の判定を出せていないので、修正工程へ進まず Step 5 の中断カードで追加情報を求める。

## bug-report.md のフォーマット
`branch` / `head` / `count` は持たない。
`/bughunt` は自己修正ループの外にあり、渡すのは疑わしい箇所であってコミットに紐づく判定ではないので、対象同一性の照合も連続失敗のカウントも要らない。

```markdown
---
fixed: false [常に false。/fix が修正を適用したときだけ true に書き換える]
---

# バグ報告: [機能名]

## サマリ
- 症状: [一文]
- 再現可否: [再現OK / 再現できず]
- 期待する挙動: [...]
- 実際の挙動: [...]

## 再現手順
1. [...]

## 疑わしい箇所
[一次特定であり確定診断ではない]
- [path]:[line] — [なぜ疑わしいか]

## 想定する修正範囲
- [触るファイル・関数の見当]

## 回帰テストの観点
- [この症状が再発しないことを確認する観点。実行はしない]
```

## 進め方

### Step 1: 引数の確認
- `$ARGUMENTS[0]` が無ければ「使い方: /bughunt <feature>」を表示して終了

### Step 2: バグ報告の受領

`.specs/<feature>/bug-report.md` があれば前回までの調査結果として読み込み、既に埋まっている項目は聞き直さない。
症状・再現手順・期待する挙動・実際の挙動のうち不足している項目だけを質問して補い、サマリと再現手順の欄に一旦書き出す。
これが調査エージェントの起点になる。

### Step 3: bug-investigator へ委譲

`bug-investigator` サブエージェントを起動し、feature 名を渡す。
調査中の大量のコード読み・コマンド出力をメインコンテキストに載せないためと、調査に強いモデルを当てるため。
bug-investigator は `bug-report.md` の症状を起点に再現を確認し、再現できたらコードを調べて「再現可否 / 疑わしい箇所 / 想定修正範囲 / 回帰テストの観点」を、再現できなければ「再現できず + 必要な追加情報」を返す。

### Step 4: 書き出し

bug-investigator の所見を「bug-report.md のフォーマット」で `.specs/<feature>/bug-report.md` にマージ保存する。
再現できなかった場合は「再現できず」と必要な追加情報を記録し、Step 5 の中断カードで報告する。
追加情報が得られたら Step 3 から再委譲する。

### Step 5: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### バグ調査中断` にし、1 行目に中断理由を書き、`bug-report.md` に記録済みなら生成物の行を残し、次の一手は「追加情報を添えて `/bughunt <feature>`」だけにする。

```markdown
### バグ調査完了
<症状と一次特定した原因を 1 行>

生成物: `.specs/<feature>/bug-report.md`

### 要確認
- <一次特定にとどまり断定できなかった点・他の可能性> — 該当: <path>:<line>
<無ければこのブロックを省略>

### 次の一手
- 原因を確定して直す: `/fix <feature>`
- 本番 tag に当てる: `/hotfix <feature> [tag]`
  <本番稼働中の tag に当てる必要が無いと分かっているなら省く>
- 再調査する: `/bughunt <feature>`
  <調査が甘いと感じたときだけ>
```
