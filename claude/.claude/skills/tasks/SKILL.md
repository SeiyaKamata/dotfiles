# タスク生成スキル

## 役割
設計ドキュメントから、実装者が1〜3時間で完了できる粒度のタスクリストを生成する。

## 入出力
- **入力**:
  - `.specs/<feature>/requirements.md`
  - `.specs/<feature>/design.md`
  - `.specs/<feature>/seed.md` の frontmatter（PR タイトル・ブランチ名の素材。無ければ自動生成にフォールバック）
- **出力**:
  - `.specs/<feature>/tasks.md`（実行主体とタイミングで 3 節に分ける。下記「tasks.md の 3 節」）
  - `.specs/<feature>/qa.md`（受け入れ条件から導出した QA シナリオ。`/qa` が消費する）

## モード
対象で振る舞いが変わる。判定は Step 2 で行い、以降の Step はここを参照する。

| 軸 | 値 | 分かれ目 |
|---|---|---|
| 対象 | 新規作成 / 編集 | `tasks.md` の有無 |

途中でユーザーに何も聞かない。書き切って完了カードを出し、修正は編集モードでの再実行（`/tasks <feature>`）で受ける。判断が割れる点は止まらずに安全側を採り、完了カードの「要確認」に挙げる。

## タスク設計の原則
- **粒度**: 1タスク = 1〜3時間で完了できる単一責任の作業
- **独立性**: 可能な限りタスク間の依存を減らす（実装順と stacked PR が素直になる）。特に**フェーズ境界は縦に割る**（下記「フェーズの割り方」）
- **具体性**: 「何をすれば完了か」が明確であること
- **番号体系**: 大タスク（1., 2., ...＝フェーズ）→ サブタスク（1.1, 1.2, ...）の2階層。人が実施する項目は別番号（`S<n>` / `V<n>`。下記「tasks.md の 3 節」）

## tasks.md の 3 節（実行主体とタイミング）
`tasks.md` は 1 ファイルの中を**実行主体とタイミングで 3 節に分ける**。`/impl` が配布・完了判定に使うのは `## タスク一覧` だけで、人しか実行できない項目は別の節で追跡する。**節の定義はここが正本**（Step 3・Step 4 はここを参照する）。

| 節 | ID | 実行主体 / タイミング | 消費する工程 |
|---|---|---|---|
| `## 事前セットアップ` | `S<n>` | 人が impl 前に済ませる | `/impl` が未チェックを検出して中断。別 PJ 依頼は `/handoff` がチェックを付ける |
| `## タスク一覧` | 大タスク / サブタスク | `implementer` が repo 内のファイル変更で完結する | `/impl` が配布し `[x]` を付ける。**ここだけが impl の完了条件** |
| `## マージ後の検証` | `V<n>` | 人が PR マージ後に実施する | 人がチェックを付ける。`/cleanup` が未チェックを検出して削除前に確認する |

### 振り分けの敷居
項目ごとに「**誰が実行するか**」→「**いつ実行できるか**」の順で判定する：

- **`implementer` が repo 内のファイル変更だけで完結する** → `## タスク一覧` のサブタスク。コード・設定ファイル・ドキュメントの追加や書き換え、テストの追加など
- **人の手作業が要る**（GUI 操作・Secrets や環境変数の登録・外部 SaaS の設定変更・別 PJ への変更依頼） → `## 事前セットアップ` の `S<n>`
- **デフォルトブランチへマージした後でなければ実施・観測できない** → `## マージ後の検証` の `V<n>`。例: デフォルトブランチに定義が無いと発火しないワークフロー（`workflow_run` / `workflow_dispatch`）、マージを起点にした自動処理、本番環境にデプロイして初めて確認できる挙動
- **`design.md` の記述の調査・訂正** → **どの節にも置かない**。これはタスクではなく design 工程の未確定事項なので、`/design` の編集モード再入が必要な旨を Step 5 の「要確認」に挙げる

`## タスク一覧` に人しか実行できない項目を混ぜない。混ざると `/impl` が実装可能なタスクごと巻き添えで止まる（`_Depends:_` 経由）か、`implementer` に手作業が指示として渡る。

### マージ後の検証がフェーズをまたがない
`V<n>` は `_Depends:_` の**参照先にしない**。あるフェーズのサブタスクが別フェーズのマージ後の検証結果を前提にすると、「マージにはフェーズの完了が必要で、完了にはマージが必要」という循環になる。そうなったらフェーズ境界を割り直す（マージ後検証に依存する部分を後続フェーズへ寄せる）。

## フェーズ = 大タスク = 1 PR（重要な前提）
用語の定義は `claude/CLAUDE.md`「用語集」に従う。
- **大タスク（1., 2., ...）は 1 フェーズ = 1 ブランチ = 1 PR に 1:1 で対応させる**。1 つの大タスクを複数フェーズにまたがせない／1 フェーズに複数の大タスクを詰めない。
- 大タスクが複数ある = stacked PR になる（フェーズを積み上げる運用）。
- 大タスクの粒度は「1 PR として無理なくレビューできる大きさ」を目安にする。大きすぎる場合は**大タスク自体を分割**する（実装工程では分割しない前提なので、ここで適切に割っておく）。

## フェーズの割り方（縦割り原則）
**サイズだけでフェーズを割らない。** サイズは 2 番目の基準で、1 番目は「**そのフェーズ単体で人間がレビューできるか**」。stacked PR は各 PR が単体でレビューできて初めて意味を持つ。

### 着地テスト（フェーズ境界の判定基準）
フェーズ候補ごとに「**このフェーズだけを main にマージして、そのまま放置できるか**」を判定する：

- **放置できる → 自立したフェーズ（OK）**: 既存挙動が壊れない、機能が中途半端な状態で止まらない。未使用のコードが増えるだけなら問題ない
- **放置すると main が壊れる／機能が中途半端な状態で止まる → 横割りになっている。割り直す**

「そのフェーズだけでは動かない」ことは問題ではない（動作確認は feature 全体の `/qa` が担う）。問題なのは「**そのフェーズだけでは妥当か判断できない**」状態。後続フェーズを見ないと良し悪しを言えないフェーズは、レビューが実質スキップされる。

### 縦割り / 横割り
- **横割り（避ける）**: 技術レイヤーで割る。例「p1: モデル層 → p2: API → p3: 画面」。p1 は使われないコードの塊になり、単体では妥当性を判断できない
- **縦割り（推奨）**: ユーザーから見た機能の単位で割り、各フェーズがレイヤーを貫通する。例「p1: 一覧の表示 → p2: 絞り込み → p3: 一括操作」。各フェーズが単体で意味を持ちレビューできる

### 例外: 準備フェーズ
以下は機能として縦に貫通しないが、**それ自体で妥当性を判断できる**ので自立フェーズとして認める：
- 依存ライブラリの更新、既存コードの移設・リネーム（挙動を変えない）
- 後続フェーズが乗るスキーマ／基盤の追加のみ（追加だけで既存を壊さない）

判定は同じ着地テストで行う。「この移設は正しいか」「このスキーマは妥当か」が feature 完成前でもレビュアーに判断できるなら OK。

### 縦に割れないとき
設計上どうしても縦に割れない（レイヤー間の依存が強すぎる 等）場合は、**無理に分けず 1 フェーズ（単一 PR）にまとめる**。判断できない PR を 3 本出すより、大きい PR を 1 本出す方がレビューは機能する。

## ブランチ名・PR タイトルルール
命名の形式は `claude/CLAUDE.md`「PR / ブランチ命名」に従う。tasks が**各フェーズ（大タスク）の最終的なブランチ名と PR タイトルを確定して tasks.md に明記**する（impl / sync-to-remote はこれを読む）。

**PR を運用するかどうかは判定しない**（`/tasks` はその層にない）。常にフェーズ＝ブランチ＝1 PR の前提で命名し、PR を作らない repo での着地は `/sync-to-remote` が吸収する（判定条件は `claude/CLAUDE.md`「PR 運用の有無」）。

**ブランチ名**:
- 単一フェーズ = `<feature>`、複数フェーズ = `<feature>-p1`, `-p2`, ...（`pN` を `p(N-1)` にスタック）

**PR タイトル**: `【鎌田QA】<pr_title>[：<フェーズ内容>]（PR<N>/<M>）`
- `<pr_title>`: `seed.md` frontmatter の `pr_title`（例 `[SEC-16005] ATM Auth0移行`）。frontmatter が無い／`pr_title` 空なら設計・フェーズ内容から自動生成したタイトル
- `：<フェーズ内容>`: 総フェーズ数 `M≥2`（stacked）のときだけ付ける。単一 PR では付けない
- `（PR<N>/<M>）`: 常に付ける（`M`＝総フェーズ数。単一なら `（PR1/1）`）
- `【鎌田QA】` は固定 prefix

タスク一覧では各大タスク（フェーズ）の見出し直下に、確定した**ブランチ名（base 付き）と PR タイトル**を明記する。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`（feature）が未指定なら「使い方: /tasks <feature>」を表示して終了

### Step 2: コンテキスト収集とモード判定
読み込む：
- `.specs/<feature>/requirements.md` と `.specs/<feature>/design.md`（必須。無ければ `/spec` `/design` を案内して終了）
- `.specs/<feature>/seed.md` の frontmatter — `pr_title` / `branch_name` / `ticket_key` を PR タイトル・ブランチ名の素材にする（無い／空なら自動生成）
- `.specs/<feature>/tasks.md` / `qa.md`（あれば）

`tasks.md` の有無で分岐する：
- **無い → 新規作成モード**: Step 3 へ。
- **有る → 編集モード**: 既存の `tasks.md` / `qa.md` をベースに、まず現在の `requirements.md` / `design.md` と突き合わせてズレを洗い出す（未マッピングの要件・設計にあるがタスク化されていないコンポーネント など）。ズレとユーザーの変更要望に該当する箇所だけを Step 3 で直す。どちらも無ければ Step 3・Step 4 を飛ばして Step 5 へ。
  - **再起動されたときは白紙に戻さない。** 既存の `tasks.md` / `qa.md` をベースに、渡された変更要望に該当する箇所だけを直す（レビューの指摘を受けて再実行される場合も同じ）。

### Step 3: タスク生成
設計の各コンポーネントを実装タスクにマッピングする：
1. まず大タスク（フェーズ）を決める。**「フェーズの割り方（縦割り原則）」に従い、フェーズ候補ごとに着地テストを通す**（落ちたら割り直す／縦に割れないなら 1 フェーズにまとめる）。各フェーズについて「このフェーズをマージした後に main がどういう状態になるか」を 1 行で言語化し、`着地状態:` として見出し直下に書く。フェーズが確定したら**各フェーズのブランチ名と PR タイトルを確定する**（「ブランチ名・PR タイトルルール」に従う。総フェーズ数 `M` が決まるので `（PR N/M）` もここで確定させる）
2. 各大タスクをサブタスクに分解する
3. 依存関係を確認し、`_Depends:_` に前提タスクを明記して実装順を決める
4. 各サブタスクに「完了条件」を1行で記述する
5. **QA シナリオを導出する** — `requirements.md` の受け入れ条件から `qa.md` のシナリオ（`前提 / 手順 / 期待 / _Requirements: N_`）を起こす。**ローカルでブラウザ操作により検証できる受け入れ条件だけ**をシナリオ化する（下記「QA シナリオの範囲」）
6. **人が実施する項目を洗い出す** — feature の完成に必要だが `implementer` が実行できない項目を、「tasks.md の 3 節」の敷居で `## 事前セットアップ`（`S<n>`）と `## マージ後の検証`（`V<n>`）に振り分ける（下記）

設計に書かれていない判断（依存の切り方・フェーズ境界の取り方など）は止まらずに素直な案を採り、Step 5 の「要確認」に挙げる。

#### 事前セットアップの洗い出し（`S<n>` に何を書くか）
`implementer` には実行できず、**impl より前に人が済ませないと実装が進まない**項目を `## 事前セットアップ` に記録する。人の作業を tasks.md の外へ追い出さない（誰かがやらないと feature は完成しないので、記録から消えると追跡できなくなる）。

- **記録する**: GitHub Secrets や環境変数の登録、外部 SaaS の管理画面での設定変更、クラウドリソースの手動作成、**この作業ディレクトリからは直接編集できない別 PJ の変更**（別 PJ の API/DB スキーマ/共有ライブラリ/画面 の変更が要る、別 PJ 側で先に対応が終わらないとこの PJ の実装・結合ができない）。
- **記録しない**: この PJ 内でファイル変更として完結するもの（`## タスク一覧` へ）、単なる外部 API の呼び出し（相手 PJ に変更を頼まないもの）。
- **書く内容**: 何をするか 1 行・`種別:`・理由・どのフェーズ/大タスクをブロックするか。別 PJ 依頼では実装手順や受け入れ条件を書かない（依頼先の `/spec` が起こす。`/handoff` 参照）。
- **`種別:` は 2 値**。`別 PJ 依頼: <PJ略称>` か `repo 内セットアップ` のどちらかを書く。`/handoff` は前者だけを自分の消費対象として拾うので、値を崩さない。
- ブロックされる大タスク/サブタスクの `_Depends:_` に `S<n>` を含め、セットアップ未完了のまま着手しないようにする。
- 人の事前作業が無ければこの見出しは省略してよい。

#### マージ後の検証の洗い出し（`V<n>` に何を書くか）
デフォルトブランチへマージした後でなければ実施・観測できない確認を `## マージ後の検証` に記録する。`/impl` は読まないので完了条件を妨げず、記録は `tasks.md` に残るので追跡できる。

- **記録する**: デフォルトブランチに定義が無いと発火しないワークフローの実行確認、マージを起点にした自動処理の結果確認、`qa.md` のローカル QA では検証できないがマージ後なら確認できる受け入れ条件（下記「QA シナリオの範囲」）。
- **記録しない**: マージ後にも検証できないもの（実時間の経過待ち・本番専用インフラ依存など）は `qa.md` の `## ローカル QA 対象外` に残す。
- **書く内容**: 何を確認するか 1 行・`対象フェーズ:`（どのフェーズのマージ後に実施するか）・手順・期待（合格と判定できる結果）・`_Requirements:_`。
- **`対象フェーズ:` は `## タスク一覧` に存在する大タスク番号を指す**。stacked PR では「どの PR のマージ後か」が引けないと実施できない。
- マージ後にしか確認できないものが無ければこの見出しは省略してよい。

#### QA シナリオの範囲（qa.md に何を書くか）
`qa.md` は `/qa` が `qa-browser`（Playwright）で**ローカル起動したアプリをブラウザ操作して検証する**ためのもの。ローカルのブラウザ操作で確認できることだけをシナリオにする。**受け入れ条件を無理に全網羅しようとしない**（網羅は tasks.md 側の責務）。

- **書いてよい（ブラウザで観測可能）**: 画面遷移・表示内容・フォーム入力と送信結果・バリデーションエラー表示・一覧/詳細の表示・ボタン活性/非活性・トースト/モーダル・権限による画面差分・UI に反映される状態変化。
- **書かない（ローカルのブラウザでは検証できない）**: メール/SMS/プッシュの実送信・外部 API や決済プロバイダの実通信・Webhook 受信・cron/バッチ/スケジュール実行・本番専用インフラや環境変数依存の挙動・実時間の経過待ち（長時間 TTL 等）・DB を直接見ないと分からない副作用・サードパーティアカウントを要する操作。
- **代替できるなら書く**: 上記「書かない」項目でも、UI 上に結果が現れるなら**その UI 表示を期待値**にする（例: 「確認メール送信」→ 実送信ではなく「送信完了メッセージが画面に出る」ことを確認する）。UI に一切現れないものはシナリオから除外する。
- **除外したものは行き先を 2 つに分ける**:
  - **マージ後なら検証できる** → `tasks.md` の `## マージ後の検証` に `V<n>` として記録する（`qa.md` には書かない）。デフォルトブランチに定義が無いと発火しないワークフロー、マージを起点にした自動処理などが該当する
  - **マージ後にも検証できない** → qa.md 末尾の `## ローカル QA 対象外` に理由付きで箇条書きし、検証手段（手動確認 / CI / 別途）を1行添える。実時間の経過待ち・本番専用インフラ依存などが該当する

### Step 4: 書き出し
Step 3 の内容を次のフォーマットで `.specs/<feature>/tasks.md` と `.specs/<feature>/qa.md` に書く（編集モードでは上書き）。ユーザー確認は取らない。

**tasks.md**

```markdown
# 実装タスク: [機能名]

## 事前セットアップ
- [ ] S1. [人が impl 前に何をするか 1 行]
  - 種別: repo 内セットアップ
  - 理由: [なぜ人の手作業が必要か]
  - ブロック対象: [これが終わらないと進めないフェーズ/大タスク]（例: 大タスク1）
- [ ] S2. [依頼先PJ（略称可）に何を依頼するか 1 行]
  - 種別: 別 PJ 依頼: [依頼先PJ（略称可）]
  - 理由: [なぜこの PJ の変更が必要か]
  - ブロック対象: [この依頼が終わらないと進めないフェーズ/大タスク]（例: 大タスク2）

## タスク一覧

- [ ] 1. [大タスク名]
  - ブランチ: `<feature>-p1`（base: `<デフォルトブランチ>`）
  - PR タイトル: `【鎌田QA】<pr_title>：[フェーズ1の内容]（PR1/2）`
  - 着地状態: [このフェーズをマージした後の main の状態を1行で。例「一覧画面が表示できる。絞り込み UI はまだ無い」]
- [ ] 1.1 [サブタスク名]
  - [実装内容の説明]
  - 完了条件: [何をもって完了とするか]
  - _Requirements: 1, 2_

- [ ] 1.2 [サブタスク名]
  - [実装内容の説明]
  - 完了条件: [何をもって完了とするか]
  - _Requirements: 3_

- [ ] 2. [大タスク名]
  - ブランチ: `<feature>-p2`（base: `<feature>-p1`）
  - PR タイトル: `【鎌田QA】<pr_title>：[フェーズ2の内容]（PR2/2）`
  - 着地状態: [このフェーズをマージした後の main の状態を1行で]
- [ ] 2.1 [サブタスク名]
  - _Depends: 1.1, 1.2, S2_
  - 完了条件: [何をもって完了とするか]
  - _Requirements: 4_

## マージ後の検証
- [ ] V1. [マージ後に何を確認するか 1 行]
  - 対象フェーズ: 大タスク1 のマージ後
  - 手順: [どう実施するか]
  - 期待: [合格と判定できる結果]
  - _Requirements: 5_
```

`## 事前セットアップ`:
- `S<n>`: 連番の ID。ブロックされるタスクの `_Depends:_` から参照する。
- `種別:`: `repo 内セットアップ` か `別 PJ 依頼: <PJ略称>` のどちらか。`/handoff` は後者だけを消費対象として拾う。
- チェックボックス: 別 PJ 依頼は `/handoff` が依頼書（seed.md）を書いたら `[x]` に更新する（＝依頼済みの印。相手 PJ 側の完了ではなく「投げた」ことを表す）。それ以外は人が実施して `[x]` を付ける。
- 人の事前作業が無ければこのセクションは省略してよい。

`## マージ後の検証`:
- `V<n>`: 連番の ID。**`_Depends:_` の参照先にしない**（フェーズの完了とマージが循環する）。
- `対象フェーズ:`: `## タスク一覧` に存在する大タスク番号を指す。stacked PR で「どの PR のマージ後か」を引くために必須。
- チェックボックス: 人が実施して `[x]` を付ける。`/impl` の完了条件には含まれない。
- マージ後にしか確認できないものが無ければこのセクションは省略してよい。

**qa.md**

```markdown
# QAシナリオ: [機能名]

## シナリオ一覧
- [ ] S1. <シナリオタイトル>
  - 前提: <開始状態>
  - 手順: 1.<操作> 2.<操作> 3.<操作>
  - 期待: <ブラウザ画面上で観測できる期待結果>
  - _Requirements: <対応する要件番号>_
- [ ] S2. ...

## ローカル QA 対象外
- <ブラウザで検証できない受け入れ条件>（_Requirements: N_）— 検証手段: <手動確認 / CI / 別途>
```

- `S<n>`: 連番のシナリオ ID。`/qa` が `qa-browser` の結果配列とこの ID で対応づける。
- チェックボックス: `/qa` が合否で `[x]`（pass）/`[ ]`（fail のまま）に更新する。
- 各シナリオは requirements.md の受け入れ条件と対応づける。**ローカルのブラウザ操作で検証できるものだけ**を載せ、期待値は必ず画面上で観測できる事象にする。
- ブラウザで検証できない受け入れ条件は `## ローカル QA 対象外` に理由と検証手段付きで記載する。対象外が無ければこの見出しは省略してよい。

書き出しの時点で次を満たす：
- [ ] 全要件がいずれかのタスクにマッピングされている
- [ ] 各タスクに完了条件が書かれている
- [ ] タスクの順序が論理的（依存関係が正しい）
- [ ] サブタスクが適切な粒度（大きすぎ・小さすぎではない）
- [ ] **各フェーズが着地テストを通っている**（そのフェーズだけを main にマージして放置しても、既存挙動が壊れず／機能が中途半端な状態で止まらない）
- [ ] **各フェーズが単体でレビュー可能**（後続フェーズを見ないと妥当性を判断できないフェーズが無い＝レイヤーでの横割りになっていない。横割りなら縦に割り直す／割れないなら 1 フェーズにまとめる）
- [ ] 各フェーズ（大タスク）に `着地状態:` が 1 行書かれている
- [ ] 各フェーズに `ブランチ:`（base 付き）と `PR タイトル:` の行があり、`claude/CLAUDE.md`「PR / ブランチ命名」の形式どおりで `（PR N/M）` の M が総フェーズ数と一致している
- [ ] `qa.md` の各シナリオがローカルのブラウザ操作だけで検証できる（実送信・外部通信・バッチ等を含まない）
- [ ] ブラウザで検証できない受け入れ条件を、マージ後に検証できるなら `V<n>` へ、できないなら `## ローカル QA 対象外` へ逃がしてある
- [ ] **`## タスク一覧` の各サブタスクが `implementer` の repo 内ファイル変更だけで完結する**（人の手作業・マージ後の確認が混ざっていない）
- [ ] 人が impl 前に済ませる項目を `## 事前セットアップ` に `S<n>` で洗い出し、`種別:` が 2 値のどちらかで、ブロックされるタスクの `_Depends:_` から参照してある（該当があれば）
- [ ] 各 `V<n>` に `対象フェーズ:` と `期待:` があり、`対象フェーズ:` が `## タスク一覧` に存在する大タスク番号を指している（該当があれば）
- [ ] **`_Depends:_` に `V<n>` が現れない**（あるフェーズが別フェーズのマージ後検証を前提にしていない）

### Step 5: 出力

次の完了カードを**コードフェンスで囲まず**プレーンテキストで出力して終了する。カードの前後に作業サマリ・所感・補足を足さない。

✅ タスク分解完了
<何フェーズ・何タスクに分解したかを 1 行>
- <主要な結果 最大 3 行>
📄 .specs/<feature>/tasks.md
📄 .specs/<feature>/qa.md

要確認:
- <設計に根拠が無く、こちらの判断で決めた点>（該当: <大タスク番号 / 節名>）

次の一手:
▶ 実装に進む：/impl <feature>
▶ タスクを直す：/tasks <feature>（編集モードで再実行）

カードは**やったこと**（`✅` 〜 `📄`）・**要確認**・**次の一手**の 3 ブロックに分ける。混ぜない。

- やったこと: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。タスクの一覧・フェーズの割り方の根拠は tasks.md に書き、カードには出さない。📄 行は 1 成果物 1 行（行数上限は主要な結果にだけ課す）。
- 要確認: 聞かずに書き切るぶん、**設計に根拠が無いまま決めた判断を全部ここに挙げる**。フェーズ境界の取り方、依存の切り方、QA シナリオから外した受け入れ条件など。**`design.md` の記述の調査・訂正が要ると分かった場合も、どの節にも置かずここに挙げる**（`/design` の編集モード再入が要る旨を添える）。無ければブロックごと省略する（無理に絞らず、有るものは全部出す）。
- 次の一手: `▶ <何をするか>：<コマンド>` の形で、選べる道を全て出す。次スキルは自動起動せず、修正の要否も問わず、ユーザーがどれかを実行するのを待つ。

**中断時**: 同じブロック構成でヘッダを `⚠ タスク分解中断` に差し替える。

- やったこと: 一言サマリに中断理由（`design.md` が無い など）。書き出し前に止まったなら 📄 行は省略する。
- 次の一手: 復帰コマンド（`▶ タスクを作り直す：/tasks <feature>` など）。未完成のタスクのまま `/impl` へ進む道は出さない。

## 完了条件
全要件をカバーするタスクが `.specs/<feature>/tasks.md` に、QA シナリオが `.specs/<feature>/qa.md` に書き出せたら完了。次工程の起動は完了条件に含めない（呼び出し元が判断する）。
