# タスク生成スキル

## 役割
設計ドキュメントから実装タスクを生成する。粒度の基準は下記「タスク設計の原則」に従う。

## 入出力
- **入力**:
  - `.specs/<feature>/requirements.md`
  - `.specs/<feature>/design.md`
  - `.specs/<feature>/tasks.md`、あれば
- **出力**:
  - `.specs/<feature>/tasks.md` — 詳細は下記「tasks.md の 2 節」
  - `.specs/<feature>/qa.md` — 受け入れ条件から導出した QA シナリオ。詳細は下記「QA シナリオの範囲」

## モード
`tasks.md` の有無で、新規作成モードと編集モードのどちらで動くかが決まる。
判定は Step 2 で行い、以降の Step はここを参照する。

| 対象 | 分かれ目 |
|---|---|
| 新規作成 | `tasks.md` が無い |
| 編集 | `tasks.md` がある |

## 判断ポリシー
途中でユーザーに何も聞かない。
書き切って完了カードを出し、修正は編集モードで`/tasks <feature>` を再実行して受ける。
判断が割れる点は止まらずに安全側を採り、完了カードの「要確認」に挙げる。

## タスク設計の原則
- **粒度**: 1タスク = 1〜3時間で完了できる単一責任の作業
- **独立性**: 可能な限りタスク間の依存を減らす。実装順が素直になる
- **具体性**: 「何をすれば完了か」が明確であること
- **番号体系**: 大タスクは 1, 2, ... 、サブタスクは 1.1, 1.2, ... の2階層。人が実施する項目は別番号 `S<n>` を使う。詳細は下記「tasks.md の 2 節」。検証シナリオの `S<n>` / `V<n>` は `qa.md` 側の番号体系で、こことは別。詳細は下記「QA シナリオの範囲」

## tasks.md の 2 節
`tasks.md` は 1 ファイルの中を**実行主体とタイミングで 2 節に分ける**。`/impl` が配布・完了判定に使うのは `## タスク一覧` だけで、人しか実行できない項目は別の節で追跡する。**「やること」だけを持ち、「検証すること」は `qa.md` に置く**。QA シナリオの範囲は下記「QA シナリオの範囲」に従う。**節の定義はここが正本**。Step 3・Step 4 はここを参照する。

| 節 | ID | 実行主体 / タイミング | 消費する工程 |
|---|---|---|---|
| `## 事前セットアップ` | `S<n>` | 人が impl 前に済ませる | `/impl` が未チェックを検出して中断。別 PJ 依頼は `/handoff` がチェックを付ける |
| `## タスク一覧` | 大タスク / サブタスク | `implementer` が repo 内のファイル変更で完結する | `/impl` が配布し `[x]` を付ける。**ここだけが impl の完了条件** |

### 振り分けの敷居
項目ごとに「**誰が実行するか**」→「**いつ実行できるか**」の順で判定する：

- **`implementer` が repo 内のファイル変更だけで完結する** → `## タスク一覧` のサブタスク。コード・設定ファイル・ドキュメントの追加や書き換え、テストの追加など
- GUI 操作・Secrets や環境変数の登録・外部 SaaS の設定変更・別 PJ への変更依頼など、**人の手作業が要る** → `## 事前セットアップ` の `S<n>`
- **検証**、受け入れ条件を満たすかの確認 → タスクではなく `qa.md` 側の QA シナリオ。ローカルで検証できるかデプロイ後でないと検証できないかは「QA シナリオの範囲」の分類に従う
- **`design.md` の記述の調査・訂正** → **どの節にも置かない**。これはタスクではなく design 工程の未確定事項なので、`/design` の編集モード再入が必要な旨を Step 5 の「要確認」に挙げる
- `## タスク一覧` に人しか実行できない項目を混ぜない。混ざると、`_Depends:_` 経由で実装可能なタスクごと `/impl` が巻き添えで止まるか、`implementer` に手作業が指示として渡る

### デプロイ環境QAシナリオを実装の前提にしない
サブタスクの `_Depends:_` は `qa.md` の `## デプロイ環境QAシナリオ` の `V<n>` を**参照先にしない**。サブタスクがデプロイ後の検証結果を前提にすると、「マージには実装の完了が必要で、完了にはマージが必要」という循環になる。詳細は `qa.md` 側の定義を参照。

## 大タスク = 関心のグルーピング
用語の定義は `claude/CLAUDE.md`「用語集」に従う。

- 大タスクは**関心の単位**でまとめる。ユーザーから見た機能の単位、触る対象が同じもの、同じ判断で良し悪しが決まるもの
- **数を合わせる目標を持たない。** 1 つでも 5 つでもよい
- 実装順の制約は `_Depends:_` で表す。大タスクの並び順だけに依存を委ねない

### 単一サブタスクは折り畳む
**サブタスクが 1 つしかない大タスクを作らない。** そのサブタスクを大タスクに昇格させ、完了条件・`_Requirements:_`・`_Depends:_` を大タスクの行に書く。グルーピングする対象が 1 つなら、グループは情報を持たない。

サブタスクを持つ大タスクの行には**詳細を書かない**。完了条件・`_Requirements:_` はサブタスク側に置く。コンテナだけの大タスクに詳細を重複させると、どちらが正かが読み手に分からなくなる。

### 後回しにできるテスト
受け入れ条件に紐づくテストのうち、**コア実装が既に満たしていて後から足せる**ものは `- [ ]*` で書く。`/impl` は既定で実装するが、未完了でも中断せず、`/test` も FAIL の理由にしない。

**テストの書き方、TDD を採るかはここで規定しない。** プロジェクト固有の判断なので `design.md` と `implementer` への品質水準指定で扱う。

## 出力は tasks.md と qa.md だけ
**リモートへの反映に関わるものを一切出力しない**。`/tasks` はその層にない。タイトル・ブランチ名・変更の束ね方はどれも実装後に決まるので、`/sync-to-remote` が実物のコミット列を見て決める。ここで先回りして書くと、実物と食い違ったまま残る。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`、feature が未指定なら「使い方: /tasks <feature>」を表示して終了

### Step 2: コンテキスト収集とモード判定
**読み込む**:
- `.specs/<feature>/requirements.md` と `.specs/<feature>/design.md` — 必須。無ければ `/spec` `/design` を案内して終了
- `.specs/<feature>/tasks.md` と `qa.md` — 既存があれば読む

**モード判定**、`tasks.md` の有無で分岐する:
- **無い → 新規作成モード**: Step 3 へ。
- **有る → 編集モード**: 既存の `tasks.md` / `qa.md` をベースに、まず現在の `requirements.md` / `design.md` と突き合わせてズレを洗い出す。
  未マッピングの要件、設計にあるがタスク化されていないコンポーネント、などが該当する。
  ズレとユーザーの変更要望に該当する箇所だけを Step 3 で直し、白紙に戻さない。どちらも無ければ Step 3・Step 4 を飛ばして Step 5 へ。
  レビューの指摘を受けて再実行される場合も同じ。

### Step 3: タスク生成
設計の各コンポーネントを実装タスクにマッピングする。依存の切り方・大タスクのまとめ方など、設計に書かれていない判断は上記「判断ポリシー」に従う：
1. まずサブタスクを洗い出し、「大タスク = 関心のグルーピング」に従って**関心の単位で大タスクにまとめる**
2. 大タスクごとにサブタスクを並べ、粒度を 1〜3 時間に整える
3. 依存関係を確認し、`_Depends:_` に前提タスクを明記して実装順を決める
4. 各サブタスクに「完了条件」を1行で記述する
5. **QA シナリオを導出する** — `requirements.md` の受け入れ条件から `qa.md` のシナリオを起こす。検証できる環境ごとに
   `## ローカルQAシナリオ` / `## デプロイ環境QAシナリオ` / `## ローカルQA対象外` に振り分ける。詳細は下記「QA シナリオの範囲」
6. **人が事前に実施する項目を洗い出す** — feature の完成に必要だが `implementer` が実行できない事前作業を
   `## 事前セットアップ` に `S<n>` として記録する。詳細は下記

#### 事前セットアップの洗い出し
`S<n>` に何を書くか。`implementer` には実行できず、**impl より前に人が済ませないと実装が進まない**項目を
`## 事前セットアップ` に記録する。人の作業を tasks.md の外へ追い出さない。誰かがやらないと feature は
完成しないので、記録から消えると追跡できなくなる。

- **記録する**: GitHub Secrets や環境変数の登録、外部 SaaS の管理画面での設定変更、クラウドリソースの手動作成、
  **この作業ディレクトリからは直接編集できない別 PJ の変更**。別 PJ の API/DB スキーマ/共有ライブラリ/画面 の
  変更が要る、または別 PJ 側で先に対応が終わらないとこの PJ の実装・結合ができない、が該当する。
- **記録しない**: この PJ 内でファイル変更として完結するものは `## タスク一覧` へ送る。相手 PJ に変更を
  頼まない単なる外部 API の呼び出しも記録しない。
- **書く内容**: 何をするか 1 行・`種別:`・理由・どの大タスク/サブタスクをブロックするか。別 PJ 依頼では
  実装手順や受け入れ条件を書かない。依頼先の `/spec` が起こす。`/handoff` 参照。
- **`種別:` は 2 値**。`別 PJ 依頼: <PJ略称>` か `repo 内セットアップ` のどちらかを書く。`/handoff` は前者だけを自分の消費対象として拾うので、値を崩さない。
- ブロックされる大タスク/サブタスクの `_Depends:_` に `S<n>` を含め、セットアップ未完了のまま着手しないようにする。
- 人の事前作業が無ければこの見出しは省略してよい。

#### QA シナリオの範囲
qa.md に何を書くか。`qa.md` は検証できる環境ごとに節を分ける：

| 節 | ID | 検証環境・タイミング | 消費する工程 |
|---|---|---|---|
| `## ローカルQAシナリオ` | `S<n>` | `/qa` が Playwright を使う `qa-browser` でローカル起動したアプリをブラウザ操作して検証する | `/qa` が結果でチェックを更新する |
| `## デプロイ環境QAシナリオ` | `V<n>` | デフォルトブランチへマージ・デプロイした後でなければ実施・観測できない確認 | デプロイ後の QA 工程が消費する。`/impl` は読まないので完了条件を妨げない |
| `## ローカルQA対象外` | なし | どちらの環境でも検証できない | 記録するだけ。検証手段は手動確認 / CI / 別途に委ねる |

**受け入れ条件を無理に全網羅しようとしない**。網羅は tasks.md 側の責務。

- **`## ローカルQAシナリオ`に書いてよい**: ブラウザで観測可能な内容。画面遷移・表示内容・フォーム入力と送信結果・バリデーションエラー表示・一覧/詳細の表示・ボタン活性/非活性・トースト/モーダル・権限による画面差分・UI に反映される状態変化。
- **ローカルのブラウザでは検証できない**: メール/SMS/プッシュの実送信・外部 API や決済プロバイダの実通信・Webhook 受信・cron/バッチ/スケジュール実行・本番専用インフラや環境変数依存の挙動・長時間TTLなど実時間の経過待ち・DB を直接見ないと分からない副作用・サードパーティアカウントを要する操作。
- **代替できるなら `## ローカルQAシナリオ`に書く**: 上記「検証できない」項目でも、UI 上に結果が現れるなら、その UI 表示を期待値にする。UI に一切現れないものはシナリオから除外する。
- **除外したものは行き先を 2 つに分ける**:
  - **マージ後、デプロイ後に検証できる** → `## デプロイ環境QAシナリオ` に `V<n>` として記録する。デフォルトブランチに定義が無いと発火しないワークフロー、マージを起点にした自動処理などが該当する。書く内容: 何を確認するか 1 行、手順、期待は合格と判定できる結果、`_Requirements:_`。**実施タイミングは書かない**。常に feature 全体がデフォルトブランチへマージされた後に実施するため。個別の変更単位に紐づける欄は持たない
  - **マージ後にも検証できない** → `## ローカルQA対象外` に理由付きで箇条書きし、検証手段は手動確認 / CI / 別途のいずれかを1行添える。実時間の経過待ち・本番専用インフラ依存などが該当する

### Step 4: 書き出し
Step 3 の内容を次のフォーマットで `.specs/<feature>/tasks.md` と `.specs/<feature>/qa.md` に書く。編集モードでは上書きする。

**tasks.md**

```markdown
# 実装タスク: [機能名]

## 事前セットアップ
- [ ] S1. [人が impl 前に何をするか 1 行]
  - 種別: repo 内セットアップ
  - 理由: [なぜ人の手作業が必要か]
  - ブロック対象: [これが終わらないと進めない大タスク/サブタスク]
- [ ] S2. [依頼先PJに何を依頼するか 1 行]
  - 種別: 別 PJ 依頼: [依頼先PJ]
  - 理由: [なぜこの PJ の変更が必要か]
  - ブロック対象: [この依頼が終わらないと進めない大タスク/サブタスク]

## タスク一覧

- [ ] 1. [大タスク名]
- [ ] 1.1 [サブタスク名]
  - [実装内容の説明]
  - 完了条件: [何をもって完了とするか]
  - _Requirements: 1, 2_

- [ ] 1.2 [サブタスク名]
  - [実装内容の説明]
  - 完了条件: [何をもって完了とするか]
  - _Requirements: 3_

- [ ]* 1.3 [後回しにできるテストのサブタスク]
  - [コア実装が既に満たしている受け入れ条件のテスト網羅]
  - _Requirements: 1_

- [ ] 2. [サブタスクが 1 つしかないので大タスクに昇格させた作業]
  - [実装内容の説明]
  - 完了条件: [何をもって完了とするか]
  - _Depends: 1.1, 1.2, S2_
  - _Requirements: 4_
```

`## タスク一覧`:
- **大タスク**: 関心のグルーピング。詳細を書かない条件は上記「単一サブタスクは折り畳む」を参照。
- **`- [ ]*`**: 後回しにできるテストのサブタスク。詳細は上記「後回しにできるテスト」。

`## 事前セットアップ`:
- `S<n>`: 連番の ID。ブロックされるタスクの `_Depends:_` から参照する。
- `種別:`: `repo 内セットアップ` か `別 PJ 依頼: <PJ略称>` のどちらか。`/handoff` は後者だけを消費対象として拾う。
- チェックボックス: 別 PJ 依頼は `/handoff` が依頼書 `seed.md` を書いたら `[x]` に更新する。依頼済みの印であり、相手 PJ 側の完了ではなく「投げた」ことを表す。それ以外は人が実施して `[x]` を付ける。
- 人の事前作業が無ければこのセクションは省略してよい。

**qa.md**

```markdown
# QAシナリオ: [機能名]

## ローカルQAシナリオ
- [ ] S1. <シナリオタイトル>
  - 前提: <開始状態>
  - 手順: 1.<操作> 2.<操作> 3.<操作>
  - 期待: <ブラウザ画面上で観測できる期待結果>
  - _Requirements: <対応する要件番号>_
- [ ] S2. ...

## デプロイ環境QAシナリオ
- [ ] V1. [マージ後に何を確認するか 1 行]
  - 手順: [どう実施するか]
  - 期待: [合格と判定できる結果]
  - _Requirements: 5_

## ローカルQA対象外
- <どちらの環境でも検証できない受け入れ条件> — _Requirements: N_ — 検証手段: <手動確認 / CI / 別途>
```

- `## ローカルQAシナリオ` の `S<n>`: 連番のシナリオ ID。`/qa` が `qa-browser` の結果配列とこの ID で対応づけ、合否に応じて pass なら `[x]`、fail のままなら `[ ]` に更新する。requirements.md の受け入れ条件と対応づけ、**ローカルのブラウザ操作で検証できるものだけ**を載せ、期待値は必ず画面上で観測できる事象にする。
- `## デプロイ環境QAシナリオ` の `V<n>`: 連番の ID。**`_Depends:_` の参照先にしない**。実装の完了とマージが循環するため。**実施タイミングは「feature 全体がデフォルトブランチへマージされた後」**で、個別の変更単位に紐づける欄は持たない。デプロイ後の QA 工程が実施してチェックを付ける。`/impl` の完了条件には含まれない。デプロイ後にしか確認できないものが無ければこのセクションは省略してよい。
- `## ローカルQA対象外`: どちらの環境でも検証できない受け入れ条件を理由と検証手段付きで記載する。対象外が無ければこの見出しは省略してよい。

**完了ゲート:** 次を満たして書き出したか。
- 全要件がいずれかのタスクにマッピングされている
- 各タスクに完了条件が書かれている
- タスクの順序が依存関係として論理的に正しい
- 「タスク設計の原則」（粒度・独立性・具体性）
- 「大タスク = 関心のグルーピング」（単一サブタスクは折り畳む・後回しにできるテスト）
- 「振り分けの敷居」「事前セットアップの洗い出し」
- 「QA シナリオの範囲」（ローカル/デプロイ環境/対象外の振り分け）
- 「デプロイ環境QAシナリオを実装の前提にしない」

### Step 5: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### タスク分解完了
<何個の大タスク・何タスクに分解したかを 1 行>
- <主要な結果 最大 3 行>

生成物:
- `.specs/<feature>/tasks.md`
- `.specs/<feature>/qa.md`

### 要確認
- <設計に根拠が無く、こちらの判断で決めた点> — 該当: <大タスク番号 / 節名>

### 次の一手
- 実装に進む: `/impl <feature>`
- タスクを直す: `/tasks <feature>`
```

カードは 3 ブロックに分ける。**タスク分解完了**、続けて**要確認**、最後に**次の一手**。

- タスク分解完了: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**。無ければ行ごと省略する。
  生成物のパスは見出しブロックの末尾に列挙する。行数上限は主要な結果にだけ課す。
  タスクの一覧・グルーピングの根拠は tasks.md に書き、カードには出さない。
- 要確認: 聞かずに書き切るぶん、**設計に根拠が無いまま決めた判断を全部ここに挙げる**。大タスクのまとめ方、依存の切り方、QA シナリオから外した受け入れ条件など。**`design.md` の記述の調査・訂正が要ると分かった場合も、どの節にも置かずここに挙げる**。`/design` の編集モード再入が要る旨を添える。無ければブロックごと省略する。
- 次の一手: `- <何をするか>: <コマンド>` の形で、選べる道を全て出す。どれを選ぶかは、このカードを受け取った人間や `/orchestrator` の判断に委ねる。

**中断時**: 同じブロック構成で見出しを `### タスク分解中断` に差し替える。

- タスク分解中断: 一言サマリに中断理由。`design.md` が無い、などが該当する。書き出し前に止まったなら生成物の行は省略する。
- 次の一手: 復帰コマンド。`- タスクを作り直す: /tasks <feature>` など。未完成のタスクのまま `/impl` へ進む道は出さない。

## 完了条件
全要件をカバーするタスクが `.specs/<feature>/tasks.md` に、QA シナリオが `.specs/<feature>/qa.md` に書き出せたら完了。
