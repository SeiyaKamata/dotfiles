# 計画スキル

## 役割
要望から、何を作るかの要件、どう作るかの設計、実装するタスク列、確かめるQAシナリオを 1 つの `plan.jsonc` に作る。
人が全体を読んで承認し、`implementer` は担当する `tasks` の 1 要素を読んで実装し、`/qa` は `scenarios.local` を読んで検証する。

要件と設計を同じ文書で同時に動かす。
設計の段階で要件が実コードと合わないと分かったとき、上流の文書へ戻らずその場で直すため。

`repo` `notion_url` `pr_title` `branch_name` `title` は `feature.jsonc` が持つ正本で、`plan.jsonc` には書かない。
`feature.jsonc` が無ければ作り、空のキーを埋める。

## 判断が割れる点の扱い
起動した人が直接答えられる状況かで分ける。

- 人が会話にいるとき: 未確定の分岐を Step 3 で `/grilling` に渡して詰める
- `/orch` や agent から起動されて人がいないとき: `/grilling` を呼ばない。最も素直な解釈を採って進め、採った案と捨てた案を `decisions` に理由付きで書く

どちらでも、特定の 1 行に紐づく判断は該当行の `question` に、紐づかないものは `open_questions` に書く。

## 要件の書き方

### 観点

- ユーザー行動: ユーザーが X をしたとき何が起きるべきか。常に埋める
- エラーケース: 異常系と境界値の振る舞い。常に埋める
- 非機能要件: 性能・セキュリティ・可用性の期待値。影響する変更のときだけ埋め、無ければ Requirement を起こさない

### 型

型は EARS の 5 型で分けるが、文は日本語語順で書く。

| 型 | 書き方 | 目印 |
|---|---|---|
| 常時 | `<振る舞い>` | 矢印なし |
| イベント駆動 | `<イベント>とき → <振る舞い>` | 「とき」 |
| 状態駆動 | `<前提>あいだ → <振る舞い>` | 「あいだ」 |
| オプション機能 | `<機能・条件>の場合 → <振る舞い>` | 「場合」 |
| エラー処理 | `【異常】<トリガー> → <振る舞い>` | `【異常】` |

オプション機能型は、権限・プラン・機能フラグのように恒常的な構成の有無で分岐する要件に使う。
一時的なトリガーなら「とき」、継続する状態変化なら「あいだ」を使う。

### 主体と文

主体ごとに `subjects` の要素を立て、その下に Requirement を並べる。
各行は主語を落として「条件 → 振る舞い」に揃える。
1 つの Requirement の主体は 1 つにし、流れの中で主体が入れ替わるときは主体ごとに分ける。
Requirement 番号は主体をまたいで連番にする。

- 括弧は「あれば」「任意」のような 1〜2 語のラベルだけに使う
- 受け入れ条件の行は、トリガーと結果が観測できる振る舞いだけにする
  - 用語や値の定義は、それを使う振る舞いの行に組み込む
  - 変更しない範囲の宣言は `out_of_scope` に置く
- 1 行に 1 振る舞いだけ書く。同じ条件で結果だけが違う項目に限り 1 行へ畳んでよい
- 1 Requirement は判定の軸が 1 つの塊だけにする。軸が複数なら分ける
- 例示は書かず、条件を言い切る
- 「適切に」「必要に応じて」のような曖昧語は避け、テスト可能な表現にする
- スコープ外に EARS は使わない
- 表は行数にかかわらず `appendix` に置き、要件からは「詳細は付録」と 1 行で参照する

## 設計の判断基準

### 既存を踏襲する
同種の処理が repo に既にあるなら、その構成・命名・レイヤ分け・エラー処理・テストの置き方をそのまま採る。

- 設計を組む前に、近い責務のコードを Grep / Glob で探して踏襲元を特定する
- 逸脱は要件が既存の形で満たせないときだけにし、`deviations` に書く
- 踏襲元が無いときだけ新しく決める
  - repo 全体で優勢なパターンに合わせ、比較した代替案と却下理由を `decisions` に書く

### コンポーネントの境界を明確にする
各コンポーネントの責務と触る場所を決め、隣接するコンポーネントの責務に踏み込まない。
責務が重なるなら、一方に寄せるか 1 つに統合し、その決定を `decisions` に書く。
1 feature は 1 リポジトリに閉じる。別リポジトリの変更が要るなら `setup` の別 PJ 依頼にする。

## タスク分解の原則
- 粒度: 1 タスクは 1 体の `implementer` に渡せる関心の単位にする
  - ユーザーから見た機能の単位、触る対象が同じもの、同じ判断で良し悪しが決まるものをまとめる
  - タスク名は 1 つの関心を表す名詞句にし、「と」で関心が繋がるなら分ける
  - 条件や例外が複数あるだけなら 1 つに畳む
  - 完了の基準は受け入れ条件で、タスクには書き写さず `req` に任せる
  - 数の目標は持たない
- 順序: タスクは番号順に直列で実装されるので、内側のドメインやロジックから、外側の入口や画面の順に振る
  - 1 つのタスクが内側と外側をまたぐなら層で分ける
- テストを書くか TDD を採るかはリポジトリの規約に従う

### 実行主体で分ける
impl の完了条件は `tasks` だけで、人しか実行できない項目は `setup` の `S<n>` で追跡する。
`tasks` に人の作業を混ぜると、`depends` 経由で impl が止まるか、`implementer` に手作業が渡る。

| 項目 | 行き先 |
|---|---|
| コード・設定ファイル・ドキュメント・テストの追加や書き換え | `tasks` のタスク |
| GUI 操作・Secrets や環境変数の登録・外部 SaaS の設定変更・別 PJ への変更依頼 | `setup` |
| 受け入れ条件を満たすかの検証 | `scenarios` |
| 設計の記述の調査・訂正 | どこにも置かず、調べて `summary` `decisions` `deviations` を直す。調べきれなければ `decisions` に推測として書く |

別 PJ への変更依頼は、別 PJ の API・DB スキーマ・共有ライブラリ・画面の変更が要る場合と、別 PJ 側の対応が先に終わらないと結合できない場合を指す。
外部 API を呼ぶだけの場合は含めない。

## シナリオの振り分け

`scenarios` は検証できる環境ごとに 3 つの配列に分け、ID は配列ごとの連番にする。

- `local`: `/qa` がローカル起動したアプリをブラウザ操作して検証する。ID は `Q<n>`
- `deploy`: デフォルトブランチへマージ・デプロイした後でなければ観測できない確認。ID は `V<n>`
- `excluded`: どちらの環境でも検証できず、検証手段を手動確認・CI・別途に委ねるもの。ID なし

振り分けは「ブラウザで観測できるか」で決める。
画面遷移・表示内容・フォームの送信結果・入力エラーの表示は `local` に入れる。
メールの実送信・外部 API の実通信・cron 実行のようにブラウザの外で起きるものでも、結果が UI に現れるならその表示を期待値にして `local` に入れる。
UI に一切現れないものだけを次の 2 つに分ける。

- マージ・デプロイ後になら検証できる: `deploy`
  - マージを起点にした自動処理や、デフォルトブランチでしか発火しないワークフローが該当する
  - 常に feature 全体のマージ後に実施するので、実施タイミングや変更単位との対応は書かない
- マージ後にも検証できない: `excluded`
  - 実時間の経過待ちや、本番専用インフラ依存が該当する

結果が UI に現れるかは `decisions` にある「失敗の可視性」の判断に従う。
受け入れ条件の全網羅は目的にしない。

## plan.jsonc の書き方

### decisions と deviations
人が承認のために読む項目で、`summary` に地の文を 3〜5 文で書き、`decisions` と `deviations` を並べる。
該当が無ければ空配列にする。
1 画面に収め、超えるなら説明を削って決定だけを残す。

- `decisions`: 複数の案から選んだ形。Step 5 の固定チェックリストに該当した項目と、`/grilling` で確定した決定もここ
  - 踏襲元に合わせただけの項目は書かない。踏襲元はタスクの `follows` に出る
  - 固定チェックリストに該当した項目は踏襲でも書き、何が起きると困るかを理由に書く
- `deviations`: 要件の記述から挙動・記録粒度・可視性を変えた点と、踏襲元と違う形にした点
  - 「本来はこうだが、こうする」の文型で揃える

`decision` は読点を使わない 1 文で言い切る。
`reasons` は 1 要素に 1 つの内容だけを書き、捨てた案があれば採らない理由も書く。
確認方法は `confirm` に書く。

調べきれなかったことは、`reasons` に「〜と推測するため」と書き、`confirm` に確認方法を書く。
「〜のため発生しない」のような断言は書かず、確認済みなら根拠を、未確認なら推測の形で書く。
人が確認する項目は `setup` だけに書く。

### facts
設計の前提にした主張と、`/verify` が返した確認の種類を並べる。
確認の種類は、実データ、コード、未検証のどれかで、コードなら `path:行` を添える。
未検証の主張を前提にした設計は、`decisions` に推測として書く。

### setup
`to` に依頼先 PJ を書き、repo 内の作業なら空文字にする。
`done` は人が実施してから自分で `true` にする。
ブロックされるタスクは `depends` で `S<n>` を参照する。

### tasks
`implementer` が repo 内のファイル変更で完結する項目。
`req` `depends` `follows` `touch` は、該当が無ければ省く。

- `touch` は 1 ファイル 1 要素で書き、手順やコードは書かない
  - `kind` は `N` 新規、`M` 変更、`D` 削除
  - 触るシンボルがあれば `symbols` に 1 シンボル 1 要素で書く。シンボル名は調査に基づく予定で、実装で変わってよい
- `depends` が参照できるのは `S<n>` だけ
  - タスクの前後関係は番号順で表す
  - `scenarios.deploy` の `V<n>` を前提にすると、マージにも完了にも相手が要る循環になる
- `details` は、狙いの文だけでは `implementer` が迷う作業があるときに限って書く
  - 判断・付録・要件に書いてあることと、狙いの言い換えは書かない
- `done` は、`implementer` の完了報告を受けて `/impl` が `true` にする

### appendix
複数のタスクが共有する型・テーブル・API の受け口・画面の入出力と、擬似コードと、要件から参照する表を、決まった形だけで書く。
共有する形があるなら必ず置く。
内側のタスクが実装し、外側のタスクが呼ぶ契約として、実装より先に固定する。
理由や比較は書かず、表題ごとに節を分ける。
単一のタスクの中で決まる形はそのタスクの細部に書く。
図にするなら Mermaid で、ノード ID は英数字とアンダースコアだけにし、ラベルに `()` `[]` `"` `/` `@` を含めない。

## plan.jsonc のフォーマット
`implementer` と `/qa` と後続の skill が読む計画と、人が読む HTML の元データを兼ねる。
`$CLAUDE_WORK_DIR/plan.jsonc` に上書きする。
書式の誤りと、全 Requirement がいずれかのタスクの `req` に現れているかは、書いた直後にフックが指摘して返す。
`question` は判断で埋めたときだけ採った解釈と理由を書き、無ければ空文字にする。
検討経緯は書かず、決まったことだけを書く。

## 進め方

### Step 1: 開始 Step の判定

- `$CLAUDE_WORK_DIR/plan.jsonc` が有る: 読み、Step 9 へ進む
- 無く、`$CLAUDE_WORK_DIR/feature.jsonc` が有る: `title` と `memo` を要望の材料にする
- どちらも無く、会話文脈に要望も無い: 「使い方: /plan <要望>」を表示して終了する

### Step 2: 要件の下書きと未確定の分岐の列挙

out-of-scope を列挙し、in-scope の項目だけを Requirement に起こす。
in-scope は列挙しない。
続けて、まだ決まっていない分岐を箇条書きで並べる。
並べること自体は無条件でやる。

### Step 3: 未確定の分岐を詰める

分岐が 1 件以上あり、人が会話にいるなら `/grilling` を呼んで分岐の一覧を渡す。
確定した決定と捨てた枝を受け取り、`decisions` に反映する。

分岐が 0 件、または人がいないときは呼ばない。
人がいないときは「判断が割れる点の扱い」に従い、暫定で決めて進む。
取り返しがつかないもの、つまり顧客への出し方・お金・外部への公開と、本人しか知らない事実は暫定で決めず、`open_questions` に書く。

### Step 4: 前提の事実確認

設計の前提になる事実を主張として並べ、`/verify` で確かめる。
対象は次のとおり。

- 踏襲元になる既存コードと、同じことをする既存の仕組みの有無
- 別 PJ の実装状況。`requirements` に「実装済み」のような記載があるもの
- 環境変数と設定値の投入先
- 要件が前提にしている API・権限・データの実在

結果を `facts` に書く。
食い違いは該当タスクの細部に書き、要件の修正要否を `deviations` に出す。
未検証は `decisions` に推測として書く。

### Step 5: 設計

「設計の判断基準」に従って踏襲元とコンポーネント境界を決める。

- 既存機能の拡張: 統合ポイントを Grep で洗い、周辺の実装の形に合わせる。新しい層や命名体系は持ち込まない
- 新規機能: repo 内に近い責務のコードを探し、無いことを確認してからパターンや依存ライブラリを調べる
  - 必要なら WebSearch を使い、ライブラリは repo に既に入っているものを優先する

組んだ設計に次を、要件に書かれていなくても確認する。
該当したものは `decisions` に書き、該当しなければ何も書かない。

- テナント / 認可スコープ: 親の ID をスコープとして受け取っているのに、子のクエリでその条件を付けずに引いていないか
  - ジョブ引数やキュー経由の値は後から再実行されうるので、実行時の整合も見る
- リトライの有無: 例外の catch や握り潰しでフレームワークのリトライを殺していないか
- 失敗の可視性: 処理は成功と表示されたのに、実際には何も実行されていない経路が無いか
  - 結果が履歴やログに残らない設計は特に見る
- 非可逆な操作: 削除・外部送信・課金・マイグレーションを含むか
- 新規依存の追加: repo にまだ無いライブラリや外部サービスを持ち込むか
- 宣言とコードの食い違い: 参照しないと宣言したデータを、クエリの `includes` / `select` / join に残していないか

### Step 6: タスク分解とシナリオ導出

「タスク分解の原則」に従って、設計の各コンポーネントを関心の単位でタスクにまとめ、内側から外側の順に番号を振る。
「実行主体で分ける」で `setup` 行きの項目を `S<n>` として起こし、ブロックされるタスクの `depends` に足す。

続けて受け入れ条件から `scenarios` を導出する。
手順に書く画面と操作の手がかりは、`appendix` の画面に関する記述を使い、無ければ要件が触る既存の画面を Grep / Glob で探す。
振り分けは「シナリオの振り分け」に従い、各シナリオに対応する要件番号を `requirements` に書く。

### Step 7: 書き出し

Step 2〜6 の内容を「plan.jsonc のフォーマット」で `$CLAUDE_WORK_DIR/plan.jsonc` に書く。

続けて `$CLAUDE_WORK_DIR/feature.jsonc` のメタを揃える。
`feature.jsonc` が無ければ、次の 5 キーだけで新規に作る。
有れば、既存のキーは残し、空のキーだけを埋める。
- `repo`: 今いる worktree の `git rev-parse --path-format=absolute --git-common-dir` の basename
- `title`: 日本語の 20 字以内の名詞句
- `branch_name`: 英小文字・数字・ハイフンだけの `<type>/<短い英語の説明>`。`title` と要件の内容から決める
- `pr_title`: 固定 prefix `【鎌田QA】` で始める。指定があればその文字列の前に付け、prefix が既にあれば足さず、無ければ `【鎌田QA】<title>`
- `notion_url`: 材料に無ければ空文字

### Step 8: 点検

書き出した `plan.jsonc` が次を満たしているか見直し、外れていれば直す。
- 共有する形が `appendix` に、`implementer` が推測せずに書ける具体度で書かれている
- タスクの番号順が、内側から外側の順になっている
- 各シナリオの期待がブラウザ画面上で観測できる形になっている
- 「要件の書き方」「設計の判断基準」「タスク分解の原則」「plan.jsonc の書き方」「Step 5 の固定チェックリスト」を満たしている

### Step 9: 提示

`open "$CLAUDE_WORK_DIR/plan.html"` で HTML を開く。
`open_questions`、`decisions`、`deviations` の各項目を 1 行ずつ並べて出力する。

### Step 10: 要確認と判断とコメントの議論

未解決の要確認、`decisions`、`deviations`、または未対応のコメントを 1 件選ぶ。
未対応のコメントは、`$CLAUDE_WORK_DIR/comments.jsonc` の `comments` のうち、`file` が `plan.html` で `status` が `open` のもの。

項目はユーザーに尋ねる。
コメントは、`quote` が指す箇所に本文の意図を反映し、判断が割れるときだけユーザーに尋ねる。
決まったら `plan.jsonc` の該当箇所を直し、Step 8 の点検をする。
要件の行を直したときは、その行の `question` を空文字にする。
コメントを反映したら、そのコメントの `status` を `done` にする。
`done` が `true` のタスクは番号と本文を変えない。
ユーザーが直したい点を直接伝えたときも、同じ手順で反映する。

### Step 11: 出力

次を出して終了する。
- 結果: 要件・設計・シナリオを確定した。シナリオはローカル・デプロイ環境・対象外の件数を添える
- 詳細: `$CLAUDE_WORK_DIR/plan.html`
- 次の一手: `/impl`
