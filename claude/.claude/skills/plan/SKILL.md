# 実装計画スキル

## 役割
要件から、`implementer` が迷わずコードを書けるレベルの技術設計と、それを実装するタスク列を作る。
人が全体を読んで承認し、`implementer` は担当する `tasks` の 1 要素を読んで実装する。

## 判断が割れる点の扱い
Step 2〜6 では、ユーザーに質問も承認要求もせず、`plan.jsonc` の書き出しまで走り切る。
判断が割れる点は最も素直な案を採り、採った案と捨てた案を `decisions` に理由付きで書く。
人は Step 7 の一覧を見て、Step 8 で詰める。

## 設計の判断基準

### 既存を踏襲する
同種の処理が repo に既にあるなら、その構成・命名・レイヤ分け・エラー処理・テストの置き方をそのまま採る。

- 設計を組む前に、近い責務のコードを Grep / Glob で探して踏襲元を特定する
- 逸脱は要件が既存の形で満たせないときだけにし、`deviations` に書く
- 踏襲元が無いときだけ新しく決める
  - repo 全体で優勢なパターンに合わせ、比較した代替案と却下理由を `decisions` に書く

### コンポーネントの境界を明確にする
各コンポーネントの責務と触る場所を決め、隣接するコンポーネントの責務に踏み込まない。
責務が重なるなら、一方に寄せるか 1 つに統合し、その決定を `decisions` に書く。
1 feature は 1 リポジトリに閉じる。別リポジトリの変更が要るなら `setup` の別 PJ 依頼にする。

## タスク分解の原則
- 粒度: 1 タスクは 1 体の `implementer` に渡せる関心の単位にする
  - ユーザーから見た機能の単位、触る対象が同じもの、同じ判断で良し悪しが決まるものをまとめる
  - タスク名は 1 つの関心を表す名詞句にし、「と」で関心が繋がるなら分ける
  - 条件や例外が複数あるだけなら 1 つに畳む
  - 完了の基準は受け入れ条件で、タスクには書き写さず `req` に任せる
  - 数の目標は持たない
- 順序: タスクは番号順に直列で実装されるので、内側のドメインやロジックから、外側の入口や画面の順に振る
  - 1 つのタスクが内側と外側をまたぐなら層で分ける
- テストを書くか TDD を採るかはリポジトリの規約に従う

### 実行主体で分ける
impl の完了条件は `tasks` だけで、人しか実行できない項目は `setup` の `S<n>` で追跡する。
`tasks` に人の作業を混ぜると、`depends` 経由で impl が止まるか、`implementer` に手作業が渡る。

| 項目 | 行き先 |
|---|---|
| コード・設定ファイル・ドキュメント・テストの追加や書き換え | `tasks` のタスク |
| GUI 操作・Secrets や環境変数の登録・外部 SaaS の設定変更・別 PJ への変更依頼 | `setup` |
| 受け入れ条件を満たすかの検証 | どこにも置かない |
| 設計の記述の調査・訂正 | どこにも置かず、調べて `summary` `decisions` `deviations` を直す。調べきれなければ `decisions` に推測として書く |

別 PJ への変更依頼は、別 PJ の API・DB スキーマ・共有ライブラリ・画面の変更が要る場合と、別 PJ 側の対応が先に終わらないと結合できない場合を指す。
外部 API を呼ぶだけの場合は含めない。

## plan.jsonc の書き方

### decisions と deviations
人が承認のために読む項目で、`summary` に地の文を 3〜5 文で書き、`decisions` と `deviations` を並べる。
該当が無ければ空配列にする。
1 画面に収め、超えるなら説明を削って決定だけを残す。

- `decisions`: 複数の案から選んだ形。Step 3 の固定チェックリストに該当した項目もここ
  - 踏襲元に合わせただけの項目は書かない。踏襲元はタスクの `follows` に出る
  - 固定チェックリストに該当した項目は踏襲でも書き、何が起きると困るかを理由に書く
- `deviations`: 要件の記述から挙動・記録粒度・可視性を変えた点と、踏襲元と違う形にした点
  - 「本来はこうだが、こうする」の文型で揃える

`decision` は読点を使わない 1 文で言い切る。
`reasons` は 1 要素に 1 つの内容だけを書き、捨てた案があれば採らない理由も書く。
確認方法は `confirm` に書く。

調べきれなかったことは、`reasons` に「〜と推測するため」と書き、`confirm` に確認方法を書く。
「〜のため発生しない」のような断言は書かず、確認済みなら根拠を、未確認なら推測の形で書く。
人が確認する項目は `setup` だけに書く。

### setup
`to` に依頼先 PJ を書き、repo 内の作業なら空文字にする。
`done` は人が実施してから自分で `true` にする。
ブロックされるタスクは `depends` で `S<n>` を参照する。

### tasks
`implementer` が repo 内のファイル変更で完結する項目。
`req` `depends` `follows` `touch` は、該当が無ければ省く。

- `touch` は 1 ファイル 1 要素で書き、手順やコードは書かない
  - `kind` は `N` 新規、`M` 変更、`D` 削除
  - 触るシンボルがあれば `symbols` に 1 シンボル 1 要素で書く。シンボル名は調査に基づく予定で、実装で変わってよい
- `depends` が参照できるのは `S<n>` だけ
  - タスクの前後関係は番号順で表す
  - `qa.jsonc` の `V<n>` を前提にすると、マージにも完了にも相手が要る循環になる
- `details` は、狙いの文だけでは `implementer` が迷う作業があるときに限って書く
  - 判断・付録・要件に書いてあることと、狙いの言い換えは書かない
- `done` は、`implementer` の完了報告を受けて `/impl` が `true` にする

### appendix
複数のタスクが共有する型・テーブル・API の受け口・画面の入出力と、擬似コードを、決まった形だけで書く。
共有する形があるなら必ず置く。
内側のタスクが実装し、外側のタスクが呼ぶ契約として、実装より先に固定する。
理由や比較は書かず、表題ごとに節を分ける。
単一のタスクの中で決まる形はそのタスクの細部に書く。
図にするなら Mermaid で、ノード ID は英数字とアンダースコアだけにし、ラベルに `()` `[]` `"` `/` `@` を含めない。

## plan.jsonc のフォーマット
`implementer` と後続の skill が読む計画と、人が読む HTML の元データを兼ねる。
`.specs/plan.jsonc` に上書きする。
書式の誤りと、全 Requirement がいずれかのタスクの `req` に現れているかは、書いた直後にフックが指摘して返す。

```jsonc
{
  "summary": "[何をどう作るかを 3〜5 文で]",
  "decisions": [
    { "decision": "[選んだ形]", "reasons": ["[理由]"], "confirm": "" }
  ],
  "deviations": [
    {
      "decision": "要件 [番号] は[元の記述]だが、[採った形]にする",
      "reasons": ["[理由]"],
      "confirm": "[確認方法。未確認のときだけ。無ければ空文字]"
    }
  ],
  "setup": [
    {
      "id": "S1",
      "title": "[人が impl 前に何をするか 1 文。実装手順や受け入れ条件は書かない]",
      "to": "[依頼先 PJ。repo 内の作業なら空文字]",
      "reason": "[なぜ人の手作業か。なぜその PJ の変更が必要か]",
      "done": false
    }
  ],
  "tasks": [
    {
      "id": 1,
      "title": "[タスク名]",
      "done": false,
      "req": [1, 2],
      "depends": ["S2"],
      "follows": "[形を合わせる既存コードのパス。無ければ空文字]",
      "touch": [
        {
          "kind": "M",
          "path": "path/to/file",
          "note": "",
          "symbols": [
            { "kind": "N", "name": "symbol", "note": "[追加するものの一言]" },
            { "kind": "M", "name": "symbol", "note": "[変更点の一言]" }
          ]
        },
        { "kind": "N", "path": "path/to/new_file", "note": "[役割の一言]", "symbols": [] }
      ],
      "goal": "[このタスクで何を達成するかを 1〜2 文で]",
      "details": ["[迷う作業の細部。1 要素に 1 つの振る舞い]"]
    }
  ],
  "appendix": [
    {
      "title": "[表題]",
      "lines": ["[共有する型・テーブル・API の受け口・画面の入出力、または擬似コードを 1 行ずつ]"]
    }
  ]
}
```

## 進め方

### Step 1: 開始条件の確認と分岐

`.specs/requirements.jsonc` が無ければ `/spec` を案内して終了する。
`.specs/plan.jsonc` が既に有れば、`plan.jsonc` と `requirements.jsonc` を読み、Step 7 へ進む。

### Step 2: 踏襲元と設計の前提の確定

「設計の判断基準」に従って踏襲元を探し、コンポーネント境界を決める。

- **既存機能の拡張**: 統合ポイントを Grep で洗い、周辺の実装の形に合わせる。新しい層や命名体系は持ち込まない
- **新規機能**: repo 内に近い責務のコードを探し、無いことを確認してからパターンや依存ライブラリを調べる
  - 必要なら WebSearch を使い、ライブラリは repo に既に入っているものを優先する

設計の前提になる repo 外の事実は、設計の前に裏取りする。

- **別 PJ の実装状況**: `requirements.jsonc` に「実装済み」のような記載があれば、その PJ のデフォルトブランチのコードを Read / Grep で確認する
  - `mkworktree <bare repo> <リポジトリ名>-<今の worktree のディレクトリ名>` で展開する。同名の worktree があればそれを使う
  - bare repo は、自分の `git rev-parse --git-common-dir` と同じ親ディレクトリの `<リポジトリ名>`。見つからないか bare でなければ確認を諦め、`decisions` に推測として書く
  - 食い違いは該当タスクの細部に書き、要件の修正要否を `deviations` に出す
- **環境変数・設定値**: ローカルと各デプロイ環境の投入先ファイルを実リポジトリで特定する
  - 「インフラ側で対応」とスコープ外に出す前にデプロイ定義の有無を確認し、特定できなければ `decisions` に推測として書く

### Step 3: 固定チェックリストの適用

組んだ設計に次を、要件に書かれていなくても確認する。
該当したものは `decisions` に書き、該当しなければ何も書かない。

- **テナント / 認可スコープ**: 親の ID をスコープとして受け取っているのに、子のクエリでその条件を付けずに引いていないか
  - ジョブ引数やキュー経由の値は後から再実行されうるので、実行時の整合も見る
- **リトライの有無**: 例外の catch や握り潰しでフレームワークのリトライを殺していないか
- **失敗の可視性**: 処理は成功と表示されたのに、実際には何も実行されていない経路が無いか
  - 結果が履歴やログに残らない設計は特に見る
- **非可逆な操作**: 削除・外部送信・課金・マイグレーションを含むか
- **新規依存の追加**: repo にまだ無いライブラリや外部サービスを持ち込むか
- **宣言とコードの食い違い**: 参照しないと宣言したデータを、クエリの `includes` / `select` / join に残していないか

### Step 4: タスク分解

「タスク分解の原則」に従って、設計の各コンポーネントを関心の単位でタスクにまとめ、内側から外側の順に番号を振る。
「実行主体で分ける」で `setup` 行きの項目を `S<n>` として起こし、ブロックされるタスクの `depends` に足す。

### Step 5: 書き出し

Step 2〜4 の内容を「plan.jsonc のフォーマット」で `.specs/plan.jsonc` に書く。

### Step 6: 点検

書き出した `plan.jsonc` が次を満たしているか見直し、外れていれば直す。
- 共有する形が `appendix` に、`implementer` が推測せずに書ける具体度で書かれている
- タスクの番号順が、内側から外側の順になっている
- 「設計の判断基準」「タスク分解の原則」「plan.jsonc の書き方」「Step 3 の固定チェックリスト」を満たしている

### Step 7: 提示

`decisions` と `deviations` の各項目を 1 行ずつ並べて出力する。

### Step 8: 判断とずれとコメントの議論

`decisions` と `deviations` の未解決の項目か未対応のコメントを 1 件選ぶ。
未対応のコメントは、`.specs/comments.jsonc` の `comments` のうち、`file` が `plan.html` で `status` が `open` のもの。

項目はユーザーに尋ねる。
コメントは、`quote` が指す箇所に本文の意図を反映し、判断が割れるときだけユーザーに尋ねる。
決まったら `plan.jsonc` の該当箇所を直し、Step 6 の点検をする。
コメントを反映したら、そのコメントの `status` を `done` にする。
`done` が `true` のタスクは番号と本文を変えない。
ユーザーが直したい点を直接伝えたときも、同じ手順で反映する。

### Step 9: 出力

次を出して終了する。
- 結果: 判断とずれを確定した
- 詳細: `.specs/plan.html`
- 次の一手: `/scenarios`
