# 実装計画スキル

## 役割
要件から、`implementer` が迷わずコードを書けるレベルの技術設計と、それを実装するタスク列を作る。
人が全体を読んで承認し、`implementer` は担当するタスクの節を読んで実装する。

## 判断が割れる点の扱い
途中でユーザーに質問も承認要求もせず、`plan.md` の書き出しまで走り切る。
判断が割れる点は最も素直な案を採り、採った案と捨てた案を `### 判断` に理由付きで書く。
人は書き出された `plan.md` を読んで直しを指示し、編集モードの `/plan` がそれを反映する。

## 設計の判断基準

### 既存を踏襲する
同種の処理が repo に既にあるなら、その構成・命名・レイヤ分け・エラー処理・テストの置き方をそのまま採る。

- 設計を組む前に、近い責務のコードを Grep / Glob で探して踏襲元を特定する
- 逸脱は要件が既存の形で満たせないときだけにし、`### ずれ` に書く
- 踏襲元が無いときだけ新しく決める。repo 全体で優勢なパターンに合わせ、比較した代替案と却下理由を `### 判断` に書く

### コンポーネントの境界を明確にする
各コンポーネントについて、責務と触る場所、隣接するコンポーネントの責務に踏み込まない範囲を決める。
複数のコンポーネントが同じファイル・同じ責務を担当する重なりがあれば、どちらか一方に寄せるか 1 つに統合し、その決定を `### 判断` に書く。
1 feature は 1 リポジトリに閉じる。別リポジトリの変更が要るなら、それは epic の別 feature か `## 事前セットアップ` の別 PJ 依頼になる。

## タスク分解の原則
- 粒度: 1 タスクは 1 体の `implementer` に渡せる範囲にする
  - タスク名は 1 つの関心を表す名詞句にし、「と」で関心が繋がるならタスクを分ける
  - 同じ作業の中で条件や例外が複数あるだけなら 1 つのタスクに畳む
  - 完了の基準は要件の受け入れ条件で、タスクには書き写さず `Req:` に任せる
- 独立性: タスク間の依存をできるだけ減らす
  - 実装順が素直になる
- テストを書くか、TDD を採るかはリポジトリの規約に従い、feature ごとには書かない

### 実行主体で分ける
タスクは実行主体で 2 節に分ける。
impl の完了条件は `## タスク一覧` だけで、人しか実行できない項目は `## 事前セットアップ` で追跡する。

| 項目 | 行き先 |
|---|---|
| コード・設定ファイル・ドキュメント・テストの追加や書き換え | `## タスク一覧` のタスク |
| GUI 操作・Secrets や環境変数の登録・外部 SaaS の設定変更・別 PJ への変更依頼 | `## 事前セットアップ` の `S<n>` |
| 受け入れ条件を満たすかの検証 | どの節にも置かない |
| 設計節の記述の調査・訂正 | どの節にも置かず、調べて設計節を直す。調べきれなければ `### 判断` に推測として書く |

`## タスク一覧` に人しか実行できない項目を混ぜると、`Depends:` 経由で実装可能なタスクごと impl が止まるか、`implementer` に手作業が指示として渡る。

別 PJ への変更依頼は、この作業ディレクトリからは直接編集できない別 PJ の API・DB スキーマ・共有ライブラリ・画面の変更が要る、または別 PJ 側の対応が先に終わらないと実装・結合できない場合を指す。
相手 PJ に変更を頼まない単なる外部 API の呼び出しは含めない。

### タスク = 関心のグルーピング
- タスクは関心の単位でまとめる
  - ユーザーから見た機能の単位、触る対象が同じもの、同じ判断で良し悪しが決まるもの
- 数を合わせる目標を持たない
  - 1 つでも 5 つでもよい

## plan.md の書き方

### 方針
人が計画を承認するために読む節で、地の文の 3〜5 文の下に 2 つの見出しを置く。
該当が無い見出しは省く。

- `### 判断`: 複数の案から選んだ形。Step 4 の固定チェックリストで該当した項目の扱いもここ
  - 踏襲元に合わせただけの項目は書かない。踏襲元はタスクの `Follows:` に出る
  - ただしチェックリストで該当した項目は踏襲でも書き、理由に何が起きると困るかを書く
- `### ずれ`: 要件の記述から挙動・記録粒度・可視性を変えた点と、踏襲元と違う形にした点。「本来はこうだが、こうする」の文型で揃える

各項目は決定を 1 行目に書き、理由・捨てた案・確認方法は下の段の `-` に書く。
1 行目は読点を使わない 1 文で言い切り、1 行目だけを縦に読めば決定の一覧になるようにする。
下の段は 1 項目に 1 つの内容だけを書き、複数あれば項目を分ける。

調べきれなかったことは、1 行目に決定を書き、下の段に理由として「〜と推測するため」を書き、その下に `確認:` で確認方法を書く。
「〜のため発生しない」「〜に収まる」「実質〜」のような断言は書かず、確認済みなら根拠を、未確認なら推測の形で書く。
調べて分かったことは、使った判断の理由に根拠として書く。
人が確認する項目は `## 事前セットアップ` だけに書く。

1 画面に収める。超えるなら説明を削り、決定だけを残す。
ファイル名・ファイル単位の変更内容は書かない。

### 事前セットアップ
人が impl 前に済ませる項目で、ID は `S<n>`。チェックは人が実施してから自分で付ける。
別 PJ への依頼は `To:` に依頼先 PJ を書き、`To:` が無い項目は repo 内の作業。
ブロックされるタスクは `Depends:` で `S<n>` を参照する。

### タスク一覧
`implementer` が repo 内のファイル変更で完結する項目で、ID は `Task 1`, `Task 2`, ... の 1 階層。
ファイル単位の変更内容は、タスクの細部の `-` にだけ書く。
細部は例外で、狙いの文だけでは `implementer` が迷う作業があるときに限って書く。
判断・付録・要件に書いてあることと、狙いの文の言い換えは細部に書かない。

- タスクのメタ情報のキーは `Req:` `Depends:` `Follows:` の 3 つで、該当が無いキーは書かない
- `Depends:` の参照先にできるのは `S<n>` と他のタスクの番号だけで、`qa.md` の `V<n>` は参照先にしない
  - デプロイ後の検証結果を前提にすると、「マージには実装の完了が必要で、完了にはマージが必要」という循環になる
- 見出しの `[ ]` が完了のチェックボックスで、`implementer` の完了報告を受けて `/impl` が `[x]` にする

### 付録
複数のタスクが共有する型・テーブル・API の受け口・画面の入出力と、擬似コードを、決まった形だけで書く。
理由や比較は書かず、表題ごとに節を分ける。
単一のタスクの中で決まる形は付録に出さず、そのタスクの細部に書く。
データの流れを図にするなら Mermaid で、ノード ID は英数字とアンダースコアだけにし、ラベルに `()` `[]` `"` `/` `@` を含めない。

## plan.md のフォーマット

該当しない節は節ごと省略し、空節を並べない。
ただし `## 方針` と `## タスク一覧` は常に置く。

```markdown
# 実装計画: [機能名]

## 方針
[何をどう作るかを 3〜5 文で]

### 判断
- [選んだ形]
  - [理由。捨てた案があれば、それを採らない理由も]

### ずれ
- 要件 [番号] は[元の記述]だが、[採った形]にする
  - [理由]
- `path/to/file` は[既存の形]だが、[違う形]にする
  - [理由]

## 事前セットアップ
- [ ] S1. [人が impl 前に何をするか 1 文]
  - [なぜ人の手作業が必要か]
- [ ] S2. [依頼先 PJ に何を依頼するか 1 文。実装手順や受け入れ条件は先回りして書かない]
  - To: [依頼先 PJ]
  - [なぜこの PJ の変更が必要か]

## タスク一覧

### [ ] Task 1: [タスク名]
- Req: 1, 2
- Follows: `path/to/file` [このタスクが形を合わせる既存コード。無ければ行ごと省略]

[このタスクで何を達成するかを 1〜2 文で]

- [ファイル単位の変更内容などの細部。要るときだけ 1 項目に 1 つ]

### [ ] Task 2: [タスク名]
- Req: 3
- Depends: 1, S2

[狙いを 1〜2 文で]

## 付録: [表題]
[共有する型・テーブル・API の受け口・画面の入出力、または擬似コードを、決まった形だけで]
```

## 進め方

### Step 1: 開始条件の確認とモード判定

- `$ARGUMENTS[0]` が未指定なら「使い方: /plan <feature>」を表示して終了
- `.specs/<feature>/requirements.md` が無ければ `/spec <feature>` を案内して終了
- frontmatter の `repo` が今いる worktree の `git rev-parse --path-format=absolute --git-common-dir` の basename と違えば、Step 9 の中断カードで「`<repo>` の worktree で叩く」と案内して終了

`.specs/<feature>/plan.md` の有無で分岐する:
- **無い**: 新規作成モード。Step 2 へ
- **有る**: 編集モード。既存 `plan.md` と現在の `requirements.md` を突き合わせ、新要件の未反映・削除された要件の残存のようなズレと変更要望に該当する箇所だけを Step 2〜6 で直す
  - どちらも無ければ Step 2〜8 を飛ばし、Step 9 で「変更なし」と報告して終了
  - タスク節だけに閉じる変更なら Step 5〜6 だけを直す。`[x]` 済みのタスクは番号と本文を変えない

### Step 2: 踏襲元とコンポーネント境界の確定

「設計の判断基準」に従って踏襲元を探し、コンポーネント境界を決める。
踏襲元を探す範囲はモードに応じて変える:
- **編集モード**: 直す箇所の周辺だけ
- **既存機能の拡張**: 統合ポイントを Grep で洗い、その周辺の実装の形に合わせる
  - 新しい層・新しい命名体系は持ち込まない
- **新規機能**: まず repo 内に近い責務のコードを探し、無いことを確認してからアーキテクチャパターン・依存ライブラリを調査する
  - 必要なら WebSearch を使い、ライブラリは repo に既に入っているものを優先する

### Step 3: 外部環境の確認

- **別 PJ の実装状況・挙動**: `requirements.md` に「実装済み」のような記載があれば、その PJ のデフォルトブランチを worktree に展開し、Read / Grep で確認する
  - bare repo は自分の bare repo `git rev-parse --git-common-dir` と同じ親ディレクトリにある `<リポジトリ名>` を採り、`git -C <bare repo> rev-parse --is-bare-repository` が `true` でなければ確認を諦めて `### 判断` に推測として書く
  - `git -C <bare repo> fetch origin` で最新化してから `dest=$(mkworktree <bare repo> <リポジトリ名>-<feature>)` で切る。同名の worktree が既にあればそれを使う
  - 依頼元の作業ツリーは remote に載っているとは限らないので、デフォルトブランチのコードを正とする
  - 食い違いは該当するタスクの細部に書き、`requirements.md` 側の修正要否を `### ずれ` に出す
- **環境変数・設定値の導入**: ローカル・各デプロイ環境の投入先ファイルを実リポジトリで特定してから設計する
  - 「インフラ側で対応」とスコープ外に出す前にデプロイ定義の有無を確認し、特定できなければ `### 判断` に推測として書く

### Step 4: 固定チェックリストの適用

組んだ設計に対して次を、要件に書かれていなくても確認する。
該当したものは `### 判断` に書き、該当しなければ何も書かない。

- **テナント / 認可スコープ**: 親の ID をスコープとして受け取っているのに、子のクエリでその条件を付けずに引いていないか
  - ジョブ引数・キュー経由の値は永続化されて後から再実行されうるので、投入時に整合していても実行時に整合しているとは限らない
- **リトライの有無**: 例外の catch や握り潰しでフレームワークのリトライを殺していないか
  - 殺すなら明示的な決定として `### 判断` に書く
- **失敗の可視性**: 「処理は成功と表示され、実際には何も実行されていない」が成立する経路が無いか
  - 結果が履歴・ログに残らない設計は特に見る
- **非可逆な操作**: 削除・外部送信・課金・マイグレーションを含むか
  - 外部送信はメール・通知・Webhook を含む
- **新規依存の追加**: repo にまだ無いライブラリ・外部サービスを持ち込むか
- **宣言とコードの食い違い**: 設計本文で参照しないと宣言したデータを、クエリ側の `includes` / `select` / join に残していないか

### Step 5: タスクへの分解

設計の各コンポーネントを実装タスクにマッピングする。
1. 作業を洗い出し、「タスク = 関心のグルーピング」に従って関心の単位でタスクにまとめ、「タスク分解の原則」の粒度に整える
2. タスク間の依存関係を確認し、`Depends:` に前提のタスクを明記して実装順を決める

### Step 6: 事前セットアップの洗い出し

「実行主体で分ける」で `## 事前セットアップ` 行きと判定した項目を `S<n>` として起こし、ブロック対象のタスクの `Depends:` に `S<n>` を足す。

### Step 7: 書き出し

Step 2〜6 の内容を「plan.md のフォーマット」で `.specs/<feature>/plan.md` に書く。
編集モードでは上書きする。

### Step 8: 点検

書き出した `plan.md` が次を満たしているか見直し、外れていれば直してから Step 9 へ進む。
- 全 Requirement がいずれかのタスクの `Req:` に現れる
- 共有する形が `## 付録:` に、`implementer` が推測せずに書ける具体度で書かれている
- `Depends:` が循環せず、実装順として成り立つ
- 「設計の判断基準」「タスク分解の原則」「plan.md の書き方」「Step 4 の固定チェックリスト」を満たしている

### Step 9: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### 実装計画中断` にし、1 行目に中断理由を書き、書き出し前なら生成物の行を省き、次の一手は `/plan <feature>` と `/spec <feature>` だけにする。

```markdown
### 実装計画完了
<何を設計し、何個のタスクに分解したかを 1 行>

生成物: `.specs/<feature>/plan.md`

### 次の一手
- QA シナリオを作る: `/scenarios <feature>`
- 計画を直す: `/plan <feature>`
```
