# 実装計画スキル

## 役割
要件から、実装者が迷わずコードを書けるレベルの技術設計と、それを実装するタスク列を作る。
`plan.md` の読み手は、判断を承認する人と、手順を実行する `implementer` の二者で、前半を人が読む節、後半を implementer が読む節に分ける。
実装作業とその前提となる人の作業を扱い、受け入れ条件を満たすかの検証は書かない。

## 判断が割れる点の扱い
このスキルは人と会話しながら進める。
設計でもタスク分解でも判断が割れる点は、書き出す前に地の文で問いを出して応答を待ち、決めたことだけを `plan.md` に書く。
`【要確認】` の付記は使わない。

## 読み手ごとの粒度

前半の `## 方針` `## 影響範囲` は人が読む。
- 判断だけを書く。何を選び、何を捨て、なぜか
- ファイル単位の変更内容を書かない。それは `## タスク一覧` の実装内容に書く
- 2 節を合わせて 1 画面に収める。超えるなら説明を削り、決定だけを残す

後半の `## 事前セットアップ` 以降は implementer が読む。
- 複数の大タスクや複数リポジトリが共有する型・テーブル・API の受け口は `## 付録: <表題>` に決まった形だけで書き、理由や比較を書かない。理由は `## 方針` にある
- 単一の大タスクの中で決まる形は、そのサブタスクの実装内容に書く
- 同じ内容を前半と後半に二度書かない

## 設計の判断基準

### 既存を踏襲する
同種の処理が repo に既にあるなら、その構成・命名・レイヤ分け・エラー処理・テストの置き方をそのまま採る。

- 設計を組む前に、近い責務のコードを Grep / Glob で探して踏襲元を特定する
- 逸脱は要件が既存の形で満たせないときだけにする
  - 踏襲元と違う形にした点と理由を控える
- 踏襲元が無いときだけ新しく決める
  - repo 全体で優勢なパターンに合わせ、比較した代替案とその却下理由を控える

### コンポーネントの境界を明確にする
各コンポーネントについて、責務と触る場所、隣接するコンポーネントの責務に踏み込まない範囲を決め、`## 影響範囲` に書く。
複数のコンポーネントが同じファイル・同じ責務を担当する重なりがあれば、どちらか一方に寄せるか 1 つに統合する。
feature が複数リポジトリにまたがるときは、各コンポーネントが担当するリポジトリも決める。

## 方針の書き方

`## 方針` は人が計画を承認するために読む唯一の節で、次を漏らさず書く。

- 何をどう作るか、何を捨てたか、なぜか
- 要件の記述から挙動・記録粒度・可視性が変わる点。要件は何と書いていて、設計ではどう変えたか
- 踏襲元と違う形にした点。対象・踏襲元のパス・理由
- Step 5 の固定チェックリストで該当した項目と、それをどう扱うか
- 設計が成り立つために置いた前提と、その確認方法

前提は根拠を示さずに影響を打ち消す記述の代わりに置く。
「〜のため発生しない」「〜に収まる」「実質〜」のような断言を書かず、確認済みなら根拠を、未確認なら前提として書く。

| 確認方法 | 使う場面 |
|---|---|
| 実測する | 件数・時間・サイズなど数で決まるもの |
| 該当コードを読む | 既存実装の挙動を前提にしているもの |
| 仕様の持ち主に聞く | 運用・業務上の前提を置いているもの |

## タスク分解の原則
- 粒度: 1 タスクは 1〜3 時間で完了できる単一責任の作業にする
- 独立性: タスク間の依存をできるだけ減らす
  - 実装順が素直になる

### 大タスク = 関心のグルーピング
- 大タスクは関心の単位でまとめる
  - ユーザーから見た機能の単位、触る対象が同じもの、同じ判断で良し悪しが決まるもの
- 数を合わせる目標を持たない
  - 1 つでも 5 つでもよい
- 実装順の制約は `_Depends:_` で表す
  - 大タスクの並び順だけに依存を委ねない

### 複数リポジトリにまたがる feature
`## 影響範囲` にリポジトリを明記した場合、大タスクはリポジトリ境界を跨がない。
各大タスク行に `_Repo: <repo名>_` を付与し、同じリポジトリの大タスクを隣接させる。
番号は feature 全体で連番のままとする。
単一リポジトリの feature では `_Repo:_` を付けない。

### 単一サブタスクは折り畳む
サブタスクが 1 つしかない大タスクを作らない。
そのサブタスクを大タスクに昇格させ、完了条件・`_Requirements:_`・`_Depends:_` を大タスクの行に書く。
グルーピングする対象が 1 つなら、グループは情報を持たない。

サブタスクを持つ大タスクの行には詳細を書かない。
完了条件・`_Requirements:_` はサブタスク側に置く。
コンテナだけの大タスクに詳細を重複させると、どちらが正かが読み手に分からなくなる。

### 後回しにできるテスト
受け入れ条件に紐づくテストのうち、コア実装が既に満たしていて後から足せるものは `- [ ]*` で書く。
`*` 付きは未完了でも feature の完了を妨げない印になる。

テストの書き方、TDD を採るかはリポジトリの規約に従い、feature ごとには書かない。

## タスク節の構成
タスクは実行主体で 2 節に分ける。
impl の完了条件は `## タスク一覧` だけで、人しか実行できない項目は `## 事前セットアップ` で追跡する。

- `## 事前セットアップ`: 人が impl 前に済ませる項目。ID は `S<n>`
- `## タスク一覧`: `implementer` が repo 内のファイル変更で完結する項目。ID は大タスク 1, 2, ... とサブタスク 1.1, 1.2, ... の 2 階層

### 振り分け

| 項目 | 行き先 |
|---|---|
| コード・設定ファイル・ドキュメント・テストの追加や書き換え | `## タスク一覧` のサブタスク |
| GUI 操作・Secrets や環境変数の登録・外部 SaaS の設定変更・別 PJ への変更依頼 | `## 事前セットアップ` の `S<n>` |
| 受け入れ条件を満たすかの検証 | どの節にも置かない |
| 設計節の記述の調査・訂正 | どの節にも置かず、会話で確定させてから設計節を直す |

`## タスク一覧` に人しか実行できない項目を混ぜると、`_Depends:_` 経由で実装可能なタスクごと impl が止まるか、`implementer` に手作業が指示として渡る。

別 PJ への変更依頼は、この作業ディレクトリからは直接編集できない別 PJ の API・DB スキーマ・共有ライブラリ・画面の変更が要る、または別 PJ 側の対応が先に終わらないと実装・結合できない場合を指す。
相手 PJ に変更を頼まない単なる外部 API の呼び出しは含めない。

`_Depends:_` の参照先にできるのは `S<n>` と他のサブタスクだけで、`qa.md` の `V<n>` は参照先にしない。
サブタスクがデプロイ後の検証結果を前提にすると、「マージには実装の完了が必要で、完了にはマージが必要」という循環になる。

## plan.md のフォーマット

該当しない節は節ごと省略し、空節を並べない。
ただし `## 方針` と `## 影響範囲` と `## タスク一覧` は常に置く。
大タスクごとに踏襲元があれば、その大タスクの行に `_踏襲元: path/to/file_` を付ける。
要件とタスクの対応は各サブタスクの `_Requirements:_` で表し、対応表は別に作らない。

```markdown
# 実装計画: [機能名]

## 方針
[何をどう作るか、何を捨てたかを 3〜5 文で。ファイル名は出さない]

- 要件からの変更: [要件は何と書いていて、設計ではどう変えたか。なぜか。無ければ行ごと省略]
- 踏襲元からの逸脱: [対象]。踏襲元は `path/to/file`。[理由。無ければ行ごと省略]
- [固定チェックリストで該当した項目]: [どう扱うか。無ければ行ごと省略]
- 前提: [設計が成り立つために置いた前提]。確認方法: [確認方法。無ければ行ごと省略]

## 影響範囲
- [コンポーネント名]: [責務と、隣のコンポーネントに踏み込まない範囲]。触る場所は [ディレクトリや層の粒度]。複数リポジトリにまたがるときは `リポジトリ: <repo名>` を添える
- [...]

## 事前セットアップ
[人の事前作業が無ければ節ごと省略。チェックは人が実施してから自分で付ける]
- [ ] S1. [人が impl 前に何をするか 1 行]
  - 種別: repo 内セットアップ [別 PJ 依頼: <PJ略称> か repo 内セットアップ の 2 値で、値を崩さない]
  - 理由: [なぜ人の手作業が必要か]
  - ブロック対象: [これが終わらないと進めない大タスク/サブタスク。その行の _Depends:_ にも S1 を含める]
- [ ] S2. [依頼先PJに何を依頼するか 1 行。実装手順や受け入れ条件は先回りして書かない]
  - 種別: 別 PJ 依頼: [依頼先PJ]
  - 理由: [なぜこの PJ の変更が必要か]
  - ブロック対象: [この依頼が終わらないと進めない大タスク/サブタスク]

## タスク一覧

- [ ] 1. [大タスク名]
  - _踏襲元: path/to/file_ [この大タスクが形を合わせる既存コード。無ければ行ごと省略]
- [ ] 1.1 [サブタスク名]
  - [どのファイルに何を書くか。ファイル単位の変更内容はここにだけ書く]
  - 完了条件: [何をもって完了とするか]
  - _Requirements: 1, 2_

- [ ] 1.2 [サブタスク名]
  - [実装内容の説明]
  - 完了条件: [何をもって完了とするか]
  - _Requirements: 3_

- [ ]* 1.3 [後回しにできるテストのサブタスク]
  - [コア実装が既に満たしている受け入れ条件のテスト網羅]
  - _Requirements: 1_

- [ ] 2. [サブタスクが 1 つしかないので大タスクに昇格させた作業]
  - [実装内容の説明]
  - 完了条件: [何をもって完了とするか]
  - _Depends: 1.1, 1.2, S2_
  - _Requirements: 4_
  - _Repo: [repo名]_ [複数リポジトリにまたがる feature のときだけ]
  - _踏襲元: path/to/file_

## 付録: [表題]
[複数の大タスクや複数リポジトリが共有する型・テーブル・API の受け口・画面の入出力を決まった形だけで書く。擬似コードもここ。データの流れを図にするなら Mermaid でノード ID は英数字とアンダースコアだけにし、ラベルに `()` `[]` `"` `/` `@` を含めない。無ければ節ごと省略し、複数あれば表題ごとに節を分ける]
```

## 進め方

### Step 1: 開始条件の確認とモード判定

- `$ARGUMENTS[0]` が未指定なら「使い方: /plan <feature>」を表示して終了
- `.specs/<feature>/requirements.md` が無ければ `/spec <feature>` を案内して終了

`.specs/<feature>/plan.md` の有無で分岐する:
- **無い**: 新規作成モード。Step 2 へ
- **有る**: 編集モード。既存 `plan.md` と現在の `requirements.md` を突き合わせ、新要件の未反映・削除された要件の残存のようなズレと変更要望に該当する箇所だけを Step 2〜7 で直す
  - どちらも無ければ Step 2〜9 を飛ばし、Step 10 で「変更なし」と報告して終了
  - タスク節だけに閉じる変更なら Step 6〜7 だけを直す。`[x]` 済みのタスクは番号と本文を変えない

### Step 2: 踏襲元の特定

「設計の判断基準: 既存を踏襲する」に従って踏襲元を探す。
探す範囲はモードに応じて変える:
- **編集モード**: 直す箇所の周辺だけ
- **既存機能の拡張**: 統合ポイントを Grep で洗い、その周辺の実装の形に合わせる
  - 新しい層・新しい命名体系は持ち込まない
- **新規機能**: まず repo 内に近い責務のコードを探し、無いことを確認してからアーキテクチャパターン・依存ライブラリを調査する
  - 必要なら WebSearch を使い、ライブラリは repo に既に入っているものを優先する

### Step 3: コンポーネント境界の確定

「設計の判断基準: コンポーネントの境界を明確にする」に従って確定する。

### Step 4: 外部環境の確認

- **別 PJ の実装状況・挙動**: `requirements.md` に「実装済み」のような記載があれば、その PJ のデフォルトブランチを worktree に展開し、Read / Grep で確認する
  - bare repo は自分の bare repo `git rev-parse --git-common-dir` と同じ親ディレクトリにある `<リポジトリ名>` を採り、`git -C <bare repo> rev-parse --is-bare-repository` が `true` でなければ確認を諦めて `## 方針` の前提に出す
  - `git -C <bare repo> fetch origin` で最新化してから `dest=$(mkworktree <bare repo> <リポジトリ名>-<feature>)` で切る。同名の worktree が既にあればそれを使う
  - 依頼元の作業ツリーは remote に載っているとは限らないので、デフォルトブランチのコードを正とする
  - 食い違いは該当するサブタスクの実装内容に書き、`requirements.md` 側の修正要否は会話で確認する
- **環境変数・設定値の導入**: ローカル・各デプロイ環境の投入先ファイルを実リポジトリで特定してから設計する
  - 「インフラ側で対応」とスコープ外に出す前にデプロイ定義の有無を確認し、特定できなければ `## 方針` の前提に出す

### Step 5: 固定チェックリストの適用

組んだ設計に対して次を、要件に書かれていなくても確認する。
該当したものは `## 方針` に書き、該当しなければ何も書かない。

- **テナント / 認可スコープ**: 親の ID をスコープとして受け取っているのに、子のクエリでその条件を付けずに引いていないか
  - ジョブ引数・キュー経由の値は永続化されて後から再実行されうるので、投入時に整合していても実行時に整合しているとは限らない
- **リトライの有無**: 例外の catch や握り潰しでフレームワークのリトライを殺していないか
  - 殺すなら明示的な決定として `## 方針` に書く
- **失敗の可視性**: 「処理は成功と表示され、実際には何も実行されていない」が成立する経路が無いか
  - 結果が履歴・ログに残らない設計は特に見る
- **非可逆な操作**: 削除・外部送信・課金・マイグレーションを含むか
  - 外部送信はメール・通知・Webhook を含む
- **新規依存の追加**: repo にまだ無いライブラリ・外部サービスを持ち込むか
- **宣言とコードの食い違い**: 設計本文で参照しないと宣言したデータを、クエリ側の `includes` / `select` / join に残していないか

### Step 6: タスクへの分解

設計の各コンポーネントを実装タスクにマッピングする。
依存の切り方・大タスクのまとめ方など、設計に書かれていない判断は「判断が割れる点の扱い」節に従う。
1. サブタスクを洗い出し、「大タスク = 関心のグルーピング」に従って関心の単位で大タスクにまとめる
2. 大タスクごとにサブタスクを並べ、「タスク分解の原則」の粒度に整える
3. 依存関係を確認し、`_Depends:_` に前提タスクを明記して実装順を決める
4. 各サブタスクに完了条件を 1 行で書く

### Step 7: 事前セットアップの洗い出し

「振り分け」で `## 事前セットアップ` 行きと判定した項目を `S<n>` として起こし、ブロック対象のタスクの `_Depends:_` に `S<n>` を足す。

### Step 8: 書き出し

Step 2〜7 の内容を「plan.md のフォーマット」で `.specs/<feature>/plan.md` に書く。
編集モードでは上書きする。

### Step 9: 点検

書き出した `plan.md` が次を満たしているか見直し、外れていれば直してから Step 10 へ進む。
- 全 Requirement がいずれかのサブタスクの `_Requirements:_` に現れる
- 共有する形が `## 付録:` に、implementer が推測せずに書ける具体度で書かれている
- `## 方針` `## 影響範囲` にファイル単位の変更内容が無く、合わせて 1 画面に収まる
- `## 方針` に根拠のない断言が残っていない
- `_Depends:_` が循環せず、実装順として成り立つ
- 「読み手ごとの粒度」「設計の判断基準」「方針の書き方」「Step 5 の固定チェックリスト」「タスク分解の原則」「タスク節の構成」を満たしている

### Step 10: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### 実装計画中断` にし、1 行目に中断理由を書き、書き出し前なら生成物の行を省き、次の一手は `/plan <feature>` と `/spec <feature>` だけにする。

```markdown
### 実装計画完了
<何を設計し、何個の大タスク・何サブタスクに分解したかを 1 行>

生成物: `.specs/<feature>/plan.md`

### 次の一手
- QA シナリオを作る: `/scenarios <feature>`
- 計画を直す: `/plan <feature>`
```
