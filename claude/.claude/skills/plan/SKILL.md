# 実装計画スキル

## 役割
要件から、`implementer` が迷わずコードを書けるレベルの技術設計と、それを実装するタスク列を作る。
人が全体を読んで承認し、`implementer` は担当する `tasks` の 1 要素を読んで実装する。

## 判断が割れる点の扱い
Step 2〜8 では、ユーザーに質問も承認要求もせず、`plan.jsonc` の書き出しまで走り切る。
判断が割れる点は最も素直な案を採り、採った案と捨てた案を `decisions` に理由付きで書く。
人は Step 9 の一覧を見て、Step 10 で詰める。

## 設計の判断基準

### 既存を踏襲する
同種の処理が repo に既にあるなら、その構成・命名・レイヤ分け・エラー処理・テストの置き方をそのまま採る。

- 設計を組む前に、近い責務のコードを Grep / Glob で探して踏襲元を特定する
- 逸脱は要件が既存の形で満たせないときだけにし、`deviations` に書く
- 踏襲元が無いときだけ新しく決める。repo 全体で優勢なパターンに合わせ、比較した代替案と却下理由を `decisions` に書く

### コンポーネントの境界を明確にする
各コンポーネントについて、責務と触る場所、隣接するコンポーネントの責務に踏み込まない範囲を決める。
複数のコンポーネントが同じファイル・同じ責務を担当する重なりがあれば、どちらか一方に寄せるか 1 つに統合し、その決定を `decisions` に書く。
1 feature は 1 リポジトリに閉じる。別リポジトリの変更が要るなら、それは `setup` の別 PJ 依頼になる。

## タスク分解の原則
- 粒度: 1 タスクは 1 体の `implementer` に渡せる範囲にする
  - タスク名は 1 つの関心を表す名詞句にし、「と」で関心が繋がるならタスクを分ける
  - 同じ作業の中で条件や例外が複数あるだけなら 1 つのタスクに畳む
  - 完了の基準は要件の受け入れ条件で、タスクには書き写さず `req` に任せる
- 順序: タスクは番号順に 1 つずつ直列で実装されるので、内側から外側の順に番号を振る
  - 内側はドメインやロジック、外側はそれを呼ぶ入口や画面
  - 1 つのタスクが内側と外側をまたぐなら層で分ける
- テストを書くか、TDD を採るかはリポジトリの規約に従い、feature ごとには書かない

### 実行主体で分ける
タスクは実行主体で 2 節に分ける。
impl の完了条件は `tasks` だけで、人しか実行できない項目は `setup` で追跡する。

| 項目 | 行き先 |
|---|---|
| コード・設定ファイル・ドキュメント・テストの追加や書き換え | `tasks` のタスク |
| GUI 操作・Secrets や環境変数の登録・外部 SaaS の設定変更・別 PJ への変更依頼 | `setup` の `S<n>` |
| 受け入れ条件を満たすかの検証 | どの節にも置かない |
| 設計の記述の調査・訂正 | どこにも置かず、調べて `summary` `decisions` `deviations` を直す。調べきれなければ `decisions` に推測として書く |

`tasks` に人しか実行できない項目を混ぜると、`depends` 経由で実装可能なタスクごと impl が止まるか、`implementer` に手作業が指示として渡る。

別 PJ への変更依頼は、この作業ディレクトリからは直接編集できない別 PJ の API・DB スキーマ・共有ライブラリ・画面の変更が要る、または別 PJ 側の対応が先に終わらないと実装・結合できない場合を指す。
相手 PJ に変更を頼まない単なる外部 API の呼び出しは含めない。

### タスク = 関心のグルーピング
- タスクは関心の単位でまとめる
  - ユーザーから見た機能の単位、触る対象が同じもの、同じ判断で良し悪しが決まるもの
- 数を合わせる目標を持たない
  - 1 つでも 5 つでもよい

## plan.jsonc の書き方

### 方針
人が計画を承認するために読む項目で、`summary` に地の文を 3〜5 文で書き、`decisions` と `deviations` の 2 つを並べる。
該当が無いものは空配列にする。

- `decisions`: 複数の案から選んだ形。Step 4 の固定チェックリストで該当した項目の扱いもここ
  - 踏襲元に合わせただけの項目は書かない。踏襲元はタスクの `follows` に出る
  - ただしチェックリストで該当した項目は踏襲でも書き、理由に何が起きると困るかを書く
- `deviations`: 要件の記述から挙動・記録粒度・可視性を変えた点と、踏襲元と違う形にした点。「本来はこうだが、こうする」の文型で揃える

各項目は `decision` に決定を書き、理由・捨てた案は `reasons` に、確認方法は `confirm` に書く。
`decision` は読点を使わない 1 文で言い切り、`decision` だけを縦に読めば決定の一覧になるようにする。
`reasons` は 1 要素に 1 つの内容だけを書き、複数あれば要素を分ける。

調べきれなかったことは、`decision` に決定を書き、`reasons` に理由として「〜と推測するため」を書き、`confirm` に確認方法を書く。
「〜のため発生しない」「〜に収まる」「実質〜」のような断言は書かず、確認済みなら根拠を、未確認なら推測の形で書く。
調べて分かったことは、使った判断の理由に根拠として書く。
人が確認する項目は `setup` だけに書く。

1 画面に収める。超えるなら説明を削り、決定だけを残す。
ファイル名・ファイル単位の変更内容は `touch` に書き、ここには書かない。

### 事前セットアップ
人が impl 前に済ませる項目で、ID は `S<n>`。`done` は人が実施してから自分で `true` にする。
別 PJ への依頼は `to` に依頼先 PJ を書き、`to` が空の項目は repo 内の作業。
ブロックされるタスクは `depends` で `S<n>` を参照する。

### タスク一覧
`implementer` が repo 内のファイル変更で完結する項目で、ID は `tasks` の `id` の 1, 2, ... の 1 階層。
触るファイルとシンボルは、タスクの `touch` に書く。
細部は例外で、狙いの文だけでは `implementer` が迷う作業があるときに限って書く。
判断・付録・要件に書いてあることと、狙いの文の言い換えは `details` に書かない。

- タスクのメタ情報のキーは `req` `depends` `follows` `touch` の 4 つで、該当が無いキーは省く
- `touch` は、触るファイルを 1 ファイル 1 要素で書く
  - 要素は `kind` `path` `note` `symbols` を持つ。`kind` は `N` 新規、`M` 変更、`D` 削除のどれか
  - ファイルの中で触るシンボルがあれば `symbols` に、`kind` `name` `note` を 1 シンボル 1 要素で書く
  - 手順やコードは書かない
  - シンボル名は調査に基づく予定で、実装で変わってよい
- `depends` の参照先にできるのは `S<n>` だけで、タスクの番号と `qa.jsonc` の `V<n>` は参照先にしない
  - タスクの前後関係は番号順で表す
  - デプロイ後の検証結果を前提にすると、「マージには実装の完了が必要で、完了にはマージが必要」という循環になる
- `done` が完了のフラグで、`implementer` の完了報告を受けて `/impl` が `true` にする

### 付録
複数のタスクが共有する型・テーブル・API の受け口・画面の入出力と、擬似コードを、決まった形だけで書く。
共有する形があるなら必ず置く。
内側のタスクが実装し、外側のタスクが呼ぶ契約として、実装より先に固定する。
理由や比較は書かず、表題ごとに節を分ける。
単一のタスクの中で決まる形は付録に出さず、そのタスクの細部に書く。
データの流れを図にするなら Mermaid で、ノード ID は英数字とアンダースコアだけにし、ラベルに `()` `[]` `"` `/` `@` を含めない。

## plan.jsonc のフォーマット
`implementer` と後続の skill が読む計画と、人が承認のために読む HTML の元データを兼ねる。
`.specs/plan.jsonc` に上書きし、同じ内容から `.specs/plan.html` を生成する。
該当しない項目は、`decisions` `deviations` `setup` `appendix` を空配列にする。
ただし `summary` と `tasks` は常に埋め、複数のタスクが共有する形があれば `appendix` も埋める。
末尾カンマは書かない。
文字列の中の二重引用符は `\"` に、改行は `\n` にエスケープする。
`id` と `req` の要素は整数、`depends` の要素は `S<n>` の文字列で書く。
`appendix` の本文は、改行を `\n` で書かず、1 行を 1 要素とする `lines` の配列に分ける。

```jsonc
{
  "summary": "[何をどう作るかを 3〜5 文で]",
  "decisions": [
    { "decision": "[選んだ形]", "reasons": ["[理由。捨てた案があれば、それを採らない理由も]"], "confirm": "" }
  ],
  "deviations": [
    {
      "decision": "要件 [番号] は[元の記述]だが、[採った形]にする",
      "reasons": ["[理由]"],
      "confirm": "[確認方法。未確認のときだけ。無ければ空文字]"
    }
  ],
  "setup": [
    {
      "id": "S1",
      "title": "[人が impl 前に何をするか 1 文。別 PJ への依頼は依頼先に何を頼むか 1 文。実装手順や受け入れ条件は先回りして書かない]",
      "to": "[依頼先 PJ。repo 内の作業なら空文字]",
      "reason": "[なぜ人の手作業か。なぜその PJ の変更が必要か]",
      "done": false
    }
  ],
  "tasks": [
    {
      "id": 1,
      "title": "[タスク名]",
      "done": false,
      "req": [1, 2],
      "depends": ["S2"],
      "follows": "[このタスクが形を合わせる既存コードのパス。無ければ空文字]",
      "touch": [
        {
          "kind": "M",
          "path": "path/to/file",
          "note": "",
          "symbols": [
            { "kind": "N", "name": "symbol", "note": "[追加するものの一言]" },
            { "kind": "M", "name": "symbol", "note": "[変更点の一言]" }
          ]
        },
        { "kind": "N", "path": "path/to/new_file", "note": "[役割の一言]", "symbols": [] }
      ],
      "goal": "[このタスクで何を達成するかを 1〜2 文で]",
      "details": ["[狙いの文だけでは迷う作業の細部。要るときだけ 1 要素に 1 つの振る舞い]"]
    }
  ],
  "appendix": [
    {
      "title": "[表題]",
      "lines": ["[共有する型・テーブル・API の受け口・画面の入出力、または擬似コードを、決まった形だけで 1 行ずつ]"]
    }
  ]
}
```

## 進め方

### Step 1: 開始条件の確認と分岐

- `.specs/requirements.jsonc` が無ければ `/spec` を案内して終了
- `feature.jsonc` の `repo` が今いる worktree の `git rev-parse --path-format=absolute --git-common-dir` の basename と違えば、Step 9 の中断報告で「`<repo>` の worktree で叩く」と案内して終了

`.specs/plan.jsonc` の有無で分岐する:
- **無い**: Step 2 へ
- **有る**: `plan.jsonc` と `requirements.jsonc` を読み、Step 2〜8 を飛ばして Step 9 へ進む

### Step 2: 踏襲元とコンポーネント境界の確定

「設計の判断基準」に従って踏襲元を探し、コンポーネント境界を決める。
踏襲元を探す範囲は場面に応じて変える:
- **既存機能の拡張**: 統合ポイントを Grep で洗い、その周辺の実装の形に合わせる
  - 新しい層・新しい命名体系は持ち込まない
- **新規機能**: まず repo 内に近い責務のコードを探し、無いことを確認してからアーキテクチャパターン・依存ライブラリを調査する
  - 必要なら WebSearch を使い、ライブラリは repo に既に入っているものを優先する

### Step 3: 外部環境の確認

- **別 PJ の実装状況・挙動**: `requirements.jsonc` に「実装済み」のような記載があれば、その PJ のデフォルトブランチを worktree に展開し、Read / Grep で確認する
  - bare repo は自分の bare repo `git rev-parse --git-common-dir` と同じ親ディレクトリにある `<リポジトリ名>` を採り、`git -C <bare repo> rev-parse --is-bare-repository` が `true` でなければ確認を諦めて `decisions` に推測として書く
  - `dest=$(mkworktree <bare repo> <リポジトリ名>-<今の worktree のディレクトリ名>)` で切る。同名の worktree が既にあればそれを使う
  - 依頼元の作業ツリーは remote に載っているとは限らないので、デフォルトブランチのコードを正とする
  - 食い違いは該当するタスクの細部に書き、`requirements.jsonc` 側の修正要否を `deviations` に出す
- **環境変数・設定値の導入**: ローカル・各デプロイ環境の投入先ファイルを実リポジトリで特定してから設計する
  - 「インフラ側で対応」とスコープ外に出す前にデプロイ定義の有無を確認し、特定できなければ `decisions` に推測として書く

### Step 4: 固定チェックリストの適用

組んだ設計に対して次を、要件に書かれていなくても確認する。
該当したものは `decisions` に書き、該当しなければ何も書かない。

- **テナント / 認可スコープ**: 親の ID をスコープとして受け取っているのに、子のクエリでその条件を付けずに引いていないか
  - ジョブ引数・キュー経由の値は永続化されて後から再実行されうるので、投入時に整合していても実行時に整合しているとは限らない
- **リトライの有無**: 例外の catch や握り潰しでフレームワークのリトライを殺していないか
  - 殺すなら明示的な決定として `decisions` に書く
- **失敗の可視性**: 「処理は成功と表示され、実際には何も実行されていない」が成立する経路が無いか
  - 結果が履歴・ログに残らない設計は特に見る
- **非可逆な操作**: 削除・外部送信・課金・マイグレーションを含むか
  - 外部送信はメール・通知・Webhook を含む
- **新規依存の追加**: repo にまだ無いライブラリ・外部サービスを持ち込むか
- **宣言とコードの食い違い**: 設計本文で参照しないと宣言したデータを、クエリ側の `includes` / `select` / join に残していないか

### Step 5: タスクへの分解

設計の各コンポーネントを実装タスクにマッピングする。
1. 作業を洗い出し、「タスク = 関心のグルーピング」に従って関心の単位でタスクにまとめ、「タスク分解の原則」の粒度に整える
2. 内側から外側の順になるようにタスクの番号を振る

### Step 6: 事前セットアップの洗い出し

「実行主体で分ける」で `setup` 行きと判定した項目を `S<n>` として起こし、ブロック対象のタスクの `depends` に `S<n>` を足す。

### Step 7: 書き出し

Step 2〜6 の内容を「plan.jsonc のフォーマット」で `.specs/plan.jsonc` に書く。

### Step 8: 点検

書き出した `plan.jsonc` が次を満たしているか見直し、外れていれば直してから Step 9 へ進む。
- 全 Requirement がいずれかのタスクの `req` に現れる
- 共有する形が `appendix` に、`implementer` が推測せずに書ける具体度で書かれている
- タスクの番号順が、内側から外側の順になっている
- 「設計の判断基準」「タスク分解の原則」「plan.jsonc の書き方」「Step 4 の固定チェックリスト」を満たしている

### Step 9: 提示

`decisions` と `deviations` の各項目を 1 行ずつ並べて出力する。
項目が無ければ「判断とずれなし」と書く。
既存の `plan.jsonc` を読み込んだときは、未対応のコメントの件数も 1 行で添える。
未対応のコメントは、`.specs/comments.jsonc` の `comments` のうち、`file` が `plan.html` で `status` が `open` のもの。

既存の `plan.jsonc` を読み込んだときは Step 10 へ進む。
新規に書き出したときは「次は `/scenarios`。直したい点は伝えれば反映する」を 1 行添えて終了する。

中断したときは、中断理由を 1 行で出し、`/plan` か `/spec` で再開できる旨を添えて終了する。

### Step 10: 判断とずれとコメントの議論

既存の `plan.jsonc` を読み込んだときだけ行う。
`decisions` と `deviations` の未解決の項目か未対応のコメントを 1 件選ぶ。
項目は、ユーザーに尋ねる。
コメントは、`quote` が指す箇所に本文の意図を反映し、判断が割れるときだけユーザーに尋ねる。
決まったら `plan.jsonc` の該当箇所を決定内容に直し、「設計の判断基準」「タスク分解の原則」「plan.jsonc の書き方」に従って Step 8 の点検をする。
コメントを反映したら、そのコメントの `status` を `done` にする。
`done` が `true` のタスクは番号と本文を変えない。
ユーザーが直したい点を直接伝えたときも、同じ手順で反映する。

未解決の項目か未対応のコメントが残っていれば、Step 10 に戻って次の 1 件を扱う。
全件を終えたら「判断とずれは確定。次は `/scenarios`」の 1 行で終了する。
ユーザーが打ち切ったときはそこで終了する。
