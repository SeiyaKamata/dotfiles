# PRコメント対応

## 役割
自分のPRに付いた未解決のレビューコメントに対応し、各コメントに返信する。スレッドの「解決済み」化はしない（解決はレビュアーに委ねる）。

## 入力
- `.specs/<feature>/requirements.md`（Step 2.5 で所在を特定して読み込む。**読み取り専用**。Edit / Write はしない）
- PR のコメント（インライン + 会話 + レビュー総評。Step 2 で `gh` から取得）

## 用語（前提）
用語は `claude/CLAUDE.md`「用語集」に従う。**フェーズ = 大タスク = ブランチ = 1 PR**。複数フェーズは stacked PR。stacked のときは **feature の全 PR を横断**して未解決コメントを集め、**指摘の付いた PR のブランチ（フェーズ）で修正**する。下位フェーズを直したら stack を rebase 伝播して上位ブランチに反映する（自走で安全に伝播できないと判断したら報告して停止）。

## 自走モード（`auto` 引数）
`$ARGUMENTS` に `auto` が含まれる場合：
- **全 author（人間 + CodeRabbit）のコメント**を対象にする。author で絞り込まない
- Step 3 の「対応方針を人間と議論する」は自動判断に読み替える（要件照合の分類と実コードでの裏取り結果から自分で方針を決める。手順は Step 3 auto 分岐）
- 次の 4 つを理由に処理を中断しない: **①人間コメントの存在 ②質問・議論系コメントの存在 ③「矛盾」「要件の見直しが必要」と確定したこと ④未検証の指摘の存在**。いずれも根拠を返信・報告に載せて次のコメントへ進む

引数なしの単体起動は**1 件ずつユーザーと方針を確定していく逐次確認フロー**であり、全件を一括提示しない（手順は Step 3）。

## 進め方
各 Step は順番に実行する。完了ゲートを通過するまで次へ進まない。

1. 対象PRを特定する
2. 未返信の未解決コメントを集める（インライン + 会話 + レビュー総評）
2-0. 0 件なら報告して終了する（両モード共通）
2.5. requirements.md を読み込む
3. コメントごとに対応方針を決める（`auto`: 自己判断 / 単体起動: 逐次確認）
4. 対応が必要なものを実装する
5. 各コメントに返信する
6. 結果を報告する

### Step 1: 対象PRを特定する（単一 / stacked）

現在のブランチから判定する：
- 現在のブランチが `<feature>-pN`（末尾 `-p` + 数字）→ **stacked の可能性**。feature 名を求めてフェーズブランチの PR を番号順に列挙する：
  ```
  for b in $(git branch --list "<feature>-p*" | sed 's/^[ *]*//' | sort -t p -k2 -n); do
    gh pr list --head "$b" --json number,title,url --jq '.[]'
  done
  ```
  2 件以上ヒットしたら **stacked モード**（Step 2 以降を全 PR 横断で行い、各指摘はその PR のブランチで対応する）。
- それ以外は単一 PR：
  ```
  gh pr view --json number,title,url
  ```
検出できれば人間に確認する（`auto` は確認不要）。検出できなければPR番号を聞く。

**完了ゲート:** 対象PR（stacked なら全 PR）と feature 名（`<feature>-pN` → `<feature>`、それ以外はブランチ名をそのまま feature 候補とする）を確定したか。

### Step 2: 未解決コメントを集める

インラインのコメントだけ見るとレビュー総評や会話コメントを取りこぼすため、**3種類すべて**を集める。

**① インラインのレビューコメント（返信先 id つき）**
```
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments \
  --jq '[.[] | select(.in_reply_to_id == null)] | sort_by(.path, .line)'
```
`select(.in_reply_to_id == null)` でルートコメントのみ取得する。`line != null` でフィルタするとファイル全体へのコメント（line: null）が漏れるので使わない。

**② 解決済みスレッドの除外**
①には解決済みも含まれる。未解決スレッドを reviewThreads で取得し、`path` + `line` + 本文で①と突き合わせて、解決済みのものを対象から外す：
```
gh pr view <PR番号> --json reviewThreads \
  --jq '[.reviewThreads[] | select(.isResolved == false) | {path, line, body: .comments[0].body}]'
```

**③ PR会話タブの一般コメント**
```
gh api repos/{owner}/{repo}/issues/<PR番号>/comments --jq '.[] | {user: .user.login, body}'
```

**④ レビューの総評**（Approve / Request changes 時の本文）
```
gh pr view <PR番号> --json reviews --jq '.reviews[] | select(.body != "") | {author: .author.login, state, body}'
```

**④' 返信済みの除外**（author を絞らず全コメントを対象にするため、再収集で同じコメントに何度も返信しないよう必要）
自分の login を取得する:
```
gh api user --jq '.login'
```

インラインは①のフィルタ（`select(.in_reply_to_id == null)`）を外した 1 回の取得で全コメント（ルート + 返信）を集め、ルートごとに自分の返信有無を見る。**①の取得と統合してよい**（取得回数を増やさない）:
```
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments \
  --jq '[.[] | {id, in_reply_to_id, user: .user.login}]'
```
ルート = `in_reply_to_id == null` のコメント。あるルート `R` について、`in_reply_to_id == R.id` かつ `user == <自分の login>` のコメントが 1 件以上あれば `replied = true` として対象から外す。

会話コメント・レビュー総評はスレッド構造を持たないため、返信本文に埋めたマーカー `<!-- rc-replied: <kind>:<id> -->`（`kind` は `conversation` | `review-summary`）を自分のコメントから走査して除外する:
```
gh api repos/{owner}/{repo}/issues/<PR番号>/comments \
  --jq '[.[] | select(.user.login == "<自分の login>") | .body] | join("\n")' \
  | grep -o 'rc-replied: [a-z-]*:[0-9]*'
```
抽出した `<kind>:<id>` の集合に含まれる会話コメント・総評を対象から外す。

**除外の順序:** 解決済みスレッドの除外（②）→ 返信済みの除外（④'）。両方を通ったものが対応対象になる。

**stacked のときは PR 単位で判定する。** 返信済み集合・マーカーの走査は PR ごとに行う（横断して混ぜると別 PR の同 id と衝突する）。

**完了ゲート:** ①③④を取得し、②で解決済みを、④'で返信済みを除外した、**未返信の未解決コメント**一覧ができたか。

### Step 2-0: 0 件ゲート（両モード共通）

Step 2 で得た「未返信の未解決コメント」一覧が空なら、Step 2.5 以降（要件読込・方針確認・実装・返信）をいずれも実行しない。未解決コメントが無いことと次の分岐を報告して終了する。auto ・単体起動のどちらでも同じ扱いにする。

**完了ゲート:** 一覧が空でないことを確認したか、または空であることを確定して報告のうえ終了したか。

### Step 2.5: 要件を読み込む

Step 1 で確定した feature 名を入力に、対象 PR の `requirements.md` を特定して読み込む。

**所在特定（上から順に試す）:**
```
# 1. 直接ヒットを試す
test -f .specs/<feature>/requirements.md

# 2. 外れたら .specs 配下を列挙し、ブランチ名に最も近いものを選ぶ（Step 3.5 の tasks.md 特定と同じ流儀）
find . -path './.git' -prune -o -name 'requirements.md' -print | grep '\.specs/'
```
- 単一ヒット → それを使う。複数ヒットして選べない → 単体起動はユーザーに確認、`auto` は特定失敗として扱う。0 件 → 特定失敗。
- **Read のみで扱う。Edit / Write はしない**（requirements.md は読み取り専用）。

**読み込んで保持する照合基準:**
- 「## スコープ」節の「含む」「含まない」の各項目（「含まない」は理由込み）
- 各 `### Requirement N` の受け入れ条件
- stacked の場合、feature 単位の 1 つの requirements.md を **全 PR 共通**の照合基準として使う。

**特定失敗時のフォールバック:** 要件照合を行わず、既存の方針判断（実コードでの裏取り）だけでコメント対応を続行する。**単体起動・`auto` のいずれでも中断しない**。Step 6 で「要件未照合」を報告する。

**完了ゲート:** requirements.md を読み込んで照合基準を保持したか、または特定できないことを確定してフォールバックを宣言したか。

### Step 3: 対応方針を決める（`auto`: 自己判断 / 単体起動: 逐次確認）

コメントごとに「対応する／対応しない（理由つき）」を決める。`auto` は自分で確定し、単体起動は 1 件ずつユーザーと確定する（手順は本 Step 末尾の「手動分岐」）。

**コメントごとに次の属性を Step 6 まで持ち回る**（表形式で保持する）:

| 属性 | 値域 |
|---|---|
| `classification` | `整合` \| `矛盾` \| `スコープ外` \| `無関係` \| `未照合` |
| `verification` | `成立` \| `不成立` \| `未検証` \| `対象外` |
| `policy` | `対応` \| `非対応` \| `保留` \| `回答` |

`verification` の `対象外` は「矛盾／スコープ外と分類した」「人間の指摘」「質問・議論系」など**裏取りを実施しなかった**ケースを指す。`未検証` は**裏取りを実施したが成立・不成立を判定できなかった**ケースだけに使う。この 2 つを混同すると Step 6 の未検証件数が意味を失う。

**要件照合を実コードの裏取りより先に行う。** requirements.md を読み込めた場合、対応・非対応を問わず**対象コメント全件**を requirements.md と照合し、各コメントを次の 4 分類のいずれか 1 つに分類する。「矛盾」「スコープ外」と判定した指摘はコードを触らないため、この後の裏取りには進めない。

| 分類 | 判定基準 | コード修正 | 返信の引用元 | tasks.md | 完了カード |
|---|---|---|---|---|---|
| 整合 | 指摘に従うと受け入れ条件を満たす方向に近づく | 既存の方針判断（裏取り）に委ねる | 引用不要 | 非対応なら既存どおり記録 | — |
| 矛盾 | 指摘に従うと受け入れ条件を破る | **しない** | Requirement 番号 + 該当受け入れ条件 | **記録する** | — |
| スコープ外 | 「含まない」いずれかの項目に該当する | **しない** | 該当「含まない」項目（理由込み） | 既存どおり記録 | `/spinoff` を提示 |
| 無関係 | requirements.md が言及していない領域（スタイル・実装品質など） | 既存の方針判断に委ねる | 引用不要 | 非対応なら既存どおり記録 | — |

「整合」「無関係」は照合結果を理由に方針を変えず、既存の方針判断に従う。

**矛盾のサブ分岐:** 指摘の方が妥当で要件側を直すべきと判断した場合も、コードは修正せず「矛盾」と同じ扱い（返信・tasks.md 記録）としたうえで、**要件の見直しが必要と判断した旨**を返信に含める。**requirements.md はこの場で書き換えない。**

`auto` は「矛盾」「要件の見直しが必要」と**確定した**ことを理由に処理を中断しない。根拠を添えて返信し、次のコメントへ進む。

**判定に迷うケースの逃げ道**（auto が詰まって停止しないために必須）:
- 「整合」か「無関係」で迷う → どちらでも方針は変わらないので、どちらかに寄せて先へ進む。
- 「矛盾」か「スコープ外」で迷う → 「含まない」項目への該当を優先して判定する。
- 単体起動で確信が持てない → 分類と根拠を添えて人間の判断を仰ぐ。`auto` は**中断せず**、根拠にした要件を返信に明記して先へ進む。

requirements.md を特定できなかった場合は、この要件照合を行わず既存の方針判断だけで進む。単体起動での提示手順は本 Step 末尾の「手動分岐」に書く。

**要件照合で「整合」「無関係」と分類した AI（CodeRabbit）の指摘だけ、方針を決める前に実コードで裏を取る。** 「矛盾」「スコープ外」と分類した指摘は裏取りに進まず非対応にする（上表のとおり）。AI レビューは誤検知を含み、
鵜呑みで直すと問題のないコードを壊す。指摘された箇所を開き、その条件が実際に成立しうるか
（呼び出し元・型・既存のガード節・テストの有無まで）と影響範囲を確認する。不成立と判断したら
**修正せず、確認した根拠を添えて返信する**（Step 5）。成立とも不成立とも確認できない場合は、
単体起動なら人間に判断を渡し、`auto` 時は自動で直さず未検証として報告する。人間の指摘・質問議論系コメントには裏取りを行わない（`verification = 対象外`）。

#### Step 3 auto 分岐: 方針決定則

`auto` は次の表に従って全件の方針を自分で確定する（人間に問わない）。

| 入力 | 方針 | 返信内容 |
|---|---|---|
| 分類 = 矛盾 | 非対応 | Requirement 番号 + 該当受け入れ条件（Step 5 の表のまま） |
| 分類 = スコープ外 | 非対応 | 該当「含まない」項目（理由込み） |
| 分類 = 整合／無関係 かつ AI の指摘 かつ 裏取り = 成立 | 対応 | 対応内容 |
| 分類 = 整合／無関係 かつ AI の指摘 かつ 裏取り = 不成立 | 非対応 | 不成立と判断した根拠 |
| 分類 = 整合／無関係 かつ AI の指摘 かつ 裏取り = 未検証 | 非対応 | 未検証である旨 + 確認した範囲 |
| 分類 = 整合／無関係 かつ 人間の指摘 | 対応 | 対応内容 |
| 質問・議論系（コード修正を求めていない） | 回答 | コードと `.specs/` を根拠にした回答。根拠が無ければ確認した範囲と不明点 |

人間の指摘は裏取りの成否で非対応にしない。AI 指摘の裏取りは誤検知対策であり、レビュアーの要求である人間の指摘には適用せず、実コードの確認は対応方法を決めるためだけに行う。分類が `未照合`（requirements.md を特定できず）のときは分類による非対応を行わず、AI 指摘は裏取りしたうえで方針を決め、人間の指摘は対応として扱う。

#### Step 3 手動分岐: 1 件ずつ逐次確認

単体起動（引数なし）は全件を一括提示せず、1 件ずつユーザーと方針を確定する。

冒頭で総件数を 1 回提示する:
```
未解決コメント <総件数> 件。1 件ずつ方針を確認します。
```

以降、1 件ごとに次を提示して回答を待つ。`y/n` では保留を表現できないため番号付き 3 択にする:
```
[<n>/<総件数>] <path>:<line>（<author>）

<コメント本文>

要件照合: <分類>（根拠: Requirement <N> / 「含まない」項目「<項目>」）
裏取り: <成立 / 不成立 / 未検証 / 対象外（人間の指摘・質問系）>
提案: <対応する / 対応しない>（理由: <理由>）

1: 対応する
2: 対応しない
3: 保留（この PR では判断しない）
```
- `1` が選ばれたら `policy = 対応` にする。
- `2` が選ばれたら非対応の理由を確認したうえで `policy = 非対応` に記録する。
- `3` が選ばれたら `policy = 保留` として実装・返信の対象から外し、次の件へ進む（記録は Step 3.5）。
- **未確定のまま次の件を提示しない。** 件数が多くても一括確認には切り替えない。

---

**Step 3 全体の完了ゲート（auto 分岐・手動分岐に共通）:** すべてのコメントに方針が付き（`auto` は全件確定、単体起動は 3 択で全件確定または保留）、要件照合を行った場合は全件の分類が済み、整合／無関係の AI 指摘は実コードでの裏取り結果が付いたか。

### Step 3.5: 対応しない項目・保留項目を tasks.md に追記する

「対応しない」と決めたコメント、または「保留」としたコメントが1件以上ある場合、`.specs/` 配下の `tasks.md` に追記する。要件と矛盾する指摘（要件側を直すべきと判断したものを含む）・スコープ外の指摘も「対応しない」項目として記録対象に含める。

**tasks.md の場所を特定する:**
```
find . -path './.git' -prune -o -name 'tasks.md' -print | grep '\.specs/'
```
複数見つかった場合は PR のブランチ名や機能名から最も近いものを選ぶ。見つからなければ人間に確認する。

**追記フォーマット:**
```markdown
## 残対応（PR #<番号> で見送り）

- [ ] <コメントの要点> <!-- <対応しない理由> -->
- [ ] <コメントの要点> <!-- 保留: <その場で判断できなかった点> -->
```
保留は `保留:` で始まるコメントを持つ点だけが非対応と異なる（記録先・フォーマット本体は変えない）。既に「残対応」セクションがあれば、その末尾に項目を追加する。新規セクションは `tasks.md` の末尾に追加する。

**完了ゲート:** 「対応しない」項目と「保留」項目がすべて tasks.md に記録されたか。

### Step 4: 実装する

**一括実装ゲート:** 単体起動（手動モード）では、全コメントの `policy` が確定する（対応 / 非対応 / 保留のいずれかが付く）まで実装に着手しない。`auto` は Step 3 で全件を自己確定済みなのでこのゲートは即通過する。

対応すると決めたものを実装する。

**stacked の場合**: 各指摘は**それが付いた PR のブランチ（フェーズ）で修正・コミット**する。下位フェーズを直したら、上位フェーズのブランチへ stack を rebase 伝播して再 push する（`git rebase --onto` 等）。伝播でコンフリクトが多発する・自走で安全に行えないと判断したら、対応済みぶんを報告して停止する。

**完了ゲート:** 方針どおりに実装し、stacked なら該当フェーズのブランチに反映（＋上位へ伝播）したか。

### Step 5: 各コメントに返信する

**保留を除く全レコードへの返信を必須とする。** 対応・非対応・回答（質問系）を問わず、対象としたすべてのコメントに返信する（保留は Step 3.5 で記録済みなので返信対象から外す）。対応しないと決めたコメントにも、理由を添えて返信する。

**照合根拠を返信の冒頭に置く。** Step 3 の要件照合を行った場合、返信本文の冒頭に根拠を置き、既存の返信文（対応内容・非対応理由）を続ける。

| ケース | 冒頭に置く根拠 |
|---|---|
| 矛盾 | `requirements.md の Requirement <N>「<要件名>」の受け入れ条件「<該当行>」と矛盾するため、コードは変更しません。` |
| 矛盾（要件側を直すべき） | 上記に続けて `ご指摘の方が妥当と考えるため、要件そのものの見直しが必要と判断しました（このスレッドではコードを変更しません）。` |
| スコープ外 | `本 feature の requirements.md では「含まない」項目「<該当項目>（理由: <理由>）」に該当するため、この PR では対応しません。` |
| 要件の意図への回答 | `requirements.md の Requirement <N>「<要件名>」/「スコープ」節の「<項目>」を根拠に回答します。` |
| 根拠が見つからない | 断定せず `requirements.md を確認しましたが該当する記述が見つかりませんでした。確認した範囲: <範囲>／不明点: <不明点>` |

コード修正ではなく要件・仕様の意図の説明を求めているコメントには、requirements.md の該当 Requirement または「スコープ」節を根拠に回答し、根拠にした番号・節を返信に明示する。requirements.md に該当する記述が見つからない場合は断定せず、確認した範囲と不明点を示して返信する。

**インラインコメントへの返信:**
```
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<comment_id>/replies \
  -X POST -f body="<返信内容>"
```

**会話コメント・レビュー総評への返信:** PRコメントで返す。返信本文の末尾に返信済みマーカーを埋める（次回実行時の Step 2 ④' で走査する。インラインコメントには付けない。返信の親子関係で判定できるため）。
```
gh pr comment <PR番号> --body "<返信内容>
<!-- rc-replied: <kind>:<id> -->"
```
`kind` は `conversation` | `review-summary`、`id` はそのレコードの id。

**返信が失敗した場合:** 失敗したコメントを特定できる情報（`kind` / `id` / `path` / `line` のうち特定できるもの）と失敗理由を Step 6 に渡して報告する。

スレッドの解決済み化はしない（レビュアーが解決する運用）。

**完了ゲート:** 保留を除くすべてのコメントに返信し、会話コメント・レビュー総評には返信済みマーカーを付与したか。

### Step 5.5: 再発しそうなレビュー指摘は改善提案に切り出す

コメントの中に **レビュアーの恒常的な好み・PJ の規約**（例: この PJ では必ず〜の命名を求められる、
特定の書き方は毎回 nit が付く、テストの置き場所が決まっている）と判断できるものがあれば、
**記録ではなく改善提案として切り出す**。恒久ルール（`CLAUDE.md`）へ勝手に追記しない — 反映するかは
人が判断する。

- 切り出し先の判定は `CLAUDE.md`「訂正の扱い」に従う（判定基準をここに重複させない）
- 確認を取らずに実行し、結果を完了カードの主要な結果に 1 行載せる
  （例: `- 💡 改善提案: <要点> → /spinoff`）
- **切り出さないもの**: その PR 限りの個別指摘、git log / diff で追える対応内容

**完了ゲート:** 再発しそうな指摘の有無を判断し、あれば実行したか（実行結果をカードに載せたか）。

### Step 6: 完了カードを出す

対応・非対応・保留の件数内訳を含めて、結果を末尾「完了カード」のブロックに畳んで出力する（別文での報告はしない）。
「対応しない」項目・「保留」項目のいずれかを tasks.md に追記した場合は、そのパスを 📄 行に出す（どちらも追記していなければ 📄 行を省略する）。

## 完了条件
保留を除く未対応コメントすべてへの対応・返信が完了し、「対応しない」項目・「保留」項目が tasks.md に記録され、
再発しそうなレビュー指摘があれば改善提案の切り出し先を提示したら完了。

## 出力規律
実行中の逐次ナレーション（「〜します」「〜しました」）は出さない（ツール実行はターミナルに表示されるため二重になる）。ただし修正を push して CodeRabbit の再レビューを待つなど、表示が止まる区間の開始時だけ、次の 1 行を出す（1 区間 1 回）。Step 3 の方針議論はユーザーとの対話なのでこの制限の対象外。

⏳ resolve-comments: CodeRabbit の再レビューを待機中…

## 完了カード
Step 6 で、次の完了カードを**コードフェンスで囲まず**プレーンテキストで出力して終了する。カードの前後に作業サマリ・所感・補足を足さない。次スキルは自動起動せずユーザーの実行を待つ。

- 一言サマリは 1 行。対応・非対応・保留の件数内訳を出す。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。コメントごとの指摘・返信内容はカードに列挙せず、PR のスレッドに寄せる。
- 📄 行は「対応しない」項目・「保留」項目のいずれかを tasks.md に追記した場合に出す（どちらも追記していなければ行ごと省略する）。▶ 行は完了時点で確定した分岐 1 つだけを出す。
- 主要な結果には次の条件も載せる（3 行を超える場合は件数を 1 行にまとめる。`/spinoff` `/spec` は自動起動せず提示のみ）:
  - 要件照合を行わなかった（requirements.md を特定できず） → `- ⚠ 要件未照合（requirements.md を特定できず）`
  - スコープ外の指摘が 1 件以上 → `- 💡 スコープ外 <n> 件 → /spinoff`
  - 要件の見直しが必要と判断した指摘が 1 件以上 → `- 💡 要件の見直しが必要 <n> 件 → /spec <feature>`
  - 未検証の指摘が 1 件以上 → `- ⚠ 未検証 <n> 件`
  - `auto` はこの 4 条件を完了カードでなく簡易ログに併記する（例: `次: /watch-ci（要件未照合 / スコープ外 2 件 / 未検証 1 件）`）

✅ コメント対応・返信完了
<対応件数・非対応件数・保留件数を 1 行>
- <主要な結果 最大 3 行>
📄 .specs/<feature>/tasks.md
▶ OK（修正を push した）：/watch-ci で再監視
▶ OK（追加の修正なし）：マージ / Ready for review を判断（停止点）

完了条件を満たせずに終了するときは、同じ構成でヘッダを `⚠ コメント対応中断` に差し替え、一言サマリに中断理由（rebase 伝播が安全に行えないなど）、▶ 行に復帰コマンドを書く。

自律モード（起動引数に `auto` を含む）では完了カードを出さず、確定した遷移先を 1 行の簡易ログだけ残す（例: `次: /watch-ci`）。要件未照合・スコープ外・要件の見直しが必要・未検証のいずれかがあれば、上記「完了カード」節の記法で簡易ログに併記する。次スキルの起動は呼び出し元（orchestrator）が行う。
