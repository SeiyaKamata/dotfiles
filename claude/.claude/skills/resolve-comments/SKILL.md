# PRコメント対応スキル

## 役割
自分の PR に付いた未解決のレビューコメントに対応し、各コメントに返信する。**スレッドの「解決済み」化はしない**（解決はレビュアーに委ねる）。

## 入出力
- **入力**:
  - PR のコメント（インライン + 会話 + レビュー総評。Step 2 で `gh` から取得）
  - `.specs/<feature>/requirements.md`（Step 3-1 で所在を特定。**読み取り専用**で Edit / Write はしない）
- **出力**:
  - コード修正とコメントへの返信
  - `.specs/<feature>/issues.md`（非対応・保留の記録）

## 引数
- `$ARGUMENTS` のうち数字部分: PR 番号（省略可）
- `batch`: 全件の方針を自分で確定して一括処理する（省略時は 1 件ずつ確認する）

## 対象範囲

| 起動 | 対象 |
|---|---|
| `/resolve-comments` | カレントブランチの PR |
| `/resolve-comments <PR番号>` | その PR |

常に 1 PR だけを対象にする。他フェーズの PR には踏み込まないため、rebase 伝播は発生しない。

## 用語（前提）
用語は `claude/CLAUDE.md`「用語集」に従う。

## 判断ポリシー
**逐次（既定）**: **1 件ずつユーザーと方針を確定していく逐次確認フロー**（全件を一括提示しない。手順は Step 3-4）。

**batch（`$ARGUMENTS` に `batch` を含む）**: 方針は全件自分で確定する（Step 3-4 の決定則に従う）。次の 4 つを理由に**処理を中断しない**: ①人間コメントの存在 ②質問・議論系コメントの存在 ③「矛盾」「要件の見直しが必要」と確定したこと ④未検証の指摘の存在。いずれも根拠を返信・報告に載せて次のコメントへ進む。

> **返信は外向きの発信であり、他人のレビュー指摘への「対応する / しない」の判断は人の領分**なので、既定は逐次確認にしている（自分の成果物の内容については確認しない）。`batch` は人が張り付けない場面のためのもので、判断の根拠を全件返信と完了カードに残すことで事後に追えるようにしている。

対象コメントは**逐次・batch とも全 author（人間 + CodeRabbit）**。author で絞り込まない。

## 進め方
各 Step は順番に実行する。**完了ゲート**を通過するまで次へ進まない。

### Step 1: 対象 PR の特定

「対象範囲」の表に従って決める。**上から順に判定し、最初に当たったもので確定する。**

**1. PR 番号が渡されている** → その 1 本。feature 名はその PR の head ブランチから求める：
```
gh pr view <PR番号> --json number,title,url,headRefName
```

**2. 渡されていない（既定）** → カレントブランチの PR：
```
gh pr view --json number,title,url,headRefName
```

**PR を特定できなければ中断する**（PR 番号を渡して再実行するよう復帰コマンドに書く）。特定できた場合は確認を求めず先へ進む。

**完了ゲート:** 対象 PR と feature 名（head ブランチが `<feature>-pN` なら `<feature>`、それ以外はブランチ名をそのまま feature 候補とする）を確定したか。

### Step 2: 未返信の未解決コメントを集める

インラインのコメントだけ見るとレビュー総評や会話コメントを取りこぼすため、**3 種類すべて**を集める。

**2-1 収集**

① インラインのレビューコメント（返信先 id つき）
```
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments \
  --jq '[.[] | select(.in_reply_to_id == null)] | sort_by(.path, .line)'
```
`select(.in_reply_to_id == null)` でルートコメントのみ取得する。`line != null` でフィルタするとファイル全体へのコメント（line: null）が漏れるので使わない。

② PR 会話タブの一般コメント
```
gh api repos/{owner}/{repo}/issues/<PR番号>/comments --jq '.[] | {user: .user.login, body}'
```

③ レビューの総評（Approve / Request changes 時の本文）
```
gh pr view <PR番号> --json reviews --jq '.reviews[] | select(.body != "") | {author: .author.login, state, body}'
```

**2-2 除外**

#### 解決済みスレッドの除外
①には解決済みも含まれる。未解決スレッドを reviewThreads で取得し、`path` + `line` + 本文で①と突き合わせて、解決済みのものを対象から外す：
```
gh pr view <PR番号> --json reviewThreads \
  --jq '[.reviewThreads[] | select(.isResolved == false) | {path, line, body: .comments[0].body}]'
```

#### 返信済みの除外
author を絞らず全コメントを対象にするため、再収集で同じコメントに何度も返信しないよう必要。自分の login を取得する：
```
gh api user --jq '.login'
```

インラインは①のフィルタ（`select(.in_reply_to_id == null)`）を外した 1 回の取得で全コメント（ルート + 返信）を集め、ルートごとに自分の返信有無を見る。**①の取得と統合してよい**（取得回数を増やさない）：
```
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments \
  --jq '[.[] | {id, in_reply_to_id, user: .user.login}]'
```
ルート = `in_reply_to_id == null` のコメント。あるルート `R` について、`in_reply_to_id == R.id` かつ `user == <自分の login>` のコメントが 1 件以上あれば `replied = true` として対象から外す。

会話コメント・レビュー総評はスレッド構造を持たないため、返信本文に埋めたマーカー `<!-- rc-replied: <kind>:<id> -->`（`kind` は `conversation` | `review-summary`）を自分のコメントから走査して除外する：
```
gh api repos/{owner}/{repo}/issues/<PR番号>/comments \
  --jq '[.[] | select(.user.login == "<自分の login>") | .body] | join("\n")' \
  | grep -o 'rc-replied: [a-z-]*:[0-9]*'
```
抽出した `<kind>:<id>` の集合に含まれる会話コメント・総評を対象から外す。

#### nitpick の除外
レビュー bot が nitpick（軽微・任意）と分類した指摘は対応対象から外す。bot 自身が「対応しなくてよい」と申告しているものに要件照合・裏取り・返信のフル手順を回すのは費用に見合わない。除外した件数は Step 5 の「要確認」に出し、拾うかは人に委ねる。

**除外の順序:** 解決済みスレッドの除外 → 返信済みの除外 → nitpick の除外。すべてを通ったものが対応対象になる。

**2-3 0 件ゲート（逐次・batch 共通）**

一覧が空なら Step 3 以降（要件読込・方針確認・実装・返信）を**いずれも実行しない**。未解決コメントが無いことと次の分岐を報告して終了する。

**完了ゲート:** 3 種類を取得し、解決済みと返信済みを除外した**未返信の未解決コメント**一覧ができたか。または空であることを確定して報告のうえ終了したか。

### Step 3: 方針を決める

コメントごとに「対応する／対応しない（理由つき）」を決める。**次の属性を Step 5 まで持ち回る**（表形式で保持する）：

| 属性 | 値域 |
|---|---|
| `classification` | `整合` \| `矛盾` \| `スコープ外` \| `無関係` \| `未照合` |
| `verification` | `成立` \| `不成立` \| `未検証` \| `対象外` |
| `policy` | `対応` \| `非対応` \| `保留` \| `回答` |

**確定順序**: `classification` は 3-2、`verification` は 3-3、`policy` は 3-4 で埋まる。3 つとも 3-4・Step 4・Step 5 から参照される。

`verification` の `対象外` は「矛盾／スコープ外と分類した」「人間の指摘」「質問・議論系」など**裏取りを実施しなかった**ケース。`未検証` は**裏取りを実施したが成立・不成立を判定できなかった**ケースだけに使う。この 2 つを混同すると Step 5 の未検証件数が意味を失う。

**3-1 照合基準を読み込む**

Step 1 で確定した feature 名を入力に、対象 PR の `requirements.md` を特定して読み込む。

所在特定（上から順に試す）:
```
# 1. 直接ヒットを試す
test -f .specs/<feature>/requirements.md

# 2. 外れたら .specs 配下を列挙し、ブランチ名に最も近いものを選ぶ
find . -path './.git' -prune -o -name 'requirements.md' -print | grep '\.specs/'
```
- 単一ヒット → それを使う。複数ヒットして選べない → 逐次はユーザーに確認、`batch` は特定失敗として扱う。0 件 → 特定失敗
- **Read のみで扱う。Edit / Write はしない**

読み込んで保持する照合基準:
- 「## スコープ」節の「含む」「含まない」の各項目（「含まない」は理由込み）
- 各 `### Requirement N` の受け入れ条件

**特定失敗時のフォールバック:** 要件照合を行わず、実コードでの裏取りだけで続行する。**逐次・batch のどちらでも中断しない**。Step 5 で「要件未照合」を報告する。

**3-2 要件照合（裏取りより先に行う）**

requirements.md を読み込めた場合、対応・非対応を問わず**対象コメント全件**を照合し、次の 4 分類のいずれか 1 つに分類する。「矛盾」「スコープ外」と判定した指摘はコードを触らないため、裏取りには進まない。

| 分類 | 判定基準 | コード修正 | 返信の引用元 | issues.md | 完了カード |
|---|---|---|---|---|---|
| 整合 | 指摘に従うと受け入れ条件を満たす方向に近づく | 裏取りに委ねる | 引用不要 | 非対応なら記録 | — |
| 矛盾 | 指摘に従うと受け入れ条件を破る | **しない** | Requirement 番号 + 該当受け入れ条件 | **記録する** | — |
| スコープ外 | 「含まない」いずれかの項目に該当する | **しない** | 該当「含まない」項目（理由込み） | 記録する | `/spinoff` を提示 |
| 無関係 | requirements.md が言及していない領域（スタイル・実装品質など） | 裏取りに委ねる | 引用不要 | 非対応なら記録 | — |

「整合」「無関係」は照合結果を理由に方針を変えず、裏取りの結果に従う。

**矛盾のサブ分岐:** 指摘の方が妥当で要件側を直すべきと判断した場合も、コードは修正せず「矛盾」と同じ扱い（返信・issues.md 記録）としたうえで、**要件の見直しが必要と判断した旨**を返信に含める。**requirements.md はこの場で書き換えない。**

**判定に迷うケースの逃げ道**（`batch` が詰まって停止しないために必須）:
- 「整合」か「無関係」で迷う → どちらでも方針は変わらないので、どちらかに寄せて先へ進む
- 「矛盾」か「スコープ外」で迷う → 「含まない」項目への該当を優先して判定する
- 逐次で確信が持てない → 分類と根拠を添えて人間の判断を仰ぐ。`batch` は**中断せず**、根拠にした要件を返信に明記して先へ進む

**3-3 実コードでの裏取り**

**「整合」「無関係」と分類した AI（CodeRabbit）の指摘だけ**、方針を決める前に実コードで裏を取る。AI レビューは誤検知を含み、鵜呑みで直すと問題のないコードを壊す。

指摘された箇所を開き、その条件が実際に成立しうるか（呼び出し元・型・既存のガード節・テストの有無まで）と影響範囲を確認する。不成立と判断したら**修正せず、確認した根拠を添えて返信する**。成立とも不成立とも確認できない場合は、逐次なら人間に判断を渡し、`batch` は自動で直さず未検証として報告する。

**人間の指摘・質問議論系コメントには裏取りを行わない**（`verification = 対象外`）。

**3-4 方針の確定**

#### batch
次の表に従って全件の方針を自分で確定する（人間に問わない）。

| 入力 | 方針 | 返信内容 |
|---|---|---|
| 分類 = 矛盾 | 非対応 | Requirement 番号 + 該当受け入れ条件 |
| 分類 = スコープ外 | 非対応 | 該当「含まない」項目（理由込み） |
| 分類 = 整合／無関係 かつ AI の指摘 かつ 裏取り = 成立 | 対応 | 対応内容 |
| 分類 = 整合／無関係 かつ AI の指摘 かつ 裏取り = 不成立 | 非対応 | 不成立と判断した根拠 |
| 分類 = 整合／無関係 かつ AI の指摘 かつ 裏取り = 未検証 | 非対応 | 未検証である旨 + 確認した範囲 |
| 分類 = 整合／無関係 かつ 人間の指摘 | 対応 | 対応内容 |
| 質問・議論系（コード修正を求めていない） | 回答 | コードと `.specs/` を根拠にした回答。根拠が無ければ確認した範囲と不明点 |

**人間の指摘は裏取りの成否で非対応にしない。** AI 指摘の裏取りは誤検知対策であり、レビュアーの要求である人間の指摘には適用せず、実コードの確認は対応方法を決めるためだけに行う。分類が `未照合` のときは分類による非対応を行わず、AI 指摘は裏取りしたうえで方針を決め、人間の指摘は対応として扱う。

#### 逐次（既定）
全件を一括提示せず、1 件ずつユーザーと方針を確定する。冒頭で総件数を 1 回提示する：
```
未解決コメント <総件数> 件。1 件ずつ方針を確認します。
```

以降、1 件ごとに次を提示して回答を待つ。`y/n` では保留を表現できないため番号付き 3 択にする：
```
[<n>/<総件数>] <path>:<line>（<author>）

<コメント本文>

要件照合: <分類>（根拠: Requirement <N> / 「含まない」項目「<項目>」）
裏取り: <成立 / 不成立 / 未検証 / 対象外（人間の指摘・質問系）>
提案: <対応する / 対応しない>（理由: <理由>）

1: 対応する
2: 対応しない
3: 保留（この PR では判断しない）
```
- `1` → `policy = 対応`
- `2` → 非対応の理由を確認したうえで `policy = 非対応`
- `3` → `policy = 保留`。実装・返信の対象から外し、次の件へ進む（記録は Step 4-3）
- **未確定のまま次の件を提示しない。** 件数が多くても一括確認には切り替えない

**完了ゲート:** すべてのコメントに方針が付き（`batch` は全件確定、逐次は 3 択で全件確定または保留）、要件照合を行った場合は全件の分類が済み、整合／無関係の AI 指摘は裏取り結果が付いたか。

### Step 4: 対応

**4-1 実装**

**一括実装ゲート:** 逐次では、全コメントの `policy` が確定する（対応 / 非対応 / 保留のいずれかが付く）まで実装に着手しない。`batch` は Step 3 で全件を自己確定済みなので即通過する。

対応すると決めたものを実装する。

**4-2 返信**

#### 返信文言の組み立て

**保留を除く全レコードへの返信を必須とする**（対応・非対応・回答のいずれでも）。保留は 4-3 で記録済みのため返信対象から外す。非対応と決めたコメントには理由を添える。

**照合根拠を返信の冒頭に置く。** 要件照合を行った場合、返信本文の冒頭に根拠を置き、既存の返信文（対応内容・非対応理由）を続ける。

**根拠はファイルパスではなく文言の引用で示す。** `.specs/` は gitignore されており PR の diff にも GitHub 上にも出ないため、レビュアー（CodeRabbit を含む）はそのファイルを開けない。ファイル名・パスを書かず、該当する受け入れ条件・「含まない」項目の**文言を返信本文に転記**する。

| ケース | 冒頭に置く根拠 |
|---|---|
| 矛盾 | `本 feature の要件「<要件名>」の受け入れ条件「<該当行を転記>」と矛盾するため、コードは変更しません。` |
| 矛盾（要件側を直すべき） | 上記に続けて `ご指摘の方が妥当と考えるため、要件そのものの見直しが必要と判断しました（このスレッドではコードを変更しません）。` |
| スコープ外 | `本 feature のスコープ外です。「含まない」と定めた項目「<該当項目を転記>」（理由: <理由>）に該当するため、この PR では対応しません。` |
| 要件の意図への回答 | `本 feature の要件「<要件名>」/ スコープの「<項目を転記>」を根拠に回答します。` |
| 根拠が見つからない | 断定せず `本 feature の要件を確認しましたが該当する記述が見つかりませんでした。確認した範囲: <範囲>／不明点: <不明点>` |

コード修正ではなく要件・仕様の意図の説明を求めているコメントには、requirements.md の該当 Requirement または「スコープ」節を根拠に回答し、根拠にした番号・節を返信に明示する。

#### 送信

インラインコメントへの返信：
```
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<comment_id>/replies \
  -X POST -f body="<返信内容>"
```

会話コメント・レビュー総評への返信: PR コメントで返す。返信本文の末尾に返信済みマーカーを埋める（次回実行時の Step 2-2 で走査する。インラインコメントには付けない — 返信の親子関係で判定できるため）：
```
gh pr comment <PR番号> --body "<返信内容>
<!-- rc-replied: <kind>:<id> -->"
```
`kind` は `conversation` | `review-summary`、`id` はそのレコードの id。

#### 返信が失敗した場合

失敗したコメントを特定できる情報（`kind` / `id` / `path` / `line` のうち特定できるもの）と失敗理由を Step 5 に渡して報告する。

スレッドの解決済み化はしない（「役割」参照）。

**4-3 非対応・保留を issues.md に記録**

「対応しない」と決めたコメント、または「保留」としたコメントが 1 件以上ある場合、`.specs/<feature>/issues.md` に追記する（`<feature>` は Step 1 で確定した feature 名）。要件と矛盾する指摘（要件側を直すべきと判断したものを含む）・スコープ外の指摘も記録対象に含める。ファイルが無ければ新規作成する。

```markdown
## 残対応（PR #<番号> で見送り）

- [ ] <コメントの要点> <!-- <対応しない理由> -->
- [ ] <コメントの要点> <!-- 保留: <その場で判断できなかった点> -->
```
保留は `保留:` で始まるコメントを持つ点だけが非対応と異なる（記録先・フォーマット本体は変えない）。同じ PR 番号の「残対応」セクションが既にあればその末尾に追加し、無ければファイル末尾に新規セクションを追加する。

**完了ゲート:** 方針どおりに実装し、保留を除く全コメントに返信し、非対応・保留を issues.md に記録したか。

### Step 5: 出力

完了カードの共通仕様（CLAUDE.md）に従う。見出しは `### コメント対応・返信完了` / 中断時 `### コメント対応中断`。

```markdown
### コメント対応・返信完了
<対応件数・非対応件数・保留件数を 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/issues.md`

### 要確認
- 未検証 <n> 件（裏取りで成立・不成立を判定できなかった指摘）
- スコープ外 <n> 件 → /spinoff
- 要件の見直しが必要 <n> 件 → /spec <feature>
```

#### 改善提案への切り出し

**再発しそうなレビュー指摘は改善提案に切り出す。** コメントの中に**レビュアーの恒常的な好み・PJ の規約**（例: この PJ では必ず〜の命名を求められる、特定の書き方は毎回 nit が付く、テストの置き場所が決まっている）と判断できるものがあれば、記録ではなく**改善提案として切り出す**。恒久ルール（`CLAUDE.md`）へ勝手に追記しない。
