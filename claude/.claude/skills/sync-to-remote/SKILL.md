# リモート反映スキル

## 役割
コミット後の変更を**リモートへ着地させる**。`claude/CLAUDE.md`「PR 運用の有無」の判定に従い、`あり` なら draft PR を作り、`なし` ならフェーズブランチをデフォルトブランチへ取り込んで push する。

PR を作る場合、**対象は「今いるブランチのフェーズ」1 本**。stacked 運用では base 側の PR が無いとスタック関係を表現できないため、未作成の下位フェーズがあればそれも番号順に作る（＝**冪等**）。

## 用語（前提）
用語は `claude/CLAUDE.md`「用語集」に従う。**フェーズ = 大タスク = ブランチ = 1 PR**。複数フェーズは stacked PR（`pN` の base は `p(N-1)`、`p1` の base はデフォルトブランチ）。

## PR 運用の有無（吸収するのはこのスキルだけ）
**上流の工程（`/spec`〜`/commit`）はすべて PR 運用を前提に動く。** `/impl` は PR の有無に関わらず必ずフェーズブランチを切り、`/tasks` は必ず PR タイトルを発行する。運用差を吸収するのはこのスキル 1 つだけで、他の工程に分岐を持ち込まない。

判定条件・`不明` のときの倒し方は `claude/CLAUDE.md`「PR 運用の有無」に一元化してある。ここでは判定結果だけを使う：

- `あり` → Step 1 以降で draft PR を作る
- `なし` → Step 1' でフェーズブランチをデフォルトブランチへ取り込んで push する

`不明` を `あり` に倒したときは、単体起動ならその判断を完了カードに 1 行添える。

## 呼ばれ方（前提）
orchestrator は**フェーズループの中から**このスキルを呼ぶ（各フェーズの `/commit` 直後）。全フェーズを積んでから一斉に呼ぶ運用ではない。理由は orchestrator の「なぜフェーズごとに PR を出すのか」を参照。

このスキルは**冪等**に作られている：既に PR があるフェーズブランチはスキップするので、フェーズごとに呼んでも、取りこぼしを拾うために最後にもう一度呼んでも、同じ結果になる。

## 自走モード（`auto` 引数）
`$ARGUMENTS` に `auto` が含まれる場合：
- Step 0: 未コミットの変更があれば `/commit auto` を呼んで完了後に続行する
- Step 1: ベースブランチはデフォルトブランチを自動採用する（聞かない）
- stacked と判定したら、対象フェーズ（＋未作成の下位フェーズ）の PR を確認なしで作成する

引数なしの単体起動では Step 0 で `/commit` を呼び、Step 1 でユーザーに確認する。

## 引数
- `auto`: 自走モードフラグ（省略可）

## 進め方

### Step 0: 未コミットの変更を確認する

`git status` で未コミットの変更があるか確認する。

未コミットの変更がある場合：
- **`auto` モード** → `/commit auto` を起動し、完了後に Step 1 へ進む
- **単体起動** → `/commit` を起動し、完了後に Step 1 へ進む

変更がない場合はそのまま次へ進む。

続けて `claude/CLAUDE.md`「PR 運用の有無」に従って判定し、`あり` なら Step 1、`なし` なら Step 1' へ分岐する。

### Step 1': PR を作らない repo での着地（ローカルマージして push）

`/impl` はこの運用でもフェーズブランチを切っているので、それをデフォルトブランチへ取り込んで push する。フェーズの割り方は変えない（レビューの形が変わるだけ）。

```
DEFAULT=$(git remote show origin | grep 'HEAD branch' | awk '{print $NF}')
CURRENT=$(git branch --show-current)
```

1. `CURRENT` == `DEFAULT`（ブランチを使わず直接コミットした場合）→ マージ不要。手順 4 へ。
2. 取り込み対象を決める。stacked（`<feature>-pN`）なら**未マージの下位フェーズから番号順に**取り込む。`p1 → p2 → ...` の順を崩さない（順を飛ばすと差分が入れ子で壊れる）。既にマージ済みのブランチは対象から外す：
   ```
   git branch --merged "$DEFAULT"
   ```
3. 各対象ブランチについて、デフォルトブランチを最新化してからマージする：
   ```
   git checkout "$DEFAULT" && git pull
   git merge --ff-only <対象ブランチ> || git merge --no-ff <対象ブランチ>
   ```
   **コンフリクトが出たらその場で解決せず中断する**（自動解決は差分を壊す）。`git merge --abort` で戻し、中断カードに衝突ファイルを出して人に委ねる。
4. push する：
   ```
   git push origin "$DEFAULT"
   ```
   保護ルールで弾かれた場合は、それが想定内か（例: bypass 権限がある旨の記述がある）をプロジェクト `CLAUDE.md` と照らす。判断がつかなければ中断する。
5. Step 5 へ進み、完了カードの「PR なし」版を出す。

**冪等性**: 手順 2 でマージ済みブランチが外れ、反映済みなら push も "Everything up-to-date" で終わる。二度呼んでも同じ結果になる。

### Step 1: ベースブランチと PR 構成（単一 / stacked）を判定する

リポジトリのデフォルトブランチを取得する：
```
git remote show origin | grep 'HEAD branch' | awk '{print $NF}'
```

**`auto` モード**の場合は上記で取得したブランチをそのまま使用する。
**単体起動**の場合はユーザーに確認する（回答がなければ上記を使用）：
> マージ先のブランチはどこにしますか？（デフォルト: 上記で取得したブランチ）

次に **単一 PR か stacked PR か**を現在のブランチ名から判定する：
```
git branch --show-current
```
- 現在のブランチが `<feature>-pN`（末尾が `-p` + 数字）の形 → **stacked モード**。feature 名を `-p<数字>` を除いて求める
- 末尾が `-pN` でない（`<feature>` などの単一ブランチ） → **単一 PR モード**

**stacked モードのときは、作成対象を絞り込む**。対象は「現在のフェーズ `pN`」＋「PR が未作成の下位フェーズ `p1..p(N-1)`」だけ。既に PR があるフェーズはスキップする：
```
for i in $(seq 1 N); do
  b="<feature>-p$i"
  git rev-parse --verify "$b" >/dev/null 2>&1 || continue          # ブランチが無ければ対象外
  gh pr list --head "$b" --state all --json number --jq '.[].number' # 空なら未作成＝作成対象
done
```
- **`pN` より上のフェーズは対象にしない**（まだ実装されていない）
- 下位フェーズがスキップされるのは正常（フェーズループで既に作成済みのため）。結果として通常は **1 フェーズ 1 PR だけ**が作られる
- 対象が 0 件（現在のフェーズの PR が既にある）→ 既存 PR の URL を報告して終了する

判定後、feature 名（ブランチ名から `-pN` を除いたもの）で `.specs/<feature>/tasks.md`（各フェーズの PR タイトル）を読む。あれば PR タイトルは tasks.md の対応表を使い、無ければ従来どおりコミットメッセージから生成する。

### Step 1.5: 作業ブランチを確認・作成する（単一 PR モードのみ）

**この Step が「デフォルトブランチのまま push しようとしていないか」の押さえである。** `/commit` は
push しないため同じ判定を持たない（`/commit` Step 1 の除外理由を参照）。push を実行するのはこの
スキルなので、ここで確実にブランチへ載せ替える。

現在のブランチがベースブランチと同じ場合、**必ず新しいブランチを作成してからPRを作る**。
ブランチ名はコミット内容から自動で命名する（例: `feat/add-login`, `fix/typo-in-readme`）。
```
git checkout -b <ブランチ名>
```
既に別のブランチにいる場合はそのまま進む。stacked モードではフェーズブランチが既に存在するので新規作成しない。

### Step 2〜4: PR を作成する

言葉づかい（タイトル・本文共通）:
IT・ビジネスの専門用語を避け、読んだ人が知識に関わらず理解できる言葉で書く。
- 避ける例: リファクタリング、マイグレーション、エンドポイント、スキーマ、デプロイ、バリデーション
- 言い換え例: 「コードの整理」「テーブル構造の変更」「APIの受け口」「データの形式」「本番環境への反映」「入力値の確認」

利用可能なラベルを取得しておく：
```
gh label list
```

#### 単一 PR モード
1. 変更内容を確認する：
   ```
   git log origin/<ベースブランチ>..HEAD --oneline
   git diff origin/<ベースブランチ>..HEAD --stat
   ```
2. 下記テンプレートで本文を組み立てる。
3. draft PR を作成する（未 push なら先に `git push -u origin HEAD`）：
   ```
   gh pr create --draft --base <ベースブランチ> --title "<タイトル>" --body "<本文>" --assignee @me --label "<ラベル>"
   ```

#### stacked モード
Step 1 で絞り込んだ**作成対象フェーズだけ**を番号順に作成する（通常は現在のフェーズ 1 本）。各 PR の base は 1 つ下のフェーズ（`p1` はデフォルトブランチ）：

各対象フェーズ `pN`（`base` = `pN==p1` ならデフォルトブランチ、そうでなければ `<feature>-p(N-1)`）について：
```
git push -u origin <feature>-pN
git log <base>..<feature>-pN --oneline      # この PR に含まれる差分（前フェーズとの差分）
git diff <base>..<feature>-pN --stat
gh pr create --draft --base <base> --head <feature>-pN \
  --title "<タイトル>" --body "<本文>" --assignee @me --label "<ラベル>"
```
- 各 PR の本文は**そのフェーズの差分だけ**をもとに書く（前フェーズの変更を含めない）。
- PR 本文の Summary 冒頭に stacked の位置を明記する（例: `stacked PR 2/3（base: <feature>-p1）`）。
- **`tasks.md` に `着地状態:` があれば、`## このPRをマージした後の状態` として本文に転記する**。stacked PR はそれ単体では feature が完成しないため、レビュアーが「どこまでできていれば正しいのか」を判断する material になる。
- 作成順は `p1 → p2 → ...`（base 側の PR を先に作る）。

**PR本文テンプレート:**
```
## Summary
（変更の概要を1〜3行で。stacked の場合は位置と base を明記）

## 変更内容
（git diffの結果をもとに変更ファイルと変更内容を箇条書き）

## このPRをマージした後の状態
（tasks.md の `着地状態:` を転記。単一 PR モードでは省略してよい）
```
タイトルは **tasks.md の対応表で確定した各フェーズの PR タイトル**をそのまま使う（`【鎌田QA】…（PR N/M）` の形）。tasks.md が無い／未記載の場合のみ、そのフェーズ（単一なら全体）の最初のコミットメッセージをベースに作成する。

### Step 5: 完了カードを出す

**PR 運用あり**: 今回**作成した** PR の URL を番号順に、既存でスキップしたフェーズがあればその URL も「（既存）」と添えて、末尾「完了カード」の 🔗 行にまとめて出力する（stacked の全体像が分かるように）。報告はカードに畳み、別文で書かない。

**PR 運用なし**: 末尾「完了カード（PR なし）」を出す。PR が無いので `/watch-ci` には進まない（CI が回るならデフォルトブランチ側で回る）。

## エラー処理
- `gh pr create` が「ブランチがpushされていない」エラーになった場合: `git push -u origin <対象ブランチ>` を実行してから再試行する
- `gh pr create` が「head branch is the same as base branch」エラーになった場合: base と head が同じになっていないか確認する（単一モードは Step 1.5 で新ブランチを作る）

## 完了条件
- **PR 運用あり**: 対象フェーズの draft PR を作成（既存ならスキップ）し、URL を報告したら完了。
- **PR 運用なし**: 対象フェーズをデフォルトブランチに取り込んで push し、反映内容を報告したら完了。

次工程の起動は完了条件に含めない。

## 完了カード
Step 5 で、次の完了カードを**コードフェンスで囲まず**プレーンテキストで出力して終了する。カードの前後に作業サマリ・所感・補足を足さない。次スキルは自動起動せずユーザーの実行を待つ。

- 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。PR 本文の内容はカードに転記しない。
- 🔗 行は **1 PR 1 行**で本数ぶん出す（行数上限は主要な結果にだけ課す）。既存でスキップした PR は URL の後に「（既存）」と添える。

✅ draft PR 作成完了
<作成した PR の本数と構成（単一 / stacked N/M）を 1 行>
- <主要な結果 最大 3 行>
🔗 <作成した PR の URL>
🔗 <作成した PR の URL（stacked で複数作った場合は 1 本 1 行）>
▶ OK：/watch-ci

完了条件を満たせずに終了するときは、同じ構成でヘッダを `⚠ draft PR 作成中断` に差し替え、一言サマリに中断理由、▶ 行に復帰コマンドを書く（作成できた PR があれば 🔗 行は残す）。

## 完了カード（PR なし）
「PR 運用の有無」が `なし` だった場合は、上のカードの代わりに次を出す。🔗 行は無い（PR が無いため）。

✅ デフォルトブランチへ反映完了
<どのブランチを <デフォルトブランチ> に取り込んで push したかを 1 行>
- <主要な結果 最大 3 行>
▶ OK：/cleanup

判定が `不明` から `あり` に倒れて PR を作った場合は、上の通常カードの主要な結果に「PR 運用の判定が付かなかったため PR を作成した」旨を 1 行入れる。

マージやコンフリクトで止まったときは、ヘッダを `⚠ デフォルトブランチへの反映中断` に差し替え、一言サマリに中断理由（衝突ファイル・保護ルール等）、▶ 行に復帰手順を書く。

自律モード（起動引数に `auto` を含む）では完了カードを出さず、遷移先を 1 行の簡易ログだけ残す（例: `次: /watch-ci`）。次スキルの起動は呼び出し元（orchestrator）が行う。
