# リモート反映スキル

## 役割
コミット後の変更を**リモートへ着地させる**。あわせて **PR を何本に割るかを判定する唯一の工程**でもある。`claude/CLAUDE.md`「PR 運用の有無」の判定に従い、`あり` なら draft PR を作り、`なし` ならデフォルトブランチへ取り込んで push する。

**分割の判定はここだけが持つ。** `/tasks` も `/impl` も PR 分割を決めない。`/impl` は実装ブランチ `<feature>` を 1 本切るだけ。判定材料は**実装後のコミット済みの実物**、diff とコミット列で、実装前の見積りではない。

**冪等**に作られている：既に PR があるブランチ・既にマージ済みのブランチはスキップするので、取りこぼしを拾うために何度呼んでも同じ結果になる。

## 入出力
- **入力**: カレントブランチとコミット済みの差分・コミット列／`.specs/<feature>/seed.md` の frontmatter の `pr_title`。無ければコミットメッセージから作る
- **出力**: draft PR（PR 運用あり）またはデフォルトブランチへの push（PR 運用なし）／分割した場合はフェーズブランチ `<feature>-pN`

## PR 運用の有無
吸収するのはこのスキルだけ。**上流の工程（`/spec`〜`/commit`）はすべて PR 運用を前提に動く。** `/impl` は PR の有無に関わらず必ず実装ブランチを切る。運用差を吸収するのはこのスキル 1 つだけで、他の工程に分岐を持ち込まない。

判定条件・`不明` のときの倒し方は `claude/CLAUDE.md`「PR 運用の有無」に一元化してある。ここでは判定結果だけを使う：

- `あり` → Step 3-1 で draft PR を作る
- `なし` → Step 3-2 でデフォルトブランチへ取り込んで push する

## 呼ばれ方
前提として、用語は `claude/CLAUDE.md`「用語集」に従う。**フェーズはこのスキルが実装後に確定する PR 単位**で、実装前には存在しない。分割しなければフェーズは現れず単一 PR になる。

呼ばれ方は 2 通りある：

1. **実装ブランチ `<feature>` から初回**。`/commit` 直後 — Step 2 で分割を判定し、単一なら 1 PR、stacked なら `p1` の PR だけを作る
2. **フェーズブランチ `<feature>-pN` から再呼び出し**。前の PR が green + 全件返信済みになった後 — 次のフェーズ `p(N+1)` の PR を作る

**stacked でも全 PR を一斉に作らない。** 一斉作成すると `p1` に返ってきた CI / CodeRabbit の指摘の修正が全スタックへの rebase 伝播を要求し、それは自走で安全に行えない停止条件になる。1 本ずつ閉じてから次を作れば、修正は常に先端で完結する。詳細は `/orch`「なぜ PR を 1 本ずつ出すのか」を参照。

## 判断ポリシー
ベースブランチはデフォルトブランチを自動採用する。聞かない。未コミットの変更があれば `/commit` を呼ぶ。

どちらも**マージのコンフリクトと push の拒否では止まる**。自動解決は差分を壊すため。

## 進め方

### Step 1: 前提確認

**1-1 未コミットの変更**

`git status` で確認し、あれば `/commit` を起動して完了後に続行する。

**1-2 PR 運用の判定**

`claude/CLAUDE.md`「PR 運用の有無」に従って判定する。`不明` を安全側の `あり` に倒したときは、単体ならその判断を完了カードの「要確認」に出す。

### Step 2: 対象確定と分割判定

```
DEFAULT=$(git remote show origin | grep 'HEAD branch' | awk '{print $NF}')
CURRENT=$(git branch --show-current)
```

**2-1 呼ばれ方の判定**

- `CURRENT` が `<feature>-pN`（末尾が `-p` + 数字）→ **再呼び出し**。分割の方針は既に決まっているので 2-2〜2-3 を飛ばし、**2-6（載せ直し）を経て** `p(N+1)` を作る。実装ブランチ `<feature>` に未反映のコミットが残っていなければ「全フェーズ着地済み」として終了する
- それ以外（`<feature>` など）→ **初回**。2-2 へ

feature 名は `-p<数字>` を除いて求める。**PR タイトルの素材はここで自分で用意する**。`tasks.md` は持たない：

- `.specs/<feature>/seed.md` の frontmatter の `pr_title`（例 `[SEC-16005] ATM Auth0移行`）
- `seed.md` が無い／`pr_title` が空なら、**コミットメッセージから主題を作る**。実装後なのでコミット列が揃っている
- 固定 prefix `【鎌田QA】` を頭に付ける（`claude/CLAUDE.md`「PR / ブランチ命名」）

**2-2 実物を読む**

分割の判定材料は**実装後のコミット済みの実物**だけ。

```
git log origin/"$DEFAULT"..HEAD --oneline
git diff origin/"$DEFAULT"..HEAD --stat
```

**2-3 分割の判定**

**既定は単一 PR。** 分割は stacked のコストを払う例外なので、払う理由が要る。次の 4 つの**いずれかに該当するときだけ** stacked を検討する：

| 理由 | 内容 |
|---|---|
| (a) レビュー負荷 | 1 PR に収めるとレビュアーが一度に見る量が過大。**1 つの機能として完結するので feature を分けられないが、量が大きい**ケースがこれに当たる — feature を分けられるなら spec 段階で分けるべきで、ここには来ない |
| (b) リスク分離 | 危険な変更（破壊的マイグレーション・広範なリネーム）を安全な変更から切り離して先に着地させたい |
| (c) 着地の緊急度差 | 一部を先に本番へ出したい |
| (d) レビュアーが違う | 領域ごとに別の人が見る |

**どれにも該当しなければ分割しない。判定に迷ったら単一 PR に倒す**。PR を 1 本余分に出すより、割った PR が単体で判断できない方が害が大きい。

**分割しない側に働く力**（判定材料として必ず参照する）:
- 載せ直しの手間 — 前のフェーズに修正が入るたび、次のフェーズを作る前に実装ブランチを載せ直す必要がある（2-6）。コンフリクトすれば人を呼ぶ
- CI の重複実行 — 同じコードが PR の本数ぶん回る
- 後続 PR が着地までブロックされる
- force push が draft PR に限られる（`claude/CLAUDE.md`「force push」）

**割ってはいけないもの:**
- **1 つの契約を共有するコミット群**は同じ PR に入れる。片側だけ着地すると壊れた状態になる（例: 出力側と読み取り側の両端を変える修正）
- **量だけを理由に割らない。** 変更行数・ファイル数は理由 (a) の判断材料に留め、閾値で機械的に決めない

**2-4 分割点を決める**

stacked と判定した場合のみ。コミット列から分割点を選ぶ。`/commit` が Inside-out でコミットを分割しているので、**コミットの境界がそのまま分割点になる**。1 つのコミットを複数の PR に分けない。

各分割点について**着地テスト**を通す：

> **そこまでをデフォルトブランチにマージして放置しても、既存挙動が壊れず／機能が中途半端な状態で止まらないか**

- 通る → 分割点として採用してよい。「そのフェーズだけでは動かない」ことは問題ではない。未使用のコードが増えるだけなら OK。問題なのは「**そこまででは妥当か判断できない**」状態
- 落ちる → その分割点は採らない
- **どの分割点も落ちる → 分割せず単一 PR にする**。判断できない PR を 3 本出すより、大きい PR を 1 本出す方がレビューは機能する

**作るのは `p1` のブランチだけ**。後続は前の PR が閉じてから 2-6 で作る。先に全部作ると、`p1` に入った修正が後続に反映されない：

```
git branch <feature>-p1 <分割点1のコミット>
```

**残りの分割点は SHA で覚えない。** 2-6 の載せ直しでコミットの SHA が変わるため、「どのコミットまでを次のフェーズに入れるか」を**コミットの内容**で記録して完了カードに報告する。

分割の方針が確定したら**総 PR 数 `M`** が決まる。PR タイトルはここで組み立てる（形式は `claude/CLAUDE.md`「PR / ブランチ命名」）：

- **単一 PR**: `【鎌田QA】<pr_title>` — `：<フェーズ内容>` と `（PR N/M）` は付けない
- **stacked**: `【鎌田QA】<pr_title>：<フェーズ内容>（PR<N>/<M>）` — `<フェーズ内容>` はそのフェーズのコミット列から 1 行で書く

**2-5 対象の絞り込み**

- **単一モード** → 対象は `<feature>` 1 本
- **stacked モード** → 対象は **その周の 1 フェーズだけ**（初回なら `p1`、再呼び出しなら 2-6 で作った `p(N+1)`）
- 既に PR があるブランチ・既にデフォルトブランチへマージ済みのブランチはスキップする：
  ```
  gh pr list --head "<対象ブランチ>" --state all --json number --jq '.[].number'   # 空なら作成対象
  git branch --merged "$DEFAULT" | grep -qF "<対象ブランチ>" && echo skip           # マージ済みなら対象外
  ```
- 対象が 0 件 → 既存 PR の URL（PR 運用なしなら反映済みである旨）を報告して終了する

**2-6 前のフェーズの先端へ載せ直す**

再呼び出しのときだけ。

`p1` を閉じる過程で CI 修正や CodeRabbit 対応のコミットが `p1` に積まれている。実装ブランチ `<feature>` はそれを持っていないので、**そのまま次のフェーズを切ると差分に「前の修正の打ち消し」が現れる**。

次のフェーズを作る前に、実装ブランチを前のフェーズの先端へ載せ直す：

```
git checkout <feature>
git rebase <feature>-pN          # 直前に閉じたフェーズの先端に載せ直す
git branch <feature>-p(N+1)      # 載せ直した先端（または次の分割点）を指す
```

- **実装ブランチは push しない**ので、この rebase は他人が見ているブランチを書き換えない（安全）
- **コンフリクトが出たら自動解決せず中断する**。`git rebase --abort` で戻し、中断カードに衝突ファイルを出して人に委ねる
- 載せ直した結果、次のフェーズに入れる差分が空になったら（前のフェーズの修正で吸収された）、そのフェーズは作らず「全フェーズ着地済み」として終了する

### Step 3: 反映

#### 3-1 PR 運用あり（draft PR を作る）

**単一モードでは、先に作業ブランチへ載せ替える。** カレントブランチがベースブランチと同じ場合、**必ず新しいブランチを作成してから PR を作る**。ブランチ名はコミット内容から自動で命名する（例: `feat/add-login`）。

```
git checkout -b <ブランチ名>
```

**この押さえが「デフォルトブランチのまま push しようとしていないか」の最終防波堤である。** `/commit` は push しないため同じ判定を持たない。push を実行するのはこのスキルなので、ここで確実にブランチへ載せ替える。既に別のブランチにいる場合はそのまま進む。stacked ではフェーズブランチが既に存在するので新規作成しない。

利用可能なラベルを取得しておく：

```
gh label list
```

**単一モード:**
```
git log origin/<ベースブランチ>..HEAD --oneline
git diff origin/<ベースブランチ>..HEAD --stat
gh pr create --draft --base <ベースブランチ> --title "<タイトル>" --body "<本文>" --assignee @me --label "<ラベル>"
```
未 push なら先に `git push -u origin HEAD`。

**CodeRabbit は本文の `@coderabbitai ignore` で作成時から無効化する。** 作成後に `pause` をコメントする方式では、作成時の Webhook で既にレビューが走ってしまい間に合わない。本文テンプレートに埋め込んでおくことで、CodeRabbit は最初から一切レビューしない。**再度有効化する操作（本文の行を外す・`review` コメントを送るなど）はこのスキルの範囲外**で、セルフレビュー後に人が行う。

**stacked モード:** Step 2-5 で絞り込んだ**1 フェーズだけ**を作成する。base は 1 つ下のフェーズ（`p1` はデフォルトブランチ）：
```
git push -u origin <feature>-pN
git log <base>..<feature>-pN --oneline      # この PR に含まれる差分（前フェーズとの差分）
git diff <base>..<feature>-pN --stat
gh pr create --draft --base <base> --head <feature>-pN \
  --title "<タイトル>" --body "<本文>" --assignee @me --label "<ラベル>"
```
- 各 PR の本文は**そのフェーズの差分だけ**をもとに書く。前フェーズの変更を含めない
- Summary 冒頭に stacked の位置を明記する（例: `stacked PR 2/3 — base: <feature>-p1`）
- **残りのフェーズはここでは作らない。** この PR が CI green + 未返信の未解決コメントなしになってから、`<feature>-pN` に checkout して `/sync-to-remote` を再度呼ぶ

**PR 本文テンプレート:**
```
@coderabbitai ignore

## Summary
（変更の概要を1〜3行で。stacked の場合は位置と base を明記）

## 変更内容
（git diff の結果をもとに変更ファイルと変更内容を箇条書き）

## このPRをマージした後の状態
（Step 2-4 の着地テストで言語化した状態を 1 行で。単一モードでは省略してよい）
```

**stacked では「マージした後の状態」を必ず書く。** それ単体では feature が完成しないため、レビュアーが「どこまでできていれば正しいのか」を判断する材料になる。Step 2-4 の着地テストを通したときに判断した内容をそのまま書けばよい。

**言葉づかい（タイトル・本文共通）:** IT・ビジネスの専門用語を避け、読んだ人が知識に関わらず理解できる言葉で書く。
- 避ける例: リファクタリング、マイグレーション、エンドポイント、スキーマ、デプロイ、バリデーション
- 言い換え例: 「コードの整理」「テーブル構造の変更」「APIの受け口」「データの形式」「本番環境への反映」「入力値の確認」

#### 3-2 PR 運用なし（デフォルトブランチへ取り込んで push）

`/impl` はこの運用でも実装ブランチを切っているので、それを取り込む。

**PR 運用なしでは分割しない。** Step 2-3〜2-4 を実施せず、実装ブランチ `<feature>` をそのまま取り込む。分割はレビューの単位を作るためのもので、PR が無い repo では意味を持たない。

1. `CURRENT` == `DEFAULT`（ブランチを使わず直接コミットした場合）→ マージ不要。手順 3 へ
2. 対象ブランチを取り込む。既にフェーズブランチが存在する場合は**番号順に**。順を飛ばすと差分が入れ子で壊れる：
   ```
   git checkout "$DEFAULT" && git pull
   git merge --ff-only <対象ブランチ> || git merge --no-ff <対象ブランチ>
   ```
   **コンフリクトが出たらその場で解決せず中断する**。自動解決は差分を壊す。`git merge --abort` で戻し、中断カードに衝突ファイルを出して人に委ねる
3. push する：
   ```
   git push origin "$DEFAULT"
   ```
   保護ルールで弾かれた場合は、それが想定内か（例: bypass 権限がある旨の記述がある）をプロジェクト `CLAUDE.md` と照らす。判断がつかなければ中断する

### Step 4: 出力

完了カードの共通仕様（CLAUDE.md）に従う。

**PR 運用あり**: 見出しは `### draft PR 作成完了` / 中断時 `### draft PR 作成中断`。

```markdown
### draft PR 作成完了
<作成した PR の構成（単一 / stacked N/M）と、分割した場合は採用した理由を 1 行>
- <主要な結果 最大 3 行>

生成物: <作成した PR の URL>

### 要確認
- <PR 運用の判定が `不明` で `あり` に倒した、など>
- <stacked のとき>未作成の後続フェーズ: <残り本数> — この PR が green + 全件返信済みになったら `<feature>-pN` に switch して `/sync-to-remote` を再実行

### 次の一手
- CI を監視する: `/watch-ci`
```

**PR 運用なし**: 見出しは `### デフォルトブランチへ反映完了` / 中断時 `### デフォルトブランチへの反映中断`。生成物行の無いカードを出す。PR が無いので `/watch-ci` には進まない。CI が回るならデフォルトブランチ側で回る。

```markdown
### デフォルトブランチへ反映完了
<どのブランチを <デフォルトブランチ> に取り込んで push したかを 1 行>
- <主要な結果 最大 3 行>
```

**PR 運用なしの場合、次の一手は無いのでブロックごと省略する**（デフォルトブランチへの反映で完了するため）。

- やったこと: PR 本文の内容はカードに転記しない。生成物は **1 PR 1 行**で本数ぶん出す。既存でスキップした PR は URL の後に「（既存）」と添え、stacked の全体像が分かるようにする。
- 要確認: PR 運用の判定が `不明` だった場合は**必ず**、どちらに倒したかと根拠を書く。**分割した場合は採用した理由 (a)〜(d) と分割点の取り方を必ず出す**。既定の単一 PR から外れた判断なので根拠を残す。stacked なら未作成の後続フェーズが何本あるかも出す。
- 次の一手: PR 運用ありなら `CI を監視する: /watch-ci` の 1 行を出す。
- 中断時のやったこと: 中断理由。衝突ファイル・保護ルールでの push 拒否などが該当する。作成できた PR があれば生成物の行は残す。
- 中断時の次の一手: 復帰手順。反映できていないまま `/watch-ci` へ進む道は出さない。

## エラー処理
- `gh pr create` が「ブランチが push されていない」→ `git push -u origin <対象ブランチ>` を実行してから再試行する
- `gh pr create` が「head branch is the same as base branch」→ base と head が同じになっていないか確認する。単一モードは Step 3-1 で新ブランチを作る

## 完了条件
- **PR 運用あり**: 分割を判定し、対象 1 本の draft PR を作成（既存ならスキップ）して URL を報告したら完了。**stacked の後続フェーズの PR 作成は完了条件に含めない**。前の PR が閉じてから再呼び出しで作る
- **PR 運用なし**: 実装ブランチをデフォルトブランチに取り込んで push し、反映内容を報告したら完了

次工程の起動は完了条件に含めない。
