# プロトタイプスキル

## 役割
本番と同じ FW で、design.md の対象機能を**実際に動く形で作り切る**。モックではない。ロジック・API 結線・状態管理も**本物**にする。そこで判明した実物の制約・破綻を `design.md` に書き戻し、設計の精度を高める。

ここでの実装は**品質を問わない捨て実装（spike）**。可読性・保守性・命名・テストは**一切考えなくてよい**。とにかく動けばいい。

**いつ使うか**: 大きい修正で、かつ UI を伴うときだけ。小さい修正・バックエンドのみの修正では使わない（確かめる画面がないため）。起動判定は orchestrator が行う。

## 入出力
- **入力**: `.specs/<feature>/requirements.md` / `.specs/<feature>/design.md`
- **出力**（3 つ）:
  1. `.specs/<feature>/design.md` への書き戻し（設計の精度向上）＝**仕様の記録**
  2. `<feature>-proto` ブランチに 1 コミットして残す**動くコード**＝ impl の**流用元**
  3. `<feature>-proto` を head にした実サーバー検証用 draft PR（`@coderabbitai ignore` 入り。**マージ前提ではない**）

コードは捨てない。本番実装（`/impl`）は白紙から書き直すのではなく、この prototype コードを**読んで流用（コピー＋本番品質に整形）**する（＝「参照して昇格」）。

**ただし正典は `design.md`。** tasks / impl が仕様として参照するのは design.md であり、prototype コードはそれを速く実装するための**参考実装**にすぎない。

## モード
完了カードを出す。破壊的操作（書き込み・課金・不可逆操作）の前だけ確認を挟む。

**人の目視承認を待たない。** **作り切って動いたこと**をもって設計の妥当性を判断する。UI の受け入れ確認は `/qa` に委ね、ここでは design.md の精度向上に専念する。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`（feature）が未指定なら「使い方: /prototype <feature>」を表示して終了

### Step 2: ブランチ準備とコンテキスト収集

ブランチ名は `<feature>-proto`（impl がここから流用するので、このブランチとコードは残す）。デフォルトブランチから作成する：

```
DEFAULT=$(git remote show origin | sed -n 's/.*HEAD branch: //p')
git checkout "$DEFAULT" && git pull
git checkout -b <feature>-proto
```

続けて読み込む：
- `requirements.md` と `design.md`（画面構成・データフロー・コンポーネント構成を把握する）
- 本番の FW・コンポーネントパターン・API/データ層を Grep/Glob で確認する（本物として動かし、かつ impl が流用しやすくするため）

### Step 3: 作り切って動かす

**3-1 implementer に配布**

`/impl` と同じく、**実装は `implementer` サブエージェントに委譲する**（メインの context を実装のトークンで汚さないため）。メインが握るのは git・design.md への書き戻し・判断だけ。

`implementer` は**何をやるかを呼び出しプロンプトから受け取る**契約なので、専用モードは要らない。design.md から作業一覧を起こして渡す：

- feature 名（specs のパスを含む）
- **作業一覧**: design.md の対象機能を「動かして確かめられる単位」に割ったもの。各項目に完了条件（＝どの操作が通れば動いたと言えるか）と対応する要件を添える
- リポジトリの起動コマンド（テストコマンドは渡さない。下記のとおりテストは書かせない）
- **品質水準の指定**（ここが `/impl` との唯一の差。省略すると本番品質で作られてしまうので必ず明示する）:
  ```
  これは捨て実装（spike）です。品質は問いません。
  - 可読性・命名・責務分割・エラーハンドリングの網羅は無視してよい
  - 既存コードの規約に合わせる努力も不要
  - テストは書かない
  - ただしロジック・API 結線・状態管理は本物にする（ダミーデータやモック関数で誤魔化さない）
  - 本番のデータ・外部 API に書き込む／課金する／不可逆な操作は行わず、必要だと判断したら blockers に挙げて止まる
  ```
- ローカルで起動し、対象機能を要件どおりのフローで**通しで動かしてから報告する**こと

**3-2 報告の取り込み**

`implementer` の報告から次を拾う（報告欄の定義は `implementer` 側にある）：

| 報告欄 | 使い道 |
|---|---|
| `仕様との食い違い` | **Step 4-1 の書き戻し材料**（実物で判明したデータ構造・API 形・状態遷移の抜け・制約） |
| `自分で決めた判断` | Step 5 の「要確認」。**impl が流用するときに引き継いではいけない妥協** |
| `blockers` | 動かし切れなかった理由。設計の破綻なら Step 4-1 の差し戻し判断へ |

動かし切れていない（`状態` が「一部未達」「ブロック」）なら、追加指示を添えて再配布するか、中断する。

> ブラウザでの受け入れ確認（要件どおり画面が動くかの最終判定）は `/qa` の担当。ここでは作り切って得た**仕様上の気づき**を拾うことに専念する。

### Step 4: 書き出し

**4-1 仕様への書き戻し**

作り切って判明したことを、**ずれている階層に**書き戻す。UI を触って分かることは設計だけでなく要件レベルにも出るので、両方を行き先として持つ。

| 何が分かったか | 行き先 |
|---|---|
| 作るものは合っているが、**作り方**が違った（画面構成・コンポーネント分割・画面遷移・データ構造・API インターフェース・実物で判明した制約） | `design.md` に書き戻す |
| **作るものそのもの**が違った（操作順が使えない・この情報は要らない・ここに戻れる必要がある など、要件レベルの発見） | `requirements.md` は**この場で書き換えず**、Step 5 で `/spec <feature>`（編集モード）への差し戻しとして出す |

要件を変えると下流（design・tasks）も見直しが要るため、書き換えは `/spec` に委ねる（`claude/CLAUDE.md`「前進カスケード」に従う）。ここで requirements.md を直接触ると、下流の見直しが走らないまま設計だけ進む。

**設計が根本的に破綻していると分かった場合**も、design.md に判明した内容を書き戻したうえで差し戻しとして中断する。

**4-2 prototype コードを残す（1 コミット）**

```
git add -A
git commit -m "proto: <feature> 流用元の動作確認済み捨て実装"
```

> この 1 コミットは PR にならない参照用ブランチへの捨て実装なので、`/commit` スキルを通さず直接コミットしてよい（グローバル規約「必ず /commit を使う」の**明示的な例外**）。分割せず 1 コミットにまとめる。

**4-3 実サーバー検証用の PR を作成**

proto ブランチを push し、**実サーバーでの動作検証用**に draft PR を作成する。この PR は**マージされない前提**。

**CodeRabbit を動かさないこと。** 普通に PR を作ると自動レビューが走ってしまうので、PR 本文に必ず `@coderabbitai ignore` を入れる（このコマンドが本文にあると CodeRabbit はその PR のレビューをスキップする。リポジトリ側の設定に依らず効く）。

`/commit`・`/sync-to-remote` は**経由しない**（4-2 で直接コミット済みのため）。push と `gh pr create` を直接行う：

```
DEFAULT=$(git remote show origin | grep 'HEAD branch' | awk '{print $NF}')
git push -u origin <feature>-proto
gh pr create --draft --base "$DEFAULT" --head <feature>-proto --assignee @me \
  --title "[proto/DO NOT MERGE] <feature> 実サーバー検証" \
  --body "$(cat <<'EOF'
## Summary
実サーバーでの動作検証用の proto PR。**マージしない**（動作確認用の捨て実装で、品質は問わない）。正典は `design.md`。

@coderabbitai ignore
EOF
)"
```

### Step 5: 出力

次の完了カードを**コードフェンスで囲まず**プレーンテキストで出力して終了する。カードの前後に作業サマリ・所感・補足を足さない。

✅ 作り切り検証完了
<何を作り切って何が判明したかを 1 行>
- <主要な結果 最大 3 行>
📄 .specs/<feature>/design.md（更新）
🌿 <feature>-proto（流用元コードを保存）
🔗 <実サーバー検証用 draft PR の URL>（CodeRabbit なし／マージ前提ではない）

要確認:
- <design.md に書き戻しきれていない判断・実物で妥協した点>

次の一手:
▶ タスク分割に進む：/tasks <feature>

カードは**やったこと**（`✅` 〜 `🔗`）・**要確認**・**次の一手**の 3 ブロックに分ける。混ぜない。

- やったこと: 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。作り切って得た気づきの詳細は design.md に書き、カードには列挙しない。成果物は 1 件 1 行で 3 行出す（行数上限は主要な結果にだけ課す）。
- 要確認: `implementer` の `自分で決めた判断` を出す。動かすために入れた妥協（ハードコード・握りつぶした異常系）のうち、**impl が流用するときに引き継いではいけないもの**。無ければブロックごと省略する。
- 次の一手: **判明した内容で行き先が変わる**（該当する 1 行だけを出す）。
  - 設計の精度が上がっただけ → `▶ タスク分割に進む：/tasks <feature>`
  - **作るものが違った（要件レベルの発見）** → `▶ 要件を見直す：/spec <feature>`（編集モードで再入し、前進カスケードで design・tasks も見直す）
  - 設計が根本的に破綻していた → `▶ 設計を直す：/design <feature>`

**中断時**: 同じブロック構成でヘッダを `⚠ 作り切り検証中断` に差し替える。

- やったこと: 一言サマリに中断理由（本物として動かし切れない・設計の破綻など）。生成できた成果物の行は残す。
- 次の一手: 復帰コマンド（設計の破綻なら `▶ 設計を直す：/design <feature>`）。

## 出力規律
実行中の逐次ナレーション（「〜します」「〜しました」）は出さない（ツール実行はターミナルに表示されるため二重になる）。ただし Step 3 の作り切り実装と通し確認で表示が止まる区間の開始時だけ、次の 1 行を出す（1 区間 1 回）。破壊的操作の前の確認は対話なのでこの制限の対象外。

⏳ prototype: 作り切り実装とブラウザ検証を実行中…

## 完了条件
次の 4 つを満たしたら完了。次工程の起動は完了条件に含めない。

- [ ] 対象機能がローカルで本物として動き、要件どおりのフローを通せた
- [ ] 作り切って得た気づきを `design.md` に書き戻した
- [ ] 動くコードを `<feature>-proto` ブランチに 1 コミットして残した
- [ ] `@coderabbitai ignore` 入りの実サーバー検証用 draft PR を作成した（CodeRabbit が走らないこと）
