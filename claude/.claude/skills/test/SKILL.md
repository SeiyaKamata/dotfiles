# テストスキル

## 役割
実装後に**テスト・lint・フォーマットチェックなどの検証**を実行し、PASS/FAIL を判定する。

テスト実行はこのスキル自身が行う。大量のテストログをメインコンテキストに載せないよう、**出力は毎回ファイルにリダイレクトし、要点だけを `tail` / `grep` で読む**。読むのは exit code と失敗行に絞る。フルログはコンテキストに載せない。

## 入出力
- **入力**: git の状態。対象は実装ブランチ 1 本、フェーズを持たない
- **出力**: `.specs/<feature>/test-report.md`

## 引数
- `$ARGUMENTS[0]`: feature 名（必須）

## 対話方針
判定は完了カードで報告する。テストコマンドを判断できないときは**推測で実行せず中断する** — 誤ったコマンドの PASS は最も危険な嘘になる。その場で聞かず、`CLAUDE.local.md` への記載を中断カードで促す。手順は Step 3・Step 6。

## 進め方

### Step 1: 引数チェック
- `$ARGUMENTS[0]`（feature）が未指定なら「使い方: /test <feature>」を表示して終了

### Step 2: 対象確定

起動時に対象 feature と実行コンテキストを次の手順で確定する。

1. feature の確定 — 第 1 引数
2. ブランチの確定 — カレントブランチが実装ブランチ `<feature>` でなければ、まず自分で switch を試みる：
   ```
   git switch <feature>
   ```
   - switch できた → 実装ブランチ `<feature>` にいる。想定どおり
   - `<feature>` ブランチが存在しない → 現在のブランチをそのまま採用する（PR を作らない運用で直接コミットしているとみなす）
   - 未コミットの変更があって switch できない → 報告して中断する（stash などの作業ツリー操作はしない）
   - detached HEAD のまま `<feature>` も無い → `branch: none` として続行する。レポートは書けるが、後で `/fix` が行う branch 照合の材料は減る
3. head の確定 — `git rev-parse HEAD`

`/test` はフェーズを持たず実装ブランチ 1 本の上で 1 回ずつ回るため、対象の同一性は `branch` と `head` で判定できる。

### Step 3: テストコマンドの検出

次の順で採用し、決まった時点で以降は見ない。

1. `CLAUDE.local.md` の `## テスト` 節に記載があれば採用する。docker 等の実行ラッパ・複数コマンドの連結も可
2. 記載が無ければ、リポジトリ構成から**テストフレームワークのみ**フォールバック検出する。
   - `Gemfile` + `spec/` または `.rspec` → `bundle exec rspec`
   - `Makefile` に `test` ターゲット → `make test`
   - `package.json` に `test` スクリプト → `npm test` 等
   - `go.mod` → `go test ./...`
   - `pyproject.toml` / `pytest.ini` → `pytest`
   - `Cargo.toml` → `cargo test`
   - `mix.exs` → `mix test`
   - 複数該当する場合は変更されたファイルに対応するものを選ぶ
   - 決まったら次回のために `CLAUDE.local.md` に `## テスト` 節として書き戻す
3. それでも決まらなければ「対話方針」に従い中断し、Step 6 の中断カードへ進む

### Step 4: 実行・判定

```bash
<検出したコマンド> > .specs/<feature>/.test-output.log 2>&1; echo "exit:$?"
tail -n 50 .specs/<feature>/.test-output.log   # 必要なら grep -E "FAIL|PASS|passed|failed" も併用
```

読み方は `## 役割` の方針どおり。PASS/FAIL を判定する。

### Step 5: 記録

保存先は `.specs/<feature>/test-report.md` で、feature 単位の単一パスに固定する。既存の `test-report.md` があれば、上書きする前に前回の判定（PASS/FAIL）と `count` を読み、`count` の再計算に使う。

保存先パスに最新結果を毎回上書きして書き出す。frontmatter は `test-report` / `review` / `qa-report` で共通の形式:
```yaml
---
feature: stage-context-free
branch: stage-context-free             # Step 2 の確定値。detached・照合不可時は none
head: 4f8c1e9b2a...                    # Step 2 の確定値。git rev-parse HEAD。40文字、短縮しない
ran_at: 2026-07-28T22:45:00+0900       # この書き出し時点の時刻。date +"%Y-%m-%dT%H:%M:%S%z" で取得
fixed: false                           # 直前に /fix がこのレポートの対象コードを修正していたか
count: 1                               # この判定が何回連続で非 PASS/OK か。PASS/OK なら 1 にリセット
---
```

**`fixed` の決め方**: 新しいレポートを書き出すときは既存ファイルの値を読まず、**常に `fixed: false` を書く**。これは「まだ `/fix` が着手していない」というレポートの初期状態を表す。`fixed: true` に変えるのは `/fix` だけで、修正を適用したときにそのレポートの `fixed` フィールドだけを直接書き換える。判定内容は変えない — これが `/fix` の唯一のレポート更新である。

**`count` の決め方**: Step 2 で読んでおいた既存ファイルの**判定**（PASS/FAIL）と `count` を使う。今回の判定が FAIL で、かつ既存ファイルの判定も FAIL だったなら `count` を **+1** して書く。今回が PASS、または既存ファイルが無い／既存ファイルの判定が PASS だったなら `count: 1` にリセットする。これにより「何連続で失敗しているか」がレポート単体から読み取れる。

レポートに書く内訳は次のとおり。ターミナルには列挙しない。

```
## テスト結果: PASS / FAIL

- 実行数: N
- 成功: N
- 失敗: N

### 失敗したテスト（FAILの場合）
- [テスト名]: [エラー内容]
```

### Step 6: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### テスト実行完了 — PASS
<実行数と判定を 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/test-report.md`

### 要確認
- <実行時に判断で決めた点> — 例: 候補が複数あったテストコマンドの選択、スキップした対象

### 次の一手
- レビューに進む: `/review <feature>`
```

カードは 3 ブロックに分ける。**テスト実行完了**、続けて**要確認**、最後に**次の一手**。

- テスト実行完了: 見出しの末尾に判定（PASS / FAIL）を付ける。一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**。無ければ行ごと省略する。失敗テストの内訳は test-report に寄せ、カードには列挙しない。生成物は Step 2 で決めた保存先パスをそのまま出す。
- 要確認: 判定に影響しうる判断があれば挙げる。例: コマンドの選択・スキップ・環境依存。無ければブロックごと省略する。
- 次の一手: **判定は確定しているので該当する 1 行だけ**を出す。FAIL なら `- 失敗を直す: /fix <feature>` に差し替える。

**中断時**: 同じブロック構成で見出しを `### テスト実行中断` に差し替える。

- テスト実行中断: 一言サマリに中断理由。テストコマンドを判断できないなどが該当する。レポート未生成なら生成物の行は省略する。
- 次の一手: 復帰コマンド。判定が出ていないまま `/review` へ進む道は出さない。**テストコマンドを判断できずに中断した場合は、探した場所を要確認に挙げ、次の一手を次の 2 行にする**。コマンドを聞き直すのではなく、次回以降も効く形で解決させる：

```markdown
### 要確認
- テストコマンドを検出できず。探した場所: CLAUDE.local.md / package.json の scripts / …

### 次の一手
- CLAUDE.local.md にテストコマンドを記載する。例: `## テスト` に実行コマンドを 1 行
- 記載後に再実行する: `/test <feature>`
```

## 完了条件
対象確定を済ませ、テストを実行して PASS / FAIL を判定し、レポートに記録したら完了。**判定がどちらでも完了**。次工程の起動は完了条件に含めない。
