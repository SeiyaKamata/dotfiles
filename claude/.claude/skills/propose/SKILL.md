# 提案発行スキル

## 役割
パイプラインの各工程・PJ が「これは skill / pipeline 側で改善すべきだった」と気づいたとき、恒久ルールに直接書かず、dotfiles の単一キュー `.specs/proposals/` へ改善提案を発行する入口。**一行のルールに落ちる気づきだけを扱う**。構成規模の改善（複数ステップの追加・ファイルの新設・スキル本体の修正が要るもの）はキューに積まず、直接実装へ回す（現状は開発途上のため即時反映を優先し、後回しにしない）。

**書き込みと検証のみを担う。** クラスタ判定・再発判定・寿命管理はしない（単一実行では過去のキュー全体が見えないため原理的に持てない）。

## 入出力
- **入力**: 引数（`target` / `claim`）、または直前の工程文脈から組み立てた気づき
- **出力**: `<dotfiles>/.specs/proposals/<YYYYMMDD>-<target>-<claim-slug>.md` を**1 件だけ**

## 対話方針
各工程から呼ばれるが、**発行そのものは常に同じ動作**（呼び出し元による差を持たない）。

**無確認実行**: 発行の可否についてユーザーの事前承認を求めず、提案ファイルを書いて事後報告する。

**恒久ルール（`CLAUDE.md`）へ勝手に追記しない。** 反映するかは人が判断する。

## 引数
- 第 1 引数: `target`（対象スキル名。例 `review`）
- 第 2 引数以降: `claim`（一行の主張）
- 省略時はプロンプト本文・直前の工程文脈から組み立てる。組み立てられなければ発行しない（Step 2 の敷居）

## 提案ファイルのスキーマ
frontmatter とその意味は次のとおり（**このスキルが正本**。`.specs/proposals/` 配下にスキーマ用ファイルは無く、この節が唯一の定義）。

```markdown
---
target: <対象。下記「target の語彙」参照>
claim: <一行の主張。CLAUDE.md か対象スキルにそのまま追記できる一行。固有名詞を含めず一般化する>
date: <YYYY-MM-DD>
source_feature: <発行元 feature 名。不明なら「不明」>
status: open | applied | deferred | dropped
---

<本文。claim の背景・根拠を簡潔に>
```

**status の語彙**（発行時は常に `open`。以降の遷移は、気づいた人・セッションがその都度手動で行う）
- **`open`**: 未判断
- **`applied`**: 成果物に反映済み
- **`deferred`**: 判断済みで、今は着手しない
- **`dropped`**: 破棄

**target の語彙**（単一値のみ。リストは取らない）
- **スキル名**（例 `review` `commit` `spinoff`）: 対象が 1 スキルに収まる
- **`CLAUDE.md`**: 恒久ルール宛
- **`pipeline`**: 複数スキル・ドキュメントに跨り代表を 1 つに絞れないルール。使うときは対象群を本文に列挙する（frontmatter は単一値を保つ）

**claim の敷居**: そのまま `CLAUDE.md` か対象スキルに追記できる一行で書けないときは発行しない（Step 2 参照）。

## 進め方

### Step 1: 受付判定
気づきの種類を次の 4 分岐で判定する。判定は**カレント PJ に依存させない**（dotfiles 内で起動していても同じ基準で判定する）。

| 判定 | 行き先 |
|---|---|
| 一行のルールに落ちる（`CLAUDE.md` か対象スキルに 1 行足せば次回以降防げる） | Step 2 → 発行 |
| 構成規模（複数ステップの追加・ファイルの新設・スキル本体の修正が要る） | 発行せず、直接実装へ回して中断する。カレントが dotfiles ならこのセッションで直接編集する。PJ セッションからなら `ListAgents` で稼働中の dotfiles セッションを探し、`SendMessage` で実装を依頼する |
| skill / pipeline の改善ではなく**プロダクト側**のスコープ切り分け | 発行せず `/spinoff`（棚上げ）・別 PJ セッションとの会話（ブロッカー）を案内して中断 |
| 再発しない訂正（その場限りのタイポ・パス違い） | 何もせず終了 |

**完了ゲート:** 4 分岐のどれかに確定したか。

### Step 2: target・claim の確定（発行の敷居）
- `target`: スキル名・`CLAUDE.md`・`pipeline` のいずれか。引数または文脈から確定する
- `claim`: 「claim の敷居」に沿って一行で書く。書けないときは発行しない

**完了ゲート:** `target`・`claim` の 2 つが揃ったか（**1 つでも欠けていたら Write しない**）。

### Step 3: 発行

**3-1 発行先の判定**

開発中は対象 PJ のセッションと並行して dotfiles の `claude` セッションが常駐していることが多い。常駐セッションがあるならそちらに発行させ、無ければ現行どおり自セッションから直接書く。

1. カレント作業ディレクトリが dotfiles ルート配下（3-2 の symlink 解決結果と一致）なら、**このセッション自身が発行元**。委譲せず 3-2 以降をそのまま自セッションで実行する
2. それ以外（PJ セッションから呼ばれた場合）:
   1. `ListAgents` を呼び、稼働中セッションのうち名前から dotfiles と一意に判別できるものが**ちょうど 1 件**あるか確認する
   2. 1 件に絞れたら、そのセッションへ `SendMessage` で発行を依頼する。確定済みの `target`・`claim`・`source_feature` をそのまま渡し、「この内容で `.specs/proposals/` に 1 件発行してほしい」と伝える。委譲した時点でこのセッションの `/propose` は完了とする（返信は待たない）
   3. **0 件、または複数件で一意に絞れない場合は、3-2 以降の直接 Write にフォールバックする。** 常駐セッションの有無を確認できないことは発行を止める理由にしない — フォールバックの事実は Step 4 の完了カードに明記する

**3-2 キューの解決**（自セッションで直接 Write する場合）

symlink からハードコードせず動的に解決する。**`readlink` `test` `mkdir` は使わない** — ハーネスの allow リストにも組み込みの read-only コマンド群にも無く、毎回パーミッション判定に回って承認待ちの原因になるため。使ってよいのは `ls` / `date` と `Glob` / `Read` / `Write`。

1. `ls -ld ~/.claude/skills` を実行し、出力の `->` の右側から symlink 先を得る。相対パスなら `~/.claude/` 基準で解決する
2. 得られたパスから末尾の `/claude/.claude/skills` を取り除いた部分が dotfiles ルート。そこに `/.specs/proposals` を付ける
3. **フォールバック**（`->` が出ない・symlink でない環境）: `Glob` で `~/Develop` 配下から `**/claude/.claude/skills/propose/SKILL.md` を探し、マッチから末尾の `/claude/.claude/skills/propose/SKILL.md` を取り除いた部分を dotfiles ルートとする
4. どちらでも解決できないときは、その旨を明示エラーとして報告し**発行を中止する**

ディレクトリの存在確認も作成もしない（`Write` が親ディレクトリを作る）。

**3-3 ファイル名**

命名規則: `<YYYYMMDD>-<HHMMSS>-<target>-<claim-slug>.md`

- プレフィックスは `date +"%Y%m%d-%H%M%S"` で取得する。秒まで入れるのは、同一セッションで同じ target に複数発行しても衝突させないため（衝突しないので一覧による確認が要らなくなる）
- `claim` を kebab-case 化し先頭数語を `claim-slug` とする
- **同名衝突の確認はしない。** キューを `ls` / `Glob` で一覧しない — 既存提案のファイル名が視界に入ると、`/propose` が持たないはずの再発判定に踏み込む誘因になる

**3-4 Write**

「提案ファイルのスキーマ」に従い、確定したファイル名に**1 件だけ**書く（`status: open`、`date` は当日、`source_feature` は発行元 feature 名か「不明」）。

**再発があるかは調べない。** 同種の提案が既にキューにあっても気にせず、毎回 1 件を投げるだけにとどめる（再発判定・クラスタ化はしない）。

**完了ゲート:** 委譲した（3-1-2 で `SendMessage` 済み）か、提案ファイルを自セッションで 1 件 Write したか。

### Step 4: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。`/spinoff` は自動起動しない。

```markdown
### 提案発行完了
<target と claim を 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/proposals/<提案ファイル>`

### 次の一手
- 内容を確認し、`CLAUDE.md` / 対象スキルへの反映要否を判断する（人）
```

カードは**やったこと**・**次の一手**の 2 ブロックに分ける（発行内容は無確認で確定するが、`claim` 自体がその要約なので「要確認」は持たない）。

- やったこと: 一言サマリは 1 行（`target`・`claim` を示す）。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。根拠の詳細は提案ファイルに書き、カードには列挙しない。3-1 で委譲した場合は「dotfiles セッションへ委譲（SendMessage）」を、0 件/複数件でフォールバックした場合は「常駐セッション未特定のため自セッションで直接発行」を主要な結果に含める
- 生成物: 委譲した場合はパスが確定しないため `生成物: 委譲先セッションでの発行報告待ち` に差し替える。自セッションで書いた場合は従来どおりフルパスを示す
- 次の一手: 委譲した場合は `- 委譲先セッションからの発行報告を待つ` に差し替える

**中断時**（発行しなかった場合を含む）: ヘッダを `### 提案発行中断` に差し替え、一言サマリに理由（`claim` を一行で書けない・構成規模で直接実装へ回した・プロダクト側のスコープ切り分け・symlink 未設置など）、次の一手に代わりの行き先（`- 直接実装へ進める（自セッション or SendMessage 委譲）`、`- 棚上げする: /spinoff`、`- 別 PJ セッションと会話して詰める`）を書く（ファイル未生成なので生成物の行は省略する）。

## エラー処理
- **キューの解決に失敗する**（`ls -ld ~/.claude/skills` が symlink を示さず、Glob フォールバックも空）→ 発行を中止し、明示エラーとして報告する
- **`target` / `claim` のどちらかが確定できない** → 発行しない（Step 2 の敷居）

## 完了条件
次の 4 つの出口のいずれかに到達したら完了。**`target`・`claim` を確定できない状態では Write しない。**

- **rule 発行**: 1 件発行し、フルパスと `claim` を報告できた
- **構成規模につき直接実装へ回して終了**: 発行せず、直接実装（自セッション、または `SendMessage` 委譲）へ回した
- **案内して終了**: プロダクト側のスコープ切り分けと判定し、発行せず `/spinoff`・別 PJ セッションとの会話を案内した
- **何もせず終了**: 再発しない訂正と判定し、どちらにも回さず終了した
