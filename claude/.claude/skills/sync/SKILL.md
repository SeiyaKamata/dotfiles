# 既存PR更新スキル

## 役割
既に PR を持つブランチに積んだコミットをリモートへ push し、更新後の状態を PR に反映する。
`.specs/<feature>/comment-report.md` があれば、push の直後に承認済み項目への返信と `issues.md` 記録まで行う。

**返信は必ず push の後に行う。**
push より前に返信すると、リモートのコードがまだ古いままなのに「直しました」と返信することになり、レビュアーや CodeRabbit に「直っていない」と指摘され直す。
このスキルが push と返信をひとつの流れにまとめているのはそのため。

**新しい PR を作ることはしない。**
まだ PR を持たないブランチの初回着地、次のフェーズの新規 PR 作成は `/land` の責務。

**コード修正はしない。**
それは `/fix` の責務。
スレッドの「解決済み」化はしない。
解決はレビュアーに委ねる。

対応中にレビュアーの恒常的な好みや PJ の規約などの摩擦に気づいたら、`claude/CLAUDE.md`「ハーネスの自己強化」の「PJ 固有の運用知識の発見」に従い、そのリポジトリの `CLAUDE.local.md` に書き戻す。

## 入出力
- 入力: カレントブランチ、または引数の feature 名から解決したブランチのコミット済みの差分。
  `.specs/<feature>/comment-report.md`。あれば
- 出力: リモートへの push。
  `comment-report.md` があれば、加えて PR への返信と `.specs/<feature>/issues.md`。非対応・保留の記録

## 用語（前提）
用語は `claude/CLAUDE.md`「用語集」に従う。

## 返信文言
Step 4 で返信を組み立てるときの基準。

**返信は 2〜3 文以内に収める。**
冒頭の根拠と結論だけを書き、経緯や検討過程は書かない。
長い説明が要る場合は issues.md に詳細を残し、返信には要点だけ書く。

**全レコードへの返信を必須とする。**
対応・非対応・保留のいずれでも。
保留も返信しないとスレッドが未返信のまま残り、次の `/triage-comments` で再収集されて同じ判断を繰り返す。
非対応と決めたコメントには理由を、保留にしたコメントには何が確認できていないかを添える。

**根拠は comment-report.md の引用をそのまま使う。**
`comment-report.md` の「要件照合」欄に記録された引用を返信本文の冒頭に置き、結論を続ける。

| ケース | 返信 |
|---|---|
| 矛盾 | `本 feature の要件「<要件名>」の受け入れ条件「<該当行を転記>」と矛盾するため、コードは変更しません。` |
| 矛盾。要件側を直すべき | 上記に続けて `ご指摘の方が妥当と考えるため、要件そのものの見直しが必要と判断しました。このスレッドではコードを変更しません。` |
| スコープ外 | `本 feature のスコープ外です。「含まない」と定めた項目「<該当項目を転記>」に該当するため、この PR では対応しません。理由: <理由>` |
| 要件の意図への回答 | `本 feature の要件「<要件名>」/ スコープの「<項目を転記>」を根拠に回答します。<結論>` |
| 対応済み | `ご指摘の通り修正しました。<修正内容の要点>` |
| 保留 | `ご指摘の条件が成立するかを実コードで確認できていないため、この PR では保留とし別途記録しました。確認した範囲: <範囲>／不明点: <不明点>` |
| 根拠が見つからない | 断定せず `本 feature の要件を確認しましたが該当する記述が見つかりませんでした。確認した範囲: <範囲>／不明点: <不明点>` |

## 進め方

### Step 1: 対象ブランチの特定

```
CURRENT=$(git branch --show-current)
```
feature 名は引数で指定されていればそれ、無ければ `CURRENT` から `-p<数字>` を除いて求める。

対象ブランチに既存 PR があるか確認する：
```
gh pr view --json number,url,headRefName
```
PR が無ければ中断する。
復帰コマンドは `/land <feature>`。
「既存 PR への更新」がこのスキルの前提であり、まだ PR が無いブランチはここでは扱わない。

**完了ゲート:** 対象ブランチと PR を特定したか。

### Step 2: push

```
git push
```
未 push のコミットが無ければ push はスキップし、Step 3 へ進む。

**完了ゲート:** push が完了した、または push すべきコミットが無いことを確認したか。

### Step 3: comment-report.mdの読込

`.specs/<feature>/comment-report.md` を Read する。
無い、または `[ ]` の項目が 1 つも無ければ Step 7 へ進む。

`[ ]` の項目だけを対象にし、承認欄を見て次に振り分ける：

| 承認欄 | 扱い |
|---|---|
| `対応する` | `/fix` の修正結果と突き合わせ、修正済みなら Step 4 で返信対象、未修正なら要確認に回す |
| `対応しない` | Step 4 で返信対象 |
| `保留` | Step 4 で返信対象。加えて Step 5 で issues.md に記録 |
| 空欄・未記入 | 承認待ちとして要確認に回す。返信対象から外す |

`[x]` の項目は処理済みなので読み飛ばす。

**完了ゲート:** 全項目が上記いずれかに振り分けられたか。

### Step 4: 返信

「## 返信文言」の基準に従って、対応する / 対応しない / 保留 と確定した項目に返信を組み立てる。
`対応する` の項目は `/fix` の修正内容を要点として使う。
`保留` の項目は `comment-report.md` の裏取り欄に記録された確認範囲と不明点を使う。

インラインコメントへの返信：
```
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<comment_id>/replies \
  -X POST -f body="<返信内容>"
```

会話コメントへの返信: PR コメントで返す。
```
gh pr comment <PR番号> --body "<返信内容>"
```

返信が失敗した場合、失敗したコメントを特定できる情報、`id` / `path` / `line` のうち特定できるもの、と失敗理由を Step 7 に渡して報告する。
失敗した項目は Step 6 でチェックしない。

スレッドの解決済み化はしない。
「役割」参照。

**完了ゲート:** 対応する / 対応しない / 保留 と確定した全項目への返信が済んだか。

### Step 5: issues記録

「対応しない」と決めた項目、または「保留」の項目が 1 件以上ある場合、`.specs/<feature>/issues.md` に追記する。
要件と矛盾する指摘は要件側を直すべきと判断したものを含め、スコープ外の指摘も記録対象に含める。
ファイルが無ければ新規作成する。

```markdown
## 残対応。PR #<番号> で見送り

- [ ] <コメントの要点> <!-- <対応しない理由> -->
- [ ] <コメントの要点> <!-- 保留: <その場で判断できなかった点> -->
```
保留は `保留:` で始まるコメントを持つ点だけが非対応と異なる。
記録先・フォーマット本体は変えない。
同じ PR 番号の「残対応」セクションが既にあればその末尾に追加し、無ければファイル末尾に新規セクションを追加する。

**完了ゲート:** 非対応・保留を issues.md に記録したか。

### Step 6: comment-report.mdのチェック

返信または issues.md 記録まで済んだ項目の `[ ]` を `[x]` にする。
承認待ち・未修正・返信失敗の項目は `[ ]` のまま残す。
項目は削除せず、冒頭の未対応件数を `[ ]` の数に更新する。
対応済みが履歴として残り、次に `/triage-comments` が実行されたとき `[x]` を再提示しない。

**完了ゲート:** 処理済み項目を `[x]` にし、未対応件数を更新したか。

### Step 7: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### 更新完了
<push したコミット数と、comment-report.md を処理したかを 1 行>
- <対応件数・非対応件数・保留件数を 1 行。comment-report.md が無ければ省略>

生成物: <対象 PR の URL>
<comment-report.md を処理した場合、非対応・保留を issues.md に追記していれば>`.specs/<feature>/issues.md`

### 要確認
- 承認待ち <n> 件。comment-report.md の承認欄が空欄
- 未修正 <n> 件。承認欄は `対応する` だが /fix が未着手

### 次の一手
- CI を再監視する: `/watch-ci`
```

- やったこと: comment-report.md が無い、または `[ ]` の項目が無ければ 2 行目以降は省略する。
  コメントごとの指摘・返信内容はカードに列挙せず、PR のスレッドに寄せる。
- 要確認: 承認待ち・未修正が残っている場合に出す。
  無ければブロックごと省略する。
- 次の一手: 修正を push しただけなら `- CI を再監視する: /watch-ci`。
  承認待ち・未修正が残っているなら `- 承認・修正を待って再実行: /sync`。

**中断時**: 同じブロック構成でヘッダを `### 更新中断` に差し替える。

- やったこと: 一言サマリに中断理由。
  PR が存在しない・push が拒否された・comment-report.md が壊れている、などが該当する。
- 次の一手: 復帰コマンド。
  PR が無ければ `- 新規に着地させる: /land <feature>`。

## エラー処理
- push が拒否された（リモートが先行している）→ 自動で `git pull --rebase` はしない。
  コンフリクトの温床になるため、状況を報告して中断する

## 完了条件
- 対象 PR へ push した。または push すべきコミットが無いことを確認した
- `comment-report.md` があれば、`対応する` / `対応しない` / `保留` の全項目への返信が完了し、非対応・保留を issues.md に記録した
