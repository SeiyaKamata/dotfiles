# 既存PR更新スキル

## 役割
既に PR を持つブランチに積んだコミットをリモートへ push し、`.specs/<feature>/comment-report.md` があれば承認済み項目への返信と `issues.md` への記録まで行う。
返信は必ず push の後に行う。先に返信するとリモートのコードが古いまま「直しました」と伝えることになり、直っていないと指摘され直す。
新しい PR は作らず、コードも直さず、スレッドの解決済み化もしない。

## 返信文言

- 返信は 2〜3 文以内に収め、結論と理由だけを書く
  - 長い説明が要るなら issues.md に詳細を残す
- 対応・非対応・保留のいずれでも全レコードに返信する
  - 返信しないとスレッドが未返信のまま残り、次の収集で同じ判断を繰り返す
- 理由は 1 文で書き、内部ドキュメントの名前や節は出さない
  - レビュアーは `.specs/` を読めない

| ケース | 返信 |
|---|---|
| 意図どおり | `仕様上この挙動が意図どおりのため、この PR では変更しません。<理由を 1 文>` |
| スコープ外 | `この PR のスコープ外のため対応しません。<理由を 1 文>` |
| 対応済み | `ご指摘の通り修正しました。<修正内容の要点>` |
| 保留 | `この PR では判断できないため保留とします。確認した範囲: <範囲>／不明点: <不明点>` |

## issues.md のフォーマット

同じ PR 番号の「残対応」節が既にあればその末尾に追加し、無ければファイル末尾に節を追加する。
ファイルが無ければ新規作成する。

```markdown
## 残対応。PR #[番号] で見送り

- [ ] [コメントの要点] <!-- [対応しない理由] -->
- [ ] [コメントの要点] <!-- 保留: [その場で判断できなかった点] -->
```

## 進め方

### Step 1: 対象ブランチと PR の特定

```
CURRENT=$(git branch --show-current)
gh pr view --json number,url,headRefName
```

feature 名は引数があればそれ、無ければ `CURRENT` にする。
PR が無ければ Step 7 の中断カードで報告して終了する。

### Step 2: push

```
git push
```

未 push のコミットが無ければ push を飛ばして Step 3 へ進む。
リモートが先行していて拒否されたら、`git pull --rebase` はせず Step 7 の中断カードで報告して終了する。

### Step 3: comment-report.md の読込

`.specs/<feature>/comment-report.md` を読む。
無い、または `[ ]` の項目が 1 つも無ければ Step 7 へ進む。
`[ ]` の項目だけを承認欄で振り分ける。

| 承認欄 | 扱い |
|---|---|
| `対応する` | 修正結果と突き合わせ、修正済みなら Step 4 で返信、未修正なら要確認に回す |
| `対応しない` | Step 4 で返信 |
| `保留` | Step 4 で返信し、Step 5 で issues.md に記録 |
| 空欄 | 承認待ちとして要確認に回し、返信しない |

### Step 4: 返信

「返信文言」に従い、対応する / 対応しない / 保留 と確定した項目に返信する。
`対応する` は修正内容を要点に、`保留` は `comment-report.md` の裏取り欄の確認範囲と不明点を使う。

インラインコメントへの返信:
```
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<comment_id>/replies \
  -X POST -f body="<返信内容>"
```

会話コメントへの返信:
```
gh pr comment <PR番号> --body "<返信内容>"
```

返信が失敗した項目は、`id` / `path` / `line` のうち特定できるものと失敗理由を控えて Step 7 で報告し、Step 6 でチェックしない。

### Step 5: issues 記録

「対応しない」と「保留」の項目が 1 件以上あれば、「issues.md のフォーマット」で `.specs/<feature>/issues.md` に追記する。
要件側を直すべきと判断した矛盾、スコープ外の指摘も記録対象に含める。

### Step 6: comment-report.md のチェック

返信または issues.md 記録まで済んだ項目の `[ ]` を `[x]` にし、冒頭の未対応件数を `[ ]` の数に更新する。
承認待ち・未修正・返信失敗の項目は `[ ]` のまま残し、項目は削除しない。

### Step 7: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### 更新中断` にし、1 行目に中断理由を書き、次の一手は PR が無ければ `/land <feature>`、push が拒否されたなら状況の確認後に `/sync` を再実行する旨にする。

```markdown
### 更新完了
<push したコミット数と、comment-report.md を処理したかを 1 行>
- <対応件数・非対応件数・保留件数を 1 行。comment-report.md を処理していなければ省略>

生成物: <対象 PR の URL>
<issues.md に追記していれば>`.specs/<feature>/issues.md`

### 要確認
- 承認待ち <n> 件。comment-report.md の承認欄が空欄
- 未修正 <n> 件。承認欄は `対応する` だが修正が未着手
- 返信失敗 <n> 件。<特定情報と理由>

### 次の一手
- CI を再監視する: `/watch-ci`
- 承認待ち・未修正・返信失敗が残っていれば、解消してから再実行: `/sync`
```

要確認は該当する行だけを出し、無ければブロックごと省略する。
