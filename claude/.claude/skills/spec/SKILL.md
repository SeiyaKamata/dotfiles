# 要件策定スキル

## 役割
ユーザーの要望から EARS 形式の要件ドキュメントを作る。
「何を作るか」だけを扱い、技術的な実装方法を含む「どう作るか」は書かない。
`status: confirmed` の確定稿を書くのは `/spec` だけだけ。

## 判断が割れる点の扱い
途中でユーザーに質問もスコープ承認もしない。
判断が割れる点は最も素直な解釈を採って進め、採った解釈は該当する行の下に、インデントを下げた `【要確認】<採った解釈と理由>` の行で付記する。

## 受け入れ条件の書き方

### 観点

- **ユーザー行動**: ユーザーが X をしたとき何が起きるべきか。常に埋める
- **エラーケース**: 異常系・境界値の振る舞い。常に埋める
- **非機能要件**: 性能・セキュリティ・可用性の期待値。影響する変更のときだけ埋め、無ければ Requirement を起こさない

ユーザー行動・エラーケースの情報が下書きにも要望にも無ければ「判断が割れる点の扱い」節に従う。

### 型

型は EARS の 5 型で分けるが、**文は日本語語順で書く**。

| 型 | 書き方 | 目印 |
|---|---|---|
| 常時 | `<振る舞い>` | 矢印なし |
| イベント駆動 | `<イベント>とき → <振る舞い>` | 「とき」 |
| 状態駆動 | `<前提>あいだ → <振る舞い>` | 「あいだ」 |
| オプション機能 | `<機能・条件>の場合 → <振る舞い>` | 「場合」 |
| エラー処理 | `【異常】<トリガー> → <振る舞い>` | `【異常】` |

オプション機能型は、権限・プラン・機能フラグのように**恒常的な構成の有無**で分岐する要件に使う。
一時的なトリガーなら「とき」、継続する状態変化なら「あいだ」を使い、オプション機能型と混同しない。

### 主体の書き方

主体ごとに `###` の節を立て、その下に Requirement を `####` で並べる。
各行は主語を落として「条件 → 振る舞い」に揃える。
1 つの Requirement の主体は 1 つにする。
流れの中で主体が入れ替わるときは Requirement を主体ごとに分け、受け手側の条件に相手の動作を書く。
Requirement 番号は主体の節をまたいで連番にする。

### 文の書き方

- 括弧は「あれば」「任意」のような 1〜2 語のラベルだけに使う
  - 理由や値の組のような文の形をした補足は括弧に押し込めず、別行か読点で切る
- 受け入れ条件の行は、トリガーと結果が観測できる振る舞いだけにする
  - 用語や値の定義は、それを使う振る舞いの行に組み込む
  - 変更しない範囲や絞り込まない範囲の宣言は、スコープ外に置く
- 1 行に 1 振る舞いだけ書く
  - 同じ条件で結果だけが違う項目に限り 1 行へ畳んでよい
- 1 Requirement は、判定の軸が 1 つの塊だけにする
  - 軸が複数あるなら Requirement を分ける
- Requirement の見出しは、動機を書かなくても目的が読み取れる粒度まで分ける
- 例示は書かず、条件を言い切る
- 「適切に」「必要に応じて」のような曖昧語は避け、テスト可能・検証可能な表現にする

## requirements.md のフォーマット

検討経緯・却下した代替案は書かず、決まったことだけを書く。

```markdown
---
status: confirmed
repo: [この feature を実装するリポジトリ。bare repo のディレクトリ名]
notion_url: [下書きにあれば引き継ぐ。無ければ空文字]
pr_title: [下書きにあれば引き継ぐ。無ければ空文字]
branch_name: [下書きにあれば引き継ぐ。無ければ空文字]
---

# 要件定義: [機能名]

## 概要
[機能の目的と背景を2〜3文で]

[Requirement 全体に関わるなど、特定の 1 行に紐づかない要確認があれば `【要確認】<内容>` を 1 行で。無ければ書かない]

## スコープ外
[項目の行は外すものだけを書く。EARS は使わない。別 feature での扱いなどの補足は理由に畳む]

- [外すもの]
  - 理由: [なぜ外すか]
  - 【要確認】[判断で埋めたときだけ。採った解釈]

## 要件

### [主体]

#### Requirement 1: [要件名]
- [振る舞い]
- [イベント]とき → [振る舞い]
  - 【要確認】[判断で埋めたときだけ。採った解釈と理由]
- 【異常】[トリガー] → [振る舞い]

#### Requirement 2: [要件名]
...

### [別の主体]

#### Requirement 3: [要件名]
...

## 付録: [表題]
[表は行数にかかわらず全部ここに置き、スコープ外節と受け入れ条件からは「詳細は付録」と 1 行で参照する。無ければ節ごと省略]
```

## 進め方

### Step 1: 開始 Step の判定

- `.specs/requirements.md` が無く、会話文脈にも要望が無ければ「使い方: /spec <要望>」を表示して終了
- frontmatter の `repo` は、今いる worktree の `git rev-parse --path-format=absolute --git-common-dir` の basename から採る

`.specs/requirements.md` の有無と frontmatter の `status`、変更要望で分岐する:
- **無い**: 新規。Step 2 から書き起こす
- **有る + `status: draft`**: 下書き。本文を要望の材料として使い、Step 2 から詳細化する
- **有る + `status: confirmed` + 変更要望あり**: 該当箇所だけを直し、要望に無い不備は気づいても直さない
  - 境界に関わる要望なら Step 2 から、そうでなければ Step 3 から
- **有る + `status: confirmed` + 変更要望なし**: Step 2〜5 を飛ばし、Step 6 で「変更なし」と報告して終了

### Step 2: スコープ境界

out-of-scope を列挙する。
in-scope は列挙せず、Step 3 で Requirement に起こす。
要望から in/out を確定できない項目は、「判断が割れる点の扱い」節に従う。

### Step 3: 受け入れ条件化

in-scope の項目**だけ**を Requirement に起こす。
埋める観点・型・書式は「受け入れ条件の書き方」に従う。

要望が実質的に空で Requirement を 1 つも起こせないときだけ中断し、Step 6 の中断カードで報告する。

### Step 4: 書き出し

Step 2〜3 の内容を「requirements.md のフォーマット」で `.specs/requirements.md` に書く。

### Step 5: 点検

書き出した `requirements.md` が「受け入れ条件の書き方」と「requirements.md のフォーマット」を満たしているか見直し、外れていれば直してから Step 6 へ進む。

### Step 6: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### 要件定義中断` にし、1 行目に中断理由と `requirements.md` が未確定である旨を書き、次の一手は `/spec` だけにする。

```markdown
### 要件定義完了
<何を要件化したかを 1 行>

生成物: `.specs/requirements.md`

### 要確認
<件数>件。無ければこのブロックを省略

### 次の一手
- 実装計画に進む: `/plan`
- 要件を直す: `/spec`
```
