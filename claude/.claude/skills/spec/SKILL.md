# 要件策定スキル

## 役割
ユーザーの要望から EARS 形式の要件ドキュメントを作る。
「何を作るか」だけを扱い、「どう作るか」は `/design` に委ねる。
DB やフレームワークの選定といった技術的な実装方法は要件に含めない。

要望を受け取ってから確定稿ができるまでの唯一の入口でもある。
feature 名の決定・衝突チェックも `/spec` 自身が行うため、要望を思いついたらまずここから始める。
`/spinoff`・`/notion-import` が `status: draft` の `requirements.md` を先に置いていく場合もあり、
そのときは下書きの詳細化として扱う。
詳細は「進め方」を参照。

## 入出力
- **入力**:
  - 会話で渡された要望
  - `.specs/<feature>/requirements.md`(あれば。`status: draft` の下書き、または `status: confirmed` の確定稿)
- **出力**:
  - `.specs/<feature>/requirements.md`(frontmatter に `status: confirmed` を持つ)

## 再実行時の扱い
`requirements.md` を直したいときは `/spec <feature>` を再実行する。
既存をベースに、渡された変更要望に該当する箇所だけを直す。
白紙に戻さず、変更要望に無い不備は気づいても直さない。
変更要望が無ければ書き換えず「変更なし」と報告する。
`status: draft` の下書きを詳細化するときも同じ扱いで、書き出し時に `status: confirmed` へ更新する。

## 対話方針
途中でユーザーに何も聞かない。
質問もスコープ承認もしない。
feature 名の決定・衝突チェック・別名採番も判断が割れる点として扱い、最も素直な解釈を採って自分で確定する。
判断が割れる点は止まらずに最も素直な解釈を採り、**採った解釈は該当箇所に `【要確認: 理由】` を付記する**。

## 受け入れ条件の書き方

### 観点

埋める観点:
- **ユーザー行動**: ユーザーが X をしたとき何が起きるべきか。
  常に埋める
- **エラーケース**: 異常系・境界値の振る舞い。
  常に埋める
- **非機能要件**: 性能・セキュリティ・可用性の期待値。
  影響する変更のときだけ埋め、無ければ Requirement を起こさない

ユーザー行動・エラーケースの情報が下書きにも要望にも無ければ「対話方針」節に従う。

### 型

型は EARS の 5 型で分けるが、**文は日本語語順で書く**。

| 型 | 書き方 | 目印 |
|---|---|---|
| 常時 | `<振る舞い>` | 矢印なし |
| イベント駆動 | `<イベント>とき → <振る舞い>` | 「とき」 |
| 状態駆動 | `<前提>あいだ → <振る舞い>` | 「あいだ」 |
| オプション機能 | `<機能・条件>の場合 → <振る舞い>` | 「場合」 |
| エラー処理 | `【異常】<トリガー> → <振る舞い>` | `【異常】` |

オプション機能型は、権限・プラン・機能フラグのように**恒常的な構成の有無**で分岐する要件に使う。
一時的なトリガーなら「とき」、継続する状態変化なら「あいだ」を使い、オプション機能型と混同しない。

### 主体の書き方

Requirement ごとに主体を独立行で 1 回宣言し、各行は主語を落として「条件 → 振る舞い」に揃える。
主体が 1 つに定まらないときは主体行を省き、各行の先頭に `` `/tasks`: `` のように主体を置く。
主体が混ざる Requirement は分割を先に検討する。
主体行を省いた Requirement は、要件サマリ表の主体列に関与する主体を `・` 区切りで併記する。

### 文の書き方

- 括弧は「あれば」「任意」のような 1〜2 語のラベルだけに使う。
  理由や値の組のような文の形をした補足は括弧に押し込めず、別行か読点で切る。
- 1 行に 1 振る舞いだけ書く。
  同じ条件・同じ主体で結果だけが違う項目に限り 1 行へ畳んでよい。
- 1 Requirement あたり **6 行**を目安にし、超えるなら Requirement 自体を分ける。
- 「適切に」「必要に応じて」のような曖昧語は避け、テスト可能・検証可能な表現にする。

### 説明文との重複禁止

Requirement の説明文と受け入れ条件を重複させない。
説明文は動機、つまり「なぜこの要件が要るか」に絞り、「何をするか」は受け入れ条件だけに書く。
両方に同じ内容が出てくるなら説明文を削る。

## 進め方

### Step 1: 引数チェック・feature 名決定

- `$ARGUMENTS[0]` があれば kebab-case・3〜5 語程度に正規化し、feature 名の候補にする
- 無ければ会話文脈の要望から同じ制約で候補を生成する
- 引数も要望も無ければ「使い方: /spec [feature]」を表示して終了

候補について `.specs/<候補>/requirements.md` の有無を確認する:
- **既に存在する**: 再実行なので、その feature 名をそのまま使う
- **存在しない**: 新規。`Glob(".specs/*")` で既存 feature と衝突するか確認し、
  衝突するときは区別できる別名を自動採番する。
  末尾に連番や区別可能な語を足す。
  ユーザーに確認しない

**完了ゲート:** 既存の再実行か、衝突しない新規 feature 名かのいずれかを確定したか。

### Step 2: コンテキスト収集
読み込む:
- `.specs/<feature>/requirements.md`(あれば)

`requirements.md` の有無と frontmatter の `status`、変更要望で分岐する:
- **無い**: Step 3 から書き起こす
- **有る + `status: draft`**: `/spinoff`・`/notion-import` が置いた下書き。
  本文を要望の材料として使い、Step 3 から詳細化する。
  frontmatter の `notion_url`・`pr_title`・`branch_name` は確定稿にもそのまま引き継ぐ
- **有る + `status: confirmed` + 変更要望あり**: 「再実行時の扱い」に従い該当箇所だけ直す。
  境界に関わる要望なら Step 3 から、そうでなければ Step 4 から
- **有る + `status: confirmed` + 変更要望なし**: Step 3〜7 を飛ばし、Step 8 で「変更なし」と報告して終了

### Step 3: スコープ境界

in-scope / out-of-scope を 1 項目 1 行の箇条書きで列挙する。
EARS は使わない。
out-of-scope には「なぜ含まないか」を必ず併記する。

要望から in/out を確定できない項目は、「対話方針」節に従う。


### Step 4: 受け入れ条件化

in-scope の項目**だけ**を Requirement に起こす。
埋める観点・型・書式は「受け入れ条件の書き方」に従う。

要望が実質的に空で Requirement を 1 つも起こせないときだけ中断し、Step 7「要件定義中断」に従って報告する。

### Step 5: 分割候補の判定

Requirement が出揃ったら、次の 3 条件をすべて満たす部分集合が無いか確認する。
**既定は分割しない。**
**「大きい」は分割の理由にしない。**
大きさは 3 条件を点検するきっかけにとどめる。

1. **単独で価値が成立する**: 片方が無くてももう片方の価値が成立する
2. **受け入れ条件が相互参照しない**: 一方の期待値が他方の挙動を前提にしない
3. **新しい契約の両端を跨がない**: 新規 API の提供側と利用側、スキーマとその読み手のような組は同一 feature に置く。
   片方だけ着地すると壊れる

**候補があっても分割は実行しない**。
単一 feature として書き切り、要件サマリ表の直後に `【要確認】分割候補: Requirement N〜M（3 条件を満たす根拠）` を挙げる。
切り出しは人が完了カードの案内から `/spinoff` を起動して行う。

切り出し後に再実行されたときは、該当 Requirement を `## スコープ` の「含まない」へ理由付きで移す。

### Step 6: quick判定

`/quick`、design/tasks を介さない軽量ルート、を使うべきかを次の 3 条件で判定する。
判断基準はここが正本で、`/quick` 自身は判定ロジックを持たない。
- 変更が単一の関心事に閉じている。複数の大タスクに分ける意味がない
- 新規の外部インターフェース、API・DB スキーマ・画面構成、を伴わない
- 実装方針で悩む余地がない。設計判断そのものが不要

3 条件をすべて満たす → `quick_eligible: true`。
1 つでも外れる、または判定に迷う → `quick_eligible: false`。
迷ったときは design/tasks を経由する通常パイプラインに倒す。
design/tasks を飛ばして後戻りするコストの方が高い。

判定根拠を要件サマリ直後に `【要確認】quick判定: <true/false>。理由: <理由>` として 1 行残す。

**完了ゲート:** `quick_eligible` を true/false のいずれかに確定したか。

### Step 7: 書き出し
Step 3〜6 の内容を次のフォーマットで `.specs/<feature>/requirements.md` に書く。
書き出したら Step 8 へ。

読み手が最初に必要とするのは全体像なので、要件サマリを冒頭に置く。
検討経緯・却下した代替案は書かず、決まったことだけを書く。

frontmatter は `status: confirmed`・Step 6 で確定した `quick_eligible`・`notion_url`・`pr_title`・`branch_name` を必ず付ける。
`notion_url`・`pr_title`・`branch_name` は Step 2 で読んだ下書きにあれば値をそのまま引き継ぎ、無ければ空文字で書く。

```markdown
---
status: confirmed
quick_eligible: [true または false]
notion_url: [下書きにあれば引き継ぐ。無ければ空文字]
pr_title: [下書きにあれば引き継ぐ。無ければ空文字]
branch_name: [下書きにあれば引き継ぐ。無ければ空文字]
---

# 要件定義: [機能名]

## 概要
[機能の目的と背景を2〜3文で]

## 要件サマリ
| # | 要件 | 主体 |
|---|---|---|
| 1 | [Requirement 1 の見出しと同じ文言] | `[主体]` |
| 2 | ... | ... |
[1 行 1 要件。番号・文言・主体を本体と一致させ、番号は 1, 2, 3 と連番にする]

[Requirement 全体や分割候補など、特定の 1 行に紐づかない要確認があれば
`【要確認】<内容>` を 1 行で。無ければ書かない]

## スコープ
**含む:**
- [機能A]

**含まない:**
- [機能C]。理由は[なぜ含まないか] 【要確認: 理由】(根拠が無く判断で埋めたときだけ付記)

## 要件

### Requirement 1: [要件名]
[なぜこの要件が要るか、動機を 1 文で。受け入れ条件と重複するなら省く]

受け入れ条件・主体 `[主体]`
- [振る舞い]
- [イベント]とき → [振る舞い] 【要確認: 理由】(根拠が無く判断で埋めたときだけ付記)
- 【異常】[トリガー] → [振る舞い]

### Requirement 2: [要件名]
...

## 付録: [表題]
[対象ファイルの洗い出しなど 10 行を超える表・一覧はスコープ節に置かずここへ送り、スコープ節からは「詳細は付録」と 1 行で参照する。無ければ節ごと省略]
```

**完了ゲート:** 「受け入れ条件の書き方」「役割」「Step 3」「Step 5」「Step 7 のフォーマット」の規定を満たして `requirements.md` を書き出したか。
frontmatter に `status: confirmed` と `quick_eligible` があるか。

### Step 8: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### 要件定義完了
<何を要件化したかを 1 行>
- <主要な結果 最大 3 行>

生成物: `.specs/<feature>/requirements.md`

### 要確認
<件数>件（本文の `【要確認】` を参照）

### 次の一手
- <quick_eligible に応じて 1 行目を差し替える>
- 要件を直す: `/spec <feature>`
```

- 要件定義完了: 主要な結果が無ければその行を省略する。
- 要確認: 件数と「本文を見よ」の一言だけ。
  内容の列挙はしない。
  無ければブロックごと省略する。
- 次の一手: 1 行目は `quick_eligible` で分岐する。
  `true` → `- QA シナリオを作って直接実装する: /scenarios <feature> → /quick <feature>`。
  `false` → `- 設計に進む: /design <feature>`。
  分割候補があるときだけ `- 分割する: /spinoff <feature>` を足し、切り出す Requirement を指示して起動する旨を添える。

**中断時**: 同じブロック構成で見出しを `### 要件定義中断` に差し替える。

- 要件定義中断: 一言サマリに中断理由。
  要望が実質的に空で Requirement を起こせない、などが該当する。
  `requirements.md` が未確定である旨を添える。
  書き出し前に止まったなら生成物の行は省略する。
- 次の一手: 復帰コマンド `- 要件を作り直す: /spec <feature>`。
  未確定のまま `/design` へ進む道は出さない。
