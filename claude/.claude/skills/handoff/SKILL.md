# 他 PJ への修正依頼（handoff）

## 役割

今のタスクを進めるのに別PJの変更が必要なとき、直接編集できない相手 PJ に対し修正依頼を
`.specs/` 経由で受け渡す。相手 PJ の `.specs/<機能名>/seed.md` に要望書を書き、相手はそれを
`/spec` の入力として拾う。

**対象は「相手PJの完了を待たないと今のタスクが完了しないブロッカー」**に限る。依頼元
`tasks.md` の `## 他 PJ への handoff` に `H<n>` として洗い出されている想定で、依頼を投げたら
その `H<n>` にチェックを付ける＝**追跡義務がある**（Step 6 参照）。

**扱わないもの**: skill / pipeline 本体の改善は扱わない。持ち込まれた場合は依頼書を作らず
`/propose` を案内する（Step 1 の受付ゲート）。

**前提**: ハーネスは作業ディレクトリ外のファイル編集をブロックする。例外は各 PJ の `.specs/`
配下のみ。よって本体ファイルの編集は試みず、必ず相手 PJ の `.specs/` に書く。

**位置づけ**: seed.md は「機能要望」であって実装指示ではない。相手 PJ で `/spec` に渡すと、
質問しながら requirements.md に詳細化され、その後 design → tasks → impl と正規フローに乗る。
よって実装手順・受け入れ条件などを先回りして書かない（spec→design→tasks が生成する）。
書くのは「何を・なぜ・どこまで」に絞る。

**無確認実行**: 依頼先PJが引数・略称表・文脈から一意に決まる場合は、事前承認を求めずに
要望書を書き、結果を事後報告する（Step 2）。依頼先の候補が複数ある、または特定できない
ときだけ人間に確認する。

## 引数

- 第1引数: 依頼先 PJ のパス、または CLAUDE.md のプロジェクト略称表にある略称
- 第2引数: 機能名（`.specs/<機能名>/` のディレクトリ名になる。kebab-case）。省略時は依頼内容から自動命名する。

第1引数（依頼先 PJ）が省略・不明なときは人間に聞く。第2引数は省略時に自動命名する。

## 進め方

### Step 1: 受付判定（純化ゲート）

依頼内容が skill / pipeline 本体の改善（handoff / spinoff / propose などスキル定義や
パイプライン運用そのものの修正）であれば、このスキルの対象外。依頼書を作らず `/propose` を
行き先として案内して中断する（下記「中断カード」）。

「相手PJの完了を待たないと今のタスクが完了しないブロッカー」であることを確認できたら
Step 2 に進む。

**完了ゲート:** 依頼内容が skill / pipeline 改善でないと確認できたか（該当すれば中断済みか）。

### Step 2: 依頼先 PJ を特定する

引数のパス/略称から依頼先 PJ のルートを確定する。略称なら CLAUDE.md の対応表で解決する。

依頼先PJが引数・略称表・文脈から一意に決まる場合は、事前承認を求めずそのまま確定して進む
（無確認実行）。候補が複数ある、または特定できない場合だけ人間に確認する。

確定したら `.specs/` に書けることを確認する（存在しなければ作成方針を人間に確認）:

```
test -d <依頼先PJ>/.specs && echo writable || echo "(.specs なし)"
```

書き込める場合は続けて `ls <依頼先PJ>/.specs/` で既存 feature 一覧を取得し、Step 4 の採番の入力にする。

**完了ゲート:** 依頼先 PJ ルートと `.specs/` の書き込み可否が確定したか。

### Step 3: 依頼内容（要望）を固める

人間から修正内容を受け取り、相手が `/spec` に渡して要件詳細化できる「要望」の粒度に落とす。
実装手順や受け入れ条件まで先回りして書かない（それは相手の spec→design→tasks が作る）。

依頼先のコードを Read する前に、先に `git -C <依頼先PJ> fetch` を実行し、リモート追跡ブランチの
内容を基準に対象範囲（どのあたりのファイル・該当箇所か）を確認し、要望書の「対象範囲・既知の
手がかり」に参考情報として添える。ドキュメントや記憶を鵜呑みにせず実コードで裏取りする
（CLAUDE.md「ドキュメントを鵜呑みにしない」）。行番号を書く場合は、基準としたコミット
（`git -C <依頼先PJ> rev-parse @{u}` 等）を併記する。

**完了ゲート:** `git fetch` 済みの内容を基準に対象範囲を確認し、要望の中身が固まったか。

### Step 4: 要望書を書く

下記「スラッグ採番手順」（出力先ルート = 依頼先 PJ）で機能名を採用してから、
`<依頼先PJ>/.specs/<採用名>/seed.md` に Write する。テンプレート:

```markdown
# <タイトル: 何をしたい依頼か 1 行で>

## 背景・目的
なぜこの変更が要るか。専門用語・内部用語は本文で説明する。

## やりたいこと
相手 PJ に何を実現してほしいか。挙動・体験のレベルで書く（実装方法は指定しない）。

## 対象範囲・既知の手がかり
依頼者が実コードで確認した対象ファイルや該当箇所（参考情報。相手の調査の起点）。

## 制約・前提
外せない条件、やってほしくないこと、既存仕様との整合など。

## 拾い方
この依頼書は依頼元セッションでは編集できないため、本体は手付かず。相手 PJ で
`cd <依頼先PJ> && claude` を起動し、`/spec <機能名>` を実行して要件詳細化から始める
（`.specs/<機能名>/seed.md` は `/spec` が自動で読み込む）。
```

**完了ゲート:** seed.md を Write し、相手が `/spec` で拾える要望になっているか。

### スラッグ採番手順

`/spinoff` `/handoff` `/notion-import` 共通の手順。feature スラッグは他の feature と区別さえつけば
よい識別子なので、ユーザーに確認せず以下の順で決めて生成まで通す。

1. **候補を決める**（優先順）:
   1. 引数で明示されたスラッグ
   2. Notion の `Branch Name` の最終セグメント（`/notion-import` のみ）
   3. 入力内容から作った kebab-case の短い名前（3〜5 語程度）
2. **既存一覧を取る**: `ls <出力先ルート>/.specs/` で既存の feature ディレクトリ名を得る。
3. **空き名を採る**: 候補名が一覧に無ければそのまま採用する。既存なら `<候補>-2` `<候補>-3` … と
   連番を上げ、最初に空いている名前を採用する。明示指定でも自動命名でも扱いは同じで、衝突を
   理由に中断しない。
4. **上限**: `-99` まで空きが無ければ生成せず中断し、別名の指定を促す。
5. **生成**: 採用した名前で `<出力先ルート>/.specs/<採用名>/seed.md` を Write する（3 で空きを
   採っているため既存 seed.md の上書きは起きない）。
6. 採番の可否はユーザーに確認しない。採用した名前は完了カードの 📄 行のパスで分かるので、
   「自動命名した」「連番になった」旨の説明行は足さない。

### Step 5: 依頼元 tasks.md の handoff 項目をチェックする

依頼元（＝今いる作業ディレクトリ）の feature が `tasks` 工程で `## 他 PJ への handoff` に
この依頼を `H<n>` として洗い出している場合、依頼を投げたのでチェックを付ける。

1. カレント PJ の `.specs/*/tasks.md` から `## 他 PJ への handoff` セクションを持つものを探す
   （`grep -rl "## 他 PJ への handoff" .specs/*/tasks.md` 相当）。
2. その中の**未チェック（`[ ]`）の `H<n>` 項目**で、依頼先 PJ が今回の handoff 先と一致するものを探す。
3. 一致が1件 → `Edit` でその行の `[ ]` を `[x]` に更新する。
4. 一致が0件 → 次のいずれか。どちらもチェックを付けずに完了してよい。その旨を報告に添える。
   - 洗い出しに無い依頼（tasks を経ずに handoff した等）。
   - **棚上げ案件**（別PJ宛だがブロッカーではない）。この場合は本来 `/spinoff` の対象であり、
     `tasks.md` に `H<n>` が無いのは想定どおりなので、それ以上追跡しない。
5. 一致が複数 → どの `H<n>` を投げたか人間に確認してからチェックする。

チェックが表すのは「相手 PJ 側の完了」ではなく「**依頼を投げた**」こと。相手 PJ での実装完了は別途追う。

**完了ゲート:** 対応する `H<n>` があればチェック済みにしたか（無ければ「洗い出しに無し」または
「棚上げ案件」と判断できたか）。

### Step 6: 報告する

書いた seed.md のフルパスと、相手 PJ での拾い方（`cd <依頼先PJ> && claude` → `/spec <採用名>`）を
末尾の `## 完了カード` に畳んで報告する（カードの外に別文で書かない）。

## 完了条件

依頼先 PJ の `.specs/<採用名>/seed.md` に要望書を書き、依頼元 tasks.md に対応する
`H<n>` があればチェック済みにし、`/spec` での拾い方を報告したら完了。

## 完了カード
seed.md の Write が済んだら、次の完了カードを**コードフェンスで囲まず**プレーンテキストで出力して終了する。カードの前後に作業サマリ・所感・補足を足さない。依頼先 PJ での `/spec` は依頼元セッションから起動せず、人間の実行を待つ。

- 一言サマリは 1 行。主要な結果は `- ` の箇条書きで**最大 3 行**（無ければ行ごと省略）。依頼内容の本文は seed.md に書き、カードには列挙しない。`H<n>` のチェック結果（付けた / 洗い出しに無し）は 1 行で載せる。
- ▶ 行は依頼元セッションでは実行できない停止点なので 1 行に留める。

✅ 依頼書の受け渡し完了
<どの PJ に何を依頼したかを 1 行>
- <主要な結果 最大 3 行>
📄 <依頼先PJ>/.specs/<採用名>/seed.md
▶ OK：依頼先 PJ で /spec <採用名>（`cd <依頼先PJ> && claude` で起動）

完了条件を満たせずに終了するときは、同じ構成でヘッダを `⚠ 依頼書の受け渡し中断` に差し替え、一言サマリに中断理由（skill / pipeline 改善の持ち込み（→ `/propose`）・依頼先 PJ を特定できない・`.specs/` に書けない・連番の上限に達したなど）、▶ 行に復帰コマンドを書く（seed.md が未生成なら 📄 行は省略する）。

## エラー処理

- 依頼内容が skill / pipeline 本体の改善 → 依頼書を作らず `/propose` を案内して中断する（Step 1）
- 依頼先 PJ が特定できない / 略称が対応表にない / 候補が複数ある → 人間に確認する
- `.specs/` が存在しない → 作ってよいか人間に確認する（穴あけ対象か不明なため）
- 本体ファイルの編集がブロックされた → 想定どおり。編集は諦め `.specs/` への Write に徹する
