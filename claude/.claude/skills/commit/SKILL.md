# コミットスキル

## 役割
作業ツリーの変更を関心事ごとに分割してコミットし、結果を報告する。
push はしない。

## 判断が割れる点の扱い
途中でユーザーに質問も承認も求めない。
コミットすべきでないファイルが混ざっていると判定したときだけ Step 2 で確認し、分割で迷った判断は完了カードの要確認に出す。

## コミット分割の原則
判定基準はレビュアーが読めるかどうか。
1 コミットを見たときに、何をしていて、なぜこれだけで完結しているかを迷わず判断できる単位に割り、行数やファイル数は基準にしない。

### 1 コミット 1 関心事
分割単位はファイルではなく関心事で、「何のためにこの差分があるか」で割る。

- 挙動を変える変更と、挙動を変えない変更を分離する
  - 命名の変更や実装方式の置き換えと、バグ修正や機能追加は、同じファイル内でも別コミットにする
  - 挙動を変えない下ごしらえは `refactor:` として、それを使う `feat:` / `fix:` より前に置く
  - 1 ファイル内で混在するときは `git add -p` または `git apply --cached` で hunk 単位に割る
- 機械的な変更を、意味のある変更から隔離する
  - 純粋なリネーム・ファイル移動・フォーマット・一括置換・自動生成物は、ロジック変更と混ぜると全行が削除と追加に見えて差分が読めなくなる
- テストは、それが検証する本体と同じコミットに入れる
  - 期待と実装を一緒に読めるようにする
- 設定と機能コードは分ける
- 今回の目的と無関係な修正は別コミットに切り出す

### 依存順と緑
- 依存先を先にコミットし、後で差し替える前提のスタブや placeholder は書かない
- 使う側より先に部品を入れるときは、その部品のテストを同じコミットに入れて単体で意味が通るようにする
  - テストも使う側も無い export や import だけのコミットは作らない
- テーブル構造の変更のように単体で着地できるリスク分離コミットは、無関係な既存コードの修正より先頭に置く
- 各コミット単体でビルド・テストが壊れない状態にし、コミット単位で `git bisect` できるようにする
- 前方参照で内側だけでは完結しないときは、相互依存の最小単位を 1 コミットにまとめる

### greenfield の扱い
greenfield とは、新規追加ファイル、または noop プレースホルダやスタブからの差し替えを含む、既存内容が実質的に残らない全置換を指す。
既存内容が実質的に残る部分改変は従来どおり扱う。

greenfield ファイルには hunk 単位の分割を当てはめない。
- 完全に動く 1 成果物を 1 コミットにし、骨格だけ先に置く段階分割をしない
- 独立した成果物は成果物ごとに分け、並びは依存先が先
- 複数の新規ファイルが相互依存し、揃わないと動かないなら 1 コミットにまとめる
- テストは本体と同じコミットに入れ、機械的な変更の隔離は維持する

## コミットメッセージのフォーマット
IT・ビジネスの専門用語を避け、読んだ人が知識に関わらず理解できる日本語で書く。
リファクタリング・マイグレーション・エンドポイント・スキーマ・デプロイ・バリデーションは、コードの整理・テーブル構造の変更・API の受け口・データの形式・本番環境への反映・入力値の確認と言い換える。

```
[プレフィックス]: [絵文字] [タイトル。計画の通し番号は含めない]

背景: [なぜこの変更が必要か。自明でも「特になし」とせず、件名と重なってよいので理由を書く]
修正内容: [件名より一段具体的に、実際に変えた内容。後続コミットを見越した先行対応ならその旨を必ず書く]

Co-Authored-By: [ハーネスが指定する形式]
```

| プレフィックス | 絵文字 | 用途 |
|---|---|---|
| `feat:` | ✨ | 新機能の追加 |
| `fix:` | 🐛 | バグ修正 |
| `refactor:` | ♻️ | コードの整理 |
| `test:` | ✅ | テストの追加・修正 |
| `docs:` | 📝 | ドキュメント |
| `style:` | 💄 | フォーマット、lint |
| `chore:` | 🔨 | ツール設定 |
| `build:` | 📦️ | ビルド設定、依存関係 |

各セクションは 3 行以内を目安にし、収まらなければ複数の関心事が混ざっているサインなので分割からやり直す。
greenfield ファイルは 1 ファイルが 1 つの関心事なので、3 行を超えても混在を意味しない。
解説コラムは、読み手が知らないであろう概念・用語をこのコミットで初めて持ち込むときに限り、本文末に 1〜2 文だけ添えてよい。

## 進め方

### Step 1: ブランチチェック

コミットの可否を判断するのはこの Step だけで、後段はブランチの状態を理由にコミットを見送らない。

```
CURRENT=$(git branch --show-current)
DEFAULT=$(git default-branch)
git fetch origin "+refs/heads/${DEFAULT}:refs/heads/${DEFAULT}"
```

- `CURRENT` が空、detached HEAD → 警告へ
- `CURRENT` が `DEFAULT` と異なり、`git merge-base --is-ancestor HEAD "$DEFAULT"` が真、マージ済み → 警告へ
  - `CURRENT` が `DEFAULT` のときは自分自身の祖先で必ず真になるので判定しない
- いずれも該当しなければ Step 2 へ

`CURRENT` が `DEFAULT` と一致することは判定しない。
デフォルトブランチへのコミットはローカルで可逆で、PR を作るか直接取り込むかは完了カードの次の一手で人が選ぶ。

警告は「現在のブランチ `<CURRENT>` は <マージ済み / detached> の状態です。新しいブランチを切ってからコミットしますか？」と聞く。
「はい」なら変更内容から `<type>/<短い説明>` の形で名前を提案し、`git checkout -b <新ブランチ名> "$DEFAULT"` で切ってから Step 2 へ。
「このまま進める」ならそのまま Step 2 へ。

### Step 2: 変更の確認と除外の確定

`git status` と `git diff` で、生成物・無関係ファイルなどコミットすべきでないものが混ざっていないかを確認する。
混ざっていればそのまま進めず人に確認し、除外ファイルは作業ツリーに残してコミット計画に含めない。
人が「staged のものだけコミットしたい」と明示した場合は、staged でないものを除外リストに載せる形にし、index の状態そのものを絞り込みの指示とは解釈しない。

続けて `git reset` で index を空にする。
`git commit` は index の内容を丸ごとコミットするため、計画に含まれないファイルが staged で残っていると 1 件目に紛れ込む。

### Step 3: コミット分割

`git diff` から除外ファイルを除いたものを対象に、「コミット分割の原則」で分割計画を立てる。
関心事の切り分けがつかないファイルだけ変更前後の内容を読む。
分割した項目それぞれについて、さらに小さい関心事に割れないか見直す。
割れるなら項目を追加し、割れないところまで進んだら計画を確定する。

### Step 4: コミットの実行

計画の項目ごとに「コミットメッセージのフォーマット」でメッセージを作り、対象ファイルだけを add してコミットする。

```
git add <その項目の対象ファイル>
git commit -m "$(cat <<'EOF'
<生成したメッセージ>
EOF
)"
```

- `git add -A` / `git add .` / `git commit -a` は使わず、対象ファイルを明示する
- メッセージは変数展開を避けるため HEREDOC の literal mode `<<'EOF'` で渡す
- hunk 分割が必要なら計画で決めた方法に従う

ある項目をコミットするために他の項目の変更を作業ツリーから一時的に戻す必要があるときは、直接いじらず次の手順で退避してから行う。

```
git add -A
git commit -m "WIP: 分割前の全変更"
git branch backup/<現在のブランチ名>-commit
git reset --soft HEAD~1
```

`git reset --soft` で全変更が再び stage された状態に戻るので、そこから通常どおり計画の項目ごとに `add` してコミットする。
全項目のコミットが終わったら、取りこぼしがないか `git diff backup/<現在のブランチ名>-commit` で確認する。
差分が空ならバックアップブランチを削除して終了する。
差分が残っていれば計画に無い変更が漏れているので、追加のコミットにするか計画を見直す。

```
git diff backup/<現在のブランチ名>-commit
git branch -D backup/<現在のブランチ名>-commit
```

pre-commit hook・lint による拒否を含めコミットが失敗したら、以降のコミットは実行せず、`git reset` でその時点の add を取り消し、完了済みコミットは残したまま Step 5 の中断カードで報告する。

### Step 5: 出力

次のカードを、コードフェンス自体は出さずに中身だけ出力して終了する。
中断時は見出しを `### コミット中断` にし、1 行目に中断理由を書き、2 行目以降に `完了: [1] <件名> / [2] <件名>`、`失敗: [k] <件名> — <理由>`、`未実行: [k+1] <件名>` の 3 行を出し、次の一手は「復帰: `/commit`」と「取り消す: `git reset --soft HEAD~<完了件数>`」にする。

```markdown
### コミット完了
<ブランチ名> に <N> 件コミットしました
- <コミット件名。4 件以上なら重要度上位 3 件だけ>

### 要確認
- <分割・帰属で判断が割れた点>
<無ければこのブロックを省略>

### 次の一手
- PR を作る: `/land`
- デフォルトブランチへ直接取り込む: `git switch <デフォルトブランチ> && git merge --ff-only <ブランチ名> && git push`
  <既にデフォルトブランチにいるなら `git push` だけ>
- 取り消す: `git reset --soft HEAD~<N>`
  <実行済みだが取り返しがつくことを伝えるために常に出す>
```
