# コミットスキル

## 役割
変更内容を確認し、コミット分割からコミット実行までを行い、結果を報告する。

## 入出力
- **入力**: 作業ツリーの変更。
  `git status` / `git diff`
- **出力**: コミット。
  **ファイル成果物は持たない**ので完了カードに生成物の行は出さない

`/commit` は **push しない**。

## 対話方針
コミットして完了カードを出す。
コミットすべきでないファイルが混ざっていると判定したときだけ、Step 2 でユーザーに確認する。

## コミット分割の原則

判定基準はレビュアーが読めるかどうか。
1 コミットを見たときに、何をしていて、なぜこれだけで完結しているかを迷わず判断できる単位に割る。
行数やファイル数は分割の基準にしない。

### 1 コミット 1 関心事

分割単位はファイルではなく関心事で、「何のためにこの差分があるか」で割る。

- **挙動を変える変更と、挙動を変えない変更を分離する。**
  - 命名の変更や実装方式の置き換えと、バグ修正や機能追加は、同じファイル内でも別コミットにする。
  - 挙動を変えない下ごしらえは `refactor:` として、それを使う `feat:` / `fix:` より前に置く。
  - 1 ファイル内で混在するときは `git add -p` または `git apply --cached` で hunk 単位に割る。
- **機械的な変更を、意味のある変更から隔離する。**
  - 純粋なリネーム・ファイル移動・フォーマット・一括置換・自動生成物は、ロジック変更と同じコミットに混ぜない。
  - 混ざると全行が削除と追加に見えて差分が読めなくなる。
- **テストは、それが検証する本体と同じコミットに入れる。**
  - 期待と実装を一緒に読めるようにするため。
- 設定と機能コードは分ける。
- 同一ファイル内でも、互いに依存せず単独で意味が通る変更は関心事ごとに分ける。
- 今回の目的と無関係な修正は別コミットに切り出す。

### 依存順と緑

- 依存先を先にコミットする。
  そのコミットが依存するコードは、前のコミットですでに存在し動作している。
  スタブや placeholder に後で差し替える前提のコードは書かない。
- 使う側より先に部品を入れるときは、その部品のテストを同じコミットに入れて単体で意味が通るようにする。
  テストも使う側も無い export や import だけのコミットは作らない。
- テーブル構造の変更のように単体で着地できるリスク分離コミットは、無関係な既存コードの修正より先頭に置く。
- 各コミット単体でビルド・テストが壊れない状態にする。
  コミット単位で `git bisect` できる。
- 前方参照で内側だけでは完結しないときは、相互依存の最小単位を 1 コミットにまとめる。

### greenfield の扱い

greenfield とは、新規追加ファイル、または既存内容が実質的に残らない全置換を指す。
noop プレースホルダやスタブからフル実装への差し替えを含む。
既存内容が実質的に残る部分改変は greenfield ではなく、従来どおり扱う。

greenfield ファイルには hunk 単位の分割を当てはめず、次を既定にする。

- 完全に動く 1 成果物 = 1 コミット
- 骨格だけ先に置く段階分割をしない
- 独立した成果物は成果物ごとに分け、成果物どうしの並びは依存先が先
- テストは本体と同じコミットに入れ、機械的な変更の隔離は維持する

複数の新規ファイルが相互依存し、揃わないと動かないなら 1 コミットにまとめる。

## コミットメッセージの原則

### 背景と修正内容の2セクション

**本文フォーマットは背景と修正内容の2セクションで統一する。最重要。**
本文は常に「背景」「修正内容」の2セクションを両方書く。
件名だけで終わらせない。

```
feat: ✨ タイトル

背景: なぜこの変更が必要か
修正内容: 何を変えたか
```

### 分量の目安

**各セクションは目安 3 行以内に収める。**
3 行で説明しきれないなら、複数の関心事が 1 コミットに混ざっているサイン。
セクションを長くして対処せず、コミット分割からやり直す。
greenfield ファイルは 1 ファイルがそのままアトミックな 1 つの関心事なので、3 行を超えても関心事の混在を意味しない。

### 書き方

自明な変更でも「背景」に「特になし」のような空虚な記述はしない。
件名と重なってよいので簡潔な理由を書く。
「修正内容」は件名より一段具体的に、実際に変えた内容を書く。
内側の部品を先にコミットするとき、次にどの外側から使われるかを「修正内容」に一言添えると読み手が追いやすい。
必須ではない。
**そのコミット単体では機能的に不要だが、まだこれから作る後続コミットを見越した先行対応であるときは、その旨を必ず書く。**
**解説コラムは原則書かない。**
読み手が知らないであろう新しい概念・用語をこのコミットで初めて持ち込むときに限り、本文末に 1〜2 文だけ添えてよい。
毎回は付けない。

### 言葉遣い

**言葉遣いは日本語で書く。**
IT・ビジネスの専門用語を避け、読んだ人が知識に関わらず理解できる言葉で書く。
リファクタリング・マイグレーション・エンドポイント・スキーマ・デプロイ・バリデーションのような語は避け、「コードの整理」「テーブル構造の変更」「API の受け口」「データの形式」「本番環境への反映」「入力値の確認」のように言い換える。

### プレフィックスと絵文字

| プレフィックス | 絵文字 | 用途 |
|---|---|---|
| `feat:` | ✨ | 新機能の追加 |
| `fix:` | 🐛 | バグ修正 |
| `refactor:` | ♻️ | コードの整理 |
| `test:` | ✅ | テストの追加・修正 |
| `docs:` | 📝 | ドキュメント |
| `style:` | 💄 | フォーマット、lint |
| `chore:` | 🔨 | ツール設定 |
| `build:` | 📦️ | ビルド設定、依存関係 |

### 件名

**件名行のフォーマットは次のとおり。**

```
feat: ✨ タイトル
refactor: ♻️ タイトル
```

コミット計画の通し番号、`[1]` など、は報告での識別にだけ使い、件名には含めない。

### Co-Authored-By

**末尾に空行を挟んで `Co-Authored-By` 行を付ける。**
モデル行はハーネスが指定する形式に従う。

## 進め方
各 Step は順番に実行する。
**完了ゲート**を通過するまで次へ進まない。

### Step 1: ブランチチェック

**コミットの可否を判断するのはこの Step だけ。**
後段の Step ではブランチの状態を理由にコミットを見送らないので、ここで通した判断は後段で覆らない。
逆に、ここで止めなければそのままコミットされる。

```
CURRENT=$(git branch --show-current)
DEFAULT=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null); DEFAULT=${DEFAULT##*/}
[ -z "$DEFAULT" ] && { git remote set-head origin --auto >/dev/null; DEFAULT=$(git symbolic-ref --short refs/remotes/origin/HEAD); DEFAULT=${DEFAULT##*/}; }
```

`sed` / `awk` を使わないのは、パイプの補助コマンドが権限の allowlist に無く承認待ちで止まるため。
デフォルトブランチは `origin/HEAD` から引き、未設定のときだけ `set-head --auto` で 1 度張り直す。

判定：

- `CURRENT` が空（detached HEAD）→ 警告へ
- リモートでマージ済み（下記がマッチ）→ 警告へ
  ```
  git fetch origin
  [ "$CURRENT" != "$DEFAULT" ] && \
    git branch -r --merged "origin/$DEFAULT" --format='%(refname:short)' | grep -qxF "origin/$CURRENT"
  ```
  **`CURRENT` が `DEFAULT` と等しいときはこの判定を走らせない。**
  デフォルトブランチは自分自身にマージ済みで、`git branch -r --merged origin/main` は `origin/main` を含む。
  そのため無条件に走らせるとデフォルトブランチで必ずマッチし、下で意図的に外した判定が裏口から復活する。
- いずれも該当しなければ Step 2 へ

**`CURRENT` が `DEFAULT` と一致することは判定しない。**
デフォルトブランチへのコミットはローカルで可逆な上、可否は repo の運用方針次第で正本は `/sync` にある。
意図的な除外なので、ここに判定を戻さないこと。

**警告文:**
> 現在のブランチ `<CURRENT>` は <マージ済み／detached> の状態です。
> 新しいブランチを切ってからコミットしますか？

- 「はい」→ デフォルトブランチを最新化してから新ブランチを作成し Step 2 へ。
  ブランチ名は変更内容から `<type>/<短い説明>` の形で提案する。
  例: `fix/login-redirect`
  ```
  git checkout "$DEFAULT" && git pull
  git checkout -b <新ブランチ名>
  ```
- 「このまま進める」→ Step 2 へ

**完了ゲート:** ブランチ状態を判定し、必要なら新ブランチを切ったか。

### Step 2: 変更の確認と除外の確定

```
git status
git diff
```

生成物・無関係ファイルなど **コミットすべきでないものが混ざっていないか**を確認する。
混ざっていれば除外リストとして確定する。
**混ざっていると判定したときはそのまま進めず人間に確認する。**

> 人間が「staged のものだけコミットしたい」と明示した場合は、それを裏返して「staged でないものを除外する」形で除外リストに載せる。
> index の状態そのものを絞り込みの指示として解釈しない。

除外ファイルがあれば、委譲前に作業ツリーから隔離する。

```
git stash push --include-untracked -m "commit: 除外ファイル退避" -- <除外ファイル…>
```

これで作業ツリーから除外ファイルの内容が消え、以降の `git diff` に映らなくなる。
除外がなければこのコマンドは実行しない。

続けて index を空にする。

```
git reset
```

作業ツリーは変更されず、ステージングだけが解除される。
`git commit` は index の内容を丸ごとコミットするため、計画に含まれないファイルが staged で残っていると 1 件目のコミットに紛れ込む。
各コミットで対象ファイルだけを `git add` するので、index が空から始まれば内容を完全に制御できる。

**完了ゲート:** 変更内容を把握し、除外ファイルを stash で隔離し、`git reset` で index を空にしたか。

### Step 3: コミット分割

index は Step 2 で空にしてあるので、`git diff` が全変更になる。
関心事の切り分けがつかないファイルだけ変更前後の内容を読む。
判定できるファイルは変更前後の内容を読まない。

「コミット分割の原則」に従って分割計画を立てる。

**完了ゲート:** 分割計画を立て、各コミットが判定基準を満たすか確認したか。

### Step 4: コミットの実行

計画の項目ごとに、「コミットメッセージの原則」に従ってメッセージを生成し、対象ファイルだけを add してコミットする。
これを順番に繰り返す。

```
git add <その項目の対象ファイル>
git commit -m "$(cat <<'EOF'
<生成したメッセージ>
EOF
)"
```

守る規律:

- `git add -A` / `git add .` / `git commit -a` は使わず、対象ファイルを明示する。index を空から始める前提が崩れる。
- メッセージは変数展開を避けるため、HEREDOC の literal mode `<<'EOF'` で渡す。
- 1 ファイル内で hunk 分割が必要な場合は、計画で決めた方法に従う。

コミットが失敗したとき、pre-commit hook・lint による拒否を含む、は次の順で対応する。

1. 以降のコミットを実行しない。
2. `git reset` でその時点の `git add` を取り消して index を空に戻す。
3. 完了済みコミットはそのまま残す。
4. Step 5 で中断として報告する。

Step 2 で除外ファイルを stash していた場合は、成功・中断を問わずここで `git stash pop` で戻す。

**完了ゲート:** 全項目をコミットし終える、または中断を確定し、stash していた除外ファイルを pop し終えたか。

### Step 5: 出力

次の完了カードを、コードフェンス自体は出さずに中身だけそのまま出力して終了する。
カードの前後に作業サマリ・所感・補足を足さない。

```markdown
### コミット完了
<ブランチ名> に <N> 件コミットしました
- <コミット件名 最大 3 行>

### 要確認
- <分割で判断に迷った点>（例: 1 ファイルに 2 系統の変更が混ざったため片方に寄せた）

### 次の一手
- リモートへ反映: `/sync`
- 取り消す: `git reset --soft HEAD~<N>`
```

- やったこと: 4 件以上あるときは重要度上位 3 件だけ。
  diff の詳細は git log に寄せ、カードには列挙しない。
- 要確認: 分割・帰属で判断が割れた点を挙げる。
  無ければブロックごと省略する。
- 次の一手: `取り消す` 行は**実行済みだが取り返しがつく**ことを伝えるために常に出す。
  `--soft` なので変更内容は index に戻り、失われない。

**中断時**: コミットが途中で失敗したら、ヘッダを `### コミット中断` に差し替える。
この中断カードだけは、区分ごとに件名を列挙してよい。

```markdown
### コミット中断
<中断理由を 1 行>
- 完了: [1] <件名> / [2] <件名> …
- 失敗: [k] <件名> — <理由>
- 未実行: [k+1] <件名> …

### 次の一手
- 復帰: `/commit`（残っている変更から計画し直す）
- 取り消す: `git reset --soft HEAD~<完了件数>`
```

**完了ゲート:** カード、または簡易ログを出力したか。

## 完了条件
- 除外を確定したうえで対象の変更がすべてコミットされた
- 結果を報告した
